### 我本人直接核实过的两个缺陷（高置信度）
1. **支付回调全部 401（P0，功能致命）** —— `apps/api/src/common/api-auth.guard.ts:568-577` 的早返回清单只有 `/health`、`/openapi.json`、`/auth/login`、`/auth/development/reset-demo-password`、`/auth/refresh`、`OPTIONS`，**没有 `isPublicRoute` 的通用早返回**。而 `PUBLIC_ROUTES`（:52-67）里已登记 4 条支付/退款回调。`requiredPermissions` 对公共路由只返回 `[]`（:106-108），于是执行继续走到 :607 `resolveAccessContext(undefined)` → :637 抛 401。**客户端侧有对应早返回（:582 `isClientPublicRoute`），运营侧漏了**，是对称性缺失造成的疏漏。
   - `payment-webhook.controller.ts:9-12` 的注释却写「ApiAuthGuard 只对支付/退款回调精确路径放行」——注释与实现相反。
   - 全仓 `grep` 无 `@Public`/`SetMetadata`/`SKIP_AUTH` 旁路装饰器，`app.module.ts` 是全局 `APP_GUARD`。
2. **金额一致性校验是死代码（P1）** —— `apps/api/src/modules/rental-core/rental-funding.service.ts:274-276` 被误嵌在 `if (effectiveAmount <= 0)`（:266 开）块内，而该块 :267 必然 `throw`，故 274 行永远不可达；:277 的花括号位置错了（应在 :274 之前）。实际影响有限：`action==="initiate"` 时 `effectiveAmount` 由服务端按 `due` 计算，客户端金额本就被忽略；丢的是 API 契约断言，不是资金漏洞。

### 产品视角结论（租户/商户）
- **优势集中在"正确性"**：完整订单生命周期、逐批归还 + 异常隔离 + 养护恢复、不可变版本快照、续租/提前归还/逾时等资金边角、多空间共享客户主档、capability 按需启用。
- **无聊/劝退点**：① 完全没有面向租客的入口（小程序/App 明确不做页面），商户仍要微信+Excel 接单再录入 → 双份工作；② 跨空间汇总被列为储备项，多空间商户看不到总收入；③ 支付为模拟，不能真收钱；④ 首单前配置负担重（权限/品类/型号/定价分组/基本价/地点/日历/规则/资产套装）；⑤ 20 项菜单把"配置一次"与"每天用"混在一起；⑥ 无移动端，而领取/归还/检查恰恰是最需要手机的现场动作；⑦ `经营空间能力`、`品类与业务规则` 等系统架构词汇直接漏到商户界面。
- 核心张力：工程强度全在商户看不见的地方（正确性属卫生因素），而商户能感知的省时/赚钱界面都还在后面。
