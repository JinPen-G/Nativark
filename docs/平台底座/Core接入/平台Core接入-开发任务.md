# 平台底座与业务 Core 接入开发任务

版本：v1.5；建立日期：2026-10-31；修订日期：2026-11-14。

> 正式依据：[需求v1.5](平台Core接入-需求.md)。在两轮澄清、兼容/标准化及完整后台外壳和声明式页面要求上，补充从权威声明生成的统一能力查询。同仓分模块与原PCH任务身份继续作为实施依据，实际完成由原门槛核收。AI Native 实际依赖按固定子交付办理。当前归属见[协作接续](平台Core接入-协作接续.md)，阶段证据见[开发记录](平台Core接入-开发记录.md)。
> 本册使用独立PCH编号，不借用CAT-GOV、AIN、MCP或AGP进度；平台接入与租赁品类扩展是两个交付层级。

开发一个新 Core 从[五步快速接入](#core-quick-start)开始；查已有功能看[统一能力索引](#capability-index)，页面开发看[外壳与页面声明](#declarative-page-contract)，了解平台看[源码梳理与说明](#source-organization)和[API资料](#api-documentation)，维护时看[切片兼容门槛](#compatibility-slices)、[AI并行边界](#ai-parallel-boundary)、[标准包与分发](#core-package-standard)及[独立更新](#independent-upgrades)。实际已实现的合同与静态命令见[契约包说明](../../../packages/core-contracts/README.md)，完整业务SDK、宿主及页面接入随 PCH-02～11 交付。

## 2. 推进顺序与边界

1. **先核对再抽离：** 01→02，固定原有行为、跨层依赖和公共合同；不从移动文件开始。
2. **建立真实宿主：** 03、04在固定合同上建立无Core和多Core装配、租户Core授权、成员分配与范围；05/06共同确认事务与生命周期；07接真实授权与就绪状态，禁止临时恒真权限。
3. **先保住Rental：** 08将原业务重新装配并按受影响范围回归；不要求CAT-GOV全部完成，也不能绕过其未完门禁。
4. **证明非租赁与并存：** 10在冻结合同上交付非租赁普通业务链，验证与Rental同宿主、同租户并存及租户授权差异；普通链不依赖AI/MCP。09另证有AI工具的正向链和无工具拒绝，不能用无AI样例替代A08。
5. **资料随片收口：** 11不是最后才补的逐文件说明书；每片维护正式出口和指南，10由独立接手者验证。12收拢兼容回退与独立审查。

本轮推荐先交付版本化合同、最小样例和本地标准包接入，再接 GitHub Release 下载，最后接 Topic 发现界面；三者共用同一清单与校验链，均落在原任务内。安装可以准备一个待部署组合并提示构建/迁移/重启，不要求生产服务运行时加载外来代码。通过01基线→02合同→逐片适配与回归→本地包复现→远端发现安装推进；原08、09、12的完整门槛保留。

“前置”指本项需要的固定子交付，并非一律等前项100%；最终验收仍覆盖全部需求。并行作者必须独立工作树，Auth/Guard、shared、Prisma、AppModule、导航等公共文件指定唯一作者；不得以多专项名同时抢写。原各专项任务顺序不变。

## 3. 任务详情

### PCH-01：依赖、归属与验收组合

- 逐项追踪平台→业务和业务→平台的实际import、注入、数据库读写、事件、作业及页面消费者；区分合理宿主组合与平台内部反向依赖。
- 登记公共与业务数据所有者，识别租赁会员/企业账期、品类、地点、支付回调等容易误当公共的对象。
- 固定无Core公共宿主、Rental单Core、非租赁单Core及双Core并存的构建/运行组合；核对租户Core授权、成员分配、Core自有业务范围与UI/Agent直接消费者，避免用现有单一workspace/currentCore承载全部授权。
- 固定Rental已支持的代表链、历史保护和原未完项；冻结最小非租赁样例及不覆盖范围。样例不用资金/库存即可证明接入，不扩成完整CRM/TMS。
- 依[兼容门槛](#compatibility-slices)建立现有功能对照清单，覆盖公共平台、Rental、企业及各端、AI/MCP/Harness、外部回调与作业；固定正常/既有失败/未验状态、实际命令和基线，不能把全部现状默认视为正常。
- 按[AI 并行边界](#ai-parallel-boundary)区分已支持、开发中与当前切片必需接点，登记唯一作者和固定子交付；冻结最小样例的一条持久化业务链及标准包安装验证范围。
- 按固定Git文件集覆盖全部自有平台/Core/客户端/合同/必要脚本，核对职责、调用链、源码说明、重复逻辑、错误处理与API文档缺口；第三方、生成物和历史材料另标归属。按模块登记处理结果及未解决项，不能只盘点本次移动的文件。
- 核对[能力索引](#capability-index)的正式来源、真实生产者/直接消费者及覆盖缺口，建立功能到包出口、页面/API、源码与资料的定位关系，随所属切片修复说明和登记缺口。
- 无Core组合冻结租户登录/本人资料、成员/角色、基本资料、外观/语言及适用订阅/基础集成的真实保存与隔离验收。最小非租赁样例优先选工单创建→分派→处理→关闭，实际字段/权限由01明确。
- 在记录中登记实际工作树、构建/合同和验证入口，修正设计中尚未确定的边界，不更改原业务规则。
- 出口：可定位每个需改连接及唯一所有者，样例和回归范围明确；静态清单不当运行证明。

### PCH-02：公共合同与版本

- 将[接口设计](平台Core接入-开发任务.md#contract-design)落实为正式类型/运行时校验与唯一出口，固定Core身份、依赖、受权绑定、对象引用、注册项及错误语义。
- 区分接口版本、实现版本、数据版本、Rental品类版本与能力版本；固定向后兼容和未知必需项拒绝规则。
- 决定首期包/模块位置与宿主装配文件，注明哪些现有shared出口保持、哪些需要兼容转接；不私建同名协议。
- 同仓拆分公共合同、平台实现、行业模块和宿主组合；每个模块有正式出口和依赖检查，无Core构建不加载行业源码。固定Core注册、租户Core授权、成员Core分配和可选AI贡献的合同；成员分配复用原账号/角色授权机制，不为AI缺省伪造空工具实现。
- 固定[页面声明合同](#declarative-page-contract)：路由/菜单/面包屑/标题共用描述，正文组件和动作回调由受控代码绑定；导航、打开表单、保存、命令和确认行为分型，框架使用既有组件呈现。业务状态/参数仍有自身类型，不把任意JSON或字符串表达式作为可执行代码。
- 固定[开发能力索引](#capability-index)的JSON合同、唯一标识和出处，复用Core清单、页面/HTTP贡献与包出口生成目录。开发查询和运行工具发布分别消费自身权威来源，索引元数据用于发现和接入。
- 将[标准包设计](#core-package-standard)落实为一个权威清单 schema、类型与校验器，固定最少必需贡献、可选扩展、包内入口、版本/来源及数据兼容语义；同步最小样例与指南。发现和检查只读清单，加载代码另走受控装配。
- 固定平台发行/Core实现/合同与数据的独立版本轴、兼容规则及弃用/迁移要求；明确宿主自定义配置和Core位置，升级底座不覆盖它们。HTTP/OpenAPI贡献和模块SDK分别定义，文档字段复用正式schema，旧Rental接口保持兼容。
- 出口：真实平台生产者与Rental、非Rental消费者可按同一合同编译和验证；不向公共边界泄漏ORM/框架类型。

### PCH-03：平台宿主与多Core装配

- 提供开发者受控的模块装配，平台与行业模块单向依赖公共合同；Core注册不以URL/字符串路径动态执行不可信代码。
- 实际验证不引入任何Core及其数据库表/Seed时，公共登录、租户/角色和适用公共设置可用，租户显示联系管理员授权业务Core。
- 加入反向依赖、重复注册及兼容性门禁；未装配Core的业务入口明确关闭，公共面不因缺Rental崩溃。
- 同一宿主受控装配多个不同Core，各自注册路由/作业/页面；新增Core不覆盖原Core，不要求运行时动态安装代码。独立构建与组合构建分别验证，不能用全量构建后仅隐藏菜单证明拆分。
- 先实现本地标准包的检查和待安装准备，再复用同一路径接固定 GitHub Release 下载；锁定提交/包摘要，校验路径、入口、版本与依赖，坏包/失败不修改当前有效组合。提供可追溯的安装状态和待部署配置，不把获取包等同执行迁移或授权。
- 底座、各Core及宿主配置建立独立的版本依赖与锁定记录；支持更新指定底座或Core的候选组合，预检其他Core兼容性并保留现有业务配置，不用复制整仓或重写用户文件安装升级。
- 出口：无Rental的独立构建/运行及负例证据，而非仅注释imports或空实现。

### PCH-04：身份、租户Core授权与范围

- 保留原Auth/Guard/ALS及当前撤权，拆出Rental专属路径和能力策略的受控提供者。
- 建立命名空间业务上下文和资源范围映射；平台最小身份不要求RentalCategoryCode，缺范围不能回退全局。
- 明确SaaS管理员直接授予租户Core使用权的服务端入口；支持同租户多授权，租户管理员只能在本租户获权集合内给成员分配/收回Core。新Core不自动分配全员，成员范围与Core内角色、对象范围分别验证；客户等其他audience沿原专用授权，不混为租户员工。
- 复用原人员/角色机制保存成员分配、修订和审计；越过管理员可管理范围、跨租户、缺Core授权及并发旧修订均拒绝。成员撤权后，代表该成员执行的请求/任务复验当前权限，不借缓存或系统身份继续新增业务。
- 同时覆盖API、作业、列表/导出、直接URL与AI工具调用，未知权限码/缺策略拒绝，租户通配不越audience。
- 出口：Rental原授权等价；同租户成员分别使用不同Core，未分配Core及受限角色、跨租户/同ID、撤权和缓存回放负例成立。

### PCH-05：授权、绑定与生命周期

- 固定部署级Core集合、各租户Core授权、Core自有业务绑定及配置就绪的不同事实；实现SaaS授权管理与受控初始化，支持一个租户同时获权多个Core。
- 保持同事务初始化/审计及原幂等，失败无可经营空壳；失应答读取原操作结果。
- 提供停新、排空、历史读取及可卸载检查，识别在途业务、unknown、回调/作业和历史执行依赖。
- 分别验证租户单Core停用、部署停止某Core新准入和移除代码；停用关闭普通业务入口与新的Agent任务，保留数据、配置和原收据，其他Core/租户不受无关影响，原善后权限不授权新业务。重新授权复用原绑定，核对当前权限及依赖，不重复初始化或重放旧操作。
- Core开通无需租户在线申请，首期不新增申请流。沿用租户统一订阅到期日，Core不另设期限、收费或自动续费；Core开通不延长订阅，续费不恢复主动停用的Core或已撤销成员权限。到期、冻结、Core停用分别判定，具体新业务/善后按原订阅及Core合同执行。
- 出口：正常、失败、并发和重复生命周期行为可验；不提供Rental空间一键改CRM，不删除事实。

### PCH-06：事务、服务与异步接点

- 明确平台与Core仓储所有权、受限同事务协调能力、引用和迁移归属；保留原业务/审批/资源提交原子性。
- 对接原权益、文件ACL、通知、审计等适用服务；强弱依赖分别处理，实际缺失不可默认成功。
- Core登记事件/作业/回调处理器，固定原业务及版本、重复消费和迟到处理；复用原可靠持久机制。
- 平台拥有注册、租户授权及成员Core分配事实，业务容器和业务数据归各Core；同租户双Core仍拒绝未声明的跨Core读写。本片提供命名空间及正式调用/事件接点，跨Core业务联动不计本期交付。
- 平台和各Core迁移明确唯一所有者、版本及执行顺序，重复升级不重复迁移/初始化；已应用迁移保持不可变，必要历史执行者和业务数据保留。按实际边界合并重复校验/调用，不移除可变权限和提交点的必要复验。
- 出口：跨域越权写不被公共合同放开；错误/unknown、崩溃恢复、延迟回调及未加载模块行为有证据。

### PCH-07：后台、授权管理与端侧

- 用受控模块贡献接入路由、菜单、页面和工作台；保持React/UIArc公共壳、当前主题/语言/音效。
- 公共壳保留左侧菜单区域/搜索/收展、右侧内容容器、顶部面包屑/标题整行及铃铛/休息/面板收展；无Core只取消业务菜单、正文与业务主动作，公共设置及其保存操作正常使用。拆开当前AppShell/通知对Rental和AI展示数据的静态依赖，无业务来源显示准确空态，不启动无Core通用Agent。
- Core页面声明主/次操作后，由原PageHeader/WorkspaceHeader与ActionButton/SaveButton/ConfirmAction承担布局及反馈。动作跟随当前活动路由/对象/权限，隐藏标签页和卸载页面不遗留；导航或开弹窗不冒称写入成功，校验/确认/保存共用一次真实异步执行，错误及unknown按原结果处理。
- 将现有列表、详情、表单、QueryState、分页/过滤、请求与错误处理组合为少量可选公共模式；Core提供字段、数据方法和业务动作即可使用。自定义正文保留正式扩展入口，普通业务无需写底座CSS、修改壳/导航内部或复制通用表单与网络层；按需能力不强制全部接入。
- 绑定切换取消旧请求、隔离缓存和未保存状态；Core/租户/容器同ID不可串数据。
- Rental既有路由及各端API保持兼容，非Rental样例接真实后台页面；不以动态改文案冒充新领域。
- SaaS管理端消费受控Core注册清单并直接为租户授予/撤销使用权；租户管理员在原人员/角色管理中分配成员可用Core，普通成员只见当前获权入口。分别处理租户未开通、成员未分配、未就绪、动作无权、停用和无AI工具，撤权后刷新可见性并拒绝普通业务直接URL/API，必要善后按05处理。
- 多Core导航可以切换或按业务分组，设计阶段按可用性选择，不写死单一形式；当前Core及各自业务范围清晰，采用同样的权限、缓存与未保存保护。无租户Core授权提示联系SaaS管理员，成员缺分配提示联系租户管理员。
- SaaS 平台侧增加轻量“发现/已安装 Core”入口，读取 GitHub `nativark-core` Topic 及清单；区分平台确认与未审核社区来源、仅源码与可安装版本，展示来源/许可/兼容/状态。下载和升级由平台管理员明确发起，需部署时给出具体下一步；普通租户仍只管理已获权 Core。
- Topic 查询有缓存、分页与限流/离线提示；无网络不阻断已安装 Core。入口复用03包校验与05生命周期，不另建交易、评分或付费市场。
- 无Core租户可正常操作公共设置，保存和重启读取真实有效；Core业务设置单独贡献。版本页能区分底座与各Core当前/可更新版本、兼容要求和待部署状态，不因有新版自动改变授权或重置配置。
- 出口：直接URL/菜单权限、错误/加载/未知模块、中英文及窄窗口按原规范验收；宿主证据独立登记。

### PCH-08：Rental实际适配

- 将初始化、品类解析、能力Hook、业务服务、页面和作业连接到正式合同，保留原源码和测试。
- 不在抽离中调整租赁算法、资金、状态或品类采用政策；原未实现采用/动态编码继续关闭。
- 依据既有有效授权建立Rental租户/成员映射并核对前后等价，保留撤权和受限范围；不批量停业、不把历史角色通配成所有未来Core权限。
- 运行已有代表性报价/订单/交付/归还/结算、历史与权限定向回归，核对各直接消费者，不以mock Core完成本项。
- 每个相关切片先使原 Rental 经过兼容适配继续工作，再切新接点；旧路径/权限码/对象标识/幂等及数据保持可读，事件和作业仅一个有效执行者。最终按01完整功能清单汇集03～09各层证据，核对所有已支持功能及原未验问题，不只验一条样例链。
- 整理Rental及直接消费者的职责边界、命名和过期注释，修有依据的重复/吞错及无效兜底；行为变化另列，不能借整理改变算法或抹掉兼容条件。适配出口及HTTP文档一起核验。
- 出口：Rental成为合同的真实消费者且不退化；CAT-GOV原剩余项留原册，不重复计分。

### PCH-09：可选AI工具与Core隔离

- 从通用机制中隔离租赁场景、权限、业务reader/执行器和工具目录；保持原唯一Gateway、预算、审批与原收据。
- 非AI宿主不需模型依赖；启用AI时接真实行业动作的授权、投影、批准与恢复，不只注册工具描述。
- 固定MCP/Harness可消费的正式业务合同及适用边界，原生产者/消费者分别留证据；不替它们补第二套OAuth或发布政策。
- Core可以完全不提供AI工具，其普通注册/授权/后台链须通过，Agent对该Core明确不可用；只提供部分工具时仅开放登记范围。无Core不开放通用任务，不扫描API、页面或数据库补出工具。
- 工具目录和实际调用均按租户Core授权、适用的成员Core分配、当前用户、资源范围、工具发布及AI政策复验；一个Core的AI可用不授予另一个Core的数据访问。保留有工具的正向链、缺工具/成员未分配拒绝及撤权/unknown证据，不把“所有AI都关闭”算作本项完成。
- 不等待 AI Native 全项完成；消费原 AI-RD 提供的固定端口与已有行为，未稳定边界保留适配且只阻塞实际依赖切片。核对原任务、批准、工具/操作版本、模型账和收据恢复兼容，适配切换不得重复执行或重置用量，AI 未完项和进度留原册。
- 出口：缺依赖/撤权/重复/unknown不越界，行业适配可换而通用运行机制不需租赁实体。未获许可的真实模型/Host验证另列，不假称通过。

### 4.1 拆分前后的功能对照与切片门槛

PCH-01先在开发记录建立一份现有功能清单，引用各专项原需求/任务及已有验证入口；不重新抄写全部业务规则，也不另建进度台账。每项至少登记：用户角色及页面/API/作业入口、原行为、权限与数据所有者、源码/合同/数据基线、验证方法、原结果、切片影响、前后结果及剩余问题。基线的“正常、既有失败、未验、不涉及”必须有依据，未运行的场景不能填正常。

| 必须覆盖的范围 | 拆分时重点核对 |
| --- | --- |
| 平台、租户、账号、角色与订阅 | 登录/退出、会话失效、租户隔离、授权和到期政策；原 Rental 成员映射等价 |
| 管理后台与业务页面 | 原菜单/路由/深链接、列表/详情/写入、导出、主题/语言、未保存状态和迟到响应隔离 |
| Rental 已支持品类与业务链 | 配置/品类能力、报价、订单、库存、交付、归还、检查、结算；金额精度和历史快照 |
| 企业及已支持客户端 | 企业授权/订单/财务投影、客户网站/门户、客户与员工小程序及适用 API；保留原 audience |
| AI Native、MCP、Harness | 已支持工具及任务入口、当前授权、批准、唯一执行、模型预算和原结果恢复；未完能力另列 |
| 公共服务与异步处理 | 文件 ACL、通知、支付/业务回调、事件/作业、重复与迟到处理、重启后的原操作核对 |
| 存储、构建与运行 | 原对象/租户/成员 ID、迁移链、数据版本、环境加载、API/worker/前端组合及恢复方式 |

每个切片按同一顺序推进：

1. 固定受影响功能、直接消费者、公共文件唯一作者、旧/新合同和预期回退组合；先核对已有失败，避免失去对照。
2. 先加正式端口和调用原实现的兼容适配，再替换连接；必要时保留旧入口转接，业务规则及事务所有者不随目录改变。
3. 核对该切片正常、拒绝、幂等/并发、历史及必要恢复行为，完成必要类型/组合构建；涉及界面、数据库或真实宿主的验收按原层级取得证据。
4. 有新回归先修复或保留原有效路径，不能通过删断言、关闭业务、默认全权限或清库放行。复验通过后才能将这一切片交给 PM 集成。
5. 将固定提交、前后结果、未验项和旧适配移除条件写回原记录，同片更新受影响入口的职责说明、复杂事务/恢复注释和指南。旧路径只有消费者及历史依赖已核清后才移除，原稿由固定 Git 版本保全。

全量功能清单在01冻结、受影响项随切片验证、最终在08/12逐项核收；无需每改一行就跑全部业务。数据迁移优先采用兼容的新增结构和确定性映射，必须改变结构时提前演练；程序回退不等于数据库回滚。新旧路径不得同时写同一业务、消费同一事件或执行同一模型调用。

### 4.2 AI Native 未完时的并行边界

AI Native 不必先全部完成。PCH先拆已明确的公共身份、租户/授权、宿主/构建、业务数据归属和 Rental 接入；AI原研发继续其任务。双方只交换当前切片需要的固定接口和证据，不同步整棵活动工作树。

| AI/Core 接点状态 | 本专项处理 | 放行依据 |
| --- | --- | --- |
| 已支持且合同稳定 | 抽为窄端口，原实现通过适配供给；已有行为纳入兼容基线 | 固定源码、消费者及原正常/拒绝/恢复证据 |
| 功能开发中，当前切片无需它 | 保留原任务及实现位置，通过可选能力/版本预留接点 | 不新增假实现；该能力缺少不影响无关普通业务 |
| 功能开发中，当前切片必需它 | 由 AI-RD/Core 原作者固定最小子交付；未满足时保留旧适配，暂缓该连接替换 | 真实来源、权限、提交点及消费者可核对；不等待整个专项100% |
| 已持久化任务、批准、账和收据 | 保留原标识/工具版本/授权/预算/恢复语义，并明确唯一执行者 | 历史读、撤权、重复/unknown及重启恢复证据；不能重建任务冒充迁移 |

必须协调的最小公共面包括可信身份/范围、工具描述与发布、准备/批准/正式执行、业务事实及原收据读取、事件/回调归属。Gateway、财务预算和任务资源账继续原唯一实现；Provider SDK 与 Runtime 替换不在拆 Core 时并做。AI通用层不直接认识租赁订单，Rental适配继续使用原 Core 裁定；服务端其他受控公共工具仍沿原正式范围管理。

Auth/Guard/ALS、shared/OpenAPI、schema/迁移、AppModule/AI providers 与后台壳的公共改动由 PM 安排唯一作者。隔离文件继续推进，依赖和具体冲突写原记录供 PM 核定。本轮仅完善文档，不派 AI 助手、不改原 AI 任务百分比。

### 4.3 全平台代码梳理、源码说明与简洁实现

| --- | --- | --- |
| 根README与正式导读入口 | 平台/Core/宿主结构、常用开发入口、各模块及API/样例/验证链接 | 启动/目录/公开入口改变时同步 |
| 实际源码模块README | 入口→应用/领域服务→仓储/外部适配→直接消费者→验证，模块权限/数据/副作用边界 | 跨文件关系复杂且现有入口不足时补齐，避免复制字段和活动进度 |
| 关键源码文件头 | 简短说明负责什么、如何被调用、关键限制和必要接点 | 新建/移动或职责变化时核对；准确说明直接复用 |
| 复杂逻辑旁注释 | 为什么保留该分支、兼容条件、提交点、锁序/并发和恢复依据 | 逻辑改变时与实现同片更新 |
| 简单文件 | 用准确命名、类型和必要一句话备注说明用途 | 全量盘点确认可理解，不套长模板或逐行翻译 |

简短文件头示意如下，实际描述必须对应代码：

```text
职责：把已注册 Core 的页面贡献组合到公共后台路由。
调用方：宿主装配入口；只消费正式页面合同。
限制：不裁定业务权限；访问仍经服务端当前授权校验。
```

“避免防御性编程”落实为减少无依据的复杂度，同时保留正式业务约束：

| 代码情况 | 整理要求 |
| --- | --- |
| 在同一可信边界内反复校验同一不变输入 | 在入口验证并转换成清楚的类型，下游直接使用；避免层层可选链和同义检查 |
| 真实可变化的权限、对象修订、批准及提交条件 | 在相应信任/提交边界复验，不能因为入口验过就删除并发和撤权保障 |
| `catch`后返回空列表、默认值或成功，掩盖实际失败 | 只捕获可处理的错误，保留准确分类与上下文；错误不能变成“无数据/已成功” |
| 对明确必需依赖到处设默认值或假实现 | 装配时核验并准确报错，业务中不伪造租户、Core、价格或权限 |
| 未使用的通用层、过度参数化、多层仅转发包装 | 有真实复用或隔离价值才保留；优先直观、可追踪的服务调用 |
| 重复查询、循环查库、全量扫描或不必要串行调用 | 先确认实际访问与事务语义，沿已有索引/分页/批量能力优化，记录受影响链路的验证或测量 |

不设机械的函数行数、文件数量、注释覆盖率或性能百分比目标。验收看模块职责是否清楚、必要说明是否准确、重复与无效分支是否有依据地处理、调用/查询是否有不必要开销，以及行为是否兼容。代码质量检查复用已有lint/类型/合同和定向验证，必要的新规则围绕真实反例建立，不为检查数量制造大量脚本。

全平台梳理覆盖核对与接手质量；未完成业务功能仍按原专项实现。公共技术指南的锁定边界继续生效，发现旧规范与已批准拆分要求冲突时先记录具体条款，在所属实现切片按明确授权同步，不能悄悄修改规则来迁就源码。

### 4.4 平台与 Core 的 API 文档

| 每项API必须说明 | 内容 |
| --- | --- |
| 定位 | 用途、所属平台/Core、稳定operationId、方法/路径、版本与支持状态 |
| 使用前提 | audience、认证方式、租户/Core/成员授权、角色与业务范围；敏感字段投影和必要批准 |

| 失败 | 状态码及业务错误、无权/冲突/未就绪/缺依赖的具体含义；哪些可重读或按原操作恢复 |
| 副作用 | 只读、准备、申请批准、正式写入、原结果查询分别标注；幂等键、修订和异步/unknown语义 |

类型/schema是字段的唯一来源，OpenAPI和示例从正式定义引用或生成；暂时手写的组合内容须有DTO/控制器/消费者一致性检查，不能再造第三份私有协议。扩展合同或非HTTP端口通过类型说明与示例文档描述，不硬塞成HTTP接口。

## 5. 接口与生命周期实施设计

下列设计原建立于2026-10-31，本次随需求v1.4补充页面接入；仍不代表所有SDK/同名类型已实现或已批准部署。PCH-02须落实为唯一正式源码合同，已实现部分以正式包说明为准。

### 5.1 目标依赖方向

```text
受控宿主组合（无Core、单Core或多个Core）
  ├─ 平台公共实现：登录、租户、权限、Core注册、租户授权与成员分配
  ├─ 可选AI Native机制：仅消费当前获权、正式发布的Core工具
  ├─ Rental接入适配 → Rental Core（包含租赁经营空间与品类）
  └─ 非租赁接入适配 → 自身Core（包含自身业务范围）
          ↓
       同一版本化公共接入合同
```

公共合同不反向导入行业实现；公共实现通过受控合同调用行业贡献，不知道Rental订单、CRM线索的内部结构。宿主组合可以明确引用具体类。首期组合在构建/部署时固定，同一租户可获权使用多个已装配Core；普通业务和可选AI能力分别开放。无Core保留公共管理面，不转为通用Agent；跨Core业务联动和事务留后续场景，不要求动态热加载。

首期继续使用同一仓库，将公共合同、平台实现、各Core及宿主装配划成独立模块；同仓便于核对接口和直接消费者，不允许Core依赖其他Core内部源码或平台反向导入行业实现。沿现有npm workspaces逐步分离，源码位置和命令由PCH-02/03按实际实现确定，此处不虚构包名。

独立构建须使用实际包/模块的正式出口；现有shared含运行时产物，不能仅复制类型或继续通过admin源码别名穿透已拆边界。平台最低宿主的依赖树和初始化只包含平台自身所需模块、表和Seed，不要求生成/加载未选Core模型；组合宿主按固定版本显式选择Core及其迁移。各模块明确可复现构建和兼容版本，同仓不要求同一个版本号，也不代表本轮要发布npm包。

仓库分拆在模块边界、构建和独立接手证据稳定后，依据维护团队或发行需要决定；首期不创建多个代码仓库、不绑定微服务或拆库。代码仓库、进程、数据库是三个独立决策。

第三方 Core 可在自己的仓库开发，按同一标准导出模块并生成发布包。底座以受控依赖和组合配置消费这个包；不要求贡献者把业务实现写进底座仓库，也不要求运行时远程调用或安装 npm 公共包。开发仓库位置与安装包格式分别处理。

| 必须验证的组合 | 用途 |
| --- | --- |
| 无Core宿主 | 不加载行业依赖即可启动公共后台；无授权提示和受限Agent行为正确 |
| Rental单Core、非租赁单Core | 两者消费同一公共合同，分别拥有数据/迁移和业务范围 |
| Rental＋非租赁Core同宿主 | 同租户可双授权、成员可分别获配；其他租户可只获单Core，资源、缓存、作业、撤权互不串用 |
| 单Core停用与重新开通 | 原数据/绑定保留，按当前权限恢复，其他Core可用，不重放旧操作或恢复已撤销的成员权限 |
| 租户统一期限与主动停用 | Core不另设到期日；到期停新、保留获权善后；续费不恢复主动关闭的Core或解除冻结 |
| 不提供AI工具、有AI工具的Core | 普通业务均可用；Agent只消费已提供、已发布且当前获权的能力 |

### 5.2 标识和版本轴

| 概念 | 语义与校验 | 不得混同 |
| --- | --- | --- |
| 平台发行版本 | 一次可部署的Nativark底座及其公共能力/修复，声明合同、运行与数据兼容范围 | 所有Core必须跟随的统一版本号 |
| Core身份 | 开发者登记的稳定业务模块标识；不因版本升级改名，不复用已存在语义 | Rental品类编码 |
| Core实现版本 | 某次可执行业务模块构建及依赖；用于执行兼容与历史诊断 | 租户采用的品类模板 |
| 平台接入合同版本 | 平台与Core双方支持的结构和语义，包含必需扩展判断 | 包版本或某个HTTP接口版本 |
| 数据结构版本 | 平台/Core各自迁移前置和最低可读版本；未知版本拒绝准入 | 仅凭程序版本猜库已迁移 |
| 租户Core授权 | SaaS管理员记录的租户与Core使用关系、状态/修订及原操作；同租户可有多个授权 | Core已注册、当前页面选择或员工动作权限 |
| 成员Core使用范围 | 租户管理员在租户获权集合内，通过原人员/角色机制分配成员可用Core，保留修订及撤权事实 | 租户已开通就默认全员可用，或分配Core就具有其全部业务权限 |
| 租户订阅期限 | 复用原租户统一期限及当前服务状态；Core开通/停用独立记录，首期不设Core专属到期日 | Core注册时间、单独续费周期或AI额度 |
| 受权业务绑定 | 服务器记录的租户/业务容器与Core关联及修订 | client提交的coreId/workspaceId |
| 领域对象引用 | Core、租户、容器（如适用）、对象种类、ID和版本的受控关联 | 具有ID即拥有读取权限 |
| 原操作引用 | 定位唯一动作、输入指纹、对象版本、批准/提交及原收据 | 重试时新建ID |
| Rental内部版本 | 品类正文、开通/采用政策、能力实现、价格/规则/日历和动作快照各自管理 | Core替换或程序回退 |

命名空间的具体序列化和旧引用兼容由正式合同规定，不能随意拼接字符串使历史幂等指纹改变。迁移前后的同一原操作必须可核对。

### 5.3 接点矩阵

下列是需要交付的职责合同；必需指对应宿主能力启用时不可缺，未用能力不要求安装空实现。

| 接点 | 提供者 → 消费者 | 最小语义 | 失败/副作用与边界 |
| --- | --- | --- | --- |
| Core描述与装配 | Core/可信部署组合 → 平台 | 身份、合同/实现/数据版本、依赖、后端/前端贡献清单 | 重复/冲突/未知必需项拒绝；装配不授权业务 |
| 主体与租户 | 原可信身份服务 → 平台/Core | 当前主体、audience、租户、会话/授权修订 | 缺失、撤权或不匹配拒绝，不由模型补全 |
| 租户Core准入 | SaaS授权管理/当前准入服务 → API/UI/作业/AI工具 | 指定租户对已注册Core的使用权、修订、停新与善后条件 | SaaS管理员变更，普通租户不能自授；授权不初始化全部业务或授予所有角色权限 |
| 成员Core分配 | 租户管理员经原人员/角色授权服务 → 成员业务入口/委托任务 | 成员可用Core、当前修订、管理权限及撤权事实 | 仅在本租户获权集合内分配，动作与数据权限另验；不把客户身份转换为员工身份 |
| 业务绑定与范围解析 | 平台绑定服务＋Core范围适配 → 正式应用入口 | 当前绑定、容器归属、受权范围；领域扩展有独立schema | 不把Rental空间设为全部Core必填；缺映射拒绝，不回落全局 |
| 动作授权 | 平台当前授权机制＋Core业务政策 → API/作业/工具 | 权限资源/动作、对象及当前条件，允许或明确拒绝 | Core不能自授租户/平台角色；最终提交点按原规则复查 |
| 初始化/就绪 | Core → 生命周期协调器 | 受控初始配置、必要业务引用、就绪缺项及原操作 | 有写入；同事务与绑定/审计一致，不用空成功 |
| 业务应用/收据 | Core → Web/员工/客户/AI等适配 | 受权查询、正式命令、对象版本、幂等键、原结果读取 | 业务内核唯一裁决；只读与准备/正式写入分别声明 |
| 事务协调 | 平台与Core受限仓储 → 生命周期/批准提交点 | 明确事务所有者、资源锁与写入顺序、原子边界 | 不向任意模块暴露全库可写client；外部调用不持业务长事务 |
| 公共服务 | 原身份/权益/文件/通知/审计实现 → Core | 必需服务版本、能力范围和可信结果；文件含业务ACL委托 | 强依赖缺失拒绝相关能力；费用/额度/业务账不混算 |
| 页面贡献 | Core UI模块 → 公共React/UIArc壳 | 同源路由/菜单/面包屑/标题、正文、类型化操作、权限、对象链接和语言资源 | 壳/公共控件/标准页面与按钮由底座呈现；受控编译引用，不执行任意URL/JS；后端仍独立鉴权 |
| 事件/作业/回调 | Core登记处理器 ↔ 原可靠执行机制 | 事件schema、对象/租户/原操作、执行版本和重放政策 | 原所有者唯一处理；未知不能自动换Core重做 |
| AI/工具贡献（可选） | Core受控业务适配 → 原AI/MCP机制 | 输入输出schema、风险/副作用、授权、释放字段、批准与收据；允许明确未提供工具 | 缺少时只关闭该Core的Agent查询/操作，普通业务不受阻；注册不等于批准或允许材料外发 |
| 停用/兼容检查 | Core＋平台依赖清单 → 部署/生命周期管理 | 新准入、在途/unknown、历史执行/读依赖、兼容矩阵 | 不支持卸载则明确阻止；不能删事实模拟卸载 |

这些接点不是一个万能`execute(action, JSON)`接口：各业务命令继续有正式类型、schema、权限和幂等约束。通用机制只调已注册合同，不能发现字符串就执行任意业务。

### 5.4 三条生命周期，分别记事实

#### 5.4.1 程序装配与部署

受控包/构建校验 → 合同与依赖检查 → 数据兼容核验 → API/worker/消费者组合核验 → 允许对应新准入。

程序存在不表示租户获权。新实例进入与旧程序回退也须核验，不只检查执行安装动作的一个进程。未知必需数据或执行版本拒绝新业务，历史处理由兼容方案决定。

#### 5.4.2 租户Core授权与业务就绪

1. SaaS管理员直接办理Core开通；授权入口验证当前管理权限、目标租户及已注册Core，核对部署兼容、依赖和原授权操作，不要求租户先提交Core申请。
2. 幂等保存租户Core授权及审计；多个Core分别记录。授权不代表业务已经初始化，也不自动授予租户内每个人全部权限。
3. 租户管理员在可管理范围内给成员分配Core，服务端核对租户授权和并发修订并保存审计；开通新Core不自动为全员新增分配。成员在Core内的角色/动作/数据范围继续单独生效。
4. Core声明自己是否需要业务容器、所需配置和可配置角色；实际配置入口复核当前Core准入、适用成员分配、用户权限和资源范围。没有容器模型的Core不创建虚构经营空间。
5. 按Core合同校验初始输入，在约定事务内建立业务绑定、Core初始事实和审计，不加载演示经营数据。初始化失败时保持准确的“获权但未就绪”状态，不留下可经营空壳。
6. 提交后发布相应Core及受影响成员的缓存/导航可见变化，分别返回授权、分配或初始化的原操作收据；符合该用户权限的业务就绪后方可使用。
7. 首响应丢失时先查询对应原操作；相同键和输入返回同一结果，输入冲突拒绝，不换键增授或初始化。再次授权已有Core不重复初始化其业务数据。

Rental适配仍执行品类新开通、目标版本资格及初始化约束。存量Core/成员映射沿已有真实授权保留等价范围，不把历史账号通配到新Core；Core授权不替代Rental品类可用性或订阅权益。CAT-GOV对已有空间的品类升级是Rental内部业务操作，不走“重新安装Core”捷径。

#### 5.4.3 停新、排空与移除

- **停止新准入：** 不再创建新绑定或新业务；两者是否都停止必须由明确政策表达，不凭名称推断。
- **排空：** 禁止新任务，继续按当前授权完成允许的在途/善后和原unknown核对；执行者与历史版本仍保留。
- **历史读取：** 不自动授予旧权限，按当前安全边界提供原事实和原收据。
- **移除代码：** 只有在途、回调、作业及历史执行/读取依赖均有已验证保留路径才允许；数据不随代码移除删除。
- **改用另一Core：** 首期新宿主/新业务容器采用，不改变原业务身份；存量转换另立映射、授权、校验与恢复项目。

租户级Core停用只作用于指定租户/Core，部署级停用则覆盖该Core的部署准入，两者不可混用。停用关闭普通业务入口、查询缓存和新的Agent任务准入，保留数据、配置、权限配置、原收据和其他Core的工作；在途/unknown、迟到回调和必要历史读取仍须原合同及当前善后权限，不以保留代码或配置绕过停新。数据删除不是停用的附带操作。

重新开通由SaaS管理员明确授权，读取原Core身份、绑定与数据，不再走首次初始化；校验当前订阅、成员分配、角色/范围、实现版本及必需依赖后恢复相应入口。先前被单独撤销的成员权限不恢复，旧任务/批准/unknown均按原操作合同核对，不因开通自动重放。

Core首期沿用租户统一订阅到期日，开通或重开不延长期限；续费不改变主动停用状态、成员撤权或账号冻结。订阅到期保留已登记的Core和成员配置，但按各Core声明停止新业务、保留获权善后；期限缺失、历史兼容、收费和续费办理沿[SaaS订阅需求](../../SaaS订阅/SaaS订阅-需求.md)，不在Core授权旁另建一套收费/期限模型。

### 5.5 失败、并发和恢复合同

以下是必须表达的语义分类，实际错误码由PCH-02统一，不在文档私造与现有API冲突的码值。

| 情况 | 必须结果 | 不允许 |
| --- | --- | --- |
| 未装配/缺必需依赖 | 受影响入口不可用，公共面仍可用 | 注入假Core/全权限来启动 |
| 租户无Core授权 | 公共后台可进入并提示联系管理员；业务服务端拒绝访问 | 依据菜单、安装状态或客户端coreId自授使用权 |
| 成员未分配/被收回Core | 公共后台及其他获权Core可用；普通业务页面/API/Agent调用拒绝，提示联系租户管理员 | 租户已开通就默认全员可用，或依靠旧缓存/令牌继续使用 |
| Core停用后重新授权 | 原数据及绑定保留，复核当前准入/权限/依赖后恢复 | 重复初始化、恢复已撤销成员权限或自动重放旧操作 |
| 租户订阅已到期 | 依原政策停新，公共订阅入口及获权历史/善后可用 | 通过重开Core延期、删历史，或续费自动解除主动停用 |
| Core获权但业务未就绪 | 提示缺少配置，仅开放当前用户获权的配置入口 | 用已授权状态掩盖初始化失败或生成演示数据 |
| Core未提供AI工具 | 普通后台按原权限可用，Agent明确不能查询/操作该Core | 扫描数据库/API补工具、借其他Core的工具越界或阻止普通后台运行 |
| 无权/范围不明 | 在读写前拒绝，避免跨域资源存在性泄露 | 默认全租户、借平台管理员代理 |
| 陈旧绑定/对象修订 | 返回冲突与受控重读入口，保留用户未提交输入 | 自动覆盖或按新版本暗中重做 |
| 同键同输入重复 | 读取原状态/收据，是否可推进由原状态决定 | 重复初始化/批准消费/支付 |
| 同键不同输入 | 明确冲突 | 把旧收据当新动作结果 |
| 已证实本地事务失败 | 以原事务/操作证据判定未提交，允许的恢复按原键执行 | 仅根据UI超时认定回滚 |
| 远端/提交状态unknown | 原引用查询与人工核对，暂停新的同义副作用 | 换Core/Provider/ID“重试” |
| 不兼容旧实现 | 拒绝新准入或保持原兼容执行者；诊断可追踪 | 删除新数据以让旧程序读取 |

平台/Core同进程仅是部署形态，不自动保证任意跨模块操作同事务。必须逐提交点写明：谁持锁、谁提交、审计/批准/幂等何时成立、缓存何时可见、崩溃后读何种证据。

### 5.6 业务适配与UI安全

- 权限判断由服务端可信实现提供；前端仅消费可见性和当前上下文，不能凭“已安装Core”授予动作。
- 页面/资源/事件贡献使用命名空间，重复或冲突拒绝，不覆盖另一个Core的注册项。页面切换不保留上一租户/Core的查询结果或未授权表单。
- 必需的未知结构拒绝相关新动作；可选显示信息可以用明确通用样式，不能漏掉必填业务校验。
- 保留原UI组件和适配层，不要求CRM/TMS另建后台框架；行业页面归Core，公共壳归平台。
- AI展示、MCP工具说明和模型返回内容不是授权来源；业务文本不能触发动态代码加载或 arbitrary route。
- SaaS管理端只对受控注册清单中的Core管理租户授权，不提供任意插件上传或代码执行入口。租户管理员配置成员可用Core，菜单及直接URL/API均按当前有效授权处理；Core切换或分组导航由界面设计选择，业务归属须清晰，各Core内部资源选择独立。
- “发现 Core”只展示经过格式校验的元数据及版本；下载区的 Core 尚未注册，不能进入租户授权集合。完成受控部署后才增加可授权条目；安装错误与业务未就绪分别显示。

#### 完整外壳与声明式页面接入

底座承担整个管理后台外壳。Core作者在本Core登记路由和页面操作，框架将其放入既有布局，不让开发者重新制作左栏、面包屑行或主按钮。首期复用现有[BusinessShell](../../../apps/admin/src/components/BusinessShell.tsx)、[AppShell](../../../apps/admin/src/components/AppShell.tsx)、[WorkspaceHeader](../../../apps/admin/src/components/workspace/WorkspaceHeader.tsx)、[PageHeader](../../../apps/admin/src/components/PageHeader.tsx)和[按钮适配](../../../apps/admin/src/components/ui/ActionButton.tsx)的实际呈现/表单语义，形成可独立导入的正式页面出口，不复制第二套壳或重写vendor。

| 层次 | Core作者最小贡献 | 框架默认行为与接点 |
| --- | --- | --- |
| 路由声明 | 稳定ID/局部路径、名称/语言键、可选父级/菜单分组、页面组件、访问要求 | 同源生成侧栏、菜单搜索、父级/面包屑、标题与懒加载；全局使用Core命名空间；详情可引用本页受权标题 |
| 页面动作 | 稳定动作ID、文案、主/次操作意图、权限/可用条件及类型化处理方法 | 统一样式/位置/图标语义/动效/键盘、主次布局及窄屏溢出；无贡献不留空按钮或假操作 |
| 导航或打开表单 | 本Core已登记目标/参数，或明确的本地打开回调 | 只导航/打开，不显示业务完成；离页应用原未保存保护，拒绝未登记目标 |
| 表单保存 | 原Form绑定、字段/校验、真实onSave | 复用SaveButton校验后提交；顶部按钮与回车不重复请求，等待原Promise；失败/修订冲突保留用户输入 |
| 命令及确认动作 | 真实异步方法、适用确认文案/明确目标、当前忙碌及可用条件 | 复用ActionButton/ConfirmAction，确认前不执行，重复点击合并原在途操作；成功后按声明刷新相关数据，unknown不重试 |
| 标准业务页面 | 列表列/筛选/读取/行操作，或详情分组/表单字段 | 原列表/详情/表单模式与QueryState、分页排序/空错态；自定义内容仍用相同壳和动作入口 |
| 数据与反馈 | Core类型化API函数、资源键、刷新目标与业务错误 | 复用原认证客户端/会话代次、租户/Core/容器查询隔离、取消/迟到抑制；平台错误映射与通知；不自动造幂等键重发写入 |
| 可选通知/文件/导出 | 实际内容来源、对象目标、ACL/字段投影、正式数据方法 | 铃铛/消息中心、已登记导航、已有文件/列表能力按需组合；无来源准确空态，不扫描API自动生成业务工具 |

静态路由元数据和当前页动作共享正式身份及命名空间，不要求开发者把同一主按钮同时写到路由文件、菜单和页面JSX里。动态状态通过页面受控上下文供给；动作容器只接当前可见页面，返回、路由卸载、隐藏页签或权限/租户/Core/容器变化时撤销原贡献。特殊页面可自定义正文和受控React组件，仍使用公共动作、权限/请求及错误反馈；不强制把复杂业务写成大型JSON配置或表达式解释器。

外壳的铃铛、休息与右侧面板收展由公共宿主持有。当前通知Provider直接读取Rental待办和本地AI预览，须迁出业务来源并改为可选贡献；空Core组合也能打开通知空态。右侧面板控件及容器保留，业务Copilot内容/发送仍依正式工具与授权开放；没有Core时显示未开通信息，不生成可调用的通用Agent。休息功能复用原媒体/倒计时与身份清理，不依赖Rental空间存在，原已声明身份变化清理保持。

首期从现有列表/详情/编辑模式与轻量工单验证“声明少、默认完成多”。新增模式只解决实际重复问题，不另造全能页面引擎。正式SDK应给最短例子；当前此节为实现合同要求，具体可执行API名及示例由02/07同片落地，不用未实现的伪代码冒充已发布接口。

必要验收覆盖：无Core完整外壳/公共设置、仅声明一个工单主动作得到原样式、表单无效不提交、保存/回车单次请求、确认取消不执行、失败保留输入、双Core同名动作隔离、快速换页/撤权/隐藏页签撤去旧动作、中英/主题/窄屏及独立接手者无需修改底座内部。复用已有相关检查与必要实页验证，不为每项新增独立测试脚本。

### 5.8 Core 包与轻量分发标准

**建议采用“版本化清单＋正式模块出口＋可复现发布包”这一种接入方式。** 清单用于发现和静态校验，模块出口用于受控装配；源码、页面、AI或作业都经已有平台机制使用。不要同时维护“手工改底座”和“插件安装”两套注册逻辑。下列是实施约定，确切字段/schema、文件名及包扩展名由02固定，并在11给出能运行的命令。

| 交付内容 | 最低要求 |
| --- | --- |
| 标准清单 | Core稳定ID、显示名/简介、作者/源仓库、许可、实现版本、平台合同兼容范围、数据版本与运行前置；声明必需/可选贡献 |
| 正式模块出口 | 服务端及适用UI入口、业务权限/范围解析和必要初始化；入口限包内已声明文件，不以文本路径执行任意程序 |
| 业务实现与数据 | 自身领域/服务/仓储及前进迁移、配置schema；只申请实际用到的公共服务，不复制底座源码或依赖别树产物 |
| 可选扩展 | 页面、AI工具、文件/通知、事件/作业/回调按需声明；启用时满足其正式合同，未使用时可缺省 |
| 交付说明 | README说明业务用途与安装前置，LICENSE及所需第三方声明、生成的简明指南、最小配置例子和升级/恢复约束 |
| 可安装版本 | 一个固定版本的发布包，含声明入口/资源/迁移和需要的构建材料或产物；清单、包版本与版本Tag一致，来源提交与摘要可追溯 |

发现约定采用 GitHub 仓库 Topic `nativark-core`，它是作者自行设置的分类标签。单Core仓库根公开 `core.manifest.json` 和README，多Core仓库根用 `core.index.json` 列Core ID与本仓相对清单路径，最多20项，标识与路径各自唯一。根索引到各清单/独立Release的映射由02正式schema规定，发现先固定Git提交读取索引/清单，再按需检查发行。官方示范可同仓维护，第三方独立仓库使用同一清单标准。[实际读取与作者示例](../../../packages/core-contracts/README.md#从仓库确认-core-清单)

安装首期优先使用 GitHub Release 的固定版本包；没有包只展示源码入口。Tag须解析到提交，并核对该Release包的摘要与清单，锁定这一次下载内容；可移动Tag或同版本文件被替换时不得静默接受。摘要证明完整性，不代表发布者经过审核。首期不要求开发者另行发布npm；后续增加通道也须产出同一标准包。

安装与升级流程：

1. 平台管理员从发现列表选择版本，或指定已有Release/本地标准包，查看来源、许可、兼容条件、所需能力和数据变更。社区包标明“未审核”，发现不自动安装。
2. 下载到独占待安装目录，记录源仓库、解析后提交、版本和摘要。检查包完整性、入口/资源、版本、依赖及解包路径；检查阶段不执行Core代码，不运行包声明的安装脚本。
3. 校验通过后生成或更新受控宿主组合与锁定记录，显示“待部署”。按项目既有依赖/构建流程准备隔离候选，不在当前服务目录覆盖文件。
4. 有部署权限的人在目标环境执行所需构建、数据兼容/迁移和API/worker/前端切换，完成冒烟后登记实际运行版本。需要重启就明确提示，不伪装为已热启用。
5. 注册成功后才可由SaaS管理员授权租户，再分配成员和配置业务。升级保留原授权/数据，仍按当前权限和生命周期复验；重复请求核对原安装结果。

新版本失败时保持当前有效组合；若数据已变更，依12验证的兼容恢复方案处理，不能简单重启旧代码。未完成/失败的下载只清理本次独占临时产物，原可用包及业务数据保留。远端发现结果可缓存并手动刷新，标明查询时间和来源；离线/限流不影响已安装Core，已下载标准包走同一校验链。

静态标准检查输出文件/字段、违反规则、修复方向、严重程度和稳定退出码；机器可读输出不得混入日志或秘密。合同/业务验证是明确的后续步骤，可以执行Core代码但必须使用隔离环境。必须包含清单与入口不一致、ID/来源冲突、缺必需扩展、未知版本、摘要不符、越界压缩路径、缺UI资源及重复安装等反例；不能只测正确的样例包。

本节分工沿原任务：02固定标准，03实现包检查/安装准备，07提供发现和状态界面，10验证独立安装，11交付打包与指南，12核收分发/升级和失败兼容。R12/A12的相关前置证据由这些任务分别提供，不另立一套分发任务或重复百分比。

### 5.9 底座跟随上游与 Core 独立更新

**推荐下游维护自己的宿主组合、业务Core和部署配置，底座通过正式版本依赖取得。** 本仓首期同仓开发仍需把这些边界划开；下游也可使用Git fork，但正常业务定制不改底座内部源码。前者更新版本依赖，后者整合指定上游发行的源码变更，都进入同一个版本/数据兼容预检和部署验证流程。无需首期拆成多个仓库或服务。

| 版本/文件归属 | 更新原则 |
| --- | --- |
| Nativark底座发行 | 独立版本、发行说明和修复/新功能清单；声明支持的公共合同、运行环境和数据前置 |
| 公共Core合同 | 兼容范围可机器核对；兼容新增/修复保留旧消费者行为，破坏性变化明确新版本、迁移说明和过渡条件 |
| 各Core发行 | 各有实现版本、数据版本、所需平台合同/能力和可选扩展；不与其他Core强制同号 |
| 下游宿主组合 | 锁定底座、Core、合同及产物摘要；指定更新对象，生成可复现候选，不自动追活动分支 |
| 用户配置和业务数据 | 存在明确的部署配置/Core仓储中，模板与用户值分离；更新模板不覆盖本地密钥、租户设置或历史事实 |

正式稳定合同采用语义化兼容策略；即使实现包仍是0.x，破坏性变化也须明确标记，不能把版本号小当作可随意破坏兼容的理由。每次发行声明已验证的支持范围、弃用/迁移提示与最低可恢复组合，未声明组合先拒绝升级或要求处理具体缺口，不承诺永久兼容所有历史版本。

统一更新顺序为：

1. **查看差异。** 读取已安装底座及各Core的固定版本，选择一个目标发行；列出功能/修复、API变化、依赖/数据迁移与当前用户文件差异。
2. **兼容预检。** 升级底座时核对所有已装配Core；只升级Core时核对目标Core与当前底座/直接依赖。输出可更新、需先更新依赖或不兼容的具体原因，不自动把其他模块一并升级。
3. **准备候选。** 固定来源/版本/摘要，更新受控依赖或Git差异，保留用户Core与配置。遇到用户修改过的受管文件或冲突时停止覆盖、保全差异并定位处理；不强制重置或整目录替换。
4. **数据与切换。** 由有权限的人备份需要的数据，按平台/Core各自不可变迁移链和锁顺序执行一次前进迁移，再按兼容组合部署API/worker/前端。业务Seed不作为升级步骤，已授权Core不重复初始化。长任务和unknown固定原操作/执行版本，必要时先停新排空。
5. **验证并记版本。** 复验更新对象及直接消费者、公共登录/设置和未升级Core代表链，核对配置/授权/数据/历史任务仍在；确认后记录实际运行版本。失败按已验证兼容路径恢复，不把回滚源码等同还原数据库。

独立更新指可以分别选择和发布底座/Core版本；同进程组合可能仍需重建或重启。兼容底座新功能与修复随更新获得，新增权限、外部集成或可选功能仍通过原配置/授权启用。更新工具只组织这个流程，首期不必实现后台自动部署服务或无人值守自动迁移。

| 必须验证的组合/反例 | 观察结果 |
| --- | --- |
| 当前底座＋当前Rental/轻量样例Core | 原功能基线成立 |
| 兼容的新底座＋不改版本的两个Core | 公共修复/能力可用，两个Core及用户配置/数据仍正常 |
| 同版本底座＋仅一个Core新版本 | 目标Core获得更新，另一个Core保持原版本和行为 |
| Core需要新合同/底座，或新底座不支持某旧Core | 安装前给出依赖/迁移顺序，不覆盖有效组合 |
| 自定义Core/配置、用户改动冲突 | 正常定制被保留；冲突定位且未被覆盖，不以重建环境丢弃差异 |
| 迁移失败/中断、响应丢失、旧worker仍运行 | 根据原迁移/操作记录核对，不能重复迁移/执行；只接回已验证兼容版本 |

03落实组合与锁定，06落实迁移所有者，07展示版本/状态，10验证下游复现，11提供短操作指南，12核收升级与恢复；每项仍按原PCH计分。确切命令和更新文件列表须来自落地实现，先以已批准测试发行和隔离数据验证，不直接拿用户业务库演练。

### 快速接入：开发一个 Core 的五步

给开发者的默认起点是一份可运行的最小样例。先完成“创建工单 → 分派 → 处理/关闭 → 重启后还能读到”的轻量业务闭环，再增加所需能力；具体字段和角色由01冻结。接入指南只围绕这条路径展开，权限、数据和发布约束在相应步骤就地给出。简单工作流也可按此方式成为业务Core，通用流程引擎不属于接入前置。

| 步骤 | 只需做什么 | 应看到什么 |
| --- | --- | --- |
| 1. 从样例开始 | 取得与平台版本匹配的最小 Core 样例；设置自己的ID、名称、业务对象和访问范围 | 清单/入口检查通过，正式模块可编译；不用先了解全部平台内部代码 |
| 2. 实现自己的业务 | 实现对象校验、存储、查询/动作及范围；声明路由/主按钮，选择标准列表/详情/表单或提供正文，用公共身份/权限/API接点 | 复用现有左栏/面包屑/主按钮样式和交互；对象真实保存和读取，无权用户被拒绝，只改本Core与装配 |
| 3. 安装并开通 | 生成本地标准包，经宿主检查/受控装配后注册；SaaS管理员授权测试租户，租户管理员分配成员并完成必要配置 | 平台列出该 Core，获权成员可以进入它，未授权租户不能访问 |
| 4. 检查是否接对 | 运行统一静态检查与明确的隔离行为验证，查看页面，验证另一租户/成员、重复提交、停用重开和重启读取 | 输出能定位失败文件/规则，数据和授权隔离成立，已有 Rental 功能继续正常 |
| 5. 发布给别人用 | 按模板打包指定版本，提供 README/许可与说明，发布 GitHub Release；仓库加 `nativark-core` Topic | 别人能发现版本，并在干净宿主下载安装、授权和完成同一业务操作 |

步骤1～4的默认样例不依赖模型Key、AI工具或外部供应商；步骤5在开发者自己的发行授权下进行。本仓贡献者仍遵守适用的 AGENTS 规则。需要了解平台时看[代码阅读与说明](#source-organization)及[API资料](#api-documentation)；其他细节见[标准包](#core-package-standard)、[权限与范围](#53-接点矩阵)、[生命周期](#54-三条生命周期分别记事实)、[可选AI步骤](#步骤七按需接ai工具)和[独立更新](#independent-upgrades)。

查平台已经提供的组件、公共服务、页面或API时，使用[统一能力查询](#capability-index)按任务关键词读取，结果中的正式导入、源码和接入资料可以直接交给开发Agent。

页面开发默认从[页面声明与公共模式](#declarative-page-contract)取得路由、主动作、表单保存及列表/详情的实际例子；底座提供整个管理外壳和公共控件，Core只填写自己的内容、当前条件及真实业务方法。没有业务Core时保留公共菜单与顶部整行，不制作“去掉整个后台只剩登录”的宿主。

**PCH-11的交付要求：** 最终指南每步附确切文件/源码链接、可复制命令、必要配置、预期输出和一条最常见失败处理；同时给出 Windows/PowerShell 与已支持环境的差异。入口名必须来自已实现脚本/包，不能把本段步骤文字当现成命令。保持快速部分只读即可开始，详情由链接展开；把整份任务册或历史记录交给Agent不是该体验的完成标准。

### 快速路径之外按需查阅

最少必需的是合法清单/入口、业务范围与授权接点、真实业务实现，以及所用持久化/初始化；带后台的最小样例再提供一个页面。AI、定时作业、事件回调、文件和通知只在业务使用时接入，启用后承担对应错误、权限和恢复合同。具体字段以正式源码为准。

| 遇到的问题 | 先查哪里 |
| --- | --- |
| Core未被发现 | 仓库Topic、根清单、有效Release和发现查询状态；本地包仍可单独检查 |
| 包下载了但不能使用 | 区分校验失败、待构建/部署、未注册、租户未授权、成员未分配和业务未就绪 |
| 版本/依赖不兼容 | 对照实际平台/合同/数据版本与错误定位，使用兼容版本；不跳过门禁 |
| 页面可见但访问被拒 | 核对当前租户、成员、角色及该Core业务范围；菜单不是授权凭证 |
| Agent调用不了 | 先确认是否提供并发布工具，再核对Core授权、AI政策与当前权限 |
| 重复/超时/升级后结果不明 | 读取原操作/收据和版本，按生命周期恢复；不能换ID重新执行 |
| 想更新底座或某一个Core | 先读当前/目标发行说明与兼容预检，保留自己的Core和配置；按指定对象更新，不自动联动全部Core |
| 看不懂某个接口从哪里执行 | 从API的operationId/源码链接进入Controller/Guard，再到应用服务、仓储和调用方；缺入口记为文档问题 |

### 6.2 接手前必须取得的信息

1. Core开发者先读快速指南、同版本正式合同/样例和自己的业务需求；本仓施工另读[根AGENTS](../../../AGENTS.md)及适用路径规则。维护底座者再从[README](../../../README.md)、[文档导航](../../文档导航.md)进入本专项四册，不把全部平台开发历史作为第三方接入前提。
2. 核对工作目录、分支、HEAD、暂存区、未提交归属、合并/拣选状态及并行写入者；仅在明确工作树/文件范围施工，不接管别人的WIP。
3. 取得获准的正式合同版本、平台宿主构建、目标Core范围、公共依赖和验证环境。没有合同/样例时先做PCH-01/02，不自行发明兼容SDK。
4. 明确本轮是否只读、文档、代码、离线验证或真实环境；文件里的命令不构成启服务、连库、安装、迁移或发布授权。
5. 涉及管理后台先读[admin规则](../../../apps/admin/AGENTS.md)和[界面规范](../../公共技术资料/界面规范/管理后台-界面规范.md)。不另建UI框架，不改vendor。

### 6.3 接入顺序与每步出口

#### 步骤一：定义业务边界

给出目标Core的对象、状态、人员角色、资源范围、正式命令、读写所有者、外部副作用及历史规则。明确哪些公共服务必需、哪些可选，以及是否提供AI工具；普通业务和可选AI分别给出验收结果。业务分区由Core定义，不强制继承Rental的经营空间/品类。

例如轻量工单样例用创建、分派、处理和关闭来验证接入，字段、状态和允许转换须由样例业务合同确定；不能套用租赁领取/归还。后续CRM/TMS等按自己的领域接入，客户身份共享与业务客户资料共享是不同决定，不能默认共表。

**交付：** 一页领域边界、依赖清单及代表链；不凭“CRM”名称推出完整CRM范围。

#### 步骤二：登记Core与兼容要求

通过正式公共出口声明Core身份、实现/合同/数据版本以及后端、前端、事件/作业贡献；AI工具属于可选贡献。宿主组合可显式选中多个Core，冲突ID和缺依赖拒绝，不能替换同名的其他Core。

**交付：** Core描述和装配配置；这里不接受运行时下载脚本、任意URL或模型生成包路径。正式包名/配置文件由PCH-02交付，当前没有可复制命令。

本地样例和从 GitHub Release 取得的包均按[标准包](#core-package-standard)校验，固定来源、版本和摘要。下载成功仅说明包已取得，完成受控部署并注册后才能授权租户；没有可安装Release时不能把源码压缩包当作已就绪发行。

#### 步骤三：接入当前身份和业务范围

消费原可信主体、租户、SaaS管理员授予的Core使用权及适用的成员Core分配；提供本领域资源归属、权限资源/动作及范围解析。成员分配复用原人员/角色管理，客户等其他身份沿专用合同。把用户传来的对象ID再交服务端验证，不信任前端的Core/租户/容器字段；当前界面选择不是授权集合。

**交付：** 同租户成员使用不同Core、越过租户授权分配被拒、正常访问/受限范围、撤权、跨租户/跨audience及同ID碰撞的正反例。缺授权适配保持不可用，不能用`true`临时通路证明接入。

#### 步骤四：实现数据、初始化及正式动作

定义自己的仓储和前进迁移，经SaaS管理入口直接授予测试租户Core使用权，由租户管理员分配所需成员，再由获权人员按Core规则完成必要业务绑定/配置；授权、成员分配与业务就绪分别验证。初始化不注入虚构经营事实；正式动作保留校验、对象修订、锁、幂等与原收据。明确提交前/后失败，unknown只核对原操作。

**交付：** 数据所有权和引用说明、真实持久化、同键重复/输入冲突/并发修改/失应答行为。外部调用与业务事务分开，不能因同进程就假设所有步骤原子。

#### 步骤五：接公共服务与异步处理

按真实需要接权益、文件ACL、通知、审计、可靠事件及作业；不要为了“完整插件”安装不需要的依赖。文件归属、敏感投影和事件schema由Core明确，原回调定位原业务所有者。

**交付：** 依赖缺失/撤回、重复事件、迟到回调、重启与停用行为；没有真实供应商证据时标未验，不返回假成功。

#### 步骤六：挂载业务UI

通过[正式页面声明](#declarative-page-contract)提供路由、名称/父级、正文和操作及语言/权限要求。菜单、面包屑、页名和主按钮由框架统一呈现；列表、详情及表单优先复用已有模式，作者提供自己的字段与真实业务方法。左栏、顶部整行、铃铛、休息及收展保持公共归属，按成员当前授权展示多个Core，清晰标识业务。新Core不改壳内部判断、重复维护菜单或自写按钮样式。

**交付：** 可操作真实页面、声明式主动作、直接URL权限、空/错/加载态、校验/确认/单次保存、未保存保护与旧请求/动作清理；无Core完整外壳可用。浏览器验证和代码/类型证据分别登记。

#### 步骤七：按需接AI/工具

普通页面业务先独立可用。开发者可选择不提供AI工具，此时明确登记未提供，验证Agent不能查询或调用该Core，不阻断普通业务。确需AI时，登记严格输入输出、事实来源、字段释放、风险/副作用、业务批准与原收据查询，并由原通用任务和Gateway机制消费。MCP与Harness只经各自正式受控合同接入；工具目录及调用须核对租户Core授权、适用成员分配和当前权限，不能由扫描API或模型推断生成开放范围。

**交付：** 不启AI仍可业务运行；启用时撤权/缺依赖/重复/unknown处理正确。工具说明和模型内容不能代替授权或业务批准，不允许绕开原Core。

#### 步骤八：运行一致性与独立接手验证

使用平台正式合同测试、Rental对照和非Rental样例验证接点，包括无Core公共后台、同部署/同租户双Core、不同租户及成员授权、单Core停用重开、统一期限及有/无AI工具组合。记录冻结的平台构建，接入期间仅修改Core及允许的组合配置；需要改平台合同就停止本次冻结验证，修复后重新固定。

由独立开发者/AI按照本指南复现，不提供本会话记忆或人工隐藏步骤。收集卡点并修资料；不以作者自己演示成功当独立接手通过。

**交付：** 实际命令、退出码、环境、构建/合同标识、所改文件范围、正反例及未验项。当前测试命令应由PCH-11随真实实现补齐，不能拿`docs:check`替代Core接入测试。

#### 步骤九：升级、停用与回退

先检查API/worker/客户端/数据兼容组合和历史依赖，再开放新准入。停用保留数据/配置，重新授权复用原绑定并按当前条件恢复；订阅续费不恢复主动停用。停新、排空、历史读取和移除实现分阶段进行，未核对完unknown或在途依赖不能卸载唯一执行者。

**交付：** 最低可回退程序、历史读取、原收据、失败恢复与残留清单。改用另一Core不自动迁移旧业务数据；数据库恢复、发布和生产启用另需批准。

日常只更新底座或一个Core时，按[独立更新](#independent-upgrades)选择目标版本、检查兼容并保留用户配置/业务数据。底座修复可在合同兼容时由旧Core直接消费；目标版本不兼容则列出迁移/依赖顺序，不静默更新其他模块。

#### 发布并让别人发现

在自己的发行授权下，用实际打包入口生成与清单版本对应的发布包和摘要，在GitHub发布版本Tag/Release，README链接安装步骤、兼容范围和许可，并设置仓库Topic `nativark-core`。Topic无需平台人工逐个录入即可进入社区发现候选，但不代表平台已审核。根清单及包格式错误应有诊断，不能列成可安装。

由另一个干净宿主按发布包走一遍安装、注册、租户授权和业务验证，登记实际来源/版本/摘要与命令结果，再说明该版本可安装。外网发现或下载只做了替身/离线检查时明确未验真实GitHub；不为证明流程擅自公开现有仓库或创建发行。

### 6.6 明确禁止的接入捷径

不把CRM/TMS加进租赁枚举；不将整个Prisma client、管理员token或任意HTTP/SQL能力交给Core适配；不靠前端隐藏代替后端授权；不以空成功或全unavailable做“通用平台”；不删除原Rental/AI源码与测试；不复制另一树dist/生成物；不根据超时换原操作ID；不因资料内有命令便启服务、迁移或发布。
