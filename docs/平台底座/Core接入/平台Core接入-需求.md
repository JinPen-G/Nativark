# 平台底座与业务 Core 接入需求

版本：v1.0；建立日期：2026-10-31。

> 正式需求依据：负责人授权按“平台底座可接入不同业务 Core、Rental Core 内继续做品类治理”两个层级整理。未经明确授权，不得改变本册范围、业务边界及验收。此次只建立文档，不授权代码抽离、依赖安装、数据库迁移、启服务、部署或发布。
> 配套：[开发任务](平台Core接入-开发任务.md) · [开发记录](平台Core接入-开发记录.md) · [协作接续](平台Core接入-协作接续.md) · [接口与生命周期设计](平台Core接入-接口与生命周期设计.md) · [接入指南](平台Core接入-接入指南.md)。后两册是实施设计与接手准备，不是已经发布的 SDK/API。

## 1. 产品目标与两个层级

### 1.1 目标

将现有系统演进为可独立装配的 SaaS 平台底座。平台复用身份、租户、授权、应用框架及适用的公共服务；业务 Core 提供自己的领域对象、规则、数据、页面和业务动作。Rental Core 是首个接入模块，后续开发者或 AI 可依据正式契约接入 CRM Core、TMS Core 等，不必修改平台通用内部实现，也不必将非租赁业务伪装成租赁订单。

“便捷替换”指**工程上的独立接入、构建与部署选择**，不是经营中的空间一键变行业、运行时任意代码热插拔，亦不是租赁数据自动转换成 CRM/TMS 数据。首期同进程模块化，不预设微服务、拆库或更换 ORM。

### 1.2 层级与归属

| 层级 | 管理内容 | 不负责 |
| --- | --- | --- |
| 平台底座与 Core 接入（本专项） | Core 身份与合同、可信装配、授权和公共服务接点、页面模块接入、独立运行及替换验证 | 全行业通用订单/库存/计价引擎，行业字段配置和业务决策 |
| Rental Core | 租赁商品、资产、库存、报价、订单、交付、归还、结算及租赁规则 | 被 CRM/TMS 强行复用的万能实体或状态机 |
| Rental Core 品类治理（CAT-GOV） | 摄影/露营/车辆/工程及其他租赁类型的定义、能力组合、版本发布和空间采用 | 更换整个业务 Core、平台插件管理或跨行业数据迁移 |

CRM/TMS 是不同业务领域的 Core 示例，不作为 RentalCategoryCode 新值。租赁物流 capability 仍属于 Rental Core 的履约扩展，不因此成为独立 TMS。品类定义版本、能力实现版本、Core 实现版本、平台接入合同版本及数据结构版本分别管理，不能互相代替。

### 1.3 交付范围与不包含

必须交付：

- 可不装配 Rental Core 的平台公共能力；Rental Core 通过明确适配重新接入并保持原行为。
- Core 公共接入合同、可信注册/装配入口、生命周期与版本兼容检查。
- 身份/范围/权限、公共服务、数据和事务、后台 UI、作业/事件的真实接点。
- AI Native 与 MCP 等已批准入口的行业适配边界；未启用这些入口不阻止普通业务 Core 运行。
- 一个真实持久化的最小非租赁 Core 及代表性业务闭环，用于证明边界；完整 CRM、完整 TMS 产品另立需求。
- 可复现接入样例、接入指南、合同一致性验证、升级/停用/回退及独立接手证据。

不包含：任意插件上传或执行、插件商城、通用低代码/工作流/计价引擎、同时更换 Runtime 与 Provider SDK、跨语言/任意数据库承诺、自动把旧业务转换成新行业、同租户跨 Core 混合交易和跨库原子事务、完整 CRM/TMS、自动开源或发布。首期允许分别构建 Rental 宿主与非租赁宿主，不要求一个部署内多 Core 热切换；确需多 Core 同时经营时须另定产品绑定与隔离规则。

### 1.4 与既有依据的关系

- 原[租赁平台需求](../../租赁平台/租赁平台-需求.md)、[Rental Core 任务](<../../Rental Core/Rental Core-开发任务.md>)和[品类治理需求](<../../Rental Core/品类治理/品类治理-需求.md>)保留独立身份（品类治理按归属移入Rental Core目录）；不取消原功能，不继承或重算其完成率。原“一个租赁空间一个品类”继续约束 Rental 宿主，不提升为所有 Core 的强制领域模型。
- 原[通用 SaaS 未来方案](<../未来规划/平台底座-通用化与开源方案.md>)保留设计来源与开源愿景。本专项承接平台/Core 工程边界和接入交付，不把开源、外部身份系统全部适配或远程服务化纳入首期。
- [AI Native](<../../AI Native/AI Native-需求.md>)、[MCP 服务](../../MCP服务/MCP服务-需求.md)、[Harness 插件](../../Harness插件/Harness插件-需求.md)各自负责原机制与端侧消费；本专项只将行业耦合移到真实适配接点，不重建或恢复其他专项。
- 本专项和 CAT-GOV 不互设“全专项完成”前置。触及同一公共契约时由唯一作者提供固定版本及回归证据，分别验收平台边界和租赁业务；不能用其中一项完成代替另一项完成。

## 2. 能力与数据归属

| 领域 | 平台底座职责 | Core/适配职责 |
| --- | --- | --- |
| 身份、租户、人员与组织 | 可信主体、租户隔离、角色/授权机制、会话失效 | 业务资源归属、细粒度范围映射、动作前提；不自签权限 |
| 业务容器 | 受权绑定、生命周期记录及隔离接点 | Rental 经营空间/地点、CRM 团队或其他经定义的资源模型；不得把缺范围当全租户 |
| 商业权益 | 复用适用的订阅/权益判定与当前证据 | 声明本 Core 功能及门槛；不把 Rental 套餐/品类白名单硬套给所有 Core |
| 客户与会员 | 可复用身份引用和经明确归属的公共主档接点 | 租赁会员、企业租赁资格/授信、CRM 客户关系等具体业务；同名 customer 不自动共用表 |
| 金额与支付 | 可复用基础精度、受控支付运输等已确认公共服务 | 订单金额、租金/押金/预授权、企业应收、运输费用等业务账与提交事实 |
| 文件、通知、审计 | 存储/发送/审计基础机制和安全边界 | 文件业务 ACL、敏感字段投影、消息内容及业务事件事实 |
| 后台框架 | 登录外壳、导航容器、主题/语言/UIArc适配、查询隔离 | 业务页面、权限声明、对象链接与工作台内容 |
| AI Native | 原任务/编排、Gateway、模型预算、恢复与通用审批关联机制 | 受权事实、工具、业务批准参与者、业务执行和原收据 |

现有目录名不是归属证明。`platform` 中的租赁企业结算不因目录名称就自动成为公共服务；同库也不表示任意模块可跨表写入。先列出读写所有者，再决定保持、抽取或经适配调用。

## 3. 正式需求

### PCH-R01：依赖方向与最小宿主

1. 平台公共实现不得为启动、登录、解析租户、显示公共设置而强制导入 Rental 业务实体、控制器、作业或表。保留一个显式宿主装配层连接平台与具体 Core；该层引用 Rental 是合理的，不能把全部耦合移到另一个叫“平台”的目录后宣称完成。
2. 首期先建立包/模块边界，可继续同进程同数据库；业务模块拥有自身仓储和迁移。平台通用代码到行业内部实现的反向导入须有自动检查。
3. 未配置业务 Core 时公共管理面可启动，但业务入口明确不可用；不能默认注入 camera、演示租户、全权限或空成功适配。独立构建验证不加载 Rental 模块和 Rental 迁移/Seed。

### PCH-R02：Core 身份、合同与可信注册

1. 提供稳定 Core 标识、实现版本、接入合同版本、所需数据版本、公共依赖与可选扩展的描述和校验；同标识冲突、未知必需合同、缺依赖及不兼容组合在开放前拒绝。
2. 后端服务/路由/作业与前端模块通过开发者维护的受控装配入口注册。新增 Core 允许新增自身实现、迁移、合同和宿主组合配置，不应逐个修改平台内部领域判断。
3. 注册是部署行为，不授予租户权益、操作者权限或业务批准；不接受管理员/模型提交任意包路径、脚本、SQL、URL 来加载代码。
4. 接入合同必须有正式公共出口。既有共享协议仍从 `@rental-os/shared` 复用；若实施时独立分包，先确定唯一生产者、版本及兼容转接，禁止私有同名 DTO 和深层导入绕过出口。

### PCH-R03：当前身份、范围与动作授权

1. 复用原 Auth/Guard/ALS 的可信身份、audience、租户及撤权语义，将租赁专属路径/能力判断移入登记的 Rental 授权适配，而不是删除安全门禁。
2. 公共上下文只承载经过验证的主体/租户/受权资源范围及绑定信息，Core 可提供有命名空间、经校验的业务扩展。Rental 的 category/location 不是所有 Core 必填字段。
3. Core 声明权限资源与动作，但平台和正式业务授权共同裁决；缺策略、缺范围映射、不支持的数据范围均 fail closed。操作者、客户、员工、平台管理员不能因共用壳而互换 audience。
4. 业务请求、后台任务、缓存回放、导出及工具调用使用同一范围规则。缓存、导航隐藏、客户端声明 Core/tenant/workspace 均不能自授权；Core 注册/切换不能放宽既有租户隔离。

### PCH-R04：绑定、初始化与停用

1. 区分程序已装配、部署兼容、租户获准使用、业务容器已绑定、业务配置就绪及当前动作获准。未完成阶段不以单个 enabled 表示全部可用。
2. 平台建立受权绑定与操作记录，Core 在约定事务边界内完成业务初始化；缺实现或失败不留下可经营的空壳、不植入演示事实。重复请求和首响应丢失读取原结果，不重复初始化。
3. 现有 Rental 空间继续按原品类及采用修订运行；首次抽离只建立确定性映射，不偷换品类或给无证据历史补最新版本。
4. 关闭新准入、停止新任务、业务排空、历史只读、卸载代码分别定义。停用不等于删除数据、取消已提交业务或免除善后授权；有在途/unknown、回调、历史执行依赖时不得直接卸载唯一实现。
5. 原容器换成另一个 Core 属显式迁移项目，不作为普通设置。首期换装通过独立宿主/新业务容器验证，不把原 Rental 空间原地改成 CRM。

### PCH-R05：数据、事务与历史

1. 为平台表、Core 表、引用、公共主档和迁移链指定唯一所有者。平台只经合同读取所需业务证据，不能到各行业表中拼通用业务判断。
2. 公共外部合同不得泄漏 Prisma/Nest/供应商类型；适配器内部可沿用现有 ORM。跨模块同事务使用受限事务能力/协调器，不能把整个可写 Prisma client 当插件通用权限。
3. 保持现有业务提交、资源锁、幂等、审批消费和收据原子性；抽离目录或改依赖不能打破原事务。若未来跨进程，另定可靠提交/补偿与恢复合同，普通 HTTP 重试不等于原子事务。
4. 对象引用须消除不同 Core、租户和容器同名/同 ID 冲突；历史对象、动作、原执行版本和收据保持可定位。未知结果只能核对原操作，不借新 Core、新键或新引擎重做。
5. 迁移只前进、可核对且可演练；保留旧源码、测试和历史事实，禁止清库、重放旧资金或篡改已应用迁移。

### PCH-R06：公共服务、事件与后台作业

1. 身份、订阅权益、文件、通知、审计及适用的外部集成通过窄接点供给；强依赖缺失阻止受影响能力，弱依赖缺失仅明确降级对应功能，不能假授权或静默少做业务步骤。
2. 事件明确所有者、命名空间、schema、租户/对象关联、幂等及投递/消费结果；先保留原可靠事件/事务机制，不另建消息总线或假设恰好一次。
3. 作业由 Core 显式登记执行者、版本、范围和恢复规则；每个任务固定原业务归属。未装配 Core 不启动其作业；升级、重启、延迟事件和回调不会路由到不兼容执行者。
4. Webhook 依据原支付/业务引用和受控注册定位 Core，不能凭外部请求自报标识获得路由权限。通知受理不等于送达，集成可调用不等于正式渠道通过。

### PCH-R07：后台壳、页面与端侧合同

1. 保留 React、UIArc 适配、主题、语言、音效和布局。Core 提供类型化页面/路由/导航/权限贡献；公共壳不逐项导入行业页面或靠租赁枚举判断所有业务。
2. 路由/动作和对象链接使用受控命名空间及登记映射，未知模块/必需协议明确拒绝；不执行模型返回的任意路径或页面脚本。前端装配不代替后端授权。
3. 会话/业务绑定变化时取消旧请求，隔离查询键及页面状态，避免相同对象 ID 串 Core/租户/容器；未保存表单有明确处置，不自动提交。
4. Rental 既有 Web、客户与员工 API 的语义和历史深链接保持兼容；不因抽离要求复制后台页面。非租赁最小样例验收后台，完整非租赁小程序/APP不在首期；已有 Rental 端按受影响链路回归。

### PCH-R08：AI Native 与受控工具的可选接入

1. 普通业务 Core 无需 AI、模型 Key 或 MCP 即可运行。启用 AI 时，通用运行机制通过合同消费 Core 的事实、工具、动作、批准参与者和收据，不强制加载 Rental 订单服务。
2. 行业场景和权限留在适配层，模型不重算正式金额/库存/状态，不获得任意 SQL/HTTP/终端工具。工具注册、对外发布、字段释放及一次正式批准分开。
3. 复用唯一 Gateway、财务预算单账、任务累计资源、当前授权及原 unknown 恢复；Runtime、Provider SDK 和 Core 替换分别管理，不能借本专项启动另外两条迁移。
4. MCP及Harness沿各自专项合同消费；本专项交付业务适配接点与适用的现有消费者证据，不以接入某客户端等同全客户端通过，也不重建OAuth/工具目录。本地自付模型与委托服务端模型沿原边界处理。

### PCH-R09：Rental 适配与不退化

1. 将现有 Rental 作为真实首个适配，而不是仅保留空接口；继续消费品类解析、空间绑定、能力 Hook、价格/规则/检查快照及原业务服务。
2. 租赁品类发布和采用仍由 CAT-GOV 负责。Core 插拔不改写品类版本正文，也不能绕过未实现的正式采用/动态品类门禁。
3. 核对所有已支持的正式入口、定时作业、事件、客户端与恢复路径。按原验收层级证明授权、金额、库存、状态和历史行为不退化；原未完需求明确保留，不因本专项通过而宣布 Rental 全部完成。

### PCH-R10：非租赁样例与独立接手

1. 在同一套平台合同上提供一个最小非租赁 Core。实现前冻结样例范围与验收链，优先选择不涉及资金/库存的新领域，例如 CRM 的线索建立、授权跟进与业务阶段变更；完整CRM/TMS需求不随样例扩大。
2. 样例必须有领域校验、持久化、授权拒绝、操作幂等/并发冲突、页面和审计，不能只返回内存假数据或把 Rental 模型重命名。
3. 平台合同及公共构建冻结后，接入只改样例 Core、其迁移和批准的装配配置，不修改平台通用源码、不增加 `if coreId === sample` 特例；发现合同缺口先修合同并重新冻结，不偷偷放行。
4. 由未参与接口设计的开发者或独立 AI，在不依赖本会话记忆的条件下按指南完成构建、接入和代表性操作。记录卡点、所改文件、实际命令与退出码；无独立接手试验不得宣称“可快速接入”。不承诺未经测量的工时。

### PCH-R11：接入资料与可复现交付包

1. 同步提供模块职责图、正式公共出口、必需/可选合同、生命周期与错误语义、实现样例、权限/数据归属、迁移与回退、测试入口和运维说明。
2. 指南区分已实现、设计中和不支持；未实现接口不得给出可复制执行的假命令或虚构包名。合同源是唯一字段定义，文档解释语义与使用顺序，不复制多份易漂移接口。
3. 实施交付时固定包/合同/宿主组合、锁定依赖与产物、示例配置及运行前置；干净环境接入不依赖开发者私有 output、别树 dist、隐含本地 Key 或开发服务器。
4. 提供 Core 合同一致性测试，覆盖正常、撤权、缺依赖、失败/unknown、并发、历史兼容及停用。一次性脚手架可在边界稳定后提供，不把生成空文件当完成。

### PCH-R12：兼容升级、审查与发布门槛

1. 升级记录平台接入合同、Core实现、数据结构、作业及消费者兼容组合和最低回退版本；多个 API/worker 实例逐一核对，未知组合拒绝新准入。
2. 程序回退、Core配置停用、业务容器迁移和数据库恢复分别设计；回退不撤销已提交事实。已出现新结构/新 Core 数据后，不能接回只认识 Rental 的旧程序。
3. 完成一轮独立审查并修复已确认问题，定向复验；保留未验环境项。不递归扩展审查、不以类型或静态绿色代替真实持久化及宿主证据。
