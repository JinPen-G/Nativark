## 1. 产品目标与两个层级

### 1.1 目标

将现有系统演进为**公共能力实际可运行、对 AI 开发友好的 AI Native SaaS 底座**。平台复用身份、租户、授权、应用框架、受控AI机制及适用的公共服务；业务 Core 提供自己的领域对象、规则、数据、页面和业务动作。Rental Core 是首个接入模块，后续开发者或开发 AI 可依据正式契约、样例和验证入口接入 CRM Core、TMS Core 等，不必修改平台通用内部实现，也不必将非租赁业务伪装成租赁订单。

本次交付同时满足三件事：**现在已支持的功能继续正常使用；新 Core 按同一标准接入；别人拿到简明指南和自己的业务要求，就能让开发 Agent 实现、检查并交付可安装的 Core。** 简单体现在入口少、默认路径清楚、示例可运行和错误可定位，完整规则可按需查阅。

AI友好覆盖整个平台的可理解性：从统一入口找到模块职责、真实调用链、公共API/扩展接口和验证方法，能准确判断该改底座还是自己的Core。底座与各Core分别维护版本，使用者可在兼容范围内更新底座取得新能力/修复，或只更新一个Core，保留自己的业务实现、配置和数据。

统一能力索引支持按名称、类别和模块查询已有功能，再打开源码与接入说明。平台公共服务、UI组件、页面、API、Core及可选扩展均有可发现入口；各模块维护自身权威声明，组合目录随同版本源码生成。

“AI开发友好”指开发阶段的接口、模块边界、可运行样例、错误说明和验收步骤足以支持独立接手；业务 Agent 不因此获得编写、安装、注册或授权 Core 的权限。底座具有真实公共实现，不以空目录或模拟成功作为交付；无 Core 时不另开放通用问答、资料整理或任意工具执行产品。

“便捷接入”指**工程上的独立接入、构建与部署装配选择**。首期同仓分模块，明确正式出口、版本、仓储和迁移归属，可继续同进程同数据库；独立构建须排除未选 Core 的源码依赖和迁移/Seed。仓库分拆不作为首期门槛，边界稳定后按独立维护和发行需要决定。经营中的空间一键变行业、运行时任意代码热插拔、租赁数据自动转换成 CRM/TMS 数据均不在范围内。

### 1.2 层级与归属

| 层级 | 管理内容 | 不负责 |
| --- | --- | --- |
| 平台底座与 Core 接入（本专项） | Core 身份与合同、可信装配、租户授权、多 Core 隔离、公共服务和可选AI接点、页面模块接入、独立运行及接入验证 | 全行业通用订单/库存/计价引擎，行业字段配置和业务决策 |
| Rental Core | 租赁商品、资产、库存、报价、订单、交付、归还、结算及租赁规则 | 被 CRM/TMS 强行复用的万能实体或状态机 |
| Rental Core 品类治理（CAT-GOV） | 摄影/露营/车辆/工程及其他租赁类型的定义、能力组合、版本发布和空间采用 | 更换整个业务 Core、平台插件管理或跨行业数据迁移 |

CRM/TMS 是不同业务领域的 Core 示例，不作为 RentalCategoryCode 新值。租赁物流 capability 仍属于 Rental Core 的履约扩展，不因此成为独立 TMS。品类定义版本、能力实现版本、Core 实现版本、平台接入合同版本及数据结构版本分别管理，不能互相代替。

### 1.3 交付范围与不包含

必须交付：

- 无业务 Core 时可启动、登录和进入公共管理界面；租户无 Core 授权时提示联系 SaaS 管理员授权业务 Core。Rental Core 通过明确适配重新接入并保持原行为。
- Core 公共接入合同、可信注册/装配入口、SaaS管理员对租户的直接授权、租户管理员对成员的Core分配、生命周期与版本兼容检查。
- 同一部署可装配多个不同 Core；同一租户可同时使用多个获授权 Core。停用保留数据，重新授权后按当前条件恢复使用，其他 Core 的无关功能不受影响；首期沿用租户统一订阅期限。
- 身份/范围/权限、公共服务、数据和事务、后台 UI、作业/事件的真实接点。
- AI Native 与 MCP 等已批准入口的行业适配边界；Core可不提供AI工具，注册、授权和普通业务后台仍可用，Agent不能查询或执行该Core的业务。
- 一个真实持久化的最小非租赁 Core 及代表性业务闭环，用于证明边界；完整 CRM、完整 TMS 产品另立需求。
- 可复现接入样例、一页快速接入与详细参考、可直接交给开发 Agent 的任务模板、统一检查入口、升级/停用/回退及独立接手证据。
- Core 包清单、版本与发布包标准，GitHub `nativark-core` Topic 的轻量发现入口、固定版本下载与受控安装、状态和失败诊断；无网络时可使用同格式的本地已下载包。
- 拆分前的现有功能清单与分层验证基线，每个切片及最终组合的前后对照；已有页面、API、客户端、业务数据和异步恢复均有去向。
- 全平台自有代码的职责/依赖盘点、逐模块整理、必要源码文件备注和复杂逻辑说明，清晰的代码阅读路线及与实现同步的API文档；消除无依据的兜底、重复封装和吞错，保持必要业务与安全校验。
- 底座和各Core独立版本、上游更新/兼容预检、迁移归属、升级与恢复说明，以及保留用户自定义Core/配置/数据的升级验证。

不包含：无Core的通用Agent产品、租户或业务Agent任意上传/执行代码、交易收费型插件商城、通用低代码/工作流/计价引擎、同时更换 Runtime 与 Provider SDK、跨语言/任意数据库承诺、自动把旧业务转换成新行业、跨Core联合查询/业务联动/混合交易、跨库原子事务、完整 CRM/TMS。提供发布方法与产物规范，不自动发布任何仓库、包或生产环境。Core 可下载到待安装区，通过受控构建与部署装配生效，首期不要求运行中热加载代码。

### 1.4 开通与使用

开发者实现并通过接入检查 → 按标准发布指定版本 → 平台管理员发现或指定 Core 来源 → 下载校验并准备安装 → 部署人员按既有流程装配并完成兼容检查/注册 → SaaS管理员直接授权给租户 → 租户管理员分配成员可使用的Core → 获权人员按Core自身规则完成必要业务配置 → 当前用户按角色和数据范围使用。同一负责人可以兼任平台管理员和部署人员，但安装、部署、授权的状态分别保存；注册和租户授权均不直接赋予员工全部业务权限。本仓开发时可从本地标准包进入同一校验链。

首期租户需要开通Core时联系SaaS管理员，不新增Core在线申请或审批流程；既有订阅升级、续费申请仍按原专项运行。成员分配复用现有账号与角色管理，不能授予本租户未获授权的Core。多Core可采用切换入口或按业务分组导航，由界面实现选择；须能辨认当前Core，权限、状态和缓存互相隔离。

| 使用情形 | 应有行为 |
| --- | --- |
| 部署未装配任何Core | 公共登录、租户/账号/权限及适用公共设置可用；业务入口不可用，不能创建演示Core补齐依赖 |
| 部署有Core，当前租户尚未获授权 | 进入公共后台并提示联系管理员授权业务Core；服务端拒绝未授权Core的业务访问 |
| 租户已开通Core，当前成员未获分配 | 公共后台及本人其他获权Core可用；该Core普通业务不可访问，需要使用时联系租户管理员 |
| 租户获授权但某Core业务配置未就绪 | 保留公共面和该Core获准的配置入口，明确缺项；其他已就绪Core继续可用 |
| Core已就绪但用户缺少业务权限 | 仅开放该用户有权访问的页面和动作；Core开通不代替角色授权 |
| Core未提供AI工具 | 常规页面、API和业务动作按原权限使用；Agent明确不能查询或操作该Core |
| Core提供了AI工具 | 只在租户Core授权、适用的成员Core使用范围、当前用户权限、资源范围、已发布工具、AI权益和必要批准均满足时调用 |
| 某租户的Core被停用 | 关闭该Core普通业务入口和新的Agent任务，保留业务数据及配置；必要历史读取和在途收尾按R04受控处理，公共后台和其他Core照常可用 |
| 停用后重新授权同一Core | 复用原数据与业务绑定，复核当前权限、订阅及依赖后恢复使用，不重新初始化或自动重发旧操作 |

### 1.5 跨 Core 协作的后续方向

未来可按批准的场景关联客户/订单等对象，提供跨Core查询或由一个Core向另一个Core发起正式业务请求。本期固定Core命名空间、对象引用、受控调用及事件接点，不开放数据互通本身；同租户同时获权不等于跨Core全部数据互读。数据仍由所属Core维护，跨Core访问和动作逐项核验权限、字段和业务条件；具体设计及前置见[未来方案](../未来规划/平台底座-通用化与开源方案.md#cross-core-collaboration)。

### 1.7 GitHub 发现与安装的首期体验

开发者在独立公开仓库设置 `nativark-core` Topic，提供标准清单、README、LICENSE 和可安装 Release。平台的“发现 Core”可列出符合格式的仓库，显示来源、版本、兼容性、许可和是否经过平台确认；社区自报标签始终明确标记为未审核。Topic 负责被找到，版本 Tag 与发布包负责确定安装内容。

平台管理员选择版本后，查看兼容性及数据变更说明，下载并校验发布包，取得可复现的待部署组合。安装需要构建、迁移或重启时明确显示下一步，由有部署权限的人按简明指南完成；不能把“下载完成”显示成“业务已启用”。部署并注册成功后，继续原租户授权与成员分配流程。单个 Core 升级失败不替换当前有效版本，发生数据变更后的恢复按兼容方案办理。

没有可安装版本的仓库只能显示为“仅源码/发布包未就绪”。查询失败、GitHub 限流或网络离线时保留已安装 Core 的正常运行，提供已下载包或明确的重试入口。私有 Core 和本地自用 Core 无须公开或添加 Topic；首期不要求接入所有私有托管平台。

### 1.8 无 Core 的公共能力与轻量业务

无Core时，租户账号能够登录、退出、查看/维护本人资料与安全设置；具备相应角色的租户管理员可以管理成员/角色、租户基本资料和已提供的公共外观/语言、订阅与基础集成设置。实际字段沿既有正式规则，不把Rental的品类、商品、地点、价格等业务设置设为公共后台的前置。必要公共设置能真实保存并在重启后读取，各租户隔离；业务和Agent入口按Core及工具授权开放。

管理后台的完整外壳归底座，包括左侧导航区域及搜索/收展、右侧内容容器、顶部面包屑/当前页标题这一行，以及其右侧铃铛、休息和面板收展控件。无Core或租户尚未获业务授权时，公共菜单、面包屑和这些公共控件仍保留；业务菜单、业务页面和业务主按钮不出现，内容区显示适用的公共页面或联系管理员提示。公共设置自己的保存等操作照常使用统一动作入口。铃铛可展示空态及已实现的公共消息，不能为保留控件而读取未装配Core；面板收展保留框架交互，不因此开放无Core通用Agent。

Core也可以很小，例如工单的“创建→分派→处理→关闭”，或某一业务的简单审批/工作流。它们使用同样的身份、权限、存储、页面和可选AI接点，不必带租赁订单/库存/资金。首期最小非租赁样例优先采用简单工单，具体字段和状态由PCH-01冻结；这不把通用流程设计器、BPMN引擎或复杂工单产品变成底座内置能力。

### 1.9 以最少声明接入业务页面

Core作者只需在本Core定义页面路由、名称/上级、访问要求、正文组件及页面操作。框架从同一份声明生成菜单、面包屑和页头，将“新建工单”“保存”等操作放入已经设计好的主操作区，沿用统一按钮、主题、尺寸、图标语义、动效和反馈。作者不需重写后台壳、顶部栏、按钮CSS或逐处改底座路由判断。页面动态标题及对象动作可由本页受权数据提供，不能泄露无权对象信息。

| 开发者表达的业务内容 | 底座默认完成的公共工作 |
| --- | --- |
| 路由、名称、菜单分组、父级、正文组件与访问要求 | 导航/搜索、选中态、面包屑/页名、懒加载和不存在/无权/未就绪状态；同一声明避免多份维护 |
| 操作名称、打开页面/弹窗/提交表单/执行命令、权限与必要确认 | 统一主/次操作呈现、空间不足时的操作菜单、加载/禁用/成功/失败反馈、键盘交互与重复点击保护 |
| 表单字段、校验与保存方法 | 原表单布局、校验提示、顶部保存和回车提交共用一次真实请求、未保存提醒、冲突/失败时保留输入 |
| 列表列定义、筛选条件、数据读取及行操作 | 现有列表/工具栏、加载/空/错态、分页/排序、布局适配；有真实数据与权限合同后按需启用导出/批量等能力 |
| 详情分组、对象标识、状态与允许动作 | 原详情布局、返回/父级导航、标准状态与操作区域；领域状态含义仍由Core决定 |
| API调用、资源键、成功后需刷新的数据 | 复用认证请求、可定位错误、当前租户/Core/容器缓存隔离、撤权及离页后的旧响应处理 |
| 通知内容、受权对象目标或可选文件/作业贡献 | 复用通知展示与已注册导航、文件/作业接点；业务ACL、字段释放和服务端执行仍由原所有者裁定 |

优先把现有React/UIArc适配组合成少量可选页面模式，普通列表、详情和编辑页可直接复用；特殊业务可以提供自己的正文组件与类型化操作，仍使用同一外壳和公共服务。声明来自受控Core代码，不建设任意JSON执行器、可视化流程设计器或第二套UI框架。默认只要求实际使用的字段/能力，不让简单页面实现所有扩展，也不由框架猜测业务权限或状态机。

## 3. 正式需求

### PCH-R01：依赖方向与最小宿主

1. 平台公共实现不得为启动、登录、解析租户、显示公共设置而强制导入 Rental 业务实体、控制器、作业或表。保留一个显式宿主装配层连接平台与具体 Core；该层引用 Rental 是合理的，不能把全部耦合移到另一个叫“平台”的目录后宣称完成。
2. 首期在同一仓库建立可独立构建的包/模块边界，可继续同进程同数据库；业务模块拥有自身仓储和迁移。平台通用代码到行业内部实现的反向导入须有自动检查；同仓不允许依靠深层导入绕过公共合同。
3. 未配置业务Core或当前租户未获Core授权时，公共管理面可启动、登录并进入；租户显示联系管理员授权业务Core的提示，业务入口不可用。不能默认注入camera、演示租户、全权限或空成功适配；独立构建和公共初始化不加载任何未选Core及其迁移/Seed。
4. 无Core不启动行业作业，不开放无关的通用Agent任务；公共设置页面可用不代表Agent获准执行设置或其他操作。
5. 全量梳理本仓自有平台代码、Core及适配、UI/客户端、共享合同和必要脚本/验证入口的职责与依赖，明确保留、迁移、合并或待处理归属。第三方vendor、生成物、历史原稿单独识别并保留来源，不按代码整理重写。按模块和真实调用链推进，不只整理新建目录。
6. 目录、命名、正式出口和模块层次一致，公共实现、Core业务、宿主装配及外部适配可辨认。以实际用途决定拆分，避免一个巨型通用服务，也不为一层转发或假想扩展制造多层抽象。完整盘点与处理结果在PCH原记录可追溯，不能以文件移动数量或注释覆盖率代替验收。
7. 租户无Core仍能使用1.8所列公共面，保存设置不要求虚构业务空间、Core授权或模型Key；平台管理角色与普通租户角色仍有各自权限。

### PCH-R02：Core 身份、合同与可信注册

1. 提供稳定 Core 标识、实现版本、接入合同版本、所需数据版本、公共依赖与可选扩展的描述和校验；同标识冲突、未知必需合同、缺依赖及不兼容组合在开放前拒绝。
2. 后端服务/路由/作业与前端模块通过开发者维护的受控装配入口注册。新增 Core 允许新增自身实现、迁移、合同和宿主组合配置，不应逐个修改平台内部领域判断。
3. 注册是部署行为，不授予租户权益、操作者权限或业务批准；不接受管理员/模型提交任意包路径、脚本、SQL、URL 来加载代码。
4. 接入合同必须有正式公共出口。既有共享协议仍从 `@rental-os/shared` 复用；若实施时独立分包，先确定唯一生产者、版本及兼容转接，禁止私有同名 DTO 和深层导入绕过出口。
5. 同一部署支持注册多个不同Core；每个Core的页面、权限、对象、作业和可选工具均归自身命名空间，不覆盖其他Core。首期不要求同一Core标识同时运行多个不兼容实现版本。
6. 提供统一 Core 包清单和机器校验，约定身份/来源、显示信息、许可、实现与兼容版本、模块入口、权限与依赖、迁移资源、可选页面/AI/作业贡献。必需项与按需扩展分开；最小 Core 不为未使用能力实现空 Hook。清单、正式类型、运行时 schema 和校验器使用同一契约来源。
7. 清单只能声明包内受控入口与能力；检查包和发现仓库不得执行 Core 代码。实际模块在管理员选择、校验并进入受控组合后加载。首期 Core 是可信服务端扩展，接口边界不等于恶意代码沙箱；新 Core 不获得平台内部任意仓储或其他 Core 的通用执行接口。
8. 新 Core 遵循标准后只需增加自身包及宿主登记的组合配置，不能修改 Auth/Guard、公共后台壳、通用 AI Runtime 或平台内部判断来识别自己。Rental 也使用同一接入标准，其旧接口由适配层兼容。
9. 平台发行版本、公共合同版本和每个Core实现版本分别标识并声明支持范围；稳定公开合同的兼容修复/新增能力允许消费者按原接口继续使用。破坏性变更明确升级指引、兼容范围及过渡条件，不用同一个未标注版本悄悄改变行为。

### PCH-R03：当前身份、范围与动作授权

1. 复用原 Auth/Guard/ALS 的可信身份、audience、租户及撤权语义，将租赁专属路径/能力判断移入登记的 Rental 授权适配，而不是删除安全门禁。
2. 公共上下文只承载经过验证的主体/租户/Core归属/受权资源范围及绑定信息，Core可提供有命名空间、经校验的业务扩展。各Core自行定义业务分区并提供真实范围解析；Rental的workspace/category/location不是所有Core必填字段，不另造一套强制所有Core共用的经营空间。
3. Core 声明权限资源与动作，但平台和正式业务授权共同裁决；缺策略、缺范围映射、不支持的数据范围均 fail closed。操作者、客户、员工、平台管理员不能因共用壳而互换 audience。
4. 业务请求、后台任务、缓存回放、导出及工具调用使用同一范围规则。缓存、导航隐藏、客户端声明 Core/tenant/workspace 均不能自授权；Core 注册/切换不能放宽既有租户隔离。
5. 租户Core使用权由SaaS管理员授予、变更或撤销；租户管理员在其管理权限内给成员分配或收回可使用的Core，只能从本租户获权集合中选择。复用原账号与角色机制；成员可使用某Core不等于拥有其全部业务动作或数据权限。新Core开通不自动分配给全部成员。
6. 面向租户成员的普通业务可用范围取Core当前准入、成员Core使用范围、适用订阅权益、当前身份/角色、资源范围和业务条件的交集；AI调用还须满足R08。成员分配和撤销由服务端保存审计并校验并发修订，菜单、直接URL/API、导出、缓存回放及代表该成员执行的任务一致复验。客户、企业客户及其他audience沿原专用合同鉴权，不混为租户员工；委托或服务身份继续遵循原授权规则，不能借系统身份绕过成员撤权。

### PCH-R04：绑定、初始化与停用

1. 区分程序已装配、部署兼容、租户获准使用、Core业务绑定/配置就绪及当前动作获准。一个租户可同时拥有多个不同Core的授权，不能用单值currentCore或全局enabled作为唯一授权事实；当前页面选择只定位访问对象。
2. 平台建立受权绑定与操作记录，Core 在约定事务边界内完成业务初始化；缺实现或失败不留下可经营的空壳、不植入演示事实。重复请求和首响应丢失读取原结果，不重复初始化。
3. 现有 Rental 空间继续按原品类及采用修订运行；首次抽离只建立确定性映射，不偷换品类或给无证据历史补最新版本。
4. 关闭新准入、停止新任务、业务排空、历史只读、卸载代码分别定义。租户级Core停用关闭其普通业务入口和新的Agent任务，保留业务数据、配置、权限配置及原操作收据；不取消已提交业务、不把保留配置当有效授权。有在途/unknown、回调、历史执行依赖时不得直接卸载唯一实现，必要历史读取和收尾须有当前善后权限。
5. 原容器换成另一个 Core 属显式迁移项目，不作为普通设置。首期换装通过独立宿主/新业务容器验证，不把原 Rental 空间原地改成 CRM。
6. SaaS管理端可查看受控注册的Core及其兼容/可用状态，直接为指定租户授予或撤销使用权并保留审计；不以租户先提交申请为前置，不新增Core在线申请流程。授权按原操作幂等保存，不因重复请求重复初始化；业务初始化的对象与步骤由Core声明，不要求所有Core都创建Rental经营空间。
7. 撤销某租户某Core的新准入不影响该租户其他Core，也不撤销其他租户的授权。授权撤销后清理可见性与缓存，服务端同步执行新准入限制；在途业务、原结果核对和历史读取按当前善后权限处理，不用统一403阻断必要收尾，也不因保留收尾权限继续新业务。Core授权本身不自动产生新的收费方案、续费周期或AI额度。
8. 首期沿用租户统一订阅到期日，Core分别控制开通/停用，不另设独立有效期。Core开通不延长租户期限；续费不自动开通新Core、恢复主动停用的Core、撤销过的成员权限或解除账号冻结。租户到期按原订阅规则停止新业务、保留数据及获权善后，Rental具体动作沿用[SaaS订阅需求§4](../../SaaS订阅/SaaS订阅-需求.md#4-订阅有效期与使用状态)，其他Core须声明对应动作边界；历史期限待确认政策和原收费规则保持。
9. SaaS管理员重新授权同一Core时，复用原Core身份、业务绑定、数据和配置；校验当前订阅、成员分配、角色/范围、实现兼容与必需依赖后恢复相应入口。不会重复初始化、重建业务或恢复已撤销的成员权限，不自动执行旧任务、重放资金或换键重做unknown。停用及重新开通记录可追溯；数据删除不属于停用流程。

### PCH-R05：数据、事务与历史

1. 为平台表、Core 表、引用、公共主档和迁移链指定唯一所有者。平台只经合同读取所需业务证据，不能到各行业表中拼通用业务判断。
2. 公共外部合同不得泄漏 Prisma/Nest/供应商类型；适配器内部可沿用现有 ORM。跨模块同事务使用受限事务能力/协调器，不能把整个可写 Prisma client 当插件通用权限。
3. 保持现有业务提交、资源锁、幂等、审批消费和收据原子性；抽离目录或改依赖不能打破原事务。若未来跨进程，另定可靠提交/补偿与恢复合同，普通 HTTP 重试不等于原子事务。
4. 对象引用须消除不同 Core、租户和容器同名/同 ID 冲突；历史对象、动作、原执行版本和收据保持可定位。未知结果只能核对原操作，不借新 Core、新键或新引擎重做。
5. 迁移只前进、可核对且可演练；保留旧源码、测试和历史事实，禁止清库、重放旧资金或篡改已应用迁移。
6. 平台拥有Core注册、租户授权及成员Core分配记录，各Core拥有自身业务容器、配置、数据及迁移。多个Core同时运行不授予跨Core仓储访问；未来互通经所属Core的正式合同和明确关联接入，不默认合并同名客户或共用业务表。

### PCH-R06：公共服务、事件与后台作业

1. 身份、订阅权益、文件、通知、审计及适用的外部集成通过窄接点供给；强依赖缺失阻止受影响能力，弱依赖缺失仅明确降级对应功能，不能假授权或静默少做业务步骤。
2. 事件明确所有者、命名空间、schema、租户/对象关联、幂等及投递/消费结果；先保留原可靠事件/事务机制，不另建消息总线或假设恰好一次。
3. 作业由Core显式登记执行者、版本、范围和恢复规则；每个任务固定原Core及租户归属。未装配Core不启动其作业；已装配Core的租户级新作业只面向当前获权范围，停用后的必要收尾单独授权。升级、重启、延迟事件和回调不会路由到不兼容执行者或其他Core。
4. Webhook 依据原支付/业务引用和受控注册定位 Core，不能凭外部请求自报标识获得路由权限。通知受理不等于送达，集成可调用不等于正式渠道通过。

### PCH-R07：后台壳、页面与端侧合同

1. 保留 React、UIArc 适配、主题、语言、音效和布局。Core 提供类型化页面/路由/导航/权限贡献；公共壳不逐项导入行业页面或靠租赁枚举判断所有业务。
2. 路由/动作和对象链接使用受控命名空间及登记映射，未知模块/必需协议明确拒绝；不执行模型返回的任意路径或页面脚本。前端装配不代替后端授权。
3. 会话/业务绑定变化时取消旧请求，隔离查询键及页面状态，避免相同对象 ID 串 Core/租户/容器；未保存表单有明确处置，不自动提交。
4. Rental 既有 Web、客户与员工 API 的语义和历史深链接保持兼容；不因抽离要求复制后台页面。非租赁最小样例验收后台，完整非租赁小程序/APP不在首期；已有 Rental 端按受影响链路回归。
5. 同一后台按租户获权Core、成员分配及用户权限装配多个业务入口；SaaS管理员管理租户Core开通，租户管理员在原人员/角色管理中配置成员可用Core。导航可用Core切换或业务分组，不锁定唯一形式；当前业务归属须明确。租户未开通、成员未分配、Core未就绪、动作无权限、Core停用及未提供AI工具分别表达，不能统一显示为平台故障。
6. 1.8所列完整后台外壳和公共控件属于底座；无Core时保持左栏/面包屑行/铃铛/休息/面板收展的结构与适用交互，取消的是业务贡献。业务消息及Copilot工具通过可选提供者接入，不以导入Rental或开启通用Agent补齐外壳。
7. Core页面在自身路由/页面模块声明操作即可采用既有主按钮与反馈；框架拥有布局和动作容器，Core拥有真实业务回调。区分导航/打开弹窗、表单保存、异步命令与需确认的动作；打开表单不能显示“业务已成功”，保存只在校验和真实请求完成后显示成功。未返回或unknown的操作不得自动重发。
8. 菜单、面包屑、标题和页面权限复用同一正式路由声明；动态主操作由当前活动页提供，卸载/隐藏页、切换Core/租户/容器或撤权时撤去旧操作，不将先前页面回调和未保存表单带给下一页面。后端仍复核当前权限、对象修订、幂等及业务条件。
9. 提供1.9的标准列表/详情/表单、请求/错误与权限状态组合，复用现有控件和行为；业务作者仅填写业务数据与方法。过滤/分页/导出范围服从真实API，前端共用不创造后台权限、全量数据或第二套状态机。
10. 页面接入、主题/交互修复和合同兼容更新通过底座正式出口继承；新Core只改自身实现与受控装配，不改底座内部switch、复制壳组件、穿透私有路径或为正常页面自写覆盖样式。特殊页面可以替换正文，公共外壳及安全/反馈边界继续复用。

### PCH-R08：AI Native 与受控工具的可选接入

1. AI工具及能力说明由Core开发者自主选择提供，不作为Core注册、租户授权或普通后台使用的必需条件。Core无需AI、模型Key或MCP即可运行；启用AI时，通用机制通过合同消费该Core已登记的事实、工具、动作、批准参与者和收据，不强制加载Rental订单服务。
2. 行业场景和权限留在适配层，模型不重算正式金额/库存/状态，不获得任意 SQL/HTTP/终端工具。工具注册、对外发布、字段释放及一次正式批准分开。
3. 复用唯一 Gateway、财务预算单账、任务累计资源、当前授权及原 unknown 恢复；Runtime、Provider SDK 和 Core 替换分别管理，不能借本专项启动另外两条迁移。
4. MCP及Harness沿各自专项合同消费；本专项交付业务适配接点与适用的现有消费者证据，不以接入某客户端等同全客户端通过，也不重建OAuth/工具目录。本地自付模型与委托服务端模型沿原边界处理。
5. 未提供AI工具的Core，其业务数据和动作不可由Agent查询或调用；不能扫描页面、OpenAPI、数据库或直接HTTP绕过接入合同补出能力。只提供部分工具时仅开放对应范围；工具说明、菜单存在和Core授权均不代替真实工具发布及当前权限。
6. 同租户多Core并存时，AI工具目录按Core、租户授权、适用的成员Core使用范围、当前用户和资源范围过滤，实际调用再次复核。未授权、成员未获分配、已停用或未提供工具的Core不能因另一个Core启用了AI而被访问；首期各Core业务任务仍按自身边界执行，跨Core组合任务留后续明确场景。
7. 先固定已使用的最小 AI/Core 端口，允许可选能力以显式版本和可用状态后续增加。AI 研发继续在原机制内完成未完功能，PCH通过固定合同消费成果；共享文件由唯一作者修改。不得以 AI 未完为由停掉已有可用 AI，也不要求先重写 Runtime 才能拆出公共平台。
8. 已有任务、批准、原操作、工具版本、模型预算账和恢复状态需保持可读及可归属，适配切换不清空任务或重置用量，不让新旧执行器同时处理同一操作。尚无真实证据的 AI 场景继续标注未验，不记为 PCH 的正向验收完成。

### PCH-R09：Rental 适配与不退化

1. 将现有 Rental 作为真实首个适配，而不是仅保留空接口；继续消费品类解析、空间绑定、能力 Hook、价格/规则/检查快照及原业务服务。
2. 租赁品类发布和采用仍由 CAT-GOV 负责。Core 插拔不改写品类版本正文，也不能绕过未实现的正式采用/动态品类门禁。
3. 核对所有已支持的正式入口、定时作业、事件、客户端与恢复路径。按原验收层级证明授权、金额、库存、状态和历史行为不退化；原未完需求明确保留，不因本专项通过而宣布 Rental 全部完成。
4. 既有Rental租户和成员的Core授权映射依据当前有效角色与业务范围确定，保留原可用范围和撤权事实；不因新增成员分配模型批量停用原业务，也不把历史账号通配成所有未来Core的权限。
5. “现有功能正常”覆盖拆分时固定基线已支持的公共平台、SaaS、管理后台、Rental 各品类、企业客户、现有客户网站/门户/小程序及已支持的 AI、MCP、Harness 链路，并核对文件、通知、支付回调、作业与历史恢复等间接消费者。先形成逐项功能对照清单，不能仅以能登录或一条订单链代替全部功能。
6. 功能清单同时标注正式依据、用户角色/入口、原行为、数据与权限、固定版本及验证层级。已有失败和未验项单独保留在原专项，不能推定现在全部正常，也不能把新回归记成旧问题。拆分必须做到已证实正常的功能继续正常，原需求及待修问题不因搬迁取消。
7. 按完整功能切片逐步引入合同、适配和新装配，每片保持当前组合可用并核对受影响链路。原路由/API 语义、权限码、租户/成员/业务对象标识、金额精度、历史快照、幂等键和已提交收据保持兼容；不以清库、重建租户、关闭原功能或放松权限完成抽离。
8. 同一业务请求、事件、作业和模型调用只有一个有效执行者；过渡适配不能让新旧路径重复写业务或扣费。前后对照发现新回归时，修复或回到已验证的兼容组合后才集成该切片。最终验收覆盖整份功能清单；未验项不能被写成“所有功能正常”。
9. 简化代码与拆分同片核对行为，优先去掉重复判断/转发、死分支、无真实消费者的包装以及吞掉错误的默认成功。边界输入校验、当前授权/撤权、业务不变量、并发/幂等和事务/恢复检查保留；仅在信任级别或可变事实不同处复验。性能以受影响链路的实际调用、查询和测量为据，不以减少行数宣称高效。

### PCH-R10：非租赁样例与独立接手

1. 在同一套平台合同上提供一个最小非租赁 Core。实现前冻结样例范围与验收链，优先使用简单工单的创建、分派、处理、关闭，验证轻量Core无需资金/库存；字段、状态和范围由01确定，完整工单/工作流/CRM/TMS产品不随样例扩大。
2. 样例必须有领域校验、持久化、授权拒绝、操作幂等/并发冲突、页面和审计，不能只返回内存假数据或把 Rental 模型重命名。
3. 平台合同及公共构建冻结后，接入只改样例 Core、其迁移和批准的装配配置，不修改平台通用源码、不增加 `if coreId === sample` 特例；发现合同缺口先修合同并重新冻结，不偷偷放行。
4. 由未参与接口设计的开发者或独立 AI，在不依赖本会话记忆的条件下按指南完成构建、接入和代表性操作。记录卡点、所改文件、实际命令与退出码；无独立接手试验不得宣称“可快速接入”。不承诺未经测量的工时。
5. 在同一宿主同时装配Rental与最小非租赁Core，验证同租户双授权、另一个租户只获其中一个Core、同租户成员Core分配不同、同ID碰撞以及单Core停用/重新开通的数据保留与隔离。非租赁样例的普通业务链不依赖AI；提供和不提供AI工具的组合分别验证，不能用全关闭替代R08的AI正向接入证据。
6. 接手输入限于简明指南入口、冻结的合同/样例、明确业务小需求及已说明的环境前置。除本仓适用的开发规则外，不要求先读完平台开发历史或本会话；发生额外口头补充时视为指南缺口，补齐后复验相应步骤。
7. 同一最小样例还须从标准发布包进入另一个干净宿主，完成下载/本地包导入、校验、装配、注册、租户授权、成员分配及真实业务操作。只在作者源码树中运行成功，不证明别人可以安装使用。
8. 独立接手者须能从仓库入口定位启动/装配、可信身份、某条API的控制器到服务/仓储、页面消费者和验证入口，并完成一项有限的样例Core业务扩展。定位错误、需额外口头指路或改底座内部才能完成时，作为代码结构/说明缺口修复后复验。

### PCH-R11：接入资料与可复现交付包

1. 同步提供模块职责图、正式公共出口、必需/可选合同、生命周期与错误语义、实现样例、权限/数据归属、迁移与回退、测试入口和运维说明。
2. 指南区分已实现、设计中和不支持；未实现接口不得给出可复制执行的假命令或虚构包名。合同源是唯一字段定义，文档解释语义与使用顺序，不复制多份易漂移接口。
3. 实施交付时固定包/合同/宿主组合、锁定依赖与产物、示例配置及运行前置；干净环境接入不依赖开发者私有 output、别树 dist、隐含本地 Key 或开发服务器。
4. 提供 Core 合同一致性测试，覆盖正常、撤权、缺依赖、失败/unknown、并发、历史兼容及停用。一次性脚手架可在边界稳定后提供，不把生成空文件当完成。
5. 接入指南面向开发者和开发AI，清楚标出必需贡献、可选AI贡献、允许修改的Core/装配位置，以及注册→SaaS授权→成员分配→业务就绪→访问的验证顺序。独立接手者能按文档创建和注册新Core，不借作者私有环境、额外口头步骤或修改平台内部判断；AI开发便利不授予业务Agent自安装代码的能力。
6. 资料采用“快速接入 → 按需参考”两层。快速入口用少量步骤给出一个最小持久化 Core、该放哪些文件、如何登记/检查/运行、预期界面和失败处理，并附可复制给开发 Agent 的任务模板。接口细节、可选 AI、事件、迁移和发布按链接展开，不要求初学者一次实现全部能力。
7. 实施时提供一个面向 Core 作者的统一检查入口，先进行不加载插件代码、不连接业务环境的清单/版本/入口/依赖边界检查，再按明确命令执行隔离合同与业务验证。结果同时适合人和 Agent 阅读，指出文件/字段、原因和下一步，不能将检查通过称为完整运行验收。
8. 发布物包含与实际版本一致的简明指南、正式契约和最小样例；版本/命令由实际实现提供，文档示例随源码验证。指南从[开发任务内设接入章节](平台Core接入-开发任务.md#core-quick-start)和正式契约生成单份 `CORE_GUIDE.md` 随包交付，不另维护一套手写的第五册。标准变化同片更新类型、检查器、样例和指南。
9. 开发者可以独立发布 Core。首期明确 GitHub Topic、仓库根清单、版本 Tag/Release、标准包和校验摘要、README/许可及来源字段的要求；底座/Rental 首期同仓开发不强制第三方 Core 同仓。已有 npm 包可作后续分发通道，首期以 GitHub Release 和同格式本地包验证一条完整路径。
10. 全平台自有源码逐模块核对说明是否准确。关键入口、公共契约、复杂服务及事务/恢复边界用短文件头说明职责、调用位置/正式接点和关键限制；复杂分支解释原因。简单文件以准确名称/类型及必要一句话备注表达用途，不机械逐行翻译，也不为每个文件另写一份说明书。失真/过期注释随实现修正。
11. 统一阅读入口给出平台/Core目录职责、启动→身份→应用服务→仓储/适配→消费者→验证的导航，链接实际源码。稳定模块导读放真实模块README，正式依据/实施/证据/现场继续各归四册；不维护互相矛盾的多份架构或接口字段。
12. API文档同时面向人和开发Agent：复用现有OpenAPI机器契约、正式DTO/schema及接口说明，覆盖公开受支持的平台和Core API的用途、归属、鉴权/范围、请求/响应、错误、分页/过滤、幂等/并发、异步/原结果及副作用；示例可验证且不含真实敏感数据。业务API与Core模块SDK分别说明，Agent读取API文档不因此获得业务工具权限。
13. OpenAPI按平台与所装配Core贡献组合，命名空间/operationId/schema无冲突；无Core组合不加载Rental文档依赖。文档可通过现有API文档入口及同版本离线导出读取，未安装/未实现/已弃用能力清晰标注，客户端不能把文档存在当作执行开放。接口变更同片更新生产者、正式合同、文档/示例和直接消费者，并验证一致性。
14. 提供底座上游更新与单Core更新的短操作说明，能判断当前版本、目标版本、兼容范围、迁移步骤及失败恢复；随包指南、API文档和样例与所用版本一致，不能让旧代码读到仅适用最新版的操作步骤。
15. 简明指南必须有“声明一个路由和主操作”“带校验的保存”“最小列表/详情”的实际例子及错误处理，展示作者只改本Core与装配即可复用已设计界面。现有页面原语和新的声明入口只保留一个实际渲染/请求执行者，独立接手者不需阅读后台内部实现才能使用。
16. 提供人和开发 Agent 共用的机器可读能力索引与查询入口。每项能力给出名称/用途、归属与版本、正式导入或API/页面入口、源码及接入资料、原权限/范围/依赖声明与验证状态；类别/关键词/归属筛选和分页可逐步定位任务所需能力。清单、页面、OpenAPI、组件与公共包出口沿各自唯一来源生成，新增/迁移能力同片更新原声明和相关说明。
17. 开发目录、部署装配目录与当前主体获权工具目录分别表达。开发目录涵盖公开支持、开发中/保留源码及明确的解析缺口，运行目录只列当前主体满足Core授权、成员分配、发布/依赖/范围/政策条件的工具。执行时继续复核原授权、批准及业务约束，源码注册和目录存在仅提供定位。

### PCH-R12：兼容升级、审查与发布门槛

1. 升级记录平台接入合同、Core实现、数据结构、作业及消费者兼容组合和最低回退版本；多个 API/worker 实例逐一核对，未知组合拒绝新准入。
2. 程序回退、Core配置停用、业务容器迁移和数据库恢复分别设计；回退不撤销已提交事实。已出现新结构/新 Core 数据后，不能接回只认识 Rental 的旧程序。
3. 完成一轮独立审查并修复已确认问题，定向复验；保留未验环境项。不递归扩展审查、不以类型或静态绿色代替真实持久化及宿主证据。
4. Nativark 底座开源主体及自有内容 MIT 已获负责人确认，Rental Core 为首个示范；实际发行仍须核对第三方许可、材料和目标环境。日常任务分支提交/推送沿根规则，创建公开发行、修改仓库 Topic、部署与生产启用按对应明确授权执行，文档不代为发布。
5. 发现、下载、包校验、待部署、已注册及租户/成员授权分别记录。安装锁定来源仓库、版本、解析后的提交和包摘要；不以移动的分支 HEAD、Topic、热度或下载次数作为可信版本。重复下载/安装可核对原结果，同 Core 标识的不同来源冲突须拒绝或显式处理，不能静默替换。
6. 发布包缺文件、摘要不符、版本不兼容、未满足依赖或迁移不适用时，给出具体原因并保留当前可用组合。升级先准备和验证候选，明确 API/worker/前端及数据切换顺序；不自动追最新版，不凭 Topic 自动安装/更新/迁移。
7. 获取社区包与本地包走同一校验链，拒绝越出包目录的入口、压缩路径和链接；远端清单、README、图标作为不可信展示内容处理。访问发现服务不发送租户业务资料。发布者与完整性证据用于选择版本，不据此声称代码已审核。
8. 使用者能跟随Nativark上游指定兼容发行更新底座，保留自己的Core实现、租户/成员授权、业务数据、部署配置与秘密；业务定制通过Core/正式扩展或配置表达，不以修改底座内部源码为正常接入步骤。取得上游源码、更新依赖/组合和在目标环境部署是分别可核对的动作。
9. 每个Core可以单独更新，兼容的底座修复不要求全部Core同步发版，某个Core升级也不强制无关Core改变版本。若目标Core需要新合同/底座，或底座破坏性升级不再支持现有Core，应明确列出依赖与升级顺序并阻止不兼容组合，不自动联动升级全部模块。
10. 同仓开发保留独立版本与正式出口。安装/更新记录固定底座版本、各Core版本、公共合同/数据兼容和具体产物；同进程部署仍可能需要组合重建/重启，独立更新指版本与变更范围独立，不承诺无停机热更新。
11. 提供可复现的上游更新路径，先预检版本/依赖/数据与本地差异，再准备候选、备份必要数据、按所有者运行一次前进迁移、部署验证，最后记录实际运行版本。发现用户改过受管底座或冲突时保留差异并给出处理入口，禁止整树覆盖、强制重置、重建租户或重跑业务Seed来完成更新。
12. 验证旧底座＋当前Core、兼容新底座＋同版本Core、同版本底座＋某Core新版本和不兼容组合拒绝；底座与Core分别升级后配置/数据/历史任务/收据仍在，未升级Core照常工作。业务数据已使用新结构时按实际最低兼容版本恢复，不笼统承诺任意回退。公共新功能和修复随兼容升级可用，但新增业务权限/可选能力仍按原授权启用。
