## 1. 产品定位

Rental OS 是面向摄影设备、露营装备、车辆载具和工程设备等品类的多租户 SaaS 租赁平台。

- “SaaS 租户”是使用系统经营租赁业务的商户，不是租用设备的客户。
- “租赁客户”是向 SaaS 租户租用设备的个人或企业。
- 一个 SaaS 租户可建立多个经营空间；每个经营空间只经营一种设备品类，但可经营该品类下多个商品、资产、耗材和套装。
- 同一租户的客户主档共享；商品、资产、库存、地点、定价、订单、权益和经营报表按经营空间隔离。
- 平台提供一套通用租赁内核；车辆调度等品类独特业务使用品类 capability，物流、智能柜、人员服务、IoT、资格合规等可被多个品类复用的业务使用跨品类共享 capability，并由经营空间按需启用。
- 当前交付营运管理端和后台 API；小程序与 App 暂不开发页面，只保留独立、可版本化的客户端 API 边界。
- 旧门市租赁模块、页面、接口和数据仅作需求与实现参考；新平台不承诺兼容、迁移、投影或对账，任何新业务事实只进入 Rental Core 与通用模块。
- 车辆载具不是兼容品类，而是与摄影设备、露营装备、工程设备平级的正式品类；通用能力使用同一 Rental Core 模型，车辆专属能力通过 capability 在新模块中建设。

### 1.1 首个可经营版本 R1

R1 的目标不是同时完成整个平台蓝图，而是先证明一条真实业务语义的租赁订单可以在新 Rental Core 内完整经营。R1 选择摄影设备作为首个正式经营品类，因为它已经具备兼容性能力切片、序列化资产和套装基础，可用最少新增范围验证通用订单、检查、费用和养护是否真正闭环。露营、车辆和工程空间在各自首期必选能力完成前继续保持开发/演示模式，不得显示为正式可经营。

R1 必须包含：

- 租户、经营空间、成员权限、摄影品类档案、商品、序列化资产、数量配件、套装、经营主体和履约地点；
- 基础价格、日期/分时价格、营业日历、规则版本、优惠和可选服务；
- 租户共享客户主档以及运营人员代客创建报价和订单；当前不以小程序或 App 页面作为发布前置；
- 报价、订单确认、库存预留、资产或组件分配、配货、领取、归还、逐项检查、使用量、缺件/损坏/清洁异常、费用审核、押金或预授权处理、结算和关闭；
- 摄影器材兼容、套装附件清点、快门或适用使用量、领取归还检查和养护状态；
- 当前经营空间的订单、收入、异常和库存快照报表；
- 数据库升级、重启恢复、租户/空间隔离、幂等、并发和审计。

R1 允许明确标记的模拟支付、预授权和通知，但状态必须使用 `simulated` 或同等明确语义，不得记录或展示为真实收款、冻结、发送或送达。R1 不包含真实支付/通知 Provider、客户充值钱包、跨空间汇总、小程序/App 页面、IoT、自助设备、电子签章、外部保险，以及露营、车辆和工程设备的正式经营验收。

R1 发布门禁为：至少一张摄影订单使用真实数据库事实完成“经营配置 → 报价 → 下单 → 资源锁定 → 分配 → 领取 → 归还 → 检查 → 异常/养护 → 结算 → 报表”，任何步骤不得由静态页面数据、进程内临时状态或旧 `/store-rental/*` 事实代替；服务重启后订单、资源、资金事件、检查、费用、工单和审计结果保持一致。

## 2. 角色与数据边界

| 角色 | 职责 | 数据范围 |
| --- | --- | --- |
| SaaS 平台管理员 | 创建租户、治理经营空间开通、冻结或停用租户、查看平台审计 | 仅平台管理面，不自动获得租户业务数据权限 |
| 租户管理员 | 配置本租户经营空间、组织、账号和权限，可进入本租户全部经营空间 | 当前 SaaS 租户及其全部经营空间 |
| 经营空间管理员 | 配置所在空间的品类规则、价格、营销、通知和业务数据 | 被授权的经营空间 |
| 租户运营人员 | 管理商品、资产、库存、地点、客户、订单和履约 | 被授权的经营空间、角色与组织数据范围 |
| 租赁客户 | 注册、获取报价、下单、支付、领取和归还 | 本租户共享客户身份及自己在目标经营空间的订单与权益 |

必须满足：

- 请求中的租户身份只能来自已验证会话，不能信任客户端提交的 `tenantId`。
- 租户业务请求中的当前经营空间必须来自服务端验证过的会话上下文，不能信任客户端提交的 `workspaceId`。
- 缺少租户身份时必须拒绝访问，不得回退到演示租户。
- 平台管理员和租户管理员的权限模型必须分离。
- SaaS 平台路由不得出现在普通租户菜单中，普通租户也不得通过直接 URL 或 API 访问；SaaS 平台管理员只进入平台管理路由，不自动进入租户营运路由。
- 同一客户在不同 SaaS 租户下的数据、权益和优惠券相互隔离。
- 同一租户内共享客户主档；订单、优惠券、积分、会员等级和营销余额默认按经营空间隔离。
- 租户冻结或停用后，其账号会话立即失效；历史订单、资金和审计数据不得物理删除。

## 3. 经营品类模型

经营品类在经营空间创建时确定。经营空间产生商品、资产或订单后，不允许通过普通设置直接切换品类；变更品类必须新建经营空间或执行显式数据迁移。

层级模型：

```text
SaaS 租户
├─ 经营空间 A（唯一品类：摄影设备）
├─ 经营空间 B（唯一品类：露营装备）
└─ 租户账号通过成员关系进入一个或多个经营空间
```

- 经营空间是业务隔离边界，不替代 SaaS 租户；所有经营事实同时包含 `tenantId` 和 `workspaceId`。
- 租户管理员默认可进入本租户全部经营空间；普通账号只能进入明确授权且启用的经营空间，并可在不同空间拥有不同角色和数据范围。
- 一个业务会话只能有一个当前经营空间。右上角切换空间时，服务端必须重新校验成员资格并刷新会话上下文。
- 切换后必须取消旧请求、清空旧空间业务缓存并重新加载菜单、权限、品类和 capability；目标页面不适用于新空间时返回该空间工作台。
- 当前阶段不建设跨空间订单、收入、库存或客户消费汇总；未来汇总只能基于明确的租户级查询权限实现。

| 品类 | 典型库存 | 主要资产字段 | 使用量 | 履约地点 | 专属能力示例 |
| --- | --- | --- | --- | --- | --- |
| 摄影设备 `camera` | 序列化资产、套装 | 厂商、型号、序列号、快门数、镜头卡口、套装组件 | 快门数、使用时长 | 自营门店、合作商、仓库、寄送点 | 套装拆分、配件清点、损坏免赔 |
| 露营装备 `camping` | 数量库存、套装 | 厂商、型号、规格、尺码、容量、清洁等级 | 天数、损耗等级 | 门店、仓库、自提点、合作商 | 数量预占、套装缺件、清洁费 |
| 车辆载具 `vehicle` | 序列化资产 | 厂商、车型、车牌、VIN、里程、能源类型 | 里程、租期 | 车行门店、取还车点、停车场 | 调度、异地还车、TBox、驾驶资质 |
| 工程设备 `construction` | 序列化或数量库存 | 厂商、型号、设备编号、工时、吨位、检验证照 | 工时、班次 | 设备基地、项目现场、交付点 | 操作资质、运输、维保和安全检查 |

管理端的通用导航必须由当前经营空间的品类定义和已解析业务术语驱动。动态范围包括导航分组、通用业务菜单、面包屑和对应页面标题；路由路径、路由语义标识、权限码和 API 契约保持稳定，不得因显示文案变化而产生车辆专用路由或破坏深链接。

| 品类 | 通用管理分组 | 商品组入口 | 资产与库存入口 | 履约地点入口 |
| --- | --- | --- | --- | --- |
| 摄影设备 | 摄影器材 | 器材型号 | 器材资产与库存 | 器材门店 |
| 露营装备 | 户外装备 | 装备品类 | 装备资产与库存 | 装备仓库 |
| 车辆载具 | 车辆与车队 | 厂牌车型管理 | 车辆管理 | 门店管理 |
| 工程设备 | 工程设备 | 设备型号 | 设备台账与库存 | 设备仓库 |

- 切换经营空间后，管理端必须在新会话上下文生效时重新解析全部动态导航文案，不要求重新登录或手工刷新，且不得残留上一空间的名称。
- 通用页面不得散落 `categoryCode` 条件分支；新增品类时，只需在品类定义中补充术语和导航显示配置即可接入通用导航。缺少可选显示配置时使用明确的通用兜底名称，不得显示上一空间缓存值。
- 品类 capability 的独特页面仍由 capability 注册、实例状态和权限共同决定是否显示；动态改名不能代替 capability 实现，也不能让未启用能力的入口出现。
- SaaS 平台管理路由不使用租户经营品类术语，普通租户与平台管理面的路由分面规则保持不变。

品类定义必须同时决定：

- 业务术语和动态字段 schema；
- 序列化、数量和套装库存能力；
- 可使用的计价单位、使用量指标和押金规则；
- 领取、归还和检查模板；
- 菜单、页面、API 与集成 capability；
- 报表指标和异常规则。

Rental Core 的扩展结构必须保持为：

```text
Rental Core
├─ 通用商品、资产、库存
├─ 通用报价、订单、预占、履约
├─ 品类定义注册
├─ 计费策略注册
└─ Capability 扩展模块
```

新增品类和计费模型必须满足以下兼容规则：

- 新品类通过新增品类定义接入，定义业务术语、字段、库存模式、地点、检查模板、默认规则、支持的计费单位和 capability；不得在通用报价、订单、库存或履约主流程散落品类编码分支。
- 新计费模型通过独立计费策略接入，由统一报价入口调用；策略负责计费单位数量与金额计算，既有策略不因新增模型而修改。
- 品类独特功能通过 capability 模块建设。车辆的调度、驾驶资质、TBox、里程和异地还车属于 vehicle capability；其他品类可拥有自己的检查、清点、清洁、缺件、运输、维保等模块。
- 新增品类可以新增代码和数据库迁移，但必须是增量扩展，不要求运行时无代码配置；扩展不得改变既有品类的定义、报价结果、订单状态机和数据边界。
- 启动和自动测试必须校验：品类引用的计费策略与 capability 均已注册、默认值属于品类支持范围、品类编码不重复。

### 3.1 Rental Core 与品类扩展边界

- Rental Core 统一负责客户引用、商品、资产、数量库存、套装库存、可用性、预占、分配、释放、报价、优惠、押金、预授权、订单、支付、领取、归还、结算、通用检查、附件、异常费用、增值服务、权限、审计、通知和历史快照。
- 品类 capability 只为通用流程增加品类字段、资格和适用性校验、特有履约任务、使用量采集、检查模板、费用依据、页面入口、权限点、事件和报表维度。
- 品类 capability 可以在“商品建档、报价校验、订单确认、配货或调度、领取或交付、归还检查、结算”阶段参与处理，但不得另建客户、订单、支付、资金或库存事实体系。
- capability 不得跳过 Rental Core 的状态、权限、数据隔离、资源锁定和审计规则；需要阻止主流程时必须返回明确原因，需要收费时必须形成可解释的费用明细，需要增加过程状态时使用关联任务或子状态，不得改写核心订单历史。
- 已生成的报价和订单使用当时的品类定义、capability、规则和检查快照。之后启停或升级 capability 不得改变既有业务事实。

品类能力按以下层次组织：

| 层次 | 启用方式 | 要求 |
| --- | --- | --- |
| 品类必选 capability | 创建该品类经营空间时自动启用 | 缺少时空间不能进入可经营状态；同品类空间遵守统一基础规则 |
| 可选增强 capability | 经营空间按业务需要显式启用 | 启用前校验依赖、配置和权限；停用后不得阻断既有订单履约和历史查询 |
| 外部集成适配器 | 在对应 capability 已启用且完成服务商配置后启用 | 外部服务不可用时按业务风险降级，不得虚构回执、保单、定位或设备数据 |

- capability 应以完整业务闭环划分，例如“车辆调度”“器材兼容性”“露营清洁周转”“工程设备工时”，不得把整个品类做成不可拆分的大模块，也不得细化成一个字段一个 capability。

### 3.2 摄影设备扩展模块

#### 3.2.1 器材兼容性

- 摄影商品和资产可维护镜头卡口、传感器画幅、电池和充电器规格、供电方式、存储介质、接口以及稳定器、闪光灯、兔笼等配件兼容关系。
- 法兰距方向、画幅覆盖、供电安全等物理或安全算法由 capability 代码按实现版本维护，租户不得通过配置把物理上不成立或不安全的组合改为可用。
- 商品或资产之间的转接、适配、供电支持、存储支持、接口支持、配件适配和器材配对关系必须以结构化关系维护；不得使用逗号分隔字符串承载关系。每条关系至少包含关系类型、来源对象、目标对象、结论、依据或备注，并随能力配置版本留痕。
- 结构化关系允许按商品、资产或标准化属性匹配；保存时必须校验引用类型、必填字段、关系类型和结论，未知或歧义关系必须 fail-closed，不得因“未登记”而默认兼容。
- 报价和配货阶段按商品组合检查兼容性。明确不兼容且会导致无法使用或安全风险时阻止确认；可能不适配但仍允许使用时给出可理解提示并允许有权限人员确认例外。
- 兼容规则或关系配置变更不得反向改变有效报价和历史订单；报价和订单必须保存当时采用的器材组合、能力实现版本、配置版本、关系配置快照、兼容判断和例外确认。
- 能力配置生命周期审计必须保存变更后的完整配置快照，保证关系配置可按版本查看和解释；历史审计和历史订单不得因当前配置停用或升级而被覆盖。

#### 3.2.2 摄影套装与附件清点

- 套装结构、库存占用、分配和部分归还仍由 Rental Core 负责；摄影 capability 为机身、镜头、电池、充电器、存储卡、线材和其他附件提供必带、选带、可替代及检查语义。
- 配货和领取必须保存实际序列化器材、普通配件和数量；归还按实际组成逐件清点，识别缺件、错配和非原分配组件，不得只把父套装标记为已归还。
- 必带组件未分配、替代不满足兼容规则或关键组件检查不通过时，不得完成领取。

#### 3.2.3 使用量、检查与养护

- 摄影资产可按设备类型记录快门数、录像时长、灯具使用小时等领取前读数、归还读数和本次增量；读数异常必须允许复核并保留原始记录和修正记录。
- 使用量可作为超量费用、维护提醒或资产风险依据，具体金额由已注册计费策略或费用规则计算，capability 不直接修改订单总额。
- 检查模板可覆盖镜片、传感器、屏幕、接口、按键、外观和进水等项目；归还后需要清洁、校准或维修的资产在处理完成前不得恢复可用。
- 数据备份、器材教学、摄影助理和远程设备接入属于可选增强能力，不作为摄影经营空间首期启用前提。

摄影品类首期必须具备器材兼容性、摄影套装与附件清点、快门或适用使用量记录、领取归还检查和养护状态。

### 3.3 露营装备扩展模块

#### 3.3.1 混合库存与套装完整性

- 露营品类不得被固定为纯数量库存；经营空间可以同时使用数量库存、序列化资产和套装库存。
- 通用套装能力负责组成和库存事实，露营 capability 补充帐篷主体、内帐、外帐、地钉、风绳、支架等组件的必带、可替代、人数、容量、季节和适用环境信息。
- 配货、领取和归还按实际组成清点。部分归还只释放已交回组件，缺件或替代件必须形成检查异常和处理依据。

#### 3.3.2 清洁周转、损耗与耗材

- 需要清洁处理的露营装备归还后依次进入待检查、待清洁、待晾晒或消毒、清洁完成和可出租等适用状态；未完成必要处理不得恢复可用库存。
- 检查必须区分正常使用痕迹、可清洁污渍、破损、缺少组件和一次性耗材消耗，并据此决定正常恢复、清洁、维修、报损或异常收费。
- 一次性耗材和租赁资产必须分开管理；耗材消耗不得被错误认定为客户必须归还的资产，租赁组件也不得用耗材出库替代。

#### 3.3.3 适用性和服务扩展

- 露营商品可按人数、季节、温度、防水等级和使用场景提供适用性提示；首期提示只辅助选择，不构成对天气、安全或使用结果的保证。
- 配送搭建、现场拆收和耗材补充使用 Rental Core 通用增值服务、人员或服务容量及结算模型；露营 capability 只补充服务参数、履约模板和检查要求。

露营品类首期必须具备混合库存、露营套装完整性、清洁周转、缺件认定及耗材与租赁资产区分。

### 3.4 车辆载具扩展模块

车辆继续使用 Rental Core 的商品、资产、报价、订单、预占、支付、履约和结算体系。旧门市租赁系统仅作业务参考，不属于兼容、迁移、投影或对账范围。

#### 3.4.1 驾驶资格

- 车辆 capability 按车辆类型和经营空间规则校验驾驶证类型、有效期、准驾车型、驾龄和年龄等条件。
- 驾驶资格资料可保存在租户共享客户主档中，但每个目标车辆空间独立判断是否满足本次订单、车辆及领取时点要求。
- 报价、订单确认和领取阶段均可按规则复核；资格不满足时必须明确指出缺失或不适用项，不得仅依赖前端隐藏车辆或领取按钮。

#### 3.4.2 车辆分配、调度与替换

- 车辆订单可先预订定价车组，再由经营方分配具体车辆。预分配、锁定和改配由 Rental Core 按4.7.6.1统一管理；车辆 capability 只扩展运输调度任务的待调度、已到位等状态，以及当前位置、目标地点和计划时间，不另建订单资源分配状态机。
- 支持同级替换、升级和降级。替换必须重新校验可用性、驾驶资格、价格和客户确认要求，并保留原车辆和替换原因；不得覆盖原分配记录。
- 车辆临时不可用时可以安排替换、改约或取消，不能通过调度状态绕过 Rental Core 的库存占用和订单变更规则。

#### 3.4.3 取还车检查、里程与能源

- 取车和还车至少记录里程、油量或电量、外观损伤位置、内饰、随车物品、钥匙、证件、充电设备、照片或视频及客户确认。
- 里程能力支持包含里程、领取里程、归还里程、本次增量和超里程；燃油或电量能力记录领取值、归还值、差额、补充记录和凭证。
- 超里程、油电量差、充电或加油费用必须通过已发布规则形成费用明细。停车费、路桥费和违章等事后费用必须关联真实事件、证据、责任主体和审核记录。

#### 3.4.4 异地还车和车联网

- 异地还车必须校验目标地点的归还和车辆接收能力、可用时间及异地费用；后续车辆调回使用通用调拨或调度任务，不得把客户订单伪装成内部调拨。
- TBox 和车联网属于可选集成，可提供定位、里程、油电量、车门状态、电子围栏和远程控制等数据。未接入真实设备或服务商时不得展示实时位置、远程控制成功或其他虚构设备状态。
- TBox 不作为车辆经营空间首期启用前提；外部数据与人工检查冲突时保留双方原始事实并进入复核，不得静默覆盖。

车辆品类首期必须具备驾驶资格、车辆分配和调度、里程与油电记录、取还车检查及异地还车；TBox 在后续按需启用。

### 3.5 工程设备扩展模块

#### 3.5.1 操作资质与人员匹配

- 工程设备 capability 按设备类型检查操作证类型、发证机构、有效期、适用设备范围，以及是否允许客户自有操作员或必须使用经营方操作员。
- 客户自有操作员和经营方操作员必须分别记录身份、资质、适用设备和本次授权。资质不满足、已过期或被撤销时不得交付设备。
- 经营方提供操作员时，人员服务、容量、价格和结算使用 Rental Core 通用增值服务模型，工程 capability 负责资质匹配、班次和现场记录。

#### 3.5.2 工时、班次与使用量

- 工程资产可记录交付和归还工时表读数、本次工时、班次、包含工时、超出工时、待机或停机时间；原始读数、人工修正和证明材料必须可追溯。
- 小时、班次、包含工时和超工时费用由已注册计费策略计算；故障停机、经营方原因停机和客户原因停机分别记录，不得自动全部计入客户使用量。

#### 3.5.3 运输、进场与交付

- 工程设备可关联设备基地、项目现场、交付点、运输要求、进场条件、安装调试、现场交接、撤场和返运任务。
- 运输和安装作为通用履约费或增值服务计价；工程 capability 提供设备尺寸、重量、现场条件、安全要求和交接参数，并校验服务资源是否匹配。
- 进场条件或安全要求不满足时不得完成交付；人工例外不得绕过法定资质、设备停运和安全底线。

#### 3.5.4 安全检查、维保与故障停机

- 工程资产必须维护适用检验或证照、有效期、日常检查、安全附件和禁止使用状态。证照过期、检查不通过、维保超期或被停运的设备不得分配或交付。
- 可按累计工时、日期或其他已配置条件触发保养。归还或运行中发生故障时记录故障时间、停机时间、责任判断、替换设备、维修过程以及费用减免或客户补偿。
- 替换设备继续使用 Rental Core 的订单变更、资产替换和库存占用规则，保留原设备、替换设备和停机事实。

工程设备品类首期必须具备操作资质、工时读数、运输交付、安全检查和按工时或周期维保；操作员排班及设备远程监测可后续按需增强。

### 3.6 品类首期能力清单

| 品类 | 首期必选 capability | 后续可选增强 |
| --- | --- | --- |
| 摄影设备 | 器材兼容性、摄影套装与附件清点、使用量、领取归还检查、养护状态 | 数据备份、器材教学、摄影助理、远程设备接入 |
| 露营装备 | 混合库存、露营套装完整性、清洁周转、缺件认定、耗材区分 | 适用性推荐、配送搭建、现场拆收、耗材补充 |
| 车辆载具 | 驾驶资格、车辆分配和调度、里程油电、取还车检查、异地还车 | TBox、电子围栏、远程控制、自动网点平衡 |
| 工程设备 | 操作资质、工时读数、运输交付、安全检查、维保 | 操作员排班、远程监测、自动故障诊断 |

- 首期必选能力是品类空间进入可经营状态的业务要求；尚未建设完成时必须明确标记为不可用或限制相应业务，不得用静态演示数据伪装已经具备。
- 必选性由每个品类自己的首期清单定义，不由 capability 的全局类型单独决定。同一个跨品类共享 capability 可以在某个品类中必选、在另一个品类中可选；初始化、生产就绪、Hook 故障策略和转正式经营必须读取同一份品类必选清单。
- 新建经营空间默认处于开发模式。系统只自动启用已有真实实现且具备安全默认配置的必选能力；尚未实现或无法安全自动配置的必选能力继续列为缺失，并阻止显式创建或切换为正式经营模式。
- 可选增强 capability 启用、暂停、停用或升级时必须校验依赖关系、未完成任务和在途订单；任何变化只影响之后的新业务，历史记录继续使用原能力和规则快照。

### 3.7 品类后续扩展能力储备

本节是四个既定品类的已确认产品扩展方向，不属于当前首期交付和当前核心验收。启动其中任一 capability 前，必须再明确业务流程、字段、状态、权限、费用、异常和专项验收，不得仅凭本节名称直接宣称功能完成。

#### 3.7.1 摄影设备后续能力

- **设备健康与校准**：记录电池健康度和循环次数、传感器清洁、镜头校准、固件版本、灯具寿命等；达到经营空间设置的风险或养护阈值后进入待复核、待养护或停用，处理完成后才恢复可用。
- **数据介质安全**：记录存储介质是否包含客户数据以及数据交付、备份、客户确认和擦除结果；擦除操作必须记录操作者、时间和结果，不得在未确认数据处理要求时直接复用介质。
- **设备配置复位**：按设备类型维护标准配置，领取时保存必要配置基线，归还后检查语言、时间码、色彩、连接和自定义设置并恢复标准状态，防止上一客户配置影响下一订单。
- **项目器材规划**：按拍摄项目建立器材需求清单，检查机身、镜头、供电、存储和灯光组合，缺货时推荐兼容替代；客户确认后仍转换为 Rental Core 的普通商品、套装和服务订单行，不建立项目专属订单体系。
- **高价值器材交接**：支持指定领取人、双人复核、防拆标签、封箱编号和多次转交责任链；每次交接保存器材、附件、交接双方、时间、地点和凭证。

近期优先候选为设备健康与校准、数据介质安全和高价值器材交接；项目器材规划及自动推荐在后续阶段建设。

#### 3.7.2 露营装备后续能力

- **卫生隔离**：对霉变、虫害、异味、潮湿等情况进行专项检查；需要深度清洁或隔离的装备不得进入普通清洁队列，处理失败时进入维修、报损或淘汰流程。
- **高风险耗材与器具**：区分燃气罐、燃料、电池等可销售耗材与炉具等可归还器具，检查泄漏、过期和适用限制；禁止把危险或一次性耗材按普通可归还库存处理。
- **环境适用性**：按温度、风力、防水等级、海拔、季节和使用场景提示装备适用性；高风险选择要求客户确认，但系统提示不构成天气、安全或使用结果保证。
- **尺码与人员适配**：管理睡袋温标、服装鞋靴尺码、儿童成人规格、帐篷人数和承重，并支持同一订单内多人装备清单。
- **活动装备规划**：按人数、天数和活动场景生成建议清单并提示关键组件缺失；客户确认后仍形成普通商品、套装、耗材和服务订单行。
- **装备寿命管理**：按出租次数、损耗等级及帐篷防水层、睡袋填充、充气垫气密性等专项结果决定养护、维修或淘汰。

近期优先候选为卫生隔离、高风险耗材与器具和装备寿命管理；环境适用、尺码适配与活动规划作为后续辅助能力。

#### 3.7.3 车辆载具后续能力

- **多驾驶人管理**：一张订单可以登记主驾驶人和其他授权驾驶人，每人独立完成身份与驾驶资格审核；未通过审核的人员不得被标记为已授权驾驶人。
- **事故与理赔**：记录事故时间、地点、驾驶人、车辆状态、现场证据、第三方责任、损伤、保障或保险适用性、维修停运和责任结算；不得用事故记录覆盖原取车检查和车辆基线。
- **道路救援与替换车辆**：记录抛锚、事故和无法启动等救援事件，支持现场维修、拖车、改约、替换车辆或结束租期，并明确停运期间的费用减免和客户确认。
- **违章、停车费和路桥费**：订单完成后可追加外部事件，必须匹配发生时间、当时车辆、租期和驾驶人，经过证据校验、客户通知或申诉及经营方审核后才能形成事后费用。
- **车辆合规证照**：管理行驶证、年检、保险、营运证等适用证照及有效期；到期、失效或缺少强制证照的车辆不得分配或领取，续期审核通过后恢复。
- **整备周转**：归还后按需要进入清洁、加油、充电和随车物品补充等整备任务，达到经营空间发布的交付标准后才恢复可出租。
- **自助取还车**：支持身份核验、远程或蓝牙钥匙、自助拍照检查、车辆定位和失败后的人工兜底；外部设备未确认成功时不得把订单标记为已领取或已归还。
- **限行与电子围栏**：可按车牌、区域、时间和跨境限制进行提示或校验；定位异常只能形成风险事件和复核依据，不得单独自动认定客户违约。

近期优先候选为多驾驶人、事故与理赔、道路救援、事后费用、合规证照及整备周转；自助取还车和电子围栏在真实设备与运营能力具备后启用。

#### 3.7.4 工程设备后续能力

- **属具与附件兼容**：管理铲斗、破碎锤、货叉、钻头、吊具等属具与主机适配关系；属具单独分配、检查和归还，更换后重新校验安装、安全和计费要求。
- **项目进场**：管理项目现场资料、进场许可、安全培训、人员名单、设备证照和现场条件；任何法定或安全必备项不满足时不得完成交付。
- **施工日报与工作确认**：按日记录工时、工作内容、操作人员、停机原因和项目方确认，作为阶段结算、费用减免和争议处理依据，不覆盖设备原始工时读数。
- **停机责任与服务承诺**：区分设备故障、经营方、客户和现场原因，计算可计费工时、应减免时间，并按规则触发维修、替换设备或客户补偿。
- **运输方案**：根据设备重量、尺寸、运输要求、运输车辆承载、道路限高和现场卸货条件生成并校验运输任务；条件不满足时不得安排普通运输。
- **操作人员与班组**：管理操作员、辅助人员和安全员的资质、设备匹配、班次、签到及现场确认；人员容量和费用继续使用通用服务模型。
- **燃油与耗材**：记录领取和归还油量、补给，以及液压油、润滑油、钻头等耗材，区分正常消耗、客户采购和异常损耗。
- **遥测与故障诊断**：接收工时、油耗、位置、故障码和运行状态，形成异常停机告警；外部数据与人工工时表或项目方签字冲突时进入复核，不得静默覆盖原记录。

近期优先候选为属具兼容、项目进场、施工日报和停机责任；运输方案、人员班组、燃油耗材及遥测诊断按运营规模和设备接入条件逐步启用。

### 3.8 跨品类共享扩展模块

跨品类共享 capability 表示多个品类遵守同一业务模型、状态和接口契约，不表示业务数据跨经营空间共享。每个经营空间只可访问和使用本空间的物流任务、自助设备、服务人员、资质规则、IoT 设备、工单、合同和保障记录。

- 品类定义声明共享 capability 是否适用以及品类参数，经营空间对可选 capability 显式启用和配置；未启用时不得显示对应菜单或接受对应业务 API。
- 共享 capability 复用 Rental Core 的客户、商品、资产、地点、报价、订单、服务、费用和审计事实，不得另建平行订单、资金、库存或客户体系。
- 同一个共享 capability 可以按品类提供不同模板和校验，但通用状态、幂等、权限、空间隔离和历史快照规则保持一致。
- 外部 Provider 只是 capability 的数据或执行适配器。Provider 未配置、超时或失败时必须按该能力的业务风险降级，不得用模拟结果冒充真实履约、签署、投保、定位或设备回执。

#### 3.8.1 配送与物流 capability

- 物流能力统一管理发货、取件、运输、送达、失败和退回任务，以及取送时间窗、地点、联系人、运力容量、商品或资产交接、签收和异常凭证。
- 支持经营空间自营配送和第三方物流 Provider。第三方任务至少保存服务商、外部单号、状态、回执、费用、失败原因和最后同步时间。
- 摄影品类可补充防震、防潮和高价值交接；露营品类补充体积、件数、搭建和拆收；车辆补充送车和取车；工程设备补充重量、尺寸、承载车辆、限高、吊装和卸货条件。
- 物流任务必须关联 Rental Core 订单和履约节点，不能形成独立客户订单。第三方显示“送达”不自动等于客户已领取，仍须满足签收、资产交接和必要检查条件。
- 物流失败、改约或取消必须同步处理未执行服务容量、费用和客户通知；已经发生的运输事实不得删除。

#### 3.8.2 自助履约 capability

- 自助履约统一管理智能柜、自助仓、自助停车场、钥匙柜和无钥匙取还等自助地点、设备、柜格或车位资源。
- 支持身份核验、取件码、动态密码、蓝牙钥匙或远程授权、访问有效期、开关门和取放记录、自助检查及照片或视频凭证。
- 摄影和露营可使用智能柜或自助仓，车辆可使用自助停车场、钥匙柜或无钥匙取还；工程设备可按实际场景用于钥匙、证件或小型附件交接。
- 发出开锁或授权指令不等于领取成功；系统必须结合设备回执、柜门或车门状态、客户操作、资产确认和必要检查判断是否完成领取或归还。
- 设备离线、柜格错误、开锁失败、物品不符和网络中断必须存在人工处理路径；人工接管不得删除原设备指令和失败记录。

#### 3.8.3 人员与现场服务 capability

- 人员服务统一管理服务人员、角色、资质、可服务品类和设备、服务地点或区域、排班、可服务时间和同时服务容量。
- 订单服务任务支持待分配、已分配、已确认、已到场、服务中、已完成、已取消和履约失败等状态，并保存签到、工时或班次、现场凭证、客户确认和替换记录。
- 摄影可用于摄影助理、灯光助理和器材教学；露营可用于配送搭建、拆收和现场指导；车辆可用于送取车、代驾和道路救援；工程设备可用于操作员、安全员、安装调试和维修人员。
- 人员价格、客户应付和结算继续使用通用增值服务及费用模型；人员 capability 只负责资格、排班、分配和履约事实。
- 替换人员必须重新校验资质、时间和服务范围，并保留原分配及替换原因；经营方无法提供合格人员时按服务规则改约、取消、退款或补偿。

#### 3.8.4 IoT 与设备遥测 capability

- IoT 能力统一管理设备档案、设备与租赁资产的绑定历史、读数、状态、定位、告警、远程指令、在线状态、数据来源和 Provider 回调。
- 每条遥测数据至少保存设备、资产、数据类型、数值和单位、设备采集时间、平台接收时间、来源及质量状态；设备采集时间不得用平台接收时间替代。
- 摄影可接入快门、灯具时长和电池状态；露营可接入智能柜、温湿度或电源设备；车辆可接入位置、里程、油电量、车门和远程控制；工程设备可接入工时、油耗、故障码、位置和运行状态。
- 过期、离线或低质量数据不得展示成实时事实；指令“已发送”与“执行成功”必须分开。重复回调和重复指令使用幂等键处理。
- 遥测与人工检查、客户签字或项目方确认冲突时保留所有原始事实并进入复核，不得静默覆盖；高风险自动处置必须有可配置规则和人工兜底。

#### 3.8.5 资格与合规 capability

- 资格合规能力统一管理资格或证照类型、持有人类型、发证机构、有效期、审核状态、适用范围、核验方式、到期提醒、拒绝、撤销和复审。
- 持有人可以是个人客户、企业客户、服务人员或租赁资产；不同持有人类型的数据和权限必须分开，敏感证件按最小必要原则保存和展示。
- 摄影可配置高价值器材实名、信用或指定人员领取；露营可配置特定高风险装备的年龄或确认要求；车辆配置驾驶证和准驾车型；工程设备配置操作证、安全培训和设备适用范围。
- 共享模块负责资料、审核和状态，品类 capability 负责判断什么资格适用于目标商品、设备、服务和履约阶段。
- 报价可以提示缺失资格，订单确认和领取或交付必须按已发布规则校验，并在订单保存当时资格结果和适用规则快照。

#### 3.8.6 养护、维修与工单 capability

- 工单能力统一管理清洁、晾晒、消毒、校准、检测、整备、保养和维修任务，来源包括归还检查、定期计划、使用量阈值、IoT 告警和人工创建。
- 工单状态至少包括待处理、处理中、待复核、已完成、无法修复和已取消，并保存责任人员或外部服务商、计划及实际时间、配件耗材、成本、停运时间、预计恢复时间、处理结果和验收凭证。
- 摄影使用清洁、校准和电池更换模板；露营使用晾晒、消毒和防水修复；车辆使用清洁、加油充电、保养和维修；工程设备使用按工时维保、故障维修和安全检测。
- 资产在必须工单完成并验收前不得恢复可用。工单完成后按结果恢复可用、继续停运、转维修、报损或淘汰，不得由前端直接跳过工单修改库存状态。
- 外部维修商只能处理被授权工单和必要资料，不自动获得经营空间其他订单、客户或资产数据权限。

#### 3.8.7 电子签章与合同 capability

- 电子签章统一管理合同模板和版本、签署主体、签署顺序、订单条款快照、签署链接和有效期、签署状态、签署文件、文件摘要及 Provider 回执。
- 签署状态至少区分待发起、待签署、部分签署、已完成、已拒绝、已过期和已作废；重新发起必须生成新的签署记录，不得覆盖原签署事实。
- Provider 未真实完成签署时不得显示“已签署”。电子签署失败时可以按经营空间规则改为纸质或线下签署，但必须保存实际签署方式、文件和操作记录。
- 已完成合同不得原地修改；订单变更需要重新确认条款时生成补充协议或新签署版本，并保留与原订单及原合同的关系。

#### 3.8.8 外部保障与保险 capability

- 外部保障与保险能力统一管理产品、适用商品或订单、投保人、被保险人、保险标的、保障期间、保费、保额、免赔额、投保、承保、拒保、退保和理赔状态。
- 投保记录必须保存真实服务商、外部申请号或保单号、条款版本、回执和最后同步时间；未接入真实服务商或未承保时不得展示“已投保”。
- 事故、损坏、丢失或其他保障事件必须关联订单、检查基线、证据、责任判断和理赔记录；理赔结果与客户责任、押金或预授权处理分别记录，不得直接覆盖原异常费用。
- 商户自行提供的损坏免赔继续按 4.4.11 的合同责任减免管理，不得冒充第三方保险。

#### 3.8.9 建设优先级与启用边界

| 阶段 | 共享 capability | 定位 |
| --- | --- | --- |
| 第一组 | 资格合规、人员服务、养护维修、物流配送 | 直接支撑多个品类的正常履约，优先形成统一业务模型 |
| 第二组 | 自助履约、IoT 遥测 | 先建立统一契约，再按真实设备、地点和 Provider 逐项启用 |
| 第三组 | 电子签章、外部保险 | 在真实服务商、合同和合规要求确定后启用，不使用模拟结果替代真实业务 |

- 第一组表示规划优先级，不自动等于当前开发任务已激活；实际启动仍须写入开发任务并通过对应需求、依赖和验收门禁。
- 任一共享 capability 在新经营空间启用前必须校验品类适用性、配置完整性、权限、依赖、外部 Provider 和人工兜底路径；停用时不得阻断在途订单和历史查询。

前端动态文案不能代替后端数据模型。页面隐藏不是权限控制，后端必须按当前经营空间的品类、capability 和成员权限再次校验。

## 4. 功能需求

### 4.1 SaaS 租户、经营空间与组织权限

- 平台管理员可创建、编辑、冻结、恢复和停用 SaaS 租户。
- 平台管理员可在平台管理面查看目标租户的全部经营空间，并新增空间或编辑空间名称与状态；空间品类创建后不可直接修改，平台治理空间不等于获得空间内经营数据权限。
- 初始化租户必须在同一事务内创建租户档案、首个默认经营空间及其唯一经营品类、根组织、首个履约组织、默认角色、权限、首个管理员、编号规则和审计记录。
- 初始化失败必须整体回滚；临时密码只在初始化响应中返回一次，并强制首次登录修改。
- 租户管理员可新增、编辑、冻结和停用经营空间；新增空间必须原子创建空间档案、品类配置、默认角色、编号规则和审计记录。
- 租户内必须提供独立的“运营账号管理”和“角色权限管理”页面，不复用 SaaS 平台管理员页面。运营账号属于租户，可维护登录账号、姓名、手机号、组织、启停状态、基础角色和密码重置；创建时只返回一次临时密码，原密码不可查看。
- 角色权限遵循 RBAC。操作权限决定页面、模块及新增、编辑、审核、发布等动作；数据权限决定获准操作可访问的数据范围，两者必须分区展示和独立保存，不得用菜单可见性代替后端权限校验。
- 同一运营账号可访问一个或多个经营空间。每个空间成员关系独立保存是否允许访问、空间角色和数据范围；空间角色覆盖租户基础角色，空间数据范围覆盖角色默认范围。撤销空间访问后，旧会话不得退回租户基础权限继续访问该空间。
- 数据范围至少支持“当前租户全部、所属组织、当前经营空间、仅本人”。所有业务查询和导出必须逐模块消费服务端会话解析后的数据范围；只保存配置但未在业务查询执行过滤的模块不得标记为数据权限完成。
- 租户可维护组织、账号、经营空间成员关系、角色、按钮权限和数据范围；同一账号可进入多个经营空间。
- 资源查询与写入必须在数据库层同时附带租户、经营空间及数据范围条件；租户共享主档除外，但仍必须附带 `tenantId`。

### 4.2 产品型号、定价分组、资产与库存

- 产品型号描述品类内可管理的产品定义及其厂商、品牌、型号、规格、库存模式、默认检查模板和套装组成；车辆示例为宝马 3 系、奔驰 C 级，产品型号不得再以“舒适轿车组”等商业分组名称代替。
- 车辆型号管理是厂商车型主档：至少维护型号编码、车型显示名称、制造商、品牌、车系或车型、具体款型和能源类型，可继续扩展年款、座位数、变速方式等共享规格。首期车辆型号固定按序列化单车、单位“辆”管理，不把库存方式和单位作为运营人员反复选择的车型属性。
- 产品型号主档支持由管理员上传标准展示图片，首期每个型号最多 6 张，支持 JPG、PNG 和 WebP，单张不超过 5MB；第一张作为列表封面，删除封面后自动以前序剩余图片补位。图片必须按租户和经营空间隔离并经登录权限读取，不得向客户端暴露服务器本地存储路径。
- 型号图片表达厂牌车型或产品型号的共享外观，并作为关联资产在对应品类资产管理列表和编辑页的默认展示图；页面标题必须使用当前品类术语，不得在摄影、露营或工程空间显示“车型照片”。型号图不等同于具体资产实拍，车况、损伤、交接和事故照片仍归具体资产及履约记录维护，不得混入型号相册。
- 定价分组是经营空间内由用户建立的可预约、可定价商业分组，一个分组可包含多个产品型号；车辆显示为车组，摄影显示为器材组，露营显示为装备组，工程显示为设备组。品类术语只改变页面名称，不改变通用数据结构和服务端流程。
- 定价分组列表和编辑页必须清楚显示包含的产品型号；产品型号列表必须反向显示它当前加入的全部定价分组。同一型号可以属于多个分组，未加入任何分组时必须明确提示“未加入定价分组”，不得伪装成一对一归属。
- 具体资产归属产品型号，不直接归属定价分组。客户按定价分组预约，履约阶段从该分组成员范围内分配具体产品型号、序列化资产或数量库存。
- 车辆管理的每条记录代表一辆具体车辆，必须关联一个车辆型号并维护内部车辆编号、车牌号、VIN、所在门店和状态；颜色、首次登记日期等单车字段保存在车辆实体，制造商、品牌、车系和款型从车辆型号主档引用，不在每辆车上重复填写。
- 同一产品型号可以加入多个定价分组，但所有分组共享底层库存。可用量、预留和分配必须锁定底层产品或资产事实，不得为每个分组复制库存或分别计算后造成超卖。
- 定价分组的成员变化必须记录版本。有效报价和订单保存预约分组、当时的成员范围与名称快照，后续增删成员不得扩大或缩小既有订单可分配范围。
- 序列化资产必须独立追踪资产编号、序列号、状态、所在地点、使用量、维保和事故。
- 数量库存必须按地点记录可用、预占、在租、维修和报损数量。
- 套装必须维护组成、数量、可替代组和拆分规则。
- 套装替代组必须有且只有一个默认组成，并至少有一个替代候选；订单确认后、配货前可在同组内替换，替换时必须重新校验目标库存。
- 配货必须记录实际分配的商品组和资产或数量，不能只保留套装父商品；部分归还只释放本次归还的实际组成与数量，剩余部分继续在租。
- 最后一批归还必须进入整单归还或归还检查，以统一计算逾期、缺件、损坏和清洁等异常费用。
- 资产状态变化必须写流水并影响可用性；停用、维修或已占用资产不得再次分配。
- 商品与资产字段由品类 schema 驱动，服务端校验必填项、类型和唯一约束。

### 4.3 经营主体与履约地点

- 经营空间可维护自营经营主体和合作商，并配置结算方式和启停状态。
- 地点统一抽象为履约地点，可表示门店、仓库、自提点、寄送点、停车场、项目现场或智能柜。
- 地点可配置支持的领取、归还、配送、跨点归还和营业能力。
- 报价、下单、配货和领取必须校验地点及其经营主体启用，并按履约模式校验领取或配送能力；归还地点必须具备归还能力，库存登记地点必须具备仓储能力。
- 订单必须保存创建时的经营主体、领取地点、归还地点和履约方式快照，后续名称、联系人、地址、能力、结算方式或启停状态变化不能篡改历史订单。
- 地点或主体停用后不得承接新报价、配货或领取；已经在租的订单仍允许归还，避免因主档停用阻断客户归还与库存释放。

### 4.4 定价、优惠与增值服务

服务端是最终报价事实源。前端只提交商品、数量、租期、地点、客户、优惠券和服务选择，不提交最终应付金额。

#### 4.4.1 金额口径

金额必须按以下口径分别计算和展示：

`租赁应付 = 基础租金 + 使用量费用 + 履约费用 + 增值服务 + 已确认异常费用 - 优惠方案 - 优惠券`

`本次实收 = 租赁应付 + 应付押金`

`预授权金额 = 独立计算的冻结额度，不计入租赁应付和本次实收`

`最终结算 = 租赁应付 + 后续追加异常费用 - 已支付金额 - 已确认押金抵扣`

- 应付押金、预授权金额、已支付、待支付和可退金额必须作为独立金额字段，不得用同一个字段或明细类型混用。
- 每条收费或减免明细计算后按人民币保留两位小数，总额必须由已舍入明细汇总，保证页面、账单和财务核对时明细之和等于对应总额。
- 优惠和优惠券不得使不允许为负的费用项变成负数；押金和预授权不参与租金优惠，除非具体活动明确声明并保存规则快照。

#### 4.4.2 基础价格矩阵

- 基础定价页面必须按当前经营空间列出全部启用定价分组，以“定价分组 × 计价单位”维护当前价格；产品型号和序列化资产沿用预约分组价格，不为每个型号或每台资产重复维护基础价格。
- 页面不得以“新增基础定价记录”建立孤立价格。新建定价分组时必须同时填写至少一条“计价单位 + 基本价”，分组与基本价在同一事务保存并追加新的空间完整价格版本；不得先建未定价分组再到基础定价页初始化。
- 定价分组的新建表单只呈现计价单位和基本价，不向普通运营人员暴露押金、预授权、阶梯、日期类型、分时时段、使用量或履约费用等高级字段；这些规则由各自的规则或高级价格配置入口维护。
- 基础定价页面是当前价格与调价计划页面：当前价格只读展示，不提供初始化、直接改价或逐分组新增价格入口；所有后续价格变化从一个空间级“新增调价计划”入口统一处理。
- 页面只显示一个当前经营空间整体价格版本；表格中的所有定价分组价格都属于该整体版本，不得为每个定价分组分别显示或解释版本号。
- “基础定价、优惠方案、增值服务”已有独立左侧菜单和独立路由，各页面内不得再显示重复的三项切换 Tab。
- 每个定价分组可配置多个可用计价单位，但必须指定一个默认计价单位；调用方明确选择的计价单位没有有效价格时必须拒绝报价，不得静默改用其他单位。
- 每条价格至少包含基础单价、最低计费单位、进位规则、日期价格、阶梯价、封顶价、包含使用量、超额使用单价、押金规则和预授权规则中适用的部分。
- 升级前遗留的启用分组若没有当前有效价格，页面必须标记为历史缺口且正式报价拒绝；新流程不得再产生新的未定价分组。
- 套装可以维护独立价格，不强制等于组成商品价格之和；订单仍须保存实际分配的套装组成。
- 基础价格只在当前经营空间生效；同一 SaaS 租户的其他经营空间不得读取或复用，除非未来新增经过授权的价格复制功能。

#### 4.4.3 调价计划与价格版本

- “价格版本”是某一生效时点当前经营空间全部有效定价分组价格的完整、不可变结果；“调价计划”只记录相对当前版本的变化项，但执行时必须生成新的完整价格版本。
- 立即手工改价和定时调价必须走同一版本机制，不得存在绕过版本历史的直接覆盖入口。
- 调价计划至少保存计划名称、调整范围、生效时间、调整方式、调整前后值、调整原因、创建人、确认人、创建时间、状态和执行结果。
- 调整方式支持直接设价、增加或减少固定金额、按百分比上调或下调；系统必须在计划确认时展示每个受影响商品的最终价格，不得只展示公式。
- 调价计划状态为“草稿、待生效、已生效、已取消、执行失败”。草稿可编辑或删除；待生效只能取消，不得直接修改；已生效不可编辑、撤回或删除；错误价格只能通过新的纠正计划恢复。
- 同一经营空间、同一定价分组和计价单位不得存在无法确定唯一结果的重叠生效版本；冲突必须在计划确认时阻止，而不是到报价时临时择一。
- 每次价格变化必须能够还原上一个完整版本、变化差异、操作者、确认人和原因。历史版本不得被后续改价覆盖。

#### 4.4.4 生效时间与报价锁价

- 价格版本按租期开始时间匹配，而不是按报价创建时间匹配；未来租期必须使用覆盖该租期开始时点的已发布价格版本。
- 报价生成后在其有效期内锁定本次命中的价格、日历、优惠、服务、履约费、押金和预授权结果。锁价期间发布新价格不得改变既有报价。
- 报价过期、客户修改商品、数量、租期、地点、履约方式、优惠券或服务选择时，必须重新报价并生成新的报价快照。
- 已创建订单不得因价格计划、地点主档、商品名称或规则后续变化而自动变价。

#### 4.4.5 计价单位、进位、阶梯、日期价格与封顶

计价顺序固定为：

`确定计价单位 → 计算原始单位数 → 执行进位与最低起租 → 匹配阶梯单价 → 应用逐单位日期价格 → 计算单件租金 → 应用单件封顶 → 乘商品数量`

| 计价单位 | 业务口径 |
| --- | --- |
| 小时 | 按价格配置的小时粒度向上取整，例如每 1 小时或每 30 分钟；不足一个粒度按一个粒度计 |
| 班次 | 每开始一个配置班次计一个单位，班次时长及边界由经营空间规则定义 |
| 24 小时 | 从租期开始时刻连续切分 24 小时块，每开始一个块计一个单位 |
| 自然日 | 按经营空间营业时区计算占用的营业日期数量，结束时刻恰好为营业日零点时不占用新日期 |
| 夜 | 按经营空间营业时区计算跨越的夜晚数量，当日领取并当日归还可以为 0，再由最低起租规则决定是否收费 |
| 周 | 按连续 7×24 小时块计算，每开始一个块计一个单位 |
| 30 日月 | 按连续 30×24 小时块计算；第一阶段“月”默认指此口径，页面必须明确显示“30 日” |
| 自然月 | 作为独立计费模型保留，按日历月或月度周年计算，不得与 30 日月共用含义；启用前需单独确认跨月余量规则 |
| 使用量 | 按里程、工时、次数、电量或品类定义的指标计算，可包含基础额度及超额单价 |

- 长租阶梯默认采用“达到档位后，全部单位使用该档单价”，例如满 7 天后按 7 天的长租单价计算；水电、里程等分段累进价格必须使用独立的“分段阶梯”模型，不得与长租阶梯混用。
- 封顶价默认按“每件商品、单次租期”应用，再乘商品数量；如需整单封顶，必须作为独立订单级规则配置并明确展示。
- 工作日、周末、法定节假日和特殊日期价格不得用整段平均倍率代替。自然日和夜按每个计费日期计算；小时、班次、24 小时、周和 30 日月按每个计费块开始时所在的营业日期取价。
- 报价计算说明必须展示原始单位数、进位结果、最低起租、阶梯档位、各日期或计费块价格、封顶前后金额和商品数量，使运营人员能够根据快照复算。

#### 4.4.6 履约费、增值服务与异常费用

| 费用类型 | 定义 | 典型项目 |
| --- | --- | --- |
| 履约费用 | 完成所选领取、配送和归还方式所必需的费用 | 标准配送、上门取回、仓库出库、项目现场交接、基础运输 |
| 异地归还附加费 | 领取地点与归还地点不同所产生的履约附加费，属于履约费用 | 同区域跨点、跨区域归还、特殊地点附加费 |
| 增值服务 | 客户主动选择、不是完成基础履约所必需的可选服务 | 保险、损坏免赔、加急或指定时段配送、安装调试、操作员、摄影助理、额外配件 |
| 异常费用 | 订单履约后根据真实事件和证据追加的费用 | 逾期、超里程、超工时、损坏、缺件、额外清洁、报损 |

- 同一收费事项只能有一个价格来源。标准配送计入履约费用；加急或指定时段配送可以作为增值服务，但不得与标准配送重复收费。
- 第一阶段异地归还支持“同地点免费、不同地点固定附加费”；后续可扩展为地点组合或区域组合价。未配置或业务规则不允许的地点组合必须拒绝报价，不得按零元放行。
- 初始报价只包含当时已经确定的费用。损坏、缺件、逾期等异常费用只能在事件真实发生后追加，并保存关联订单事件、证据、计算规则、操作人和审核记录；不得回写或覆盖原报价金额。
- 优惠方案按条件自动计算折扣；优惠券必须具备领取、锁定、核销、释放、过期和作废状态；增值服务必须保存价格和条款版本。

#### 4.4.7 押金与预授权

- 押金是实际收取并可退还或抵扣的资金；预授权是冻结额度，不是付款。两者必须独立配置、独立计算、独立展示和独立记录状态，并允许同一订单同时存在。
- 押金支持免押、每件固定押金、商品行租金倍数、每单固定押金和订单押金上限；预授权支持不需要、每件固定额度、租金倍数、订单固定额度、风险附加额度和订单预授权上限。
- 第一阶段默认按各商品行计算后求和，再应用订单级上限。商品行租金倍数以该行日期价格和封顶处理后的租金为基数。
- 会员权益、企业合同或人工审批导致免押、减押或降低预授权时，必须保存减免类型、依据、审批人及当时规则快照，不能只保存金额为 0。
- 押金退款、押金抵扣、预授权发起、追加、转扣、释放和失败必须作为独立资金事件记录，不得通过修改原报价明细表达。

#### 4.4.8 报价与订单价格快照

- 报价快照必须保存本次请求、计价时点、营业时区、商品及当时名称、数量、租期、领取与归还地点、履约方式、价格版本，以及每行实际命中的计价单位、费率、原始单位数、进位、最低起租、阶梯、日期价格、封顶和使用量结果。
- 报价快照同时保存履约费用、异地归还费、增值服务及条款版本、优惠方案、优惠券、押金、预授权、日历版本、命中日期类型、金额公式、创建时间和失效时间。
- 快照保存的是本次实际命中的配置片段，不要求复制未参与本次报价的全部价格主档；只保存版本编号但无法还原命中费率，不视为完成快照。
- 订单创建时必须复制完整报价快照，并增加成交时客户、经营主体、履约地点、实际套装组成、资产或库存分配、租赁规则、取消/逾期/损坏规则和服务条款快照。
- 订单成立后的延期、换货、部分归还、异常费用、减免、押金抵扣和预授权转扣必须追加独立记录；原始报价和订单创建快照不可编辑。

#### 4.4.9 多品类计价扩展

- 摄影、露营、车辆和工程设备共用基础价格矩阵、版本、报价、押金、预授权、优惠、履约费和快照规则，不得为车辆保留另一套旧门市定价主流程。
- 通用计价模型包括小时、班次、24 小时、自然日、夜、周、30 日月、阶梯、封顶和使用量；里程、工时、快门数、次数、电量等指标通过使用量定义扩展。
- 新品类需要新的计价模型时，应新增独立模型并声明适用品类、输入指标、进位、金额公式和计算说明；新增模型不得改变既有模型含义或既有品类历史报价结果。
- 品类独特费用通过 capability 扩展，例如车辆超里程、工程设备超工时、摄影器材快门超额、露营套装清洁或缺件；最终都必须生成统一费用明细并进入订单结算和审计链。

#### 4.4.10 优惠方案与优惠券

**业务对象与边界**

- 优惠方案是客户满足条件后由系统自动计算的营销规则，客户不持有独立凭证；优惠券是发放给具体客户、具有独立权益快照和生命周期的凭证。两者必须分别配置、计算、展示和审计。
- 优惠方案和优惠券默认归属经营空间。同一租户共享客户主档不代表共享营销权益；跨空间通用券属于未来独立能力，必须明确适用空间和统一预算后才能启用。
- 优惠可以指定作用于商品租金、使用量费用、履约费用或增值服务。标准租金优惠不得含糊地减免押金、预授权或异常费用。

**资格与计算基数**

- 优惠资格可按商品、计价单位、客户类型、会员等级、新客或首单、最低租金、最低租期、领取/归还地点、履约方式、下单渠道、租期开始日期、每人次数、总使用次数和总预算配置。
- 租金优惠的最低消费默认按“商品租金 + 使用量费用”的优惠前金额计算，不包含履约费、增值服务、押金、预授权和异常费用；履约费券或增值服务券必须明确自己的优惠对象和资格基数。
- 生成报价时校验并展示资格，确认订单时重新校验资格、券状态、活动状态和预算。报价时符合条件不代表优惠券或预算已经被独占。

**优惠类型与计算顺序**

- 第一阶段优惠类型包括百分比折扣、固定金额减免和满额固定减免；满租期赠送、指定商品固定价、免履约费和指定服务减免作为独立优惠模型扩展，不得把复杂规则塞入百分比或固定金额字段。
- 计算顺序为“商品租金与使用量费用 → 自动优惠方案 → 客户选择的优惠券 → 履约费优惠 → 增值服务优惠 → 租赁应付”。每一步的计算基数和减免结果都必须保存，任何费用项不得被优惠成负数。
- 每项优惠必须支持最大优惠金额，报价明细必须说明优惠前金额、计算基数、优惠公式、实际减免金额和作用对象。

**互斥、叠加与选择**

- 每个优惠配置优先级、互斥组、是否可与其他优惠方案叠加、是否可与优惠券叠加和最大优惠金额。
- 同一互斥组只能应用一个优惠；不同互斥组仅在双方均允许叠加时才可同时应用。
- 多个互斥优惠同时满足时，默认选择对客户实际减免金额最大的一个；减免金额相同时再按优先级决定，不得按数据库装载顺序或配置创建顺序随机择一。
- 报价必须展示已应用优惠、满足但因互斥未应用的优惠及原因，并允许客户在规则允许时从其可用优惠券中选择；系统可以推荐最优券，但不得在客户明确选择后静默替换。

**优惠券模板与实例**

- 优惠券模板至少保存名称、编码、优惠类型、面值、领取时间、使用时间、适用租期、适用对象、最低消费、发行总量、总优惠预算、每人领取和使用上限、叠加规则、状态及版本。
- 模板状态为“草稿、待开始、进行中、已暂停、已结束、已作废”。暂停默认停止新发放，不自动作废已经发给客户的优惠券；批量作废存量券必须是独立高风险动作并记录原因。
- 客户优惠券必须保存客户、来源模板及版本、发放原因和时间、可使用时间、实际权益快照、当前状态、锁定订单、核销订单以及释放、过期或作废原因。
- 客户优惠券在发放时固化权益；模板后续修改、暂停或结束不得改变已发券的面值、适用条件和有效期，除非执行有权限、有原因、有审计的显式作废。

**生命周期与并发**

客户优惠券状态流转为：

`可用 → 已锁定 → 已核销`

异常流转包括“已锁定 → 订单失败或超时 → 可用”“可用 → 已过期”“可用或已锁定 → 已作废”。

- 报价阶段只校验和保存优惠计算结果，不锁定优惠券和预算；确认订单时必须在同一事务内锁定优惠券、预占活动预算并创建订单。
- 支付或订单正式生效后核销；确认失败、未支付超时或支付前取消时自动释放优惠券和预算。
- 锁定期间到达券有效期时，允许该订单在自身待支付保留时间内继续完成；释放后再按当前时间判断恢复为可用还是已过期。
- 同一客户并发领取、两个订单并发使用同一券以及多个客户争抢最后发行量或预算时，只允许符合限额的请求成功，不得超发、重复锁定或超预算。

**发行量与预算**

- 优惠券支持系统事件自动发放、运营定向发放、客户主动领取、注册/实名/首单/邀请奖励发放和按客户名单批量发放。
- 系统必须分别记录发行总量、已发放数量、每人领取次数、每人使用次数、总优惠预算、已锁定预算和已核销预算。
- 可用预算按“总预算 - 已锁定优惠金额 - 已核销优惠金额”计算；锁券时预占，订单失败时释放，核销后转为已使用预算。

**取消、退款与部分取消**

| 订单情况 | 优惠券处理 |
| --- | --- |
| 确认失败、未支付超时或支付前取消 | 立即释放 |
| 已支付、领取前因经营方原因取消 | 恢复原券；原券已过期时发放同权益补偿券 |
| 已支付、领取前因客户原因取消 | 按取消规则决定，第一阶段默认恢复一次 |
| 已领取、已部分履约或已完成 | 不自动退券，特殊补偿通过独立补偿券处理 |

- 退款按客户优惠后的实际支付金额计算；优惠券不兑换现金，也不得作为独立退款金额退还。
- 订单级优惠在订单确认时分摊到订单行并保存分摊结果。部分取消或部分退款时，必须重新判断剩余商品资格，并以各行优惠后实付为退款上限，不能直接按券面额退款。

**报价、订单快照与失效处理**

- 报价保存命中的优惠方案版本、客户优惠券及权益快照、资格判断、优惠前金额、每项计算基数、优惠金额、叠加和互斥结果，以及未应用优惠的原因。
- 报价锁定优惠计算口径，但不独占优惠券和预算。确认订单时优惠券已被其他订单使用或预算耗尽的，必须明确失败并要求重新报价，不得静默删除优惠后继续下单。
- 订单确认后保存最终优惠快照及订单行分摊；后续修改模板、暂停活动、调整优先级或作废新发放，不得改变历史订单。

**权限与审计**

- 营销编辑人员可以编辑草稿；营销发布人员可以发布、暂停和结束活动；客服只能按授权查看、补发或发放补偿券；财务查看核销、预算和退款分摊；普通运营只查看订单优惠结果。
- 编辑和发布使用独立权限。人工作废、批量发券、补偿券、预算调整和退款处理必须填写原因并记录租户、经营空间、客户、活动、订单、操作者和前后差异。

#### 4.4.11 增值服务与保障条款

**业务对象边界**

| 对象 | 判断标准 | 典型项目 |
| --- | --- | --- |
| 可租商品或配件 | 有实物、需要库存或资产追踪、通常需要归还和清点 | 镜头、电池、儿童座椅、露营灯 |
| 履约费用 | 完成所选基本交付方式必然产生 | 标准配送、上门取回、基础运输 |
| 增值服务 | 客户可选或业务规则要求的额外服务 | 安装调试、操作员、摄影助理、加急配送 |
| 保障服务 | 对风险责任、赔付范围或保险关系进行约定 | 损坏免赔、第三方保险 |
| 异常费用 | 真实履约异常发生后追加 | 损坏、缺件、逾期、额外清洁 |

- 需要归还和清点的实物必须作为商品或配件管理，不得包装成服务绕过库存、分配和归还。
- 标准配送属于履约费用；加急、指定时段或额外搬运可以作为增值服务。同一收费事项只能有一个来源，不得同时进入商品、履约费和服务费。
- 强制服务仍保存为订单服务，但必须标记触发规则和“业务规则要求”，不得伪装成客户自愿选择。

**服务定义与适用范围**

- 服务类型包括纯费用、人员、现场作业、时间预约、处理服务、风险保障和品类专属服务。
- 每个服务至少声明适用品类、商品、地点和履约方式，客户是否可选，是否可重复选择，最小和最大数量，是否需要排班或容量，是否需要接受条款，是否允许优惠，以及订单成立后是否允许增加或取消。
- 服务状态和适用资格必须在报价时检查，并在订单确认或变更时重新校验；停用服务不得用于新报价，但不改变已经锁定服务快照的订单。

**服务计价**

- 服务支持每订单、每件商品、每份或每人、每小时、每班次、每自然日、每晚、按租期、按距离/里程/工时，以及固定价格加超额价格等计价模型。
- 服务计费单位独立于商品租金单位。每日服务逐日取价；人员服务按实际服务时段计价，不得默认按设备完整租期收费。
- 服务费用按“服务单价 × 服务数量 × 服务计费单位”形成独立明细，并保存价格版本、单位数、适用对象和计算说明。
- 服务只有在优惠明确指定该服务或服务类型时才参与减免。普通服务不自动增加押金或预授权；高风险服务需要增加时必须由明确规则独立计算。

**容量、资源与预留**

- 服务分为无容量服务和有容量服务。无容量服务无需人员或资源预约；人员、安装、调试、指定时间配送、清洁工位等属于有容量服务。
- 有容量服务必须维护服务资源、适用地点、可服务时段、同时服务数量、已预留数量、已确认数量、停用和不可用状态。
- 报价阶段只检查服务容量，不长期占用；订单确认时在订单事务中预留服务容量，确认失败、取消或超时时释放。服务资源不足时不得只收费而不安排履约。
- 服务资源后续不可用时，经营方只能在客户确认后替换同等资源，或取消服务并退款；不得静默替换服务资质、时间、地点、保障范围或条款。

**可选、推荐、强制和人工服务**

- 服务选择方式为客户可选、系统推荐、条件强制和运营人工添加。
- 条件强制服务必须保存触发规则，例如客户缺少操作资质时强制操作员、高价值商品强制基础保障、特殊地点强制安装服务；改变商品、客户资质或履约方式后必须重新判断。
- 客户不得直接取消仍满足触发条件的强制服务。运营人员人工增加收费服务必须填写原因，并由客户重新确认金额和条款，不得在客户不知情的情况下增加应付。

**损坏免赔与第三方保险**

- 损坏免赔是租赁商提供的合同责任减免，至少包含保障范围、保障上限、客户自付额、不适用情形、除外责任、是否覆盖丢失/进水/误操作及条款版本。
- 损坏免赔下的客户承担金额由自付额以内金额、超出保障上限金额和不在保障范围内金额组成；每项认定必须关联检查结果、异常证据和订单条款快照。
- 第三方保险是外部保险产品，至少包含真实服务商、被保险对象、保障期间、保费、保额、免赔额、保单号、投保状态、理赔状态、条款和外部回执。
- 未选择和接入真实保险服务商前，只允许标记为模拟或预留能力，不得向客户展示“已投保”、虚构保单号或把商户损坏免赔称为保险。

**条款版本与客户确认**

- 损坏免赔、保险、操作员责任和其他高风险服务必须保存服务版本、条款版本、不可变条款快照、客户确认时间、渠道、确认人、订单以及确认时的价格和保障范围。
- 条款发布后不可原地修改；变更必须发布新版本。新报价使用新版本，有效报价和历史订单继续使用原快照，不得用当前网页条款替代历史订单条款。

**订单服务变更**

| 阶段 | 服务处理 |
| --- | --- |
| 报价阶段 | 修改服务后重新报价 |
| 订单确认前 | 可增加或移除可选服务并重新计算 |
| 已确认、服务未开始 | 按服务规则增加或取消，重新确认差额、条款并调整容量 |
| 已部分执行 | 只处理未执行部分，已执行部分保留事实 |
| 已完成 | 不得删除，只能追加退款、补偿或异常处理 |
| 风险事件已经发生 | 不得补买免赔或保险追溯覆盖既有事件 |

- 服务变更不得覆盖原订单服务，必须追加变更记录。增加收费服务时客户重新确认；人员和现场服务取消时同步释放未使用容量。

**服务履约、失败与退款**

- 有实际履约过程的服务状态为“待预留、已预留、已确认、服务中、已完成”，异常状态包括“已取消、履约失败、客户爽约、已退款、已补偿”。纯费用型服务可以在订单成立时直接确认。
- 服务记录至少保存计划和实际时间、服务人员或资源、地点、履约结果、照片/签字等凭证、失败原因和客户确认。
- 服务未开始按规则全额退款；已部分完成按未执行部分退款；已完成原则上不退；经营方履约失败全额退款并可追加补偿；客户爽约按事先发布并已确认的取消规则处理。
- 经营方无法履约时，处理顺序为提供同等替代、客户确认替代、无法替代则取消并退款，必要时发放补偿权益。

**多品类扩展**

- 摄影设备可扩展摄影助理、器材教学、数据备份和损坏免赔；露营装备可扩展配送搭建、拆收、深度清洁和耗材补充；车辆可扩展送车上门、代驾、安装和道路救援；工程设备可扩展运输、安装调试、操作员、安全培训和现场保障。
- 各品类通过统一服务、容量、条款、履约和结算模型扩展自己的服务，不得建立独立订单体系。涉及可归还实物时，服务只表达安装、配送或人员劳动，实物仍按商品库存分配和归还。

**权限与审计**

- 服务编辑维护草稿；服务发布人员发布价格和条款版本；排班调度分配服务资源；履约人员记录开始、完成和失败；客服处理改约与补偿；保障审核处理免赔和理赔；财务处理退款和费用核对。
- 人工增加收费服务、改变价格或保障范围、替换资源、取消或失败、退款、免赔审核和保险理赔必须填写原因并记录租户、经营空间、订单、服务、操作者和前后差异。

### 4.5 营业日历

营业日历同时定义日期类型、当天是否可以办理各类履约动作，以及日期价格的匹配依据；库存是否充足、资产是否可用和员工排班不属于营业日历职责。

#### 4.5.1 经营空间日历与营业时区

- 每个经营空间独立配置营业日历和唯一 IANA 营业时区；同一 SaaS 租户的不同经营空间可以使用不同日历和时区。
- 每周默认营业模板至少包含工作日、休息日、每日一个或多个营业时段，以及领取、归还和配送的默认可用时段；自助领取或归还作为地点 capability 单独声明。
- 自然日、夜、日期价格、营业时间、履约时段和跨年度判断必须使用同一营业时区，不得部分使用 UTC、部分使用经营空间时区。
- 已产生报价或订单后修改经营空间时区不得反向改变历史金额和履约约定；时区变更必须记录原因并只影响变更后生成的新报价。

#### 4.5.2 官方日历导入与空间发布

- 平台支持导入带日期、日期类型、节日名称、调休工作日、来源、来源发布日期、导入时间和版本的中国大陆官方节假日数据。
- 官方数据是公共基础来源，不得导入后自动影响全部经营空间。导入或更新官方数据时，为经营空间生成新的年度日历草稿或更新提示，由有权限的空间人员确认后发布。
- 官方日历再次调整时必须形成新的来源版本；已发布的经营空间日历、有效报价和订单不得被静默覆盖。
- 未来年度官方日历尚未发布时，系统按经营空间每周默认模板允许报价，并明确提示“未来年度官方日历尚未确认”；后续发布官方日历不得改变已锁价报价和既有订单。

#### 4.5.3 日期来源与覆盖优先级

日期规则优先级固定为：

`具体日期人工覆盖 > 当前年度已发布官方日历 > 每周默认营业模板`

- 经营空间可对具体日期覆盖日期类型、营业状态、营业时段、领取能力、归还能力、配送能力和特殊价格标记或系数。
- 人工覆盖必须保存调整原因、操作人、调整时间和生效日期；人工覆盖不改变已经生成的报价和订单。
- 移除人工覆盖表示恢复到下一优先级来源，不得把该日期变成没有来源的空白日。
- 日期详情必须能说明当前结果来自人工覆盖、官方日历还是每周模板，并展示被覆盖的原始值。

#### 4.5.4 营业状态与履约限制

| 营业状态 | 业务含义 |
| --- | --- |
| 正常营业 | 在配置时段内提供允许的领取、归还和配送服务 |
| 限时营业 | 只在指定时段提供指定履约能力 |
| 停止营业 | 不接受普通现场领取、配送或现场归还 |
| 自助营业 | 人工停业，但允许具备 capability 的智能柜、自助停车场等方式履约 |

- 停业只限制发生在当天和目标地点的领取、配送、现场归还等履约动作，不禁止租期跨过该日期；客户周五领取、周一归还时，周末门店停业不影响设备继续在租。
- 已经在租的订单不能因临时停业而失去归还渠道。经营空间必须提供自助归还、备用地点、改约或人工登记中的至少一种处理方式；因经营方停业造成的改约不得直接认定为客户逾期。
- 营业状态和日期价格相互独立。节假日加价营业应表示为正常或限时营业并配置特殊价格；不得用“停业但加价”表达。
- 报价和订单必须分别校验领取与归还时点的地点能力和营业状态；仅租期中间经过停业日不得阻止报价。

#### 4.5.5 日期类型与价格关系

- 日期类型至少包括工作日、周末、法定节假日、调休工作日和经营空间特殊日。
- 营业日历负责确定日期类型、日期来源、营业与履约限制，以及一次性价格覆盖适用的日期、日期范围或日期时间范围；营业日历不得保存商品基础价格，也不得用一个经营空间统一倍率替代所有商品的日期价格。
- 价格计划负责定义“商品 × 计价单位”的基础价格，以及“商品 × 计价单位 × 日期类型”的价格或系数；工作日、周末、法定节假日、调休工作日和经营空间特殊日均使用同一可扩展模型，不得在报价代码中硬编码成仅支持周末倍率和节假日倍率。
- 分时价格规则分为两类：周期性计价时段用于“每周五 12:00 至周一 00:00 按周末价”等重复规则；一次性日期时间覆盖用于“2026-10-01 12:00 至 2026-10-08 18:00 按国庆特殊价”等临时规则。两类规则都使用经营空间营业时区，不能把本地时段按 UTC 解释。
- 周期性计价时段由价格计划保存适用商品、计价单位、星期与时间边界、价格或系数和不可变价格版本；它可以跨星期边界。同一价格版本内，同一商品和计价单位的周期性时段不得重叠或产生无法确定优先级的结果。
- 一次性日期时间价格覆盖由营业日历保存适用范围、覆盖原因和不可变价格覆盖版本引用；具体商品、计价单位、金额或系数由价格模块保存。发布后的日历版本和价格覆盖版本都不可原地修改，任一方调整都必须生成新版本。
- 报价服务只负责按计费单位的取价时点解析并执行价格优先级，不得在接口调用方或管理端计算最终价；报价快照必须同时保存命中的取价时点、日历版本、日期类型、价格版本、周期性时段或一次性覆盖版本和实际计算结果。
- 日期与分时价格优先级固定为“具体日期时间价格覆盖 > 周期性计价时段价格 > 商品在该日期类型下的价格 > 商品基础价格”。
- 不同商品可以对同一日期类型采用不同价格策略；例如车辆节假日加价 30%、摄影器材加价 10%，不得被全空间统一倍率强制覆盖。
- 日期或日期时间价格覆盖必须纳入日历版本和报价快照，并展示覆盖原因、适用范围及开始和结束时点。

#### 4.5.6 跨日与跨年度计算

- 所有时间先换算为经营空间营业时区，再确定营业日期和计费块；不得对整个租期的日期倍率取平均。
- 每个计费单位必须产生一个明确的取价时点：小时、班次、夜、24 小时、周和 30 日月使用该计费块开始时点；自然日首个计费单位使用实际租期开始时点，后续自然日单位使用对应营业日期的开始时点。
- 分时价格按计费单位的取价时点命中。默认不因为取价时点之后进入另一价格时段而拆分小时以外的完整计费块；例如周五 14:00 开始的 24 小时计费块可以命中周末价，周五 10:00 开始的完整 24 小时计费块仍按其 10:00 取价结果执行。若某计费模型需要在时段边界拆块，必须由该计费策略显式声明、单独验收，不得作为全平台默认行为。
- 跨年度租期必须同时读取涉及年份的当前已发布日历；尚无已发布年度日历时按 4.5.2 的未来年度规则处理。
- 报价快照必须保存每个计费单位命中的取价时点、营业日期、年度、日期类型、营业状态、实际价格、价格规则来源和年度日历版本；跨年度报价不得只保存一个年份或版本号。

#### 4.5.7 年度版本与历史

- 年度日历状态为“草稿、已发布、已被替代、已作废”。每个经营空间、每个年度只能有一个当前使用的已发布版本。
- 草稿可以编辑或删除；已发布版本不可直接修改。调整已发布内容时必须复制生成新草稿，新草稿发布后原版本进入“已被替代”。
- 恢复旧规则也必须以旧内容生成新的发布版本，不得删除新版本或把旧版本原地改回。
- 新发布版本只影响发布后生成的新报价；有效报价继续使用原快照，订单始终使用订单快照。
- 订单延期或变更租期时，只重新计算新增或变更时间段，保存原依据和新增依据，不得覆盖原始租期的日历与价格快照。
- 发布记录必须保存版本号、发布人、发布时间、变更原因、与上一版本的差异、官方来源版本和人工覆盖内容。

#### 4.5.8 权限与审计

| 角色 | 日历权限 |
| --- | --- |
| SaaS 平台管理员 | 导入和维护公共官方日历来源；不得直接发布租户经营空间日历或借此查看空间业务数据 |
| 租户管理员 | 查看本租户被授权空间日历，并按空间权限管理或发布 |
| 经营空间管理员 | 编辑、审核和发布当前经营空间日历 |
| 日历编辑人员 | 新建和修改草稿，不得发布 |
| 普通运营人员 | 查看已发布日历和当日履约安排 |
| 客服或财务 | 查看历史版本及报价命中的日历依据，不得修改 |

- 编辑与发布使用独立权限。第一阶段不强制双人审批，但权限模型必须允许后续启用“编辑人不能发布自己的草稿”。
- 发布前必须展示受影响日期以及停业、营业时间、履约能力和特殊价格变化；存在未来订单时必须提示，但不得直接改变这些订单。
- 发布必须填写变更原因，并写入包含租户、经营空间、年度、版本、操作者和差异的审计记录。

#### 4.5.9 管理端月历与日期范围覆盖

- 营业日历管理端默认按自然月显示七列月历，可切换月份和年度；不得把全年每一天作为默认长列表要求租户逐日查找和修改。版本历史、差异和审计可以使用列表或明细视图，但不能替代日常月历操作。
- 月历中的全部日期由“每周默认营业模板 + 当前年度官方日历”生成。租户不能新增、删除或直接改写基础日期，只能在基础结果之上新增人工覆盖；界面动作统一命名为“新增日期覆盖”或“新增日期范围覆盖”，不得把它表达为新增日历日期。
- 每个日期格至少展示日期类型、节日或调休名称、营业状态、当前来源和人工覆盖标记，并提供可辨识的图例；存在分时价格时还要显示“分时价格”标记和简要时段，例如“12:00 后周末价”。点击日期可查看基础值、当前生效值、覆盖原因、价格时段和来源版本。
- 有编辑权限的人员可以选择单日、连续日期范围或带开始和结束时间的日期时间范围，并对所选范围统一设置日期类型、营业状态、营业与履约时段，以及一次性特殊价格覆盖引用。整日营业日历覆盖可以跨月但不得跨年度；跨年度操作必须拆成两个年度批次，分别进入各自的年度日历版本。
- 周期性计价时段不改变日期本身的工作日、周末或法定节假日分类。例如周五仍显示为工作日，但可以叠加“12:00 后周末价”；该规则由价格计划维护，月历负责展示结果并提供进入对应价格规则的操作入口，不得把周五整天改成假日。
- 营业与履约时段和计价时段必须使用不同字段、独立校验。价格在周五下午上浮不代表门店停业或停止领取；营业状态变化也不得自动生成价格变化。
- 日期范围操作只修改用户明确选择的字段，未选择字段保持原值；范围内已有人工覆盖时，提交前必须展示冲突日期和将被替换的字段，并由用户确认，不得静默覆盖。
- 一次范围提交必须作为一个原子操作处理：全部日期成功或全部失败，共用调整原因、操作者、操作时间和批次标识，只产生一次并发修订；不得出现部分日期已保存、部分日期失败的状态。
- 移除人工覆盖后，日期必须恢复到当前官方日历或每周默认模板的结果。按范围移除时同样执行原子操作，并在提交前展示恢复后的日期类型、营业状态和价格覆盖变化。
- 无编辑权限的普通运营、客服或财务只能查看其权限范围内的已发布月历、历史或报价依据，不显示新增、修改、移除和发布操作。
- 发布前影响预览必须覆盖本次日期或日期时间范围操作产生的所有日期和时段，并继续执行未来订单提示、版本差异和审计要求；首次发布也不得因为不存在上一发布版本而返回空影响范围。

### 4.6 租赁规则

租赁规则负责订单成立、支付、履约、取消、延期、逾期、资质和异常责任，不负责商品基础价格、日期分类或服务价格。经营空间按品类配置并发布规则版本。

#### 4.6.1 规则版本、生效与优先级

- 规则状态为“草稿、待生效、已生效、已被替代、已作废”。已发布规则不可原地修改；调整或恢复旧规则都必须生成新版本。
- 规则按租期开始时间匹配。未来租期使用覆盖其开始时点的已发布规则；报价生成后锁定规则，订单创建后永久使用订单快照。
- 规则优先级为“法律法规与平台安全底线 > 品类强制资质和安全规则 > 已签署企业合同或客户协议 > 经营空间已发布规则 > 品类默认规则”。
- 企业合同覆盖经营规则时必须保存合同和覆盖条款。普通人工例外不得绕过租户/空间隔离、法定证照、安全停运、库存不足、资产占用和风险发生后补买保障等底线。

#### 4.6.2 报价、订单保留与领取时限

- 报价有效期、未支付订单资源保留时间和领取宽限时间必须分别配置，不得用一个超时时间混用。
- 报价阶段不占库存、优惠券或服务容量；订单确认时原子锁定库存、优惠券、营销预算和服务容量。
- 未支付订单超过保留时间自动取消并释放全部资源。超过约定领取时间只进入待确认爽约，必须经过客户通知和最终时限后才能判定爽约。

#### 4.6.3 支付、押金与预授权时点

- 支付规则支持下单全额支付、按比例预付并在领取前付清、线下确认、企业月结或授信、到店支付，以及免预付但需要押金或预授权。
- 规则至少定义首付款比例或金额、尾款时点、押金时点、预授权发起和释放时点、支付失败、是否允许部分支付、企业授信额度、未支付取消和退款处理。
- 租赁应付、押金应付、已支付、待支付、已退款、待退款、预授权冻结、预授权转扣和预授权释放必须独立记录。
- 未接入真实支付供应商前只能使用明确标记的模拟支付，不得把内部状态展示为真实收款或真实预授权。
- R1 的模拟资金至少分为“租赁及费用实收/退款、押金、预授权”三本独立事件账。领取和关闭订单必须按各自规则校验实际待收或待退余额；不得因历史上曾收过押金、冻结过预授权或记录过一次付款，就把后来已退、已释放或仍欠款的订单当作可领取或可关闭。

#### 4.6.4 领取、配送与归还

- 规则至少定义最早和最晚领取时间、是否允许提前领取、是否允许代领及资料要求、配送签收、异地归还、归还宽限、非营业时间归还、检查模板和客户确认方式。
- 领取前必须重新校验订单和支付状态、押金或预授权、客户身份、品类资质、实际分配资产、地点能力、营业状态、强制服务及必要条款确认。
- 地点停用或停业可以阻止新的领取和配送，但不得让已在租订单失去可执行的归还路径。

#### 4.6.5 客户取消与经营方取消

- 客户取消按距离约定领取时间的区间配置，可分别定义是否允许取消、租金退款比例、履约费和服务退款、优惠券恢复、已发生成本、取消费和是否需要审核。
- 取消时间段至少覆盖领取前较长时间、领取前短时、进入领取宽限、已到领取时间和已领取后；具体阈值由经营空间发布。
- 客户原因按订单规则快照计算；经营方原因原则上全额退款并恢复优惠券。已经真实完成的配送、安装等服务按服务规则处理，不自动抹除事实。
- 已领取后不再使用普通取消流程，转为提前归还。取消费由服务端依据快照计算，运营人员不得直接输入无依据最终金额。
- 取消先以追加的冲回费用行抵销原订单应付，再追加按规则快照得到的取消费、不可退已发生成本或退款调整；不得保留原全额租金后再叠加取消费。产生待退款时必须另走资金退款事件，不能仅改订单金额冒充已退款。

#### 4.6.6 天气与不可抗力

- 天气例外按品类和官方预警条件配置，不得把所有天气统一视为免费取消。规则必须定义适用品类、触发来源、确认人、免费改期或退款范围、已发生成本及优惠券和价格保留方式。
- 天气或不可抗力处理保存事件来源、证明材料、审批人、规则原结果和最终处理结果；因经营方停业或无法履约造成的改约不得直接归责客户。

#### 4.6.7 爽约

- 爽约流程为“超过领取时间 → 待确认爽约 → 通知客户 → 到达最终时限或人工确认 → 判定爽约 → 释放资源 → 按规则结算”。
- 爽约规则定义领取宽限、最终确认时间、已支付金额、押金和预授权、履约费、已执行服务、优惠券恢复及客户风险影响。
- 人工提前判定爽约必须具备权限并填写原因。

#### 4.6.8 提前归还

- 第一阶段固定租期订单提前归还默认不自动退租金；未发生且可取消的服务或履约费用可按规则退款。企业合同或特殊规则可以允许人工审核退款。
- 允许租金退款时，必须明确计费单位、长租阶梯是否重新计算、优惠如何重新分摊，并保存调整前后金额；实际资产归还后立即释放，金额可进入待结算。
- 自动退款只可基于客户实际净付部分：商品租金按订单行快照分摊营销优惠、优惠券和会员减免；服务按实际服务状态及其净付额判断。存在多个不同商品费率而无法安全复算时进入人工审核，不得按任意第一条费率估算。

#### 4.6.9 延期

- 延期是订单变更，不得改写原订单结束时间和原报价。必须先检查商品实际占用、已分配资产、地点和后续订单；双方领取前准备与归还后周转缓冲均计入冲突区间，缓冲不计租金。预检与生效事务内均须检查，排除本单，失败不延长占用。
- 经营空间通过版本化租赁规则选择续租计费方式，并将选择固定到新订单。缺省保留“新增时段单独计费”；管理员后续修改选择不能改变已有订单的续租方式。

| 续租方式 | 价格与金额口径 |
| --- | --- |
| 新增时段单独计费 | 原租期金额及优惠不变，新增时段使用申请时适用的价格、日历和规则独立计费，不与原租期合并进位或追溯享受原优惠。 |
| 原价格全租期补差 | 使用原订单价格版本及原优惠规则，从原开始时间重算至新结束时间；最低单位、阶梯与封顶按完整租期计算。应补差额＝重算应付－原订单及历次有效续租已计应付＋已审核核减额；待审或已拒绝退款不作为已核减。 |

- 正差额依结算方式补款后生效或记入月结；零差额无需补款即可生效；负差额可续租但只生成退款待审，不自动退款。批准只核减应收，实际资金退款必须另走资金流程，不能标为已退款。后续有效重算替代旧的未审差额，避免重复退款；存在待审差额时不得直接关单。
- 原优惠方案、优惠券使用已保存规则重算，不重复核销；券预算金额与续租生效或退款核减同事务更新。无法恢复原价格或原优惠规则时拒绝偷偷使用现规则。一次性服务不重复收；显式新增服务单独报价，押金、预授权与租金分开说明。
- 逾时不是自动获得续租授权。新增时段计费保留既有逾期续租及强制先付设置；新增“原价全租期补差”对已逾时或补款前已经逾时的订单暂拒自动处理，要求人工核价，避免全租期优惠重算消除逾时费用。两种模式均不自动处理部分归还后的整单续租，不伪装为已支持部分续租。

##### 时租转日租

- 空间可启用“时租转日租”并设置小时阈值（大于0、不超过24）。按从计价起点开始的连续24小时分段，不按午夜切日；完整24小时按日价，余段严格超过阈值转一天，否则按小时计费。小时金额先达到日价时也按日价封顶；转日价替代该段小时费，不相加。
- 日价来自同一定价分组、同一价格版本的 `day_24h` 费率，缺失时拒绝发布相关规则或报价，不能拿现价补历史快照。保留正常日期类型和分时取价依据，普通报价、续租均使用相同算法。
- 两种续租模式决定计价起点：独立续租从本次新增时段开始，全租期补差从原起租时间开始。支付一天价格不代表自动获得一天占用权，仍须遵守约定归还时间。
- 例如小时价30、日价200、阈值6：5小时150，6小时180，超过6至24小时200，26小时260，31小时400（无其他日期价或优惠时）。

#### 4.6.10 逾期

- 逾期分为宽限期、轻度逾期、严重逾期及失联或疑似丢失。规则定义宽限时间、计费单位、每单位费用或租金倍数、最大费用、通知频率、下单限制、人工催收和丢失升级条件。
- 逾期明细保存应归还时间、实际归还时间、扣除宽限后的时长、单位、费率和封顶结果；金额只能依据订单规则快照生成。
- 保留已有逾时方式并修正：小时折算依据已购买计费单位代表的时长，不按短预约时长分摊；“下一周期”按实际逾时占用周期数计算，不能固定乘整单租金。
- 新增“宽限后小时比例转日费”：只扣除一次宽限，按扣除后的时长分连续24小时；每小时收原价格版本对应日价的指定百分比，不足小时向上取整；余段严格超过独立逾时阈值或小时金额达到日费时收一天，不叠加该段小时费。完整周期按日费收取，最后应用逾时倍率和总额封顶。逾时不重新享受营销优惠，正常时租阈值与逾时阈值互不覆盖。
- 当前约定归还时间使用最近一次已生效续租后的时间；未成功的申请不改变逾时起点。正常租金与逾时费用分别列明，不把日价固定推断为预约租金除以预约小时数。

#### 4.6.11 客户资质

- 品类可定义身份、年龄、驾驶证及准驾车型、操作证、安全培训、企业资质、高价值商品实名或信用要求等资质。
- 浏览商品允许查看；报价时提示缺失资质；订单确认时必须满足或进入允许的审核；领取时再次校验仍有效。要求有效的证件必须覆盖规则规定的租赁时间范围。
- 订单保存证件类型、核验结果、有效期和核验时间快照；敏感信息只保存必要字段和安全附件引用。资质规则通过统一资格入口执行，品类通过 capability 扩展具体规则。

#### 4.6.12 领取归还检查与异常责任

- 规则指定领取和归还检查模板、强制照片、使用量读数、套装清点、客户签字、异常分类及审核要求。领取检查形成交付基线，归还检查与该基线比较。
- 检查不得只保存“正常/异常”，必须保存检查项、前后值、证据、操作人和客户确认。
- 损坏、缺件、清洁和丢失按“发现异常 → 记录证据和等级 → 判断保障范围 → 计算建议费用 → 人工审核 → 客户确认或申诉 → 结算”处理。
- 异常费用可引用标准费用表、维修报价、配件重置价、清洁等级、停运损失、保障自付额和上限；默认需要人工审核，不能仅凭检查人员输入金额直接扣款。
- 客户可查看证据并申诉；费用调整必须保存原金额、调整后金额、原因和审批人。

#### 4.6.13 人工例外

- 企业合同特殊条款、天气改期、客服补偿、提前归还退款、逾期减免、异地归还许可和资质人工审核可以进入例外审批。
- 例外必须有独立权限、类型、原因、依据、原规则结果、调整结果和审批人，并作为订单追加事实保存，不得修改原规则版本或快照。
- 安全、法定资质、库存和数据权限底线不得通过普通例外审批绕过。

#### 4.6.14 规则快照、客户确认与权限

- 报价向客户展示支付和保留时间、押金与预授权、取消、爽约、提前归还、延期、逾期、损坏缺件、资质及领取归还等关键条款；订单创建时保存完整规则快照和客户确认记录。
- 新规则只影响新报价；有效报价和历史订单继续使用原快照。订单变更只为新增或变更部分保存新的适用规则，不覆盖原规则。
- 权限分为规则编辑、规则发布、订单例外、取消退款、资质审核、异常费用审核、保障审核和财务扣退款。
- 发布规则、人工覆盖、免费取消、取消/逾期减免、延期、资质人工通过、异常费用调整、押金抵扣、预授权转扣和客户申诉处理必须填写原因并记录完整审计。

### 4.7 报价与订单

#### 4.7.1 报价与订单边界

- 报价是服务端根据商品、数量、租期、地点、客户、价格、日历、规则、优惠和服务生成的不可变计算快照，不是订单，也不占库存、优惠券、营销预算或服务容量。
- 报价必须有有效期。商品、数量、租期、地点、履约方式、客户、优惠券或服务发生变化时必须重新生成；报价不可原地编辑，过期后不能直接下单。
- 一张报价默认只能成功转换为一张订单。报价阶段的可用性仅表示当时可用，提交订单时必须重新校验并原子锁定资源。

#### 4.7.2 订单范围

- 一个订单只能属于一个 SaaS 租户、一个经营空间、一个租赁客户、一个统一租期、一个领取地点、一个归还地点、一种主要履约方式和一个结算币种。
- 订单支持多商品行、多数量、序列化资产、数量库存、套装、增值服务、履约费用、押金、预授权、优惠和优惠券。
- 不同经营空间、品类、租期或完全不同履约路线必须拆分订单，不建设跨空间组合订单。

#### 4.7.2A 预约身份、企业主体与会员权益

- 每张新报价和订单都必须先选择一个处于可下单状态的个人空间会员。个人是实际使用人、身份与品类资质校验来源，也是后台代客下单和后续 App 自助下单的默认预约、签约与付款主体；不得直接以企业主档替代实际个人。
- 个人会员在当前经营空间存在有效企业员工关系时，可以从其有效企业中选择一个作为本次“企业员工预约”身份。一次报价和订单最多选择一个企业；员工关系停用、失效、跨空间或跨租户时必须拒绝报价和提交。
- 选择企业员工预约身份后，企业方案可作为本次会员权益来源；个人自行付款不妨碍使用已确认适用的企业权益。个人积分、个人营销余额、个人优惠券和个人历史订单仍属于个人，不因选择企业身份转为企业资产。
- 默认签约主体和付款主体保持个人。界面必须提供明确、默认关闭的“企业签约并付款”选择；开启后，所选企业同时成为签约主体和付款主体，使用人始终为该个人会员。企业主体不得由客户端任意传入，必须由服务端依据本次有效员工关系生成。
- 报价和订单快照必须同时保存个人会员、预约身份、企业（如有）、员工关系、签约/付款/使用主体、会员方案及版本、实际命中权益、未命中原因和权益计算结果；历史订单不得因员工关系、企业方案或会员资料后续变化而改变。
- 商品、租期、地点、履约方式、个人会员、预约身份、企业签约付款选择、服务、优惠方案或优惠券任一变化，均使旧报价不可继续提交，必须重新调用服务端报价。订单提交时再次校验个人会员状态、员工关系、资质、优惠券、预算、服务容量和库存，并在同一事务内锁定应锁定的资源。
- 管理端新建订单按“会员与预约身份/租期地点 → 租赁商品 → 增值服务与优惠 → 服务端报价 → 提交成功”组织；订单管理按状态、时间、客户/企业、履约方式和订单号检索，展示个人使用人、签约/付款主体、商品、租期、金额和各状态事实。App 只复用相同的版本化报价与下单契约，不复用后台运营令牌或页面接口。

#### 4.7.3 状态模型

- 订单主状态、支付状态、库存状态、履约状态和结算状态必须分别保存，不得用单一状态同时表达全部事实。

| 状态维度 | 典型状态 |
| --- | --- |
| 订单主状态 | 待审核、待支付、已确认、履约中、待结算、已完成、已取消、已爽约、已关闭 |
| 支付状态 | 未支付、部分支付、已支付、退款中、已退款 |
| 库存状态 | 未预留、已预留、已分配、部分释放、已释放 |
| 履约状态 | 待配货、已配货、待领取/配送、在租、部分归还、已归还 |
| 结算状态 | 未结算、待审核、待补款、待退款、已结清 |

标准主流程为：

`有效报价 → 提交订单 → 待审核（需要时）→ 待支付 → 已确认 → 已预留 → 配货/分配 → 待领取或配送 → 在租 → 部分归还（可重复）→ 全部归还 → 归还检查 → 待结算 → 已完成`

#### 4.7.4 提交订单与资源锁定

- 提交订单必须在同一事务中校验报价有效且未使用、重新校验可执行性和客户资格、创建订单、预留库存、锁定优惠券、预占营销预算、预留有容量服务、标记报价已转换并写订单事件和审计。
- 任一步失败整体回滚，不得产生孤立订单、库存占用、锁定优惠券、预算预占或服务资源。
- 重复提交同一报价或同一幂等请求只能返回同一订单，不得创建重复订单。

#### 4.7.5 审核、支付与超时

- 高价值商品、企业授信、资质人工审核、特殊价格、人工优惠、规则例外、异地归还和高风险服务可触发待审核；审核拒绝后取消并释放全部资源。
- 待支付订单超过规则保留时间自动取消并释放库存、服务容量、优惠券和预算。企业月结或授信订单可在未完成现金支付时确认，但必须保存有效授信依据。

#### 4.7.6 预留与分配

- 预留表示在目标时间范围为订单锁定商品需求，分配表示确定实际交付资产、地点数量或套装组成，两者不得混用。
- 序列化资产在配货阶段分配具体资产；数量库存按地点预留和分配数量；套装在配货时保存实际组成和允许的替代结果。
- 替换套装组件必须重新校验库存并保存替代依据。可用性需计入检查、清洁、维修、运输等周转缓冲，不得只比较客户租期。

##### 4.7.6.1 预分配、锁定和改配（2026-09-04 确认）

- 库存预留、实际资源预分配、锁定分配、办理操作锁分别管理；前三者是同一库存承诺逐步明确，不得重复扣库存。资产分配按租期与双方准备/周转缓冲判断，不得把未来排期当作即时物理占用。
- 达到订单预约确认条件后可分配；到店付款、企业月结等按原支付规则确认，不要求一律先现金全款。软预留仍按原超时规则释放。
- 序列化资产指定单件；数量库存指定型号、地点和数量；套装按实际组成展开。允许部分预分配和部分锁定，全部必要资源锁定且领取检查通过后才允许整单交付。
- 人工可以选择实际资源、保存预分配、锁定选中明细或全部已分配明细。空间可配置自动预分配开关及提前天数、自动锁定开关及领取前分钟数、人工结果保护；缺省关闭自动任务、人工保护开启。参考初值为提前7天预分配、提前120分钟锁定，管理员可修改。
- 候选只能来自当前空间、订单允诺的型号范围和可交付地点；共用型号的定价组必须共用实际库存。资产停用、维修、检查、前单实际逾期或缓冲冲突须阻断；前单仍在租但未来按时归还且周转、地点均满足时可作未来候选。锁定不代表已具备即时交付条件，领取时重新复核。
- 预分配和锁定不改变原租金。跨分组升降级、跨地点调拨及交付后换货必须走单独订单变更流程，不允许自动替客户变更商品承诺或价格。
- 同一定价组内人工改配使用下单时的型号成员快照，不随当前分组成员变化追溯扩大；保持库存方式一致，套装组件仍遵循组件替代规则。每条预留本期选择一种实际型号，可部分指定该型号的资产或数量，但整条未释放需求的库存预留须同步转移；不得只换资产而保留原型号占用。原订单行、价格和优惠快照不变。
- 已锁定资源禁止自动换货；解锁、释放和改配须独立操作权限及原因。改配新占用与旧释放须同一事务，失败整体回滚。并发操作校验版本和资源，不允许凭覆盖权限强行重复占用。
- 自动分配失败保留订单及原有效资源并标记待人工处理，不自动取消。部分资源临时失效时，阻止交付并提示处理；不能因人工保护继续交付不合格资源。
- 无论是否开启自动分配，系统按分钟检查已确认与待交付订单的有效分配：地点/型号停用、资产失效、前后单含缓冲冲突及数量不足须进入分配异常筛选；相同异常不重复追加记录，恢复时记录解除。异常本身不解除锁定、不自动换货，实际领取仍做实时复核。
- 办理操作锁记录办理人、过期时间和不可复用凭证。接手后旧页面不能继续提交；退出页面、锁过期不释放实际资源。解锁操作锁不等于解锁商品。
- 实物归还及整备状态独立于资金结算；未结尾款或退款不应单独阻塞合格资产的后续排期。续租与后单冲突必须在续租生效前解决，不能保留冲突续租。
- 列表展示预订商品与实际资源、分配进度、资金/订单状态及异常筛选，提供分配、领取、归还入口。详情顶部显示下一步操作，资源区支持选择/锁定/解锁/改配，展示品类术语和型号照片，记录前后资源、原因、操作者、时间。查看和操作权限按当前空间执行；不可执行动作明确说明原因。
- 首期不含AI调度、全局自动优化、自动跨地点调拨、自动升降级及分批交付；车辆调度、器材兼容等扩展不得另建一套订单分配状态机。

#### 4.7.7 配货与领取

- 配货重新校验资产和数量、套装完整性、地点能力、维修/停运/占用状态、强制服务和检查模板。
- 领取前完成必要付款、押金或预授权、身份和资质复核、领取检查、实际资产及套装组成确认、客户签字和条款确认。
- 第一阶段默认整单完成配货后一次领取，不支持一张订单多批领取。部分商品无法交付时必须在领取前拆分订单或取消未交付行，后续多批交付以独立履约批次能力扩展。

#### 4.7.8 部分取消与订单变更

- 领取前取消部分订单行必须作为订单变更，重新计算剩余商品资格和优惠、重新分摊订单级优惠、计算退款或补款、释放对应库存和服务、调整押金与预授权，并保存前后快照及客户确认。
- 增减商品或数量、修改租期/地点/履约方式、增减服务、更换优惠券、延期和部分取消都必须走“变更申请 → 变化部分重新报价 → 资源与资格校验 → 计算差额 → 客户确认 → 原子应用 → 追加变更版本”。
- 原订单和原订单行不得被删除或覆盖；订单详情必须展示每次变更、前后差异、补退款、操作者和客户确认。
- 领取后不能取消已交付商品，只能办理提前归还。

#### 4.7.9 领取后换货

- 领取后因资产故障或其他原因换货必须保存原资产、替换资产、原因、检查结果、时间、地点、使用量、费用和客户确认；不得直接修改原资产编号。
- 原资产进入检查、维修或停运，替换资产重新建立占用。替换商品规格或价格变化时生成订单调整，不得静默改变订单内容。

#### 4.7.10 部分归还

- 一张订单允许多次部分归还。每批次保存实际资产、数量、套装组件、归还时间和地点、使用量、初步检查、未归还部分、操作人和客户确认。
- 部分归还必须随该批归还检查提交；检查正常的本批资产或数量才可释放为可用，存在异常的本批进入检查/养护处理，剩余商品继续在租，订单不得标记全部归还。
- 最后一批归还后统一进入归还检查和结算。

#### 4.7.11 归还检查与库存恢复

- “已交回、已检查、可出租”是不同事实。归还不能直接使资产或数量库存变成可出租。
- 检查结果至少包括正常可用、待清洁、待维修、缺件、报损、丢失和人工复核；数量库存分别记录已交回数量和重新可用数量。

#### 4.7.12 结算

结算金额按以下口径汇总：

`原订单租赁应付 + 订单变更新增费用 + 逾期/超额使用/异常费用 - 订单变更减免费用 - 已退款金额 - 押金抵扣 - 已支付金额 = 待补款或待退款`

- 结算前必须确认所有商品已归还、报损或进入明确丢失处理，检查和使用量完成，服务状态处理，优惠分摊固定，押金和预授权方案确认，客户申诉和人工审核已完成或进入独立未决流程。
- 只有资源、服务、资金和异常均闭环后，订单才能完成。
- 服务容量在订单确认时转为已确认占用；归还时，已开始服务保留已使用履约事实，尚未开始服务释放容量并按已确认的服务净额与退款规则处理。不能把未来服务直接标成已完成，也不能按服务原价超过客户实付额退款。

#### 4.7.13 终态

- 已完成：履约和服务结束、库存状态明确、费用结清、押金已退或抵扣、预授权已释放或转扣且无未处理异常。
- 已取消：领取前终止订单，并按取消规则结算和释放资源。
- 已爽约：客户未领取且完成爽约确认后的终态。
- 已关闭：仅用于无法继续履约、坏账、司法/保险处理或特殊数据纠错，必须有高权限、原因以及资金和资源处理结果；不得代替正常完成或绕过结算。

#### 4.7.14 编号、来源与代客下单

- 订单号在经营空间内唯一且创建后不可修改。订单保存客户端自助、后台代客、API 渠道、企业合同等来源。
- 后台代客下单仍必须经过服务端报价、客户资格、价格、库存和规则校验，运营人员不得直接提交最终金额。

#### 4.7.15 客户视图、运营视图与权限审计

- 客户侧展示可理解状态、待办、金额、商品服务、领取归还、条款、变更和退款；不得暴露成本价、内部风控说明和内部备注。
- 运营侧展示各状态维度、库存预留与分配、支付/押金/预授权、服务容量、检查异常、订单事件时间线和审计记录。
- 代客下单、订单审核、确认收款、配货、换货、领取、归还、订单变更、取消爽约、异常审核、结算和强制关闭分别授权。
- 所有关键动作必须幂等、校验当前状态、保存操作者、时间、原因和前后差异，不得跳过必要中间状态直接修改终态。

### 4.8 会员、注册与邀请奖励

会员体系必须区分“客户是谁”“客户如何登录”和“客户在某个经营空间拥有什么资格与权益”。客户主档和客户账号在 SaaS 租户内共享；会员关系、等级、积分、营销余额、优惠券及邀请奖励默认按经营空间隔离。

- 正式系统只允许使用 `CustomerProfile + CustomerAccount + CustomerWorkspaceLink` 所代表的新客户与会员体系。旧门市租赁的 `Member`、`MembershipPlan`、`/store-rental/members*` 及对应管理页面不得继续承载新业务。
- 旧体系退出按“停止入口和写入 → 解除代码及历史外键引用 → 数据库迁移删除旧会员表”执行；旧门市会员数据不迁入新体系，也不为其建设兼容 facade 或双写。

#### 4.8.1 客户主档、客户账号与空间会员关系

- 客户主档表示真实个人或企业，保存身份、联系方式、企业资料、实名认证和品类资质等租户级资料；同一 SaaS 租户内复用，禁止跨租户共享。
- 客户账号表示客户用于小程序、App 或其他客户端登录的认证身份，在 SaaS 租户内共享。停用客户账号会阻止其登录全部经营空间，但不删除客户主档和历史业务事实。
- 空间会员关系表示客户在指定经营空间的会员身份、状态、等级和权益。一个客户可以加入同租户多个经营空间，各空间会员状态和权益互不影响。
- 订单、会员等级、积分、营销余额、优惠券、邀请关系和奖励流水必须同时归属 SaaS 租户与经营空间，默认不得跨空间读取、使用、转移或合并。
- 个人会员与企业会员使用同一客户身份框架，但必须分别提供独立列表和详情入口；企业员工和企业管理员不另建登录身份，必须引用已经存在的个人会员及其共享客户账号。

#### 4.8.2 注册、登录与协议留痕

- 客户注册必须明确目标经营空间，完成手机号或其他已启用方式的身份校验后，先在当前 SaaS 租户内查找可复用客户主档；存在时建立新的空间会员关系，不存在时创建客户主档、客户账号和空间会员关系。
- 个人会员支持两种创建渠道：后续 APP 通过独立版本客户端 API 注册，以及具备权限的后台管理员新增。当前阶段必须先固化 APP 注册、验证码、协议和幂等契约，不要求交付 APP 页面。
- 每个经营空间独立配置注册审核模式。`manual` 模式下新空间会员进入“待激活”并生成注册审核任务；`automatic` 模式下注册资料校验通过后直接成为“正常”。后台新增默认遵守同一模式，具备会员审核权限的管理员可以选择“直接通过”，但必须保存操作人和原因。
- 注册审核与实名认证、驾驶证或从业资格证等证件审核是不同事实。自动注册通过只激活空间会员，不得自动把任何证件判为已通过。
- 注册记录必须保存注册渠道、目标经营空间、邀请信息、用户协议和隐私政策版本、同意时间、认证方式及注册结果。
- 客户账号状态与空间会员状态分别管理。单个空间暂停或终止会员关系不得影响客户登录和访问其在其他空间的合法业务。
- 注册、登录和找回账号不得通过错误提示暴露某手机号、证件或企业是否属于其他客户；认证凭据和敏感身份字段必须加密或脱敏保护。
- 账号密码只保存强哈希和必要的安全元数据。后台不得查看或回显原密码，只能创建一次性临时密码、发送激活凭证或发起密码重置；临时密码首次使用后必须修改。

#### 4.8.3 重复客户识别与合并

- 同一 SaaS 租户内优先以已验证手机号识别重复个人客户，并可结合实名认证证件作进一步核验；企业客户结合统一社会信用代码和已验证联系人识别。
- 发现重复客户时不得自动跨主档搬移订单或权益。具备权限的人员可发起人工合并，明确保留主档、字段取舍、资质处理和冲突项。
- 合并后订单、支付、合同和历史事件继续保留原始业务引用；各经营空间的等级、积分、营销余额、优惠券和奖励分别保留，不得因合并转成跨空间权益。
- 合并必须保存原主档到保留主档的映射、操作人、审批人、原因、字段差异和时间；禁止跨 SaaS 租户合并客户。

#### 4.8.4 个人客户、企业客户与经办人

- 个人和企业使用统一客户框架，但资料结构分开。个人客户至少包含身份、联系方式、紧急联系人、资质和风险信息；企业客户至少包含企业名称、统一社会信用代码、联系人、开票资料、合同、授信、账期、企业资质和授权经办人。
- 企业联系人可以同时是个人客户，但订单必须明确签约主体、付款主体、使用人或经办人，不能只保存一个联系人代替企业责任主体。
- 企业会员必须具有独立企业列表和企业详情。企业详情管理企业基本资料、当前空间会员状态、企业方案、企业管理员、员工、合同、开票、授信和操作历史。
- 企业管理员必须先是个人会员，再以企业员工关系获得企业管理员角色；一家企业允许配置多个管理员。新增员工只能从当前租户已有个人会员中选择，不得在企业员工表内另存一份姓名、手机号和密码作为替代账号。
- 企业员工关系至少保存企业、个人会员、经营空间适用范围、部门、员工编号、角色、状态、生效时间、失效时间、操作人与原因。员工离职或关系停用后，不再获得新的企业优惠资格，但历史订单继续使用下单时快照。
- 同一人在一个经营空间可以加入多个企业；每张报价和订单只能明确选择一个企业作为本次签约、优惠和结算来源，禁止把多个企业方案叠加。
- 个人会员加入企业后获得该企业在目标空间的优惠资格，但其个人账号、个人等级、积分、营销余额、优惠券及个人历史订单不转为企业资产。
- 第一阶段邀请奖励只面向个人空间会员；企业客户及企业经办人的邀请奖励在另行确认规则前不得默认启用。

#### 4.8.5 实名认证与品类资质

- 实名认证结果可在同一 SaaS 租户内共享；目标经营空间仍须按自己的品类、商品和风险规则判断该认证或资质是否适用。
- 品类资质状态至少包括“未提交、待审核、已通过、已拒绝、已过期、已撤销”，并保存证件类型、有效期、审核结果和证据；车辆驾驶资质、工程设备操作资质等不得因在一个空间通过就自动绕过另一个空间的适用性校验。
- 证件类型由通用证件注册表和品类/capability 扩展共同提供。身份证件、手机号和 Email 属于通用资料；驾驶证、道路运输或从业资格证、工程设备操作证等由目标空间品类声明，不得在会员主流程中写死车辆字段。
- 每份证件至少保存证件类型、证件号码或脱敏值、签发机构、有效期、附件引用、提交来源、审核状态、审核人、审核时间、审核意见和适用范围。证件到期、撤销或被替换必须保留历史版本。
- 证件号码、证件影像和生物识别等敏感资料必须限制访问、脱敏展示并保留访问审计。

#### 4.8.6 空间会员状态

| 状态 | 业务含义 |
| --- | --- |
| 待激活 | 已建立空间会员关系，但尚未完成必要认证或激活动作 |
| 正常 | 可按空间规则下单、累积和使用权益 |
| 已暂停 | 暂停下单和使用权益，保留订单、权益和历史记录 |
| 风险受限 | 按具体风险规则限制下单、支付方式、免押或奖励，等待复核 |
| 已退出 | 客户主动退出该经营空间，不再产生新业务 |
| 已注销 | 空间会员关系完成注销，不再激活新业务，依法保留必要历史事实 |

- 空间会员状态变化只影响该经营空间，不自动停用租户级客户账号或其他空间会员关系。
- 暂停、风险限制、退出和注销必须记录原因、操作人、时间和生效范围；解除限制也必须形成独立记录，不得删除原限制事实。

#### 4.8.7 会员等级与权益

- 会员方案是独立管理模块，按经营空间维护，并通过目标类型区分个人方案和企业方案；不复用旧门市 `MembershipPlan`。方案至少包含编码、名称、目标类型、等级顺序、适用条件、权益、默认方案、推荐状态、APP 可见性、状态、生效区间和不可变版本。
- 第一阶段只实现免费方案、系统计算、后台人工授予和企业合同授予，不实现客户付费购买会员。付费会员必须等待真实支付、退款、续费和到期结算规则另行确认后才能启用。
- 会员等级按经营空间独立配置和计算，可基于已完成且未全额退款的订单数、实付租金、滚动周期消费、成长值、企业合同或授权人工授予。
- 等级规则必须定义升级、保级、降级、有效期、人工调整权限、适用权益和版本。人工授予或调整必须填写原因和有效期。
- 权益可包含租金折扣、优惠券、押金减免、预授权降低、服务权益、报价有效期延长、优先预订、专属客服以及取消或逾期宽限。
- 每类权益必须保存结构化类型、适用费用或服务、计算方式、上限、叠加规则和生效条件，不能只保存一段“权益说明”。企业员工使用企业方案时，报价和订单必须保存企业、员工关系、方案版本及实际命中权益快照。
- 优先预订不得造成库存超卖；任何会员权益不得绕过法律法规、平台安全底线、品类资质、资产停运和实际库存限制。
- 权益与优惠方案、优惠券、积分和营销余额是否叠加必须明确配置。报价和订单保存会员等级、命中权益、规则版本、计算结果及客户可理解的说明快照。
- R1 已定义的金额权益按“营销方案 → 优惠券 → 会员权益”顺序在剩余可优惠基数上计算；个人预约只使用个人方案，企业员工预约只使用所选企业方案，不叠加两套方案。每个同类金额权益取本次实际减免最大的一个并保存未命中原因、分摊和费用行。
- 报价有效期延长、优先预订、专属客服、取消或逾期宽限等非金额权益，必须先定义明确的单位、排序、适用阶段和库存/规则边界再启用。未接入对应执行点时只允许显示“未生效原因”，不得声称已享受权益。

#### 4.8.8 积分账户与流水

- 积分是经营空间发放的营销权益，不是货币或储值资金。默认不可充值、提现、转让、跨空间使用、支付押金或预授权，不计利息且不承诺固定现金兑换价值。
- 积分可来源于订单完成、注册、实名认证、首单、邀请活动、营销活动和客诉补偿。订单消费积分原则上在订单完成且满足退款冷静期后入账，不在支付时提前成为可用积分。
- 每笔积分必须写入不可变流水，状态至少包括“待确认、可用、已锁定、已使用、已过期、已撤销”。系统和运营人员不得直接修改余额，只能追加发放、锁定、使用、释放、过期、撤销或补偿流水。
- 积分按发放批次设置有效期，使用时优先消耗最早到期批次。报价只试算，订单确认时锁定，支付或订单达到规则规定的生效点后使用；失败或取消时释放，退款时按已发布规则返还或撤销。
- 已过期积分默认不恢复；确需补偿时必须以新的补偿流水发放，不得修改原过期记录。

#### 4.8.9 营销余额与抵扣顺序

- 营销余额是经营空间赠送的营销抵扣额度，不是客户储值账户。可用于活动赠送、服务补偿、邀请奖励和符合规则的订单抵扣。
- 第一阶段不允许客户充值、提现、转账、兑换现金、跨租户或跨经营空间使用，也不得抵扣押金和预授权。未来如建设真实预付钱包，必须作为独立资金账户和合规系统设计，不能复用营销余额。
- 营销余额的发放、锁定、使用、释放、过期和撤销全部通过不可变流水处理，禁止直接修改余额。
- 默认权益抵扣顺序为“自动优惠方案 → 优惠券 → 积分 → 营销余额 → 现金支付”。规则可配置各权益适用费用范围、单笔上限、最小使用单位、日/月限额和叠加关系，但不得改变已生效报价和订单快照。
- 报价必须展示每项权益的命中依据、抵扣金额、未使用原因和剩余现金应付，不得只展示最终总额。

#### 4.8.10 邀请关系与活动配置

- 邀请关系在被邀请人首次注册目标经营空间时绑定一次，保存邀请人、被邀请人、SaaS 租户、经营空间、邀请码或链接、渠道、绑定时间和状态。
- 邀请人必须是目标经营空间的正常会员。禁止自邀、重复绑定、循环邀请、注册后补绑或改绑、跨租户邀请，以及把已存在的目标空间会员重新认定为新受邀人。
- 邀请活动必须配置活动名称、经营空间、起止时间、参与资格、触发条件、邀请双方奖励、每人上限、每日和总量上限、活动预算、防刷规则、状态及版本。
- 活动状态为“草稿、待开始、进行中、已暂停、已结束、已作废”。暂停后不再接受新的资格达成；暂停前已满足触发条件的奖励默认按当时活动快照继续处理，明确作废并撤销时除外。

#### 4.8.11 奖励触发与生命周期

- 奖励触发点可配置为完成注册、通过实名认证、首次支付、首个有效订单完成或达到指定业务门槛；邀请人与被邀请人的奖励类型、金额、触发点和生效条件分别配置。
- 主要价值奖励原则上在首个有效订单完成并经过退款冷静期后生效，避免仅注册或支付即获得可套取权益。若经营空间选择更早触发，必须同时配置更严格的预算和防刷规则。
- 奖励正常生命周期为“待确认 → 待生效 → 可用 → 已使用”，异常状态包括“已过期、已撤销、已冻结、风险审核中”。
- 订单取消、退款或命中风险发生在冷静期内时取消待生效奖励；奖励已生效后再发生撤销条件，必须追加反向流水，不得删除原奖励。
- 未使用奖励可全额撤销；部分使用时撤销剩余部分并建立待追偿权益；已全部使用时建立追偿或风险记录，不得自动从客户银行卡扣款。人工豁免追偿必须具备权限、填写原因并留痕。

#### 4.8.12 防刷、幂等与预算并发

- 防刷规则至少识别重复客户、手机号或证件，自邀和循环邀请，重复业务事件，短时间集中邀请，设备、支付工具或联系方式异常集中，以及获得奖励后快速退款等风险。
- 设备、网络和支付工具等信息只能作为风险信号，不得单独作为永久封禁依据；高风险记录进入人工审核，并保留判断依据和处理结果。
- 奖励幂等键至少由“活动 + 客户 + 触发类型 + 业务对象”组成，同一事件重复通知只能发放一次。
- 奖励发放必须在同一事务内校验活动状态与版本、参与资格、个人上限、每日和总量上限、剩余预算及是否已发放；并发请求不得导致重复奖励或预算超发。

#### 4.8.13 退出、注销与隐私处理

- 客户退出经营空间、注销空间会员关系和注销整个租户客户账号是不同动作，必须分别确认影响范围。
- 注销前必须处理未完成订单、退款、押金、预授权、欠款、追偿和争议。注销后停止登录或新增业务，但订单、支付、发票、合同、权益流水和审计等法定或业务必要记录按保留期限保存。
- 未使用积分、营销余额、优惠券和待生效奖励按已发布规则失效或结清，不得兑换现金；非必要个人信息在保留期届满后删除或匿名化。
- 注销和匿名化不得破坏财务、订单、风控和审计记录的可解释性，也不得借注销规避欠款、追偿或风险限制。

#### 4.8.14 权限与审计

- 会员规则编辑与发布、等级人工调整、积分调整、营销余额调整、邀请活动编辑与发布、奖励补发与撤销、风险审核、客户合并和注销分别授权。
- 所有余额调整均通过业务流水，不提供直接改余额能力。关键流水至少保存变动类型、变动前后可用余额、原因、客户、SaaS 租户、经营空间、关联活动或订单、操作者、审批人和时间。
- 客户合并、敏感资料访问、风险限制、人工等级与权益调整、奖励补发或撤销、追偿豁免和注销必须进入审计日志，并支持按客户和经营空间还原完整时间线。

#### 4.8.15 管理端页面与操作边界

| 页面 | 页面职责 | 主要操作 |
| --- | --- | --- |
| 会员审核 | 当前空间的注册审核和证件审核中心；注册与证件使用独立任务类型和筛选 | 查看提交资料、通过、驳回、补件、批量处理允许的低风险任务、查看审核历史 |
| 个人会员 | 当前租户个人主档与当前空间会员关系；列表和详情分离 | 后台新增、开通/停用账号、重置密码、调整空间状态和方案、维护通用资料与品类证件、查看企业任职和历史 |
| 企业会员 | 企业主档与当前空间企业会员关系；列表和详情分离 | 新增企业、维护资料和状态、指定个人会员为管理员、添加/停用员工、选择企业方案、管理合同/开票/授信 |
| 会员方案 | 当前空间个人/企业方案及不可变版本 | 新建草稿、编辑、预览影响、发布、停用、恢复历史版本、查看引用会员数；被引用方案不得物理删除 |

- 页面结构可以参考 `RIMORental/02_原型和PRD/原型/营运端` 中的 `member_review.html`、`members.html`、`member_detail.html`、`corporates.html`、`corporate_detail.html` 和 `membership_plans.html`，但字段、状态、权限和业务判断以本需求为准。
- 会员查看、会员编辑、注册审核、证件审核、账号状态、密码重置、企业管理、企业员工管理、方案编辑、方案发布、权益人工调整、合并和注销分别授权；只有查看权限时不得发送写请求。

### 4.9 通知模板

- 经营空间可按订单确认、待支付、领取提醒、逾期、归还、取消、退款、审核、奖励和资产异常等事件配置通知。
- 模板必须定义渠道、变量 schema、版本、启停状态和适用事件。
- 发送记录保存模板版本、脱敏目标、状态、失败原因和业务对象。
- 真实短信、邮件、微信和 App Push 通过 provider adapter 接入，必须支持幂等、重试和回执。
- 未接入真实 Provider 时，模拟适配器只能产生 `simulated`、`simulation_failed` 等明确状态；不得写入 `sent`、`delivered` 或生成伪造的外部消息号。模拟记录不计入真实送达率。

### 4.10 报表、审计与平台治理

- 经营空间报表至少覆盖订单、收入、库存/资产利用率、地点经营、客户、优惠和异常。
- 当前阶段报表和导出只能查询当前经营空间，必须使用会话中的租户、经营空间和数据范围，不能接受客户端覆盖。
- 跨经营空间汇总报表暂不开发；数据模型需保留未来按租户汇总的可能性，但不得提前开放绕过空间权限的查询。
- 平台审计与租户业务审计分开；关键配置发布、订单动作、费用变化和权限变化必须可追溯。
- 导出、附件、打印、异步任务和外部 adapter 不单独扩成泛化后台，只围绕已确认业务场景提供能力。
- 在资产和数量库存尚无完整状态历史时，利用率只能按当前快照展示，并同时给出统计时点、分子和分母；不得用当前状态乘以查询区间伪造历史利用率。区间利用率必须等状态历史或占用时长事实可复算后再启用。

### 4.11 小程序与 App API

- 客户端 API 必须与后台运营 API 分开版本、认证和权限。
- 客户端必须明确目标经营空间；服务端按目标空间状态、品类和客户关系校验，不能把后台当前空间会话直接复用为客户授权。
- 必须支持客户注册登录、商品查询、可用性、报价、下单、订单查询、优惠券、通知和履约信息。
- 发布前必须补齐客户身份认证、签名、限流、幂等、回调验签和字段级 OpenAPI 契约。
- 当前后台运营 token API 不得直接暴露给小程序或 App。

## 5. 非功能要求

- **租户与空间隔离**：经营业务事实同时包含 `tenantId` 和 `workspaceId`，数据库查询默认 fail-closed；租户共享客户主档只按 `tenantId` 共享。
- **一致性**：订单、库存、优惠券和价格事实的关键写入使用数据库事务。
- **并发**：库存预占和优惠券锁定必须防止超卖与重复核销。
- **幂等**：支付、回调、订单状态动作、奖励和通知均需业务幂等键。
- **可追溯**：金额、规则、日历、服务和优惠保存版本快照。
- **安全**：密码只保存强哈希；仓库和文档不得保存真实或测试明文凭据。
- **历史参考**：`/store-rental/*` 不属于新平台产品接口；不得作为新页面、数据迁移、兼容 facade 或验收依据。新业务统一进入 `/rental/v1/*`。
- **可恢复**：数据库迁移必须同时验证空库部署和已有库升级，不允许静默丢数据。

## 6. 核心验收

### 6.1 R1 当前发布门禁

| 场景 | R1 验收结果 |
| --- | --- |
| 经营初始化 | 新建非 demo 空间不自动生成演示地址、电话、商品、资产或库存；缺少必填经营配置时保持待配置状态 |
| 摄影经营条件 | 摄影兼容、附件清点、使用量、领取归还检查和养护均有真实实现；缺少任一必选能力时不能切为正式经营 |
| 订单闭环 | 一张多行摄影订单可完成报价、确认、预留、分配、领取、归还、检查、异常、结算和关闭，非法动作被拒绝 |
| 资源闭环 | 序列化资产、数量配件和套装实际组成分别锁定、交接、归还，并在检查或养护完成后才恢复可用 |
| 金额闭环 | 租金、优惠、服务、押金、预授权和异常费用独立且可复算；模拟资金事件不冒充真实支付或冻结 |
| 数据可靠性 | 订单、资源、检查、费用、工单和审计全部落库，失败事务不留半成品，服务重启后结果一致 |
| 权限与隔离 | 当前租户与空间来自服务端会话；跨租户、跨空间、无权限和停用空间均被拒绝 |
| 运营可用性 | 管理端能够完成全部 R1 操作并查看明确错误、待办、审计和当前空间报表，不依赖直接改库 |

### 6.2 完整平台分阶段验收

下表是完整平台目标验收清单，不全部作为 R1 发布阻断项。物流、自助、IoT、签章、外部保险、其他品类正式经营及客户端页面，只有在对应任务从 `Reserved` 或 `Pending` 被明确激活后，才进入相应阶段的发布门禁。

| 场景 | 验收结果 |
| --- | --- |
| 租户隔离 | 两个 SaaS 租户不能通过列表、详情、导出、动作或并发请求访问对方数据；缺少租户身份直接拒绝 |
| 经营空间切换 | 同一账号可切换被授权空间；未授权或停用空间被拒绝；切换后菜单、品类、权限和缓存立即更新 |
| 空间隔离 | 同一租户的两个经营空间不能读取或修改对方的商品、资产、库存、地点、定价、订单、权益和报表数据 |
| 客户共享 | 同一客户在同租户不同空间复用唯一客户主档；订单和权益仍归属各自经营空间 |
| 品类一致性 | 摄影、露营、车辆和工程经营空间分别获得正确字段、库存、地点、定价、检查和菜单能力 |
| Capability 边界 | 四个品类共用 Rental Core 的客户引用、商品、库存、报价、订单、资金和履约事实；扩展模块只能追加品类校验、任务、读数和费用依据，不能建立平行订单或绕过核心状态权限 |
| 共享能力隔离 | 同一共享 capability 可被不同品类空间复用，但配置、设备、任务、人员、工单和记录仍按租户与经营空间隔离；未启用能力的菜单和 API 不可用 |
| 物流与自助履约 | 物流和自助任务关联原订单并保留完整交接证据；第三方送达或开锁指令不能单独把订单推进为已领取或已归还，失败时存在人工兜底 |
| 人员与资格合规 | 服务人员按排班、容量、资质和适用范围分配；客户、人员、企业和资产资格按统一状态管理并由目标品类规则判断适用性，失效资格阻止关键履约 |
| IoT 数据可信度 | 遥测区分采集和接收时间、在线状态、数据质量及指令状态；过期数据不冒充实时，重复回调幂等，外部数据与人工证据冲突时保留双方并进入复核 |
| 养护维修工单 | 检查、周期、使用量或告警可触发工单；必要工单完成并验收前资产不恢复可用，完成后按真实结果恢复、停运、报损或淘汰 |
| 签章与外部保险 | 未收到真实签署或承保回执不得显示成功；合同和保单版本不可变，补签、退保和理赔追加记录，商户损坏免赔不冒充第三方保险 |
| 摄影扩展 | 不兼容器材在报价或配货时被提示或阻止；套装按实际组件清点和归还；快门或适用使用量、检查及养护状态可追溯且正确影响可用性 |
| 露营扩展 | 同一空间支持数量、序列化和套装混合库存；归还后按清洁周转恢复可用；缺件、损耗和一次性耗材被正确区分 |
| 车辆扩展 | 驾驶资格在关键阶段复核；车型组预订可分配和替换具体车辆；里程、油电、取还车检查及异地还车形成完整履约和费用依据，未接 TBox 不影响基础流程 |
| 工程设备扩展 | 操作资质、工时读数、运输交付、安全检查和维保状态均可校验；不合规或停运设备不能分配交付，故障停机和设备替换保留完整事实 |
| Capability 启停 | 必选能力缺失时空间不能伪装为可经营；可选能力启停和升级校验依赖及在途订单，且不改变有效报价、历史订单和原始集成数据 |
| 服务端报价 | 相同输入可复算；订单可追溯价格、规则、日历、优惠和服务来源 |
| 基础价格矩阵 | 当前经营空间全部启用商品均展示当前价格或明确的“未定价”状态；同商品可配置多个单位及唯一默认单位，明确指定但未配置的单位不能被静默替换 |
| 调价与版本 | 立即和定时调价均生成新的完整不可变版本；可还原调整前后差异、原因和操作人；重叠价格在计划确认时被阻止，已生效版本不能修改或删除 |
| 生效与锁价 | 未来租期按租期开始时间命中价格；报价有效期内发布新价格不改变既有报价；报价过期或关键输入变化后重新报价 |
| 计价正确性 | 小时、24 小时、自然日、夜、周、30 日月和使用量按各自规则计算；阶梯、日期价格和单件封顶顺序固定，逐日或逐计费块明细可复算且明细之和等于总额 |
| 费用边界 | 标准履约、异地归还、可选增值服务和事后异常费用不重复收费；异常费用关联真实事件、证据、规则和审核记录，不覆盖原报价 |
| 押金与预授权 | 押金与预授权分别计算和展示，可同时存在；押金进入本次实收但不进入租赁应付，预授权只冻结额度；减免、抵扣、转扣和释放均可追溯 |
| 价格快照 | 修改或停用价格、商品、地点、日历、服务和规则后，历史报价与订单仍可仅凭自身快照解释并复算当时结果 |
| 日历来源与覆盖 | 官方日历更新不会自动影响经营空间；人工日期覆盖优先于官方日历和每周模板，移除覆盖后恢复下一优先级来源且完整保留操作记录 |
| 停业与履约 | 停业日阻止当天不允许的领取、配送和现场归还，但不阻止租期跨过该日；已在租订单始终存在可执行的归还处理路径 |
| 跨日跨年日历 | 跨日期和跨年度报价按营业时区逐日或逐计费块命中正确日历与价格，并保存所有涉及年度的版本、日期类型、来源和实际价格 |
| 日历版本权限 | 已发布年度日历不可原地修改；新版本不改变有效报价和订单；无发布权限人员不能使草稿生效，平台管理员不能代替经营空间发布 |
| 优惠资格与叠加 | 优惠按明确对象和优惠前基数判断；互斥组只命中一个最优优惠，允许叠加的优惠按固定顺序计算并说明已应用和未应用原因 |
| 优惠券生命周期 | 报价不占券；订单确认事务化锁券和预算；支付生效后核销，失败、超时或支付前取消正确释放，同一券不能被并发订单重复使用 |
| 优惠预算与隔离 | 发行量、客户限额、已锁定和已核销预算均不超限；优惠方案、优惠券和预算不能跨经营空间读取、使用或回放 |
| 优惠取消退款 | 经营方取消按规则恢复或补偿优惠券；部分取消按订单行优惠分摊和实际支付上限退款，优惠券不兑换现金 |
| 优惠历史快照 | 模板修改、暂停、结束或新版本发布不改变已发券权益和历史订单；报价和订单可解释资格、基数、互斥、分摊及最终减免来源 |
| 服务对象边界 | 可归还实物进入商品和库存，标准履约进入履约费，可选劳动或保障进入服务，真实异常进入异常费用；同一事项不重复收费 |
| 服务容量与强制规则 | 有容量服务在订单确认时预留并在失败取消时释放；强制服务说明触发规则且不能被客户端绕过，人工加费服务必须经客户重新确认 |
| 保障与条款 | 损坏免赔与第三方保险边界清楚；未接真实保险商不显示已投保；高风险服务保存不可变条款、保障范围和客户确认快照 |
| 服务变更与履约 | 已执行服务事实不可删除，风险发生后不能补买保障追溯覆盖；人员或现场服务具备资源、状态、凭证、失败替换和退款闭环 |
| 品类服务扩展 | 四个品类通过统一服务、容量、条款和结算模型表达独特服务；新增服务不改变既有品类订单和历史服务结果 |
| 规则版本与时限 | 未来租期命中正确规则版本；报价有效期、未支付资源保留期和领取宽限分别生效；新版本不改变有效报价和历史订单 |
| 取消爽约与天气 | 客户取消按时间段计算，经营方取消和经营方停业不归责客户；天气例外按品类和证据审核，爽约经过通知和最终确认才释放资源 |
| 提前归还延期逾期 | 提前归还默认不自动退租金；延期只在库存复核、增量报价和补款成功后延长；逾期按快照宽限、计费和封顶且申请延期不等于成功 |
| 资质与检查异常 | 资质在报价、确认和领取阶段按规则校验；领取基线和归还检查有逐项证据；异常费用经保障判断、规则计算、人工审核和客户申诉闭环 |
| 规则例外与审计 | 企业合同和人工例外以追加审批记录覆盖允许的经营规则，不修改原快照，且不能绕过安全、法定资质、库存和数据权限底线 |
| 报价转订单 | 报价不占资源且默认只转换一次；订单提交时库存、优惠券、预算和服务容量在同一事务锁定，重复请求不产生重复订单，失败无孤立占用 |
| 订单范围与状态 | 订单不能跨经营空间、品类或不同租期混单；主状态、支付、库存、履约和结算分别准确表达组合状态，非法状态动作被拒绝 |
| 预留分配与整单领取 | 商品需求预留和具体资产/数量/套装分配分开；第一阶段只允许整单一次领取，领取前全部资源、支付、资质、检查和条款通过 |
| 订单变更与换货 | 部分取消、延期、地点服务等关键变化均追加变更版本并原子调整金额和资源；领取后换货保留原资产和替换事实，不覆盖订单 |
| 部分归还与恢复 | 多次部分归还只释放实际交回的资产、数量和套装组件；已交回不等于可出租，检查、清洁或维修完成后才恢复可用 |
| 结算与终态 | 资源、服务、资金、押金、预授权和异常全部闭环后才能完成；取消、爽约和关闭边界明确，强制关闭不能绕过正常结算 |
| 库存一致性 | 并发确认不会超卖；取消、失败和归还正确释放资产、数量和套装组件 |
| 客户与空间会员 | 同租户重复注册复用客户主档和账号，并为目标空间建立独立会员关系；一个空间的暂停、退出或注销不影响其他空间，禁止跨租户共享或合并客户 |
| 注册与审核 | APP 契约和后台新增均先复用租户客户主档；空间可独立选择自动或人工注册审核；自动注册不自动通过身份证、驾驶证或从业资格证审核 |
| 个人与企业管理 | 个人会员、企业会员和审核使用独立页面；企业管理员和员工都引用真实个人会员；员工关系停用后不再获得新企业权益，历史订单快照不变 |
| 会员方案 | 个人与企业方案按空间版本化发布；首期不提供付费购买；租金、押金/预授权、服务和优先预订等权益结构化配置并进入报价订单快照 |
| 旧会员体系退出 | 新业务不再访问或写入旧 `Member/MembershipPlan` 及 `/store-rental/members*`；旧页面、接口、契约和表按依赖顺序删除，且不把旧门市会员数据迁入新体系 |
| 等级与权益 | 各空间独立计算和调整会员等级；报价和订单保存等级、权益和规则版本快照；优先预订、免押等权益不能绕过库存、资质和安全底线 |
| 积分与营销余额 | 积分和营销余额按空间隔离且只能通过不可变流水变动；锁定、使用、释放、过期、退款和撤销可复算，不可提现、转账、抵扣押金或预授权 |
| 邀请奖励与防刷 | 邀请关系只在目标空间首次注册时绑定；重复事件只奖励一次，并发发放不超个人上限、活动总量和预算；取消退款可按生命周期撤销或建立追偿记录 |
| 客户合并与注销 | 重复客户合并保留原订单、权益隔离和完整映射审计；注销前结清未完成业务，注销后依法保留订单资金审计并删除或匿名化非必要信息 |
| 订单履约 | 多行订单可完成确认、配货、领取、归还、异常费用和结算闭环 |
| 数据恢复 | MySQL 模式重启后订单、占用、费用、权益和审计不丢失 |
| 迁移安全 | 空库可全量部署；已有库升级前后的业务记录数量和关键字段一致 |
