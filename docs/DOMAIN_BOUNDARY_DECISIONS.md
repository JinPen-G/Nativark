# 领域边界与命名决策

本文档记录当前 MVP 的业务边界，目的是让后续从“门市汽车租赁”改造成“通用租赁平台”时，有明确的替换点。

## 当前业务定位

当前系统仍按 PRD 交付“门市租赁（汽车租赁）”：

- 营运端优先，门店端复用营运端，只通过角色权限限制。
- 企业端、用户 H5 当前只预留接口边界。
- SaaS 架构保留，当前本地只需跑 1-2 个租户。
- 分时租赁相关原型入口保留视觉位置，不开发业务逻辑。
- 外部集成先全部 mock：支付、发票、短信、TBox、地图、文件存储、AI 调度。

## 通用租赁抽象

后续改造时，不应直接把系统重写，而是把汽车领域名词映射为通用租赁概念：

| 当前汽车租赁概念 | 通用租赁概念 | 改造说明 |
| --- | --- | --- |
| 车辆 | 租赁标的实例 / Inventory Item | 具体可租的一件资产，例如相机机身、镜头、帐篷。 |
| 车型组 | 标的分组 / SKU Group / Product Group | 可替代履约的同级商品组，例如 Canon R5 同级机身组。 |
| 车牌号 | 资产编号 / 序列号 | 不同品类可能是序列号、条码、资产编码。 |
| VIN | 唯一硬件标识 | 摄影器材可能是 SN，露营装备可能没有硬件唯一号。 |
| 里程 | 使用量指标 | 可能改为快门次数、使用小时、损耗等级、无使用量。 |
| 门市/站点 | 履约网点 | 自提门店、仓库、前置仓、寄送站点。 |
| 取车验车 | 领取检查 / 出库检查 | 出库拍照、配件清点、押金确认。 |
| 还车验车 | 归还检查 / 入库质检 | 归还拍照、损坏确认、清洁费/维修费结算。 |
| TBox/CID | IoT/智能设备标识 | 非车辆品类可为空，或接入智能柜/电子锁。 |

## 当前允许保留汽车语义的位置

MVP 阶段为了贴合原型和 PRD，以下位置可以保留汽车文案：

- 页面标题和菜单：车辆档案库、车型组管理、门市租赁订单。
- `@store-rental/shared` 中的 `VehicleGroupMaster`、`VehicleInstanceSummary`。
- `store-rental` API 路径。
- 页面表格字段：车牌、VIN、车型、里程、TBox CID。

## 后续应避免继续加深绑定的位置

新增代码时尽量不要继续扩大汽车绑定：

- 新的领域服务不要再新建 `car-*`、`vehicle-*` 之外的业务专有全局模块；优先考虑 `asset`、`item`、`inventory`、`fulfillment`、`inspection` 等通用命名。
- 定价规则不要写死“日租 + 里程费”，应保留“计费周期、基础租金、超额使用费、押金、增值服务、异地履约费”。
- 履约流程不要写死“取车/还车”，内部状态应支持“领取/归还/检查/结算”，页面文案可按业务线显示汽车术语。
- 集成边界不要只支持 TBox，应该通过 `integrationPlaceholders` 扩展为 IoT、智能柜、门禁、物流、支付、通知。

## 当前阶段决策

- “租户”仅指使用 Rental OS 的 SaaS 租赁经营商；向经营商租设备的个人或企业统一称为“租赁客户”，两者不得共用模型、权限或页面。
- SaaS 平台管理员只管理租户开通与生命周期；租户管理员的全权限只在当前租户生效。具体实现和验收边界以 `SAAS_TENANT_FOUNDATION.md` 为准。
- 产品方向已确认调整为“单品类租户的通用设备租赁平台”：一个租户只配置一种租赁品类，但可管理该品类内的多个商品、资产和套装。
- 现有 `store-rental` 代码和汽车数据保留为 `vehicle` 品类的兼容基线；新增通用能力优先进入 `rental-core`、`inventory`、`fulfillment` 或 capability adapter，不继续向车辆模块增加通用功能。
- 营运端固定采用 React 19.2.8、React DOM 19.2.8 和 Ant Design 6.6.0，并提交 lockfile 固定依赖解析；旧 Vue 营运端已移除，所有前端能力统一在 `apps/admin` 开发。
- 通用化先完成共享类型、数据模型、API DTO 与汽车兼容 facade，再按业务域迁移 React 页面；不进行大爆炸式重写，也不长期双写旧车辆表和新资产表。
- 完整目标架构、数据/API 策略、React 页面顺序和切换验收以 `GENERAL_RENTAL_REACT_MIGRATION_PLAN.md` 为准。
