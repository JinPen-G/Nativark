## 一、总结论

Rental Core 与企业级基础设施的成熟度**显著高于预期**。多品类接入的标准化机制、权限门禁、支付验签链路、空间隔离这几块属于工程上真正做扎实的部分。

本次审查共确认 **51 项问题**：**P0 共 1 项**（校验逻辑死代码，资金侧无直接资损但静默放行）、**P1 共 14 项**、**P2 共 36 项**。未发现可篡改资金或越权直达的缺陷。

> **与既有报告的交叉核对**：本目录另有一份同日报告 `管理后台审查报告-20260924.md`。两份独立审查在高危项上**互相印证**（支付回调金额校验失效、分段累进阶梯缺失、报价有效期复用、dataScope 未执行、规则不按品类过滤、取整漂移均双方命中）。该报告另发现的 12 项高价值问题已全部纳入本报告（见 §2 表中 #0、#1、#10-#14、#18-#21 及 #34、#37、#43-#46），并以该报告的取证**修正了本报告初稿的一处错误结论**（见 §3-2 勘误）。

五个最需要优先处理的结论：

1. **支付回调金额一致性校验是死代码**——`rental-funding.service.ts:334-345` 括号错位，校验语句被放在必然先抛异常的块内，永不执行。下游有"收款不超应收"兜底，无直接资损，但回调金额不一致会被静默放行。
2. **分段累进阶梯完全缺失**——现有阶梯只有"达到档位后全部单位用档位单价"（长租口径）。若把里程/水电等分段累进价配进 `tiers`，金额会被整体重算而**直接算错**。
3. **报价有效期被未支付保留时间复用**——需求明令"两者必须分别配置"，实现上二者同源（`rental-core.service.ts:1904`）。这是被点名禁止的混用。
4. **数据权限（dataScope）未落到业务查询层**——`dataScope` 仅作用于用户/组织查询与员工端地点范围；后台订单、资产、客户等业务列表只按 `tenantId + workspaceId` 过滤，"所属组织/授权地点/仅本人"实际未生效。
5. **企业会员域落地上半段缺失**——企业征信表是孤儿表（写入路径缺失）、开票/合同/授信有 API 无 UI、授权经办人无任何写入入口、证件缺签发机构字段。

另一个与"标准化接入"直接相关的结论：**四个品类的首期必选能力清单全部为空**，校验机制完备但无输入，使品类门槛形同虚设。

## 三、逐项审查

### 1. Rental Core 完善度与逻辑漏洞

**结论：核心成熟度高，但发现 1 项 P0（校验死代码）+ 3 项 P1 + 若干纪律漂移。**

**P0-0 支付回调金额一致性校验为死代码（最高优先）**

```ts
// apps/api/src/modules/rental-core/rental-funding.service.ts:334-345
        if (effectiveAmount <= 0) {
          throw new ConflictException(
            input.instrument === "rental" ? "当前没有待收的租金或费用" : ...
          );
        if (!input.allowPartialInitiate && input.instrument === "rental" && input.amount !== undefined
            && Math.abs(Number(input.amount) - effectiveAmount) > 0.005) {
          throw new ConflictException("支付回调金额与当前订单待收金额不一致，请重新发起支付");
        }
        }        // ← 该 "}" 才关闭 334 行的 if
```

`if (effectiveAmount <= 0) {` 在 334 行开块，块内第一句就无条件 `throw`，因此紧随其后的金额一致性校验（342-344 行）**永远不可达**。后果：**支付回调传入的金额与订单待收金额不一致时被静默放行**。下游 `:358`「收款不能超过订单及待补款续租应收」构成兜底，故无直接资损，但该拦截语义完全失效，且掩盖了金额篡改类异常。修复为移动一行括号并补回调金额不一致的反向测试即可。

**P1-1 分段累进阶梯模型完全缺失**

现有阶梯只有一种口径——"达到档位后，全部单位使用该档单价"（长租阶梯）。需求 4.4.5 原文：「长租阶梯默认采用"达到档位后，全部单位使用该档单价"……水电、里程等**分段累进价格必须使用独立的"分段阶梯"模型**，不得与长租阶梯混用。」

实现中不存在 `tierMode`/分段累进分支，因此若运营把里程价、水电价填进 `tiers`，系统会按"满 N 单位后全部单位按该档单价"整体重算，**金额直接算错**（且不会报错）。上线任何使用量阶梯计价前必须解决。

**已正确（重要正向）**
- 空间隔离落实彻底：`resolveScopeWorkspaceId` 在 fact repository 中出现 60+ 次，空间一律取自服务端会话，不采信客户端 `workspaceId`。
- 幂等：资金与状态动作统一走 `rental-idempotent-action.service`。
- 测试覆盖广：`tests/` 137 个专项，覆盖需求 6.1 的全部 10 个场景（订单流、结算、资金门禁、分批归还、优惠券预算、续租、爽约、逾期、费用裁定、并发与恢复）。
- 四道静态门禁实跑结果：`validate-api-contracts`（430 操作）、`validate-dto-coverage`（164 DTO / 887 字段）、`validate-route-permissions`（430 路由）**全部通过**。

**P1-1 报价有效期与未支付保留时间混用**

```ts
// apps/api/src/modules/rental-core/rental-core.service.ts:1904
expiresAt: new Date(Date.now() + quote.ruleSnapshot.payment.unpaidHoldMinutes * 60_000).toISOString()
```

需求 4.6.2 原文：「报价有效期、未支付订单资源保留时间和领取宽限时间必须**分别配置**，不得用一个超时时间混用。」全仓检索无任何独立的报价有效期配置项（`报价有效期` 仅出现在会员权益标签 `quote_validity_extension`，且该权益页已注明"尚未生效"）。同时 `rental-business.service.ts:5105` 用 `quote.expiresAt` 做过期校验，因此客户看到的"报价有效期"实际等于"未支付保留时间"。

**P1-4 资金余额取整缺 EPSILON**

`rental-money.ts` 自述是"金额取整的唯一实现"，但实际：
- 有 EPSILON 的本地重复：`rental-funding-events.ts:20`、`rental-pricing-strategy.ts:91`、`rental-security-deposit.ts:28`、`rental-service-catalog.ts:42`、`rental-discount-selection.ts:49`、`staff-offline-payment.service.ts:10`

```ts

// rental-document-renderer.ts:257
return Math.round((Number.isFinite(value) ? value : 0) * 100) / 100;
```
`rental-money.ts` 的注释恰好警告过这一类"差一点"舍入边界，而资金余额正是最该稳的字段。

### 2. 多品类标准化接入

**结论：标准化接入机制已实质形成，这是全项目最规范的一块；缺口集中在"必选清单"与"术语覆盖"。**

**已正确（重要正向）**
- 新增品类只需在 `RENTAL_CATEGORY_DEFINITIONS`（`core.ts:4422`）补定义，即决定：业务术语、动态字段 schema、库存模式、计价单位、履约方式、地点类型、检查模板、默认规则、capability。
- **启动/测试期扩展门禁**（`rental-extension-registry.ts:77-122`）真实校验：品类编码不重复、默认计费单位属于支持范围、引用的计费策略已注册、默认与必选 capability 已注册且适用于该品类、初始地点类型合法。这正好满足需求 3 的"启动和自动测试必须校验"三项要求。
- **管理端与共享契约无品类分支**：`apps/admin/src` 与 `packages/shared/src` 检索 `categoryCode ===` / `!== "camera"` / `=== "vehicle"` 等**零命中**。
- ⚠️ **勘误**：初稿曾断言"通用主流程零品类分支"，该结论**有误**——正确检索（需包含 `!==` 与双引号）后在 `apps/api/src/modules/rental-core/rental-core.service.ts:4638` 命中唯一一处通用流程品类分支：

```ts
// rental-core.service.ts:4638
if (categoryCode !== "camera" || template.fields.some((field) => field.code === "kit_complete")) return template;
```

该分支位于通用检查模板读路径，违反需求 3「不得在通用报价、订单、库存或履约主流程散落品类编码分支」。实质是旧检查模板的补齐问题，应改为数据驱动回填。
- 计费单位差异被规范收敛：摄影 `[hour, day_24h, calendar_day, week]`、露营 `[calendar_day, night, week]`、车辆 `[hour, day_24h, calendar_day, week, month, usage]`、工程 `[hour, shift, calendar_day, week, month, usage]`，由品类定义声明、后端校验、前端按 `category.businessModel.pricingUnits` 渲染选项。
