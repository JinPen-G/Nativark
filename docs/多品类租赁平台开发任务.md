### 1.1 状态与放行

- 状态仅用 `Pending / In Progress / Done / Reserved`。`In Progress` 可表示已实现待验收，并不代表仍有 AI 正在执行；当前派发以第4节为准。实现进度与验收结论必须分别说清。
- 已提交、编译通过、开发者自报、静态源码断言或内存测试，均不能单独证明数据库、并发、页面可操作或可对外经营。
- 历史 `Done` 仅保留原阶段范围的验收，不自动覆盖新增要求。新的缺口用子任务承接；若证明原验收错误或回归，重开原任务并记录依据。
- 原台账的 `Partial` 统一为 `In Progress`；不提高完成度。完整平台/储备能力未做不阻塞 R1；但 R1 开放给运营使用的功能不能留无出口状态或静默放行。
- 一项任务完成：规则明确、前后端与持久化一致、权限范围正确、异常可处理、专项及必要真库/页面证据齐全，并经独立 Review。R1 通过后还须单独完成 `PILOT-01` 才能对外试点。

### 1.2 文档与协作边界

需求正文是产品口径；本台账是唯一排期、实现边界与进度入口。技术指南若残留已退出旧模块说明，不得据此复活旧体系，由 `P0-04` 收口引用。保留既有界面规范和归档，不另建开发日志、执行日报、任务包文件或重复路线图。

开发 AI 每项交付报告“任务ID、提交、实际完成、测试/数据库/页面证据、未跑内容、残留与缺口”，由 Codex 在启动、待Review、合并三节点更新本台账。默认不授权开发 AI 修改需求和任务文档，不因没有文档编辑权而省略进度报告。

### 4.2 STOCK-CLOSE-01：逐批归还、实际缓冲与库存处置

**对应需求：** 4.2、4.7.6.1、4.7.10～4.7.12。**依赖：** ACCESS-01C通过；在现有检查、归还批次和数量隔离修复上开发。

实现方式：

1. 复用 `rental-core.service.ts` 的归还/检查入口、`rental-core-fact.repository.ts`、`rental-occupancy.ts` 以及 `rental-allocation.service.ts`。先核对已完成的批次幂等、异常数量入隔离、盘点保留维修量与行锁，不重复实现。
2. 将每批检查结果定位到实际资产/组件或“产品型号+地点+数量”，不是定价分组。追加可追溯处置明细，至少有来源订单/归还批次/检查项、资源和数量、实际收到时间、适用缓冲及最早恢复时间、阻断原因、处置状态、恢复来源与审计/并发版本。复用既有字段，不足才扩结构；不得靠进程内数组维持。

### 4.3 SHARED-WORK-01A：清洁、维修工单可操作闭环

4. “处理完成”只进入待复核；只有有验收权限的动作才能确认结果并调用STOCK-CLOSE-01受控恢复。复核未通过、其他阻断未结束或缓冲未到，不显示已可租。验收与处置/库存写入使用同一事务；失败不留“工单已完成但库存没恢复”的半状态。
5. 工单处理权、验收权和查看权分别表达，优先复用语义吻合的权限，缺失则同步注册目录、Guard、角色配置与页面；不得用普通商品编辑权或订单资金权代替。当前不新增强制双人审批规则，同一账号是否同时持有处理/验收权由授权决定。
6. 新增现有管理端内的“养护工单”列表和详情：按状态/类型/资源/负责人筛选，显示来源、下一步和阻断原因；支持领取/指派任务、开始处理、填写结果上传证据、提交复核、验收通过/退回、查看历史。负责人从当前空间运营账号选择，证据复用受保护上传服务，不暴露本地路径。
7. 订单详情和资产/库存页可跳到关联工单；反向能回到具体归还批次/检查项。工单未通过验收不自动结清订单；验收合格可恢复资源，但损坏费用、争议、退款仍走既有审核资金流程。
8. 跨地点调拨、周期/工时自动计划、IoT告警、采购配件、维修商门户、复杂排班和成本结算不在本批；需要的基础备注/附件可以记录，但不自动推出这些完整业务。D-10赔偿和审批金额尚未确认，不能自行定收费标准。

最小验收：

- 一张摄影多行订单的异常归还形成工单，经处理、提交复核、验收后恢复，再被下一单正确预留；全程页面办理，不改数据库补状态。
- 一种数量库存品类复用同一流程；一次清洁合格、一次维修复核退回后再通过。只恢复关联处置数量，不放出其他未完成阻断。
- 取消/无法修复不恢复资源；无验收权限不能通过按钮或API恢复；重复/并发验收只一次，事务失败与重连后事实一致。
- 资产可以恢复而原订单仍有损坏费待审；也不能因为尾款已结而自动释放坏件。
- 只做本模块必要的浏览器链及真库；在专用环境建立自有夹具，失败也清理，不能复用超级管理员绕过权限或修改共享演示账号。

#### 4.4.1 ORDER-CLOSE-01：最新返修验收与订单事务顺序

1. 先逐项确认第7节近期提交已经包含在本分支，核对迁移、归还批次、完整优惠链、分批逾时、费用审核、续租保证金、数量隔离、锁单后计费。对已经修好并有有效专项的部分只补直接缺失证据，不能声称它们仍未开发。

4. 特别检查结算与费用审核/退款的并发：如果另一动作先改变应收或实收，结算必须按最新余额与待审状态重新判定，不能因先检查余额后锁订单而关掉欠款订单。领取资金检查与状态推进采用同样原则。

## 6. 精简验证与交付规则

### 6.1 只运行与改动直接相关的验证

- **开发、返修和合并前均不默认运行全量 MySQL E2E，也不把完整 `test:rental-foundation` 当每项门禁。** 全量仅在项目负责人再次明确要求时运行；跨模块任务同样优先最小集成真库。
- 先构建变更依赖的shared，再运行目标专项/受影响组；失败后只复测失败段及直接受影响前后段，不从第一节重跑。最终HEAD统一补一次涉及包的类型检查、契约校验、必要构建及 `git diff --check`。
- 现有可选专项包括：`tests/rental-return-batch.test.cjs`、`rental-return-quarantine.test.cjs`、`rental-extension-funding.test.cjs`、`rental-fee-review.test.cjs`、`rental-funding-gates.test.cjs`、`rental-order-settlement.test.cjs`、`rental-extension.test.cjs`、`rental-renewal-repricing.test.cjs`、`rental-service-capacity.test.cjs`、`rental-service-catalog.test.cjs`（后续文件均在tests目录）。开工以当前package.json和测试实际前置为准，不为了凑数量全跑。
- 修改DTO/API/权限时跑 `npm run contract:validate`；修改管理端时补对应页面/权限专项和相关类型检查，按任务要求做少量浏览器操作。纯后端任务不自动扩成全站视觉验收。
- `db:validate`只证明schema合法；静态源码断言不证明请求真实进入事务；内存替身不证明数据落库。金额、资源、审核竞态必须有最小真库证据。
- 每项高风险逻辑挑直接相关的少数定向变异，不再要求固定十几种变异指标；测试应能证明阻断点，不能只检查测试脚本含某字符串。
