1. 订单创建时已有的 `draft + reservation.expiresAt` 作为待支付事实，不新增一个重复的主状态。候选查询按当前租户/经营空间取出过期订单，真正取消前在订单行锁内再次确认订单仍为 `draft`，且全部软预占已经过期；已确认、已人工取消、缺少到期时间或仍有未过期占用的订单 fail-closed。
2. 新增单笔与批量超时入口。两者共用同一幂等动作键和状态机，批量遇到并发确认/人工取消只记录 `skipped`，不会把整批回滚成未知结果。
3. 超时取消复用既有取消核减事实，并在同一数据库事务内释放锁定优惠券及预算、服务容量和库存预占；管理端订单详情只在软预占确实过期时显示处理按钮。

4. 领取时间超过订单规则快照中的宽限后，订单只进入`pickup_overdue`（待确认爽约），不立即释放库存、服务容量或优惠券，也不直接收取爽约费用。候选查询和单笔操作均在服务端按租户/经营空间、当前状态和订单快照复查；订单快照没有启用爽约规则时 fail-closed，不因后续系统升级追溯改变历史订单。
5. `pickup_overdue` 必须先通过已启用的 `order.pickup_overdue` 通知模板记录客户通知时间；通知后的最终确认时限到达后，或由具备操作权限的人员提前确认并填写原因，才能进入`no_show`终态。确认时按订单快照计算固定金额/百分比/不收费三种爽约费用，并复用取消核减事实，避免重算原报价。
6. 确认爽约与资源释放在同一事务内完成：库存预占、增值服务容量和优惠券预算一并释放，事件和幂等动作可重放；订单详情提供“领取超时 / 通知客户 / 确认爽约”三个分开的操作出口，规则管理页提供宽限、最终时限和费用设置。
7. 工作台通过 `/rental/v1/workbench/todos` 聚合当前经营空间内真正可操作的待办：待支付占用超时、通知/确认爽约、逾时未归还、待裁定费用、待办理模拟退款和待处理/待验收养护工单；退款待办必须以资金事件流的负租金余额为事实，不凭审核状态虚构已发生退款。

**本段证据与边界：** `rental-order-timeout`专项5项、`rental-no-show`专项7项、`rental-workbench-todos`专项8项、API/Admin构建、`contract:validate`、路由权限检查和 AntD lint 通过；本轮专用 E2E 完成 98/98 迁移、空库无 drift、摄影多行订单、异常归还逐处置恢复、领取爽约、RC-02/RC-03 并发、重启/重连等 29 组定向断言，测试库已自动清理。管理端订单详情已浏览器验证确认→自动预分配→锁定→取机检查→租赁中；本次另用专用 `store_rental_zcode` 造最小待审费用单，浏览器完成工作台待办→详情裁定，确认应收从100增至130、待审清空，且页面仍区分裁定与实际退款；随后补做订单详情归还检查→异常隔离→自动建单→跳转养护工单管理的页面链；本轮再用独立待结算订单完成模拟收款→押金收取→预授权冻结→押金退款→预授权释放→结算关闭页面链，确认资金未收齐时结算按钮禁用、结算后订单变为已完成，并修复页面漏列资金阻断原因的缺口。真实 Provider 和“实际退款”仍未覆盖，以上资金操作明确是模拟事件；共享`store_rental`未执行迁移或写夹具，不得把本段专项结果当作生产放行。

## 6. 精简验证与交付规则

### 6.1 只运行与改动直接相关的验证

- **开发、返修和合并前均不默认运行全量 MySQL E2E，也不把完整 `test:rental-foundation` 当每项门禁。** 全量仅在项目负责人再次明确要求时运行；跨模块任务同样优先最小集成真库。
- 先构建变更依赖的shared，再运行目标专项/受影响组；失败后只复测失败段及直接受影响前后段，不从第一节重跑。最终HEAD统一补一次涉及包的类型检查、契约校验、必要构建及 `git diff --check`。
- 现有可选专项包括：`tests/rental-return-batch.test.cjs`、`rental-return-quarantine.test.cjs`、`rental-extension-funding.test.cjs`、`rental-fee-review.test.cjs`、`rental-funding-gates.test.cjs`、`rental-order-settlement.test.cjs`、`rental-extension.test.cjs`、`rental-renewal-repricing.test.cjs`、`rental-service-capacity.test.cjs`、`rental-service-catalog.test.cjs`（后续文件均在tests目录）。开工以当前package.json和测试实际前置为准，不为了凑数量全跑。
- 修改DTO/API/权限时跑 `npm run contract:validate`；修改管理端时补对应页面/权限专项和相关类型检查，按任务要求做少量浏览器操作。纯后端任务不自动扩成全站视觉验收。
- `db:validate`只证明schema合法；静态源码断言不证明请求真实进入事务；内存替身不证明数据落库。金额、资源、审核竞态必须有最小真库证据。
