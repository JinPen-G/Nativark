## 2. 验证方法与输入来源

直接加载生产 TypeScript 的实际类方法，没有复制计价、规则或状态算法。夹具文件只生成输入、空配置快照、聚合返回数据和退款行；仓储复用既有 `tests/helpers/absorbing-config-store.cjs`。退款仓储替身仅存储行、模拟事务回调失败回滚，不实现退款状态决策；状态判断由实际 PaymentRuntimeService 执行。

- 四品类定义来自 `@rental-os/shared` 的 `RENTAL_CATEGORY_DEFINITIONS`；每品类独立服务实例及独立工作空间输入。
- `tenant_001` 只是既有内存初始化器提供演示目录的匹配 ID，所有仓储均受控，没有读取真实同名租户。最初使用新合成租户时初始化器不给演示型号/地点，已改为明确标注的内存演示基线，不能称“空白真实租户已可营业”。
- 报价输入：服务实际初始化的型号/地点、第一种已启用履约方式、当前时点后 48～72 小时的租期、数量 1。不手算租金。
- 开业输入：持久配置标识为真、权威空价格/规则/日历；另一个案例仅保留实际服务输出的价格计划，独立验证缺规则。
- 报表输入：可用资产 3、已租 1、停用 2；数量库存在库 10、占用 3、维修 2；订单聚合与扫描为空。只验证库存聚合/查询条件/事实边界，不把空订单夹具当经营收入或利润验收。
- 退款输入：`pending`、金额 10 的合成退款行；受控提供商结果 `accepted / succeeded`、HTTP 503 未知错误、明确拒绝错误及内部资金写入异常。
- 历史缺失案例：基于实际生成的报价删去费率/规则快照，或给历史订单省略检查快照；是条件性缺损数据复现，不证明正常新订单会缺失这些字段。
- 未启动 Nest 应用或监听端口；仅直接调用服务类的配置初始化钩子。未实例化 PrismaClient/PrismaService，未读 `.env`。
- 新测试运行期间拦截 `net.Socket.connect` 与 `fetch`，末尾断言外部连接尝试为 0，并恢复原函数。供应商结果替身不属于真实供应商验证。

## 3. 事实口径与用例覆盖

新增共 32 个测试：四品类 × 6 个 = 24；通用 8 个。其中 3 个明确标记 `KNOWN GAP`，通过只表示稳定复现当前缺口，**不是需求安全验收通过**。

| 场景 | 实际调用与结果 | 可交给后续 AI 的口径 |
| --- | --- | --- |
| 权威空配置（四品类） | `refreshFromDatabase` 消费受控快照；`currentRule` 拒绝无生效规则；`createQuote` 先拒绝无覆盖价格计划；诊断缺规则、地点、型号、定价分组、价格版本，`ready=false` | 缺项不能重填演示配置、不能称已就绪；错误顺序由实际入口决定 |
| 有价格、无规则（四品类） | 保留实际价格计划后清空规则；`createQuote` 拒绝缺生效规则，无报价写入 | 不能拿当前默认规则补一个空权威规则集 |
| 会员读取不可用（四品类） | `tenantReadiness` 捕获 listPlans 异常，会员项 `unavailable=true / done=false`、无数量摘要 | 服务不可用与配置不存在是两种事实；会员目前是可选项，不能擅自升级为报价硬闸门 |
| 报价与建单分离（四品类） | `createQuote` 调用实际业务事实仓储 `upsertQuote`，记录仅 quote；报价阶段不写 Core 订单；内存路径 `priceVersionId` 留空 | 报价属于持久副作用候选，不是纯读，但不等于预占/付款/交付；本轮不证明真库落盘 |
| 建单重新核库存（同一组四品类用例） | 实际 `prepareOrder` 对空库存仓储拒绝“库存不足”，不写订单 | 有报价不保证能下单；该案例走旧调用方 `qualificationApproved` 分支，不证明新会员资格/订单应用事务正确 |
| 确认不等于支付或交付（四品类） | `confirmOrder` 把 draft/soft 变为 reserved/confirmed，未分配资产；重复确认和过期软预占拒绝、不再保存 | 只验证确认状态边界，不证明真实付款、锁定配货或交付已完成 |
| 原价全租期续租缺费率（四品类） | 实际 `quoteOrderExtension` 使用原价模式，费率快照为空时拒绝“缺少原订单费率快照，不能改用现价续租” | 不可补造旧价格；增量续租使用当前版本是既有业务规则，不能一概误说所有续租都必须用旧价格 |
| 旧 AI 连接测试 | 实际 `PlatformService.testAiConnection` 返回“成功”，但日志 `mock_success`、消息明确未调用外部模型，网络尝试 0 | 这是模拟/结构反馈，不是真实模型连接证据，也不是 AI Native 可用证据 |
| 经营报表 | 实际 `getOperationReport` 计算可经营资产 4、当前已租比例 0.25、数量可用 5，返回快照时间及历史口径缺口；换统计区间不改变库存快照查询；所有查询带 tenant/workspace | 当前比例不能叫历史利用率；该报表入口不输出成本利润，收入/应收不能改称利润；不是全系统成本模块不存在的证明 |
| 退款未知/受理/拒绝 | 实际 `markRefundProviderCallPending` 与 `applyProviderRefundOutcome` 输出 pending/accepted/failed，均未调用资金入账 | pending 是待核对；accepted 是提供商已受理/处理中；failed 是明确失败，不能统一叫成功 |
| 外部成功但内部入账失败 | 实际服务输出 funding_pending，保留成功时间且 fundedAt 空；再给 accepted 不降级 | 外部退款事实与内部账务完成分开说，仍需恢复/对账 |
| 成功退款入账调用 | 实际服务在资金替身成功后输出 succeeded/fundedAt，调用 refund 资金动作及固定幂等键 | 仅证明生产服务调用/状态分支；不证明资金账本、MySQL 原子性、并发幂等或外部到账 |

注意：`prepareOrder` 首次进入内存 `factContext` 会向吸收仓储写入演示 asset/stockBalance 初始化调用。本轮观察到这一行为并保留，不把它隐藏成“所有入口都是纯读”；它不是订单预占，更不是实际数据库写入。报价本身的无订单写入断言在调用建单准备之前执行。
