## 功能与入口

- `composeControlledApprovedOrder(dependencies)` 显式组合固定主线 `composePersistedOrderTaskInput` 的正式发布、场景政策、封闭计划与步骤登记，以及既有 `prepare/submit/reconcile`。缺 Core `normalizeOrderInput` 或实际授权/持久依赖即 unavailable；没有 policy seed、自动批准、Worker/AppModule 注册。
- `PrismaAuthorizedApprovedOrderInputSource` 从事务内原 step/input 生成 reference，消费实际 `ApprovedOrderInputAuthority.authorizeOrderInput`。核对当前 context、完整原 reference、tool/version、原 policyRevision、policyHash、bindingHash、有效且不晚于原输入的最早 expiry；真实原输入 DTO reader 前后复验输入/步骤事实与稳定证明。稳定摘要排除 requestId/authorizedAt。
- 准备与未提交执行共享同一个正式 adapter。未提交初检和 Core 原事务中的 prepare/commit 复验均对原批准输入 hash 与原证明；同一次提交的后续证明不得漂移。订单、审批消费与业务幂等收据仍由既有 Core 单动作事务关联，不新增通用事务框架。
- 已 COMMITTED 的 submit/reconcile 不读正式 input/plan/policy 执行证明；仍核对原批准快照、消费记录、原订单及当前读权限，不以失效执行权益抹去历史事实，也不重新创建/消费。
- 既有 generic `composeAiApprovedOrder` / `composePersistedApprovedOrder` 保留底层可注入 API；它们没有注入 executionInput 时不代表已完成正式输入接线。正式入口应使用本片 controlled 工厂，不把 generic API 的旧测试当作正式发布闭环。
- 批准仍是独立、显式的人类审批仓储步骤；工厂不会在 prepare 内批准或自动 dispatch。本片 smoke 使用实际 `PrismaAiApprovalRepository.decide` 落记录，不注入 APPROVED 布尔。人类决策服务入口、拒绝/过期/修订恢复、等待确认 executor 与结果事件交接留后续功能片。
