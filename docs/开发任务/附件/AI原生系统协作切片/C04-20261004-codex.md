## 实现要点

1. `AiTaskRunner` 只接受显式注入的 lease、步骤、授权计划和 effect 端口。依赖不完整时构造失败；不存在默认 allow-all、内存租约或供应商调用。
2. 普通运行调用 `claimRun`，恢复调用 `claimRecoveryRun`。恢复只允许通过显式 `reconcile` 端口处理 `external_unknown`；没有核对端口即 `unavailable`，不会重发原 effect。
3. 每个步骤先由仓储适配器注册并启动，再执行显式 effect；成功/失败/暂停/未知都交给步骤仓储适配器持久化。`registered.replayed` 没有终态投影时一律停止，不能把 replay 当作重发许可。
4. 总时限、单步时限、最大步骤数、最大调用数、最大输出字节数和并发上限均来自注入的可信 plan；本实现按单 lease 串行执行，`maxConcurrent` 只允许 `1`。
5. 超时、外部未知、副作用型 cleanup 失败都不自动重试；有潜在副作用时进入 `unknown`。取消请求只阻止下一步，不声称已回滚已发生的外部动作。
6. 步骤提交返回新的 run/task revision，释放租约使用最新 fencing/revision。释放应答不明不重试，而是向调用方暴露 `AI_STORAGE_UNAVAILABLE`，保留租约供后续受权恢复；effect cleanup 失败通过 `cleanupFailed` 暴露并在有副作用时进入 unknown。
7. 适配器的 command factory 必须由应用组合根提供 evidenceId、期望 revision、真实上下文和 transition reason；运行器不自行生成授权、预算、dispatch 或业务事实。

## 未验证与精确接入合同

- 未连接数据库、未执行迁移、未运行真实 MySQL 行锁/宕机/提交应答丢失测试，未启动 API、未调用模型/支付/外部网络。
- 主线组合根需要提供 `AiTaskRepository`、`AiStepRegistrationRepository`、`AiStepTransitionRepository` 的实例、真实授权 resolver、command factory、可信 plan source，以及 Gateway/工具的受控 effect/reconcile port。Gateway 必须在自己的链路中完成 dispatch admission/预算/权限；运行器不替代这些职责。
- `register` 的 replay 必须从已有仓储读取明确终态；当前仓储的 replay 返回没有终态状态，因此适配器将其作为不可继续处理，避免误重放。主线若需恢复已完成步骤，应补一个受权的只读终态查询端口，不能把 replay 标为成功。
- 运行器未自动完成 task-level `waiting_*` 或 `cancelled` transition；暂停、取消、人工接管的任务状态由现有 task transition 端口在主线授权后提交。AIN-07 审批消费和 Core 写入仍未接入。
