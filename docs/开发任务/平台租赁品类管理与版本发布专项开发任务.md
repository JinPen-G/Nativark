- 落实需求第 7.4 节的部署门槛：兼容结构和读取/执行程序先部署，全部相关 API、后台/定时任务及消费者满足要求后才开放动态写入；混用旧实例时不得提前放行，后续实例接入也检查兼容。最终管理链开放仍依赖 05～08、10，不因迁移完成提前开放功能。
- 验证最低可回退程序版本及依赖，区分品类恢复、兼容程序回退与数据库恢复；新编码事实存在后，禁止回退或重新接入仅识别四品类的程序，不能以删除新品类经营数据消除不兼容。

验收：新建空间拒绝未知、未发布、停止新开通或不在版本采用范围的编码；既有空间解析/历史履约不因停止新开通被一并拒绝。第五品类可由平台建立并被授权空间采用，专用白名单不可绕过，现有四品类及查询无损。新旧程序混用时开放被阻止，后台任务可读取新品类，兼容回退和不兼容旧程序接入拒绝有证据。对应 CAT-A02、A05、A14、A16、A21、A22。

## 7. 验证与协作约束

| 验证层 | 证明什么 | 不能替代什么 |
| --- | --- | --- |
| 静态/类型/契约 | 引用、类型、路由权限与接口文档对齐 | 真实查询、事务、页面操作和宿主行为 |
| 纯函数/组件专项 | 配置解析、组合校验、差异与界面交互 | MySQL 唯一性、外键、锁和持久化 |
| 专用真库 | 迁移、回填、隔离、并发、幂等、历史和重启 | 真实第三方网络及微信宿主 |
| 浏览器/宿主 | 后台、预约网站与小程序真实交互及跨端状态 | 真实收退款、短信送达和对象存储外网验收 |
| 独立 Review | 业务方向、跨模块风险与验收遗漏 | 未实际运行场景的执行结果 |

- 每项任务尽量形成可独立 Review 的切片；共享 schema、shared、解析服务、权限及会话文件指定单一写入负责人，不让多个 AI 同时改。
- 原有未提交改动归原作者所有，先核对归属；不能覆盖、清理或混入本专项提交。
- 数据迁移在专用克隆库先验证，备份、前后核对、失败恢复方案齐全后再申请目标环境部署；禁止依靠删表重建或改已执行迁移消除漂移。
- 任务关联的文档更新只同步已核实范围，不以本专项顺手宣布其他任务完成，也不追加收费、硬件或专业模块开发。
- 没有真实凭据、宿主或明确历史证据时，说明缺什么和允许交付到哪里；保留未完成任务，不伪造通过。

## 8. 完成定义
