## 1. 命令

```bash
npm run ops:upgrade-drill
```

指定备份、保留克隆库、指定演练端口：

```bash
npm run ops:upgrade-drill -- --file backups/store_rental_claude-20260829174533.sql --keep
```

```bash
OPS_DRILL_API_PORT=3995 npm run ops:upgrade-drill
```

专项测试：

```bash
npm run test:ops-upgrade
```

## 2. 演练步骤

| 步骤 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 验证备份 | 必须存在 `.sha256` 旁文件且匹配。升级演练只接受**已验证**的备份 |
| 2 | 恢复到升级克隆库 | 新建 `<db>_upgrade_<时间戳>`；表数、迁移条数、抽样行数与源库一致 |
| 3 | `prisma migrate deploy` | 只作用于克隆库，用**管理凭据**执行（与真实发布一致：DDL 由特权账号做） |
| 4 | 独立端口启动 API | 先确认端口空闲；以**应用账号**连接克隆库，临时进程，演练完即停 |
| 5 | 健康检查 | `/api/health` 必须回 HTTP 200 **且** `status === "ok"` |
| 6 | 回滚演练 | 从同一份备份恢复出 `<db>_rollback_<时间戳>`，并校验它停在备份时点的迁移条数 |
| 7 | 结果 | 写出 `artifacts/release/upgrade-drill-<时间戳>.json`，含人工切换步骤 |
| 8 | 清理 | 只删除本次创建且形态正确的克隆库；`--keep` 则保留并打印清理语句 |

## 3. 三条不可退让的边界

**源库只读。** 全程不对 `DATABASE_URL` 指向的库做任何写入或迁移。
`migrate deploy` 的连接串把库名换成克隆库；专项直接断言脚本里不存在对源库的
`CREATE/DROP DATABASE`，也不存在 `migrate reset` / `db push`。

**回滚靠重建，不靠 down migration。** 真实事故里 down migration 既不可靠、
也常常根本不存在。因此回滚是「从同一份已验证备份恢复出一个干净库」，
再把切换动作交给人。脚本不写 down migration，也不改写 `_prisma_migrations`。

**不碰现有服务。** API 只在一个独立端口上起一个临时进程。端口被占用时**直接失败**，
绝不去停别人的进程腾位置；脚本里没有任何 `docker stop/restart`、`taskkill`、`pkill`。

## 4. 权限与授权残留

克隆库由管理凭据创建，而 API 以应用账号连接，因此演练会把克隆库的读写权限
授给应用账号（新建库对应用账号默认不可见，实测 `P1010 Access denied`）。

MySQL 的 `DROP DATABASE` **不会**回收 `mysql.db` 里的库级授权，因此：

- 自动清理时先 `REVOKE` 再 `DROP`，顺序反了会留下一条指向已删库的孤立授权；
- `--keep` 或失败保留时，脚本会同时打印 `REVOKE` 语句，删库前请一并执行。

## 5. 失败与残留

任一步骤失败即退出非零，并且：

- **保留**本次已创建的克隆库供排查，逐个打印 `DROP DATABASE` 与（如有）`REVOKE` 语句；
- 若本次尚未创建任何库，明确输出「无残留」；
- 临时 API 进程一律结束，不留后台进程；
- 明确提示不要用 schema 回滚冒充数据恢复（见 OPS-01A §5）。

> 关于「本次新增 0 条迁移」：这不是失败，只说明备份时点已包含全部迁移。
> 此时报告里的 `upgradeExercised` 为 `false`，脚本也会在输出里说清
> 「只证明 deploy 在克隆库上可干净执行，未实际演练迁移变更」。
> 要演练真实升级，需要用**早于**待应用迁移的备份。
