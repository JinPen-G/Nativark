## 1. 当前结论

当前项目已经是一个功能覆盖较广的**车辆门市租赁 MVP + React 营运端**，但还不是完成通用化的多类型设备租赁平台。

已确认事实：

- 营运端已完全切换为 React 19.2.8 + Ant Design 6.6.0，旧 Vue 源码和运行时依赖已删除。
- NestJS API 当前有 216 个已纳入契约检查的 Controller operation。
- 车辆、网点、客户、企业、订单、费用、调度、报表和平台治理均已有第一版页面和 API。
- 数据层已有 Prisma/MySQL schema、迁移和 seed；示例环境默认把平台底座和旧车辆兼容域切到 MySQL，但完整 MySQL HTTP E2E 尚未验收。
- 内存租户列表和登录上下文已补齐 `demo=摄影设备`、`demo2=露营设备`；旧车辆 fixture 仍与 `demo` 共存，尚待迁入独立车辆样本租户。
- 前端当前主要消费 `/api/store-rental/*` 车辆兼容 API。页面使用“资产、标的、履约网点”等通用文案，不代表后端模型已经通用化。
- 支付、电子签章、通知、TBox、AI 调度和部分文件/打印能力仍包含 mock 或 reserved provider，不能按生产接入宣传。

因此，下一阶段不建议继续横向增加后台页面。应先建立通用租赁内核，防止 React 页面再次固化车辆模型。

| 层 | 当前实现 | 状态与边界 |

| 外部能力 | integrations/files/jobs/notifications/reports | 边界已建立，真实提供方接入程度不一 |
| 验证 | lint、build、React 静态契约、API 契约、报表 fixture | 已通过；缺多租户权限矩阵和真实 MySQL 核心流程 E2E |

## 4. 已确认的产品方向

- 平台面向露营设备、摄影设备、车辆载具、工程设备等多个租赁品类。
- 一个租户只经营一种租赁品类，但可经营该品类下多个商品、资产、耗材和套装。
- 租赁内核必须通用；TBox、车辆调度、工程设备资质、智能柜、物流等作为 capability adapter 按品类启用。
- 租户品类不是普通展示配置。已有业务数据的租户不能直接从车辆切到摄影，必须新建租户或执行显式数据迁移。
- 前端术语、字段、检查模板和能力显示由租户品类决定，但数据正确性必须来自后端通用模型，不能靠字符串替换。

目标核心对象：

```text
TenantRentalProfile -> RentalCategoryDefinition
RentalItemGroup -> RentalAsset / RentalStockBalance
RentalOrder -> RentalOrderLine -> Reservation / Allocation
InspectionTemplate -> InspectionRecord
UsageReading / AssetMaintenance / AssetIncident
FulfillmentLocation + capability adapters
```

## 5. 距离通用设备租赁平台的核心差距

| 缺口 | 不解决的后果 |
| --- | --- |
| `TenantRentalProfile` 与品类定义 | 无法稳定决定租户术语、字段、模板和能力 |
| 序列化资产、数量库存、套装三种库存模式 | 露营数量库存和摄影套装无法正确占用与归还 |
| 多行、多数量订单 | 一个订单不能同时租机身、镜头、灯光或多套帐篷 |
| Reservation / Allocation | 可用性、预占、确认占用和具体资产分配仍混在订单状态里 |
| 通用领取/归还检查模板 | 相机快门、组件缺失、工程安全项无法用车辆验车字段表达 |
| 通用使用量指标 | 里程、工作小时、快门数不能共用车辆里程字段 |
| `/api/rental/v1/*` 通用 API | React 会长期依赖车辆 DTO，后续每个品类都要重复改页面 |
| 车辆兼容 facade | 直接改现有 API 会破坏车辆基线和历史数据回溯 |
| 多租户与 MySQL E2E | 无法证明数据隔离、金额、占用和重启持久化正确 |

## 6. 已实现里程碑：Rental Core v0.1（内存闭环）

已在不破坏现有车辆流程的前提下，为摄影和露营两个样本租户实现通用库存与订单的最小内存闭环。

当前已完成：

- 新增 `/api/rental/v1/*`，所有业务接口从认证用户获取 `tenantId`，不接受客户端指定租户。
- 新增摄影、露营、车辆、工程设备四类品类定义、capability 和动态术语。
- 新增序列化资产、数量库存、套装组成、多行订单、软预占、确认预占和资产分配。
- 新增按品类变化的领取/归还检查模板；完成检查会推进订单并释放资产/库存占用。
- React 新增 `/rental/core` 工作台；`tenant_001` 演示摄影设备，`tenant_002` 演示露营设备。
- Prisma schema 和 `20260813000100_add_rental_core_v1` 增量迁移已生成并通过静态校验。
- 自动测试覆盖租户隔离、套装拆解预占、资产分配、取还检查、数量库存和套装/单品合并需求防超卖。

当前未完成且不能误报为已完成：

- Rental Core 运行数据仍使用进程内存；尚未实现 MySQL repository、执行迁移或补正式 seed。
- 旧 `/store-rental/*` 与 `/rental/v1/*` 尚未共用同一个通用租赁事实源，车辆 facade 仍待开发。
- 异常检查已记录，但异常费用自动入账、附件真实存储、部分归还和套装替代尚未实现。

范围：

1. 新增租户品类档案、品类能力和术语配置。
2. 新增通用标的分组、序列化资产、数量库存和套装定义。
3. 新增多行订单、数量、软占用、确认占用和实例分配。
4. 新增领取/归还检查模板、记录、异常和附件引用。
5. 建立 `/api/rental/v1/*`；`vehicle` 兼容 facade 留到 MySQL 单一事实源阶段。
6. React 新增独立 Core 工作台；原标的、资产、网点、订单页面的切换留到持久化收口后执行。

明确不包含：

- 真实支付、电子签章、短信、IoT 或 AI 自动决策接入。
- 同一租户跨多个租赁品类经营。
- 复杂插件市场或允许租户任意编程的规则引擎。
- 在通用模型落地前继续增加仅改文案的新设备页面。

验收：

| 场景 | 验收结果 |
| --- | --- |
| 摄影租户 | 一单包含机身、镜头和灯光，正确分配序列化资产和套装配件，归还后释放占用 |
| 露营租户 | 一单包含多个数量标的和套装，缺件/清洁异常进入检查与费用记录，数量库存正确 |
| 车辆租户 | 旧 `/store-rental/*` 和 React 主流程仍可用，金额、车辆占用与历史快照可对账 |
| 数据隔离 | 两个租户不能通过列表、详情、导出或动作接口访问对方数据 |
| 持久化 | MySQL 模式重启后订单、占用、检查、费用和审计记录不丢失 |

## 8. 下一次规划讨论需要决定的问题

| 决策 | 为什么现在要定 |
| --- | --- |
| 第一个正式试点选摄影还是露营 | 决定先交付序列化资产深度，还是优先验证数量/套装库存；建议摄影先上线、露营同时作为模型验收样本 |
| 套装是否允许拆分、替代和部分归还 | 直接影响库存、检查、费用和订单状态设计 |
| 一个订单是否允许跨多个履约地点 | 影响订单行分配、物流、结算和权限 |
| 露营/摄影是否需要寄送、上门取送或智能柜 | 决定 FulfillmentLocation 与物流 adapter 的首期范围 |
| 工程设备是否包含操作员、运输和资质服务 | 可能需要服务订单，不应硬塞进普通资产租赁行 |
| 现有车辆租户的数据量和上线状态 | 决定兼容 facade、迁移演练和回滚策略强度 |
| 首个真实外部 provider | 建议在通用订单闭环后按业务价值选择，不与核心模型建设并行扩散 |
