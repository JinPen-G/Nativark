# 管理后台功能审查报告（2026-09-24）

审查基线：`docs/多品类租赁平台需求说明.md`（v4.5）为主，辅以 `客户端小程序需求说明.md`、`租户端小程序需求说明.md`（实为员工履约小程序需求）、数据库 schema 与管理端/API 源码全文核对。共 8 个审查方向、10 项关注点，全部基于只读静态审查，未修改任何代码。

## 总体结论

代码库对需求的落地程度高于典型水平：**启动期门禁、幂等收口、快照不可变、金额入口 applyChargeTo、押金/预授权三本独立账、操作权限默认拒绝、三方密钥加密**等核心纪律均有实现且有测试。但按十个关注点逐项核对后，仍确认了 **18 个高级别问题、约 30 个中级别问题**。最需要优先处理的是：

1. 资金服务中一处**括号错位导致回调金额校验永不执行**（rental-funding.service.ts:334-345）；
2. **分段累进阶梯完全缺失**，里程/水电类价格若配进现有阶梯会整体算错；
3. **报价有效期与未支付保留时间混用一个字段**，直接违反 4.6.2"分别配置"；
4. **企业会员域落地上半段缺失**：企业征信表是孤儿表、开票/合同/授信有 API 无 UI、授权经办人无任何写入入口；
5. **数据权限 organization/own 两档在后端未执行**，配置界面可选但实际不生效；
6. **业务规则 tab 的规则项基本不按品类过滤**，露营空间显示班次、无小时单位的品类显示时租转日租。

## 二、品类接入标准化（关注点 2）

**结论：已形成标准化接入流程，且是本仓库最强项之一。**

- 新品类接入路径明确：在 `packages/shared/src/core.ts` 的 `RENTAL_CATEGORY_DEFINITIONS` 声明术语映射、`assetFields`（scope/type/required/unique/unit）、库存模式、计价单位白名单+默认单位、履约方式/地点类型、检查模板、默认规则、增值服务预设、能力开关；计费新模型走 `rental-pricing-strategy.ts` 独立策略注册。
- 启动期三重门禁：品类编码不重复、引用的计费策略与 capability 均已注册、默认单位属白名单——模块加载期即失败（`rental-core.service.ts:172-173`），并有 `tests/rental-core-v01.test.cjs`、`extension-consistency.test.cjs` 正反用例（含"新增品类不改既有代码"的扩展性验证）。
- 管理端通用页面全部由 terminology/assetFields 驱动，经全量 grep 无品类词硬编码（详见第四节）。

**遗留缺口**：①「自然月」计价单位无单位代码、无实现（有意延后，但未在需求台账登记为范围裁剪，验收时会被当缺陷）；② 品类定义层**未声明"规则项能力"**（哪些规则节适用于本品类），导致第七节所述的业务规则 tab 无法按品类过滤——这是接入标准里缺的一块拼图，建议在 `businessModel` 增加 `supportedRuleSections`/`supportsShiftPricing`/`supportsHourToDay` 之类声明；③ `attributeSchema`（旧）与 `assetFields`（新）双份事实源应合并。

## 六、定价-营销-优惠叠加链（关注点 6）

**结论：三层叠加链实现质量高，未发现计算错误；主要是资格维度覆盖不足与两处口径需确认。**

- **计算正确性正面确认**：层序固定为营销方案→优惠券→会员金额权益（代码顺序即计算顺序）；每层都显式扣除前层剩余基数；三层各自 `min(base,…)`+`max(0,…)` 防负；最大优惠金额三层封顶生效；互斥组按"减免额降序+优先级稳定收尾"择优而非装载顺序；券与方案叠加开关双向校验；最低消费按"商品租金+使用量"优惠前口径——全部符合 4.4.10。
- 6.1（中）**会员金额权益可减免押金/预授权**（business.service.ts:4885-4888），与 `rental-security-deposit.ts:24-25`"本模块不触碰优惠"注释**口径互相矛盾**。需求 4.4.7 允许会员权益减押，实现大概率是有意设计，但必须补注释明确"会员押金/预授权权益是例外，由报价层执行"，否则审计无法自洽。
- 6.2（高/中）**优惠方案资格维度缺 10 项**：计价单位、会员等级、新客/首单、最低租期、领取/归还地点、履约方式、下单渠道、每人次数、总使用次数、总预算（方案层完全没有预算控制，券模板有）。若 4.4.10 资格清单属本期范围，这是覆盖面最大的缺口。
- 6.3（低）互斥组内择优用的是**优惠前 gross 口径**的减免额，与"剩余基数上实际减免最大"在边缘场景可能不一致（组内方案 appliesTo 不同且前面叠加已消耗基数时）。
- 6.4（低）`fixed_amount/threshold_amount` 类型的 maximumDiscount 无 UI 入口（计算层已生效）。

## 七、业务规则与品类适配——重点两个 tab（关注点 7）

**结论：版本化与职责边界做得好，但有 4 个高级别问题：三时限未分离、取消规则颗粒度过低、规则项基本不按品类过滤、逾期缺分级。**

## 九、第三方服务对接（关注点 9）

**结论：三能力七提供方目录齐全、密钥加密与脱敏返回质量高、三条运行链均有真实实现；配置字段对照官方规范无缺失无命名错误。问题集中在证书轮换与对账格式。**

- 正面：支付（支付宝 RSA2 openapi、微信支付 v3 WECHATPAY2-SHA256-RSA2048）、短信（阿里云/腾讯云 TC3）、文件（OSS/COS/S3 SigV4）自拼 HTTP 实现协议正确；AES-256-GCM 加密、summary 只回"已配置"标记；回调验签（±300s、serial 匹配、事件表唯一键+payloadHash 幂等）+查询补偿+退款/关闭（definitive/unknown 错误分类）+对账（SHA-256 哈希幂等+差异人工确认）；出站 SSRF 防护+平台域名白名单；生产环境明确拒绝模拟路径。
