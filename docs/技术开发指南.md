## 1. 技术基线

| 层 | 技术 |
| --- | --- |
| 管理端 | React 19.2.8、React DOM 19.2.8、Ant Design 6.6.0、React Router 7.18.2、TanStack Query 5.101.4、Zustand 5.0.14、Axios 1.19.0、Vite 8.2.1 |
| API | NestJS 10、TypeScript、class-validator、Zod |
| 数据 | Prisma 5.22、MySQL、JSON 聚合快照；Redis 为异步和缓存预留 |
| 共享契约 | `packages/shared` 中的枚举、DTO、品类 schema 和业务类型 |
| 契约与测试 | 自维护 OpenAPI 文档、静态契约检查、Node 测试脚本 |

这是 npm workspaces monorepo：

```text
apps/admin       React 管理端
apps/api         NestJS API 与 Prisma
packages/shared  前后端共享契约
scripts          构建、验证和数据库辅助脚本
tests            底座与业务回归
docs             当前需求、任务、技术和数据库文档
```

## 2. 架构边界

### 2.1 通用租赁内核

`apps/api/src/modules/rental-core` 是新业务的通用内核，API 前缀为 `/api/rental/v1/*`。

当前核心对象：

```text
Tenant -> BusinessWorkspace -> WorkspaceRentalProfile -> RentalCategoryDefinition
RentalItemGroup -> RentalAsset / RentalStockBalance / RentalBundleComponent
RentalQuote -> RentalOrder -> RentalOrderLine
RentalReservation -> RentalAllocation
InspectionTemplate -> InspectionRecord
PricingPlan / DiscountPlan / Coupon / ValueAddedService
RentalRuleVersion / BusinessCalendar
RewardLedger / BenefitAccount / NotificationTemplate
```

`vehicle`、`camera`、`camping`、`construction` 共用以上核心对象。新建跨品类能力必须进入 Rental Core 或通用模块，不得添加只做字符串替换的车辆页面。

### 2.2 旧门市租赁参考模块

`apps/api/src/modules/store-rental`、管理端旧车辆页面和 `/api/store-rental/*` 是历史门市租赁实现，仅保留作业务规则与实现方式参考，不属于新平台目标架构。

- 新页面、新接口和新业务事实不得依赖或写入该模块。
- 不建设 Rental Core 到旧 DTO 的兼容 facade，不迁移或对账旧门市租赁数据。
- 车辆品类同样使用 Rental Core；调度、TBox、驾驶资质等以 capability 形式在新模块中重新建设。
- 未经项目负责人明确授权，不删除历史代码和表，也不得因其存在而改变新平台字段、流程或优先级。

### 2.3 平台管理域

`apps/api/src/modules/platform` 负责 SaaS 租户、组织、账号、角色、权限、参数和初始化。

- SaaS 平台管理员只进入平台管理面。
- 租户管理员的 `*` 只代表当前租户内全权限。
- 一个租户可拥有多个经营空间；每个空间只有一个品类，品类在空间原子初始化时确定，不能使用普通资料接口修改。
- 用户身份归属租户，用户通过成员关系进入一个或多个经营空间；角色和数据范围允许按空间配置。
- 客户主档归属租户，经营订单和权益归属经营空间。

### 2.4 基础设施域

`integrations`、`files`、`notifications`、`jobs`、`database`、`health` 和 `openapi` 提供业务需要的基础边界。未接真实供应商时必须明确标记 `mock` 或 `reserved`，不得宣传为真实支付、通知、签章、IoT 或物流。

## 3. 管理端架构

### 3.1 目录与职责

- `src/app`：路由、导航、Query Client 和全局 Provider。
- `src/components`：应用框架、页面容器和通用交互。
- `src/api`：HTTP client、DTO 适配和租赁 API。
- `src/features/rental-core`：租赁工作台、通用订单和详情。
- `src/features/catalog`：商品、资产和库存。
- `src/features/fulfillment`：经营主体和履约地点。
- `src/features/commercial`：定价、优惠、优惠券和增值服务。
- `src/features/settings`：品类和业务规则。
- `src/features/customers`：个人客户、企业客户和会员。
- 历史门市车辆页面不进入新平台菜单；后续重新建设的车辆专属页面只能在 `vehicle` 品类及对应 capability 下显示。

### 3.2 路由、菜单与权限

路由和菜单的唯一注册表是 `apps/admin/src/app/navigation.tsx`。每条业务路由定义：

- `path`；
- `permission`；
- 可选 `capability`；
- 可选适用品类 `categories`；
- 是否出现在菜单。

页面访问必须同时满足：

`权限通过 AND capability 通过 AND 品类适用`

前端判断只用于体验，后端 Guard 和数据库查询仍需独立校验。

### 3.3 经营空间切换与缓存

React Query 缓存不能跨租户或经营空间复用。登录、退出、会话更换、经营空间切换、上下文不一致或重新认证时，应取消旧请求并清空业务缓存。新增业务查询键必须包含会影响返回结果的 `tenantId` 和 `workspaceId`，不能依靠固定保鲜时间掩盖上下文变化。

右上角经营空间切换器只显示当前账号有权进入的启用空间。切换成功后必须刷新会话、权限、品类、capability、导航和工作台；当前路由不适用于目标空间时跳转目标空间工作台。前端选择值不能直接成为可信业务范围。

### 3.4 Ant Design 规范

- 使用 Ant Design 6 `ConfigProvider`、token 和官方算法，不复制官网品牌导航。
- 框架窗口允许小幅浏览器边距和整体圆角；窄屏贴边。
- 一级页面切换使用工作区上的圆角 `Segmented`，不要塞入内容 Card。
- 面包屑用于定位，可在有并列入口时提供下拉；不要统一复制“大标题 + 小标题”模板。
- 表格保持浅表头、清晰行分隔和可辨识的行操作；筛选和列控制只在真实需要时出现。
- 主题通过 token 实现；不得用大量全局 CSS 覆盖组件内部结构。

## 4. API 与认证

API 全局前缀为 `/api`，`ApiAuthGuard` 是全局 Guard。

### 4.1 请求身份

- token 解码后建立 `tenantId`、`workspaceId`、`userId` 和 `isSaasAdmin` 请求上下文；平台管理接口可无经营空间，租户经营接口必须有当前经营空间。
- 请求入口使用 `AsyncLocalStorage.run()` 建立隔离上下文。
- 缺少租户身份的租户业务请求必须 fail-closed，不能默认 `tenant_001`。
- 缺少经营空间、空间停用或用户不属于当前空间时，经营业务请求必须 fail-closed。
- SaaS 平台接口和租户业务接口必须明确分流。
- 客户端提交的 `tenantId` 或 `workspaceId` 不得覆盖认证上下文；切换空间必须调用专用会话接口并由服务端校验成员关系。

### 4.2 权限

API 权限由路径、动作、经营空间成员、权限码、品类和 capability 共同决定。新增 Controller 操作必须：

1. 定义所需权限；
2. 定义品类或 capability 限制；
3. 进入 OpenAPI 文档；
4. 通过契约检查；
5. 在经营事实 Repository 查询中附带租户、经营空间和数据范围条件；共享客户主档附带租户条件。

### 4.3 DTO 与错误

- 公共枚举和 DTO 优先定义在 `packages/shared`。
- Prisma 枚举与领域枚举在 Repository 边界显式转换。
- Controller 不直接暴露 Prisma 模型。
- 金额使用明确币种和舍入规则；禁止使用前端最终金额作为订单事实。
- 业务冲突返回稳定错误码或可识别错误消息，不能静默降级到演示数据。

## 5. Rental Core 规则

### 5.1 品类与动态字段

品类 schema 决定商品、资产、地点、使用量、资质和检查字段。前端渲染 schema，服务端再次校验必填、类型、枚举和唯一性。

### 5.2 库存

- 序列化：一件资产一次只能分配给一个有效占用。
- 数量：按地点和期间计算可用数量。
- 套装：预占时展开组成并合并相同组件需求。
- 软预占、确认预占、分配、领取、归还和取消必须形成明确状态与流水。
- 生产实现需要事务和并发控制，不能只依靠进程内对象。

### 5.3 报价与订单

报价由服务端根据商品、租期、数量、地点、客户、日历、规则、优惠券和服务计算。订单保存所有版本快照。确认订单时，订单创建、库存预占、优惠券锁定和价格事实必须原子提交。

### 5.4 奖励与通知

奖励、优惠券和通知均需租户与经营空间隔离并保持幂等。营销余额不是资金账户。通知目标必须脱敏，真实 provider 需回执、重试、验签和失败补偿。

## 6. 数据与迁移

- `schema.prisma` 是当前模型定义，migration 是部署历史，两者必须一致。
- 已共享或已应用的 migration 默认不可修改；若项目决定重建预发布基线，必须先确认所有环境可销毁并写入开发任务决策。
- 迁移不得通过无说明的 `DROP TABLE` 丢弃业务数据。
- 任何迁移同时验证空库 `migrate deploy` 和已有库升级。
- 经营空间迁移必须先为每个现有租户创建默认空间，将全部现有账号及其角色关系回填到默认空间，再回填业务表 `workspaceId`；旧行全部可归属且验证通过前不得收紧非空或唯一约束，不得根据品类名称猜测归属。
- Seed 必须可重复执行，不保存明文密码，不依赖固定演示租户作为生产兜底。
- 当前聚合 JSON 快照适用于 v0.1 恢复；生产事实需投影到规范化表并使用事务。

具体命令和安全边界见 `数据库启动与初始化.md`。

## 7. 测试与验收

基础命令：

```powershell
npm run test:rental-foundation
npm run build
git diff --check
```

`test:rental-foundation` 覆盖类型、管理端静态契约、OpenAPI、Prisma schema、Seed 类型、Rental Core、商业规则、快照恢复、SaaS 权限、会员隔离和报表 fixture。

它不等于真实 MySQL E2E。数据库改动还必须在独立测试库验证：

- 空库迁移；
- 已有库升级和数据保留；
- Seed 重复执行；
- HTTP 登录和租户初始化；
- 同租户双经营空间、同账号切换、空间成员权限和缓存清理；
- 同租户共享客户、空间级订单与权益隔离；
- 报价、订单、履约和重启恢复；
- 双租户并发隔离；
- 测试数据安全清理。

## 8. 开发流程

1. 从 `多品类租赁平台开发任务.md` 选择任务 ID。
2. 阅读 `多品类租赁平台需求说明.md` 对应规则和验收。
3. 检查前端、API、共享契约、数据库、权限、审计和测试影响。
4. 先写可验证的领域规则和异常，再补页面。
5. 保留用户无关改动，不覆盖脏工作区中的其他修改。
6. 运行标准验收；数据库任务运行专用 MySQL E2E。
7. 仅更新当前任务状态，不创建分支流水账或重复路线图。
