## 1. 用途与授权边界

未来的两条替换路线相互独立：

- **Agent Runtime：** 自研运行层 → 优先评估 DeepSeek Harness；LangGraph 为备选，以及将来退回自研或其他 Runtime。目标是替换适用的编排驱动及必要适配，而不是业务系统。Harness 的聊天界面、工具展示和插件可纳入复用评估，不等于默认开放其全部功能。
- **Provider SDK：** 原请求编码/解析 → 经验证的成熟 SDK 适配。仅涉及模型协议边界，不要求同时替换 Runtime、Gateway、出网或预算。

这不是必须接入某一框架的决定，也不承诺在途任务可无损热切换。真实包版本、许可证、Node/模块制式、TypeScript、schema 库和 saver 兼容性在实施前核验，不用历史调研版本充当已锁定版本。

**阅读优先级：先读第2B节；其新客户端范围与模型归属以本轮明确选择为准。第2、2A及第3～14节保留原服务器驱动/Gateway/预算/SDK设计，不是本次客户端实施队列。** 业务当前权限、原业务收据、幂等和源码保留仍适用，但不能把服务器模型账、Task/Run/Step或lease强加为每次本地模型调用/对话的前置，也不能将LangGraph机制直接套用为Harness已有能力。

本文件是现行未来接入方案的唯一维护入口；原开源研究归档保留，作为设计参考而非当前施工指令：[Claude 与 Codex 统一方案原文](../../历史归档/整理前快照-20261016/docs/开发任务/附件/AI原生系统文档备份/20261007-开源接入暂缓-943c15ea/开源接入统一方案-20261007-Claude与Codex整合.md)。原文引用的双方研究、历史评分和候选版本只对当时调研有效，不作为现在的完成率、节省比例或依赖锁定结论。

## 2. 不可替换的业务权威与两条路线

> 原服务器托管模型路线参考。下述Gateway/模型预算限制不适用于第2B节已明确的本地用户私有模型通道；业务权限、审批、幂等和数据保护继续保留。

Runtime 或 SDK 都不能替代当前身份/Scope/Guard/ALS、人工批准、Core 事务/幂等、文件/知识 ACL、唯一 Gateway 与预算单账。框架/SDK 专有类型留在适配层，不进入业务工具或公共 DTO。

本节保留原服务器托管模型路线的约束。第2B节本地客户端已明确采用Harness原模型接入，用户自行填写提供商和Key，不经Rental OS Gateway或AI用量账；正式实施前同步原正式依据，不能据方案草案修改当前执行代码。原完整服务器runner也不是客户端登录、模型或普通业务API的必经层。

职责仍须分清：Rental Core及原业务域负责租赁规则、报价、库存、订单和资金事实；身份授权、AI Gateway、AI预算、任务与审批分别复用 Rental OS 已有服务，不把这些全部归为 Rental Core，也不因采用 Harness 另建一套。

Provider SDK 路线尤其保持：

- 唯一 invocation/dispatch 与原 request/run/step、配置/价格/用量证据关联，禁止与旧协议双发或双记账。
- 传输、DNS/地址/重定向、凭据、取消及超时由现有受控层掌握；SDK 默认重试和故障转移不能绕过派发所有权。
- 明确请求/错误/流终态/实际 usage 映射；缺 usage 不补零，丢应答/unknown 不换 ID、Provider 或适配器重发。
- 实施时固定依赖/协议版本，先做不产生真实双副作用的差分；保留原适配器源码与回退路径。

## 2A. 优先候选：DeepSeek Harness

### 定位与已知边界

DeepSeek Harness 与 LangGraph 有重叠，但不是同一种产品。Harness 提供插件化 Agent 循环、会话历史、模型适配、工具执行和 Web 聊天应用；LangGraph 备选方案主要按图编排与 checkpoint 设计。采用 Harness 不自动获得第3～12节设想的全部图分支、子图、时间旅行或 Store 语义，需按真实需求另行核验。

候选资料以官方[仓库说明](https://github.com/deepseek-ai/deepseek-harness)、[架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)、[运行器](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md)、[模型适配](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-an-llm-adapter.md)、[工具管线](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-execution-pipeline.md)和[聊天模块](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/README.md)为准。这些是可变化的上游资料，不是本项目已锁定依赖或接入证明。

上游声明为开发者预览、存在兼容性破坏风险；[安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md)明确未经安全审计、不能视为生产就绪。运行器资料还列出整轮预算及根关闭时终态持久化的限制。正式采用前须重新核验，不能因有会话恢复就推定满足业务多进程恢复。仓库采用[MIT许可](https://github.com/deepseek-ai/deepseek-harness/blob/master/LICENSE)，修改/分发须保留相关声明，另核查第三方许可、品牌/图标及素材使用边界。

### 目标分工与真实接点

| 层次 | 拟复用内容 | 必须保留的 Rental OS 边界 |
| --- | --- | --- |
| 聊天和过程展示 | Harness 的消息流、输入区、工具过程、会话历史及适用附件视图 | 后台 UIArc/品牌、原登录态、公开任务与 Action 合同、当前来源授权；不开放开发者终端或插件市场 |
| 编排驱动 | Agent 循环和适用的多轮/取消/会话机制 | 原 Task/Run/Step、不可变输入、步骤登记、lease/fencing/CAS及累计资源；一个任务只由一个驱动推进 |
| 模型适配 | 注册调用 Rental OS 的 Harness LLM adapter | 所有请求经唯一 Gateway；原凭据、配置/能力、invocation/dispatch、预算和usage收据继续有效，不使用其直连供应商默认路径 |
| 工具管线 | 工具schema、受控注册、执行前检查和结果展示 | 调用原业务工具应用入口，逐次复验身份/scope/地点/对象和风险；Harness 的一次允许提示不等于正式人类批准 |
| 会话持久化 | 适用的 SessionPersistence 和会话事件机制 | 原任务/输入/批准/业务/费用记录仍是各自权威；明确映射和留存，不能把本地会话日志当业务账本 |
| 业务与知识 | 只接已有受权工具、检索及原结果引用 | Core/正式业务服务、知识/文件ACL和人类记忆确认不迁入插件的私有权威；缺依赖仍拒绝 |

目标关系为：Rental OS 入口 → 原当前身份与任务应用合同 → 服务器绑定的单一驱动 → Harness 循环 → 原受控模型/工具执行边界 → 原结果收据及公开事件。不得在 Harness 中再调用完整旧 runner 循环，也不得在旧 runner 内嵌第二循环；按需要提取原单步边界，两个驱动分开消费，旧实现和测试实际保留。未来适配目录可独立认领为 `ai-native/runtime-adapters/deepseek-harness/`，此处只是目标位置，不要求现在创建空目录或接口。

现有 `runner/prisma-task-application.ts` 的 start/resume/continueConfirmation/reconcile/inspect、原输入和审批接口继续作为对外语义边界；Harness 的 create/resume/cancel 只在适配层转换。原 `model-gateway.ports.ts`、Gateway组合及业务工具服务继续消费本系统合同，Harness专有类型不进入shared或业务DTO。**这些是待验证的接入设计，不是已实现Host或可直接调用的适配API。** 若当前Gateway不支持所需的工具轮次、流或输入形状，先形成最小正式契约变更并核验生产者/消费者，不能绕过它直连供应商。

### 会话、任务和提交事实的映射

| 场景 | 必须落实的映射与行为 |
| --- | --- |
| 新建或恢复会话 | 服务器绑定 tenant/workspace/audience/owner、task/run 与 Harness session、引擎/插件/格式版本；列表、读取、订阅和删除均检查当前归属，sessionId不是授权或业务幂等键 |
| 每轮模型调用 | 将实际发送内容、工具schema、输入/配置版本固定到原登记与指纹；多轮、压缩、标题、子Agent等附加请求全部经Gateway与资源/财务门，不能只登记和计量首轮 |
| 每次工具动作 | 先原授权、合法lease/fence、步骤/动作登记和资源占用，再执行；模型tool-call ID不能代替原action/operation或可信dispatch token |
| 等待输入/人类审批 | 先持久化原等待及输入/批准收据，明确解除等待与继续的唯一条件；聊天回复、插件确认或会话resume均不授予业务批准 |
| 已执行但会话落库不明 | 按原action/invocation/业务及费用收据核对；缺usage或结果不明保持unknown，禁止换会话、引擎、Provider或ID重发 |
| 取消、接管、撤权及重启 | 阻止新副作用，传递取消并有界清理；旧会话写入者不得覆盖新持有者。会话结束或崩溃修补不能直接投影为业务成功、回滚或退额 |

优先复用现有MySQL/Prisma及上游正式持久化扩展，是否需要薄适配须在获准实施时核准。事先明确会话事件序号/唯一键、原任务关联、格式版本、写入所有权、CAS/事务顺序、大小/分页上限及保留删除传播；不能把本地JSONL或单进程锁当作多租户多进程正确性证据。原事实与会话不能原子提交时明确每个中断点的只读恢复规则，不承诺框架自动提供跨系统exactly-once。

### 聊天界面和默认工具的复用限制

- 可复用聊天实现或独立界面模块，先核验其插件依赖、React/构建/模块制式、消息格式、主题、无障碍及许可证；不是将单个组件复制后就算完成接入。保留原列表、表单、人工办理和UIArc，不以采用聊天界面授权后台视觉重做。
- 上游Web的启动token/cookie及本地workspace不等于Rental OS用户/租户/经营空间；必须用原服务端身份绑定会话及订阅。iframe或反向代理只解决展示/转发，不能代替授权隔离。
- 使用显式服务器白名单组成业务Agent，**不直接采用默认开发助手工具集**：Shell、任意文件读写、代码执行、终端、任意网络、插件安装/热加载等不向业务用户开放。工具不装载/不具备后端能力，比仅在界面隐藏更重要；最小profile也不自动等于最小权限。
- 按operations/staff/customer/platform映射本系统既有audience及权限，禁止模型自选主体或扩大工具。来源、链接、附件访问和安全页面导航仍由原受权服务及固定Action映射决定。
- 业务卡片和确认入口消费本系统确定性金额/状态/版本/来源，不把工具返回文字、生成答案或聊天绿色完成态当Core结果。微信小程序/网站另按原宿主合同适配，不推定Web聊天组件可直接用于所有端。

### 获准后的采用、验收和退出

1. 锁定上游提交/依赖/插件清单与许可、安全及部署隔离门槛，明确需要复用的循环和UI，不默认引入全部应用、遥测或云服务。Runtime和UI可分开选择，Provider SDK仍独立；不因研究此方案暂停当前自研开发。
2. 先验证一条完整只读订单链：原登录/权限 → 原不可变输入与Task → Harness → 原Gateway/单账 → 原受权订单工具 → 原结果/来源展示。少量有界冒烟及必要类型检查，随后另授权验证真实环境；缺正式依赖不以替身补生产。
3. 集中核验多进程竞争、重启恢复、撤权/换空间、附加模型请求计量、已提交但会话ACK丢失、取消/接管与迟到结果；不得仅验证会话恢复就跳过原lease、unknown和原账语义。
4. 再接正式澄清/审批/受控写入和逐端宿主。只有所需能力与首发验收齐备，才让限定新任务采用新驱动；旧任务原则上由原版本完成或人工核对，禁止新旧驱动双执行作比较。
5. 回退先停止新任务选择Harness，按持久映射处理其在途任务，确认旧驱动支持同场景后再用于新任务。已有unknown不得由旧驱动重发；不得先卸载插件/存储，再推断在途动作未发生。会话与checkpoint不作未经验证的跨引擎强转，清理和迁移另行授权。

采用前仍须补齐实际版本的方法签名、业务驱动解耦范围、存储模型/索引/CAS、公开事件映射、逐场景能力差异和操作回退入口；本文不伪造已实现切换命令、不估算节省百分比、不提升原任务完成率。若安全、稳定性或适配代价不满足要求，保持自研，或重新评估下述LangGraph备选，不因“首选评估”强制采用。

## 2B. 本地客户端转向方案

### 2B.1 结论与首期范围

**目标：基于 DeepSeek Harness 的 Electron 客户端复用完整 Agent 能力，通过工具调用现有 Rental OS 业务 API；云端保留原业务、授权、资金、文件/知识及需要全天候运行的少数服务。不是把原后端完整运行器搬到本地，也不是在 Harness 外再造第二个 Agent 循环。**

本节承接负责人关于“完整 Agent 在客户端、服务端轻量”的方案请求。编排主体转向本机，但服务器身份、业务结果、批准和账务仍是权威。“轻量”指不为每个用户目标再运行一轮智能编排，不指减少业务校验或把数据库下发到客户端。本地 Host 是用户电脑中的 Node 进程，与 Rental OS 云端 API 后端分开命名。

建议首期面向租户经营者/运营人员的 Windows x64 桌面客户端，macOS 后续按同一合同验证；这是排期建议，不自动改变原多端任务。员工微信、客户小程序/预约网站以及 SaaS 平台管理继续保留原入口，不向客户暴露租户经营工具。传统管理网页继续维护，客户端通过既有页面提供人工接管。

首期交付两条完整业务链：

- 当前用户选择订单 → Agent读取受权订单/资金/履约事实 → 给出有来源解释 → 打开原订单页面。
- 用户表达预约目标 → 澄清客户/商品/租期/履约地点 → 查询目录/可用性 → Core正式报价 → 右侧方案 → 人员确认该版本 → 原建单/预约入口 → 展示原业务收据。

本地定时能力先服务于查询、汇总、提醒。通知发送、订单变更、资金或规则发布不因定时器存在成为无人执行动作；按原风险/批准规则逐项开放。平台代付模型、客户渠道和全天候自动执行不得由客户端设置偷偷启用。

### 2B.3 目标架构与权限边界

```text
Rental OS Electron客户端
  ├─ 可信界面：左侧业务/会话；中央Agent对话；右侧业务工作区
  ├─ 传统管理：已有React/UIArc页面与人工操作
  ├─ 本机Host：Harness Agent + 会话 + 调度 + 固定业务工具
  └─ 原登录的受限会话/HTTP适配
          │
          ├─ 业务工具 → 原Rental OS API → 原Guard/ALS/业务服务/Core/收据
          ├─ 平台或服务器托管BYOK模型 → 原Gateway/单账 → 外部模型
          └─ 本地私有BYOK模型（另行批准）→ Harness原模型适配 → 外部模型

Rental OS服务器
  ├─ 原认证、租户/空间/地点/角色与数据范围
  ├─ 原报价、库存、订单、企业授信、支付退款、文件/知识
  ├─ 原批准、幂等、必要任务/调用绑定、审计与账务
  └─ 少数已批准后台任务：客户端关闭后仍必须处理的确定性作业/轻量Agent
```

本机Agent不获取Prisma、数据库密码、平台模型密钥或支付凭据。读取到的订单/文档/网页内容均为数据，不能覆盖系统指令或扩展工具。UI与Host保持进程隔离；preload只公开命名操作，不暴露任意URL/method/脚本/文件路径/IPC频道代理。若使用loopback HTTP/WebSocket，核对监听地址、来源、连接认证、请求大小及生命周期；不把localhost视为天然可信。

服务端不重新规划每个客户端目标，只独立核对调用是否合法以及业务结果。不使用模型填写的user/tenant/workspace/role/approval/usage作为授权证据。服务器原资源配额控制适用的业务/模型资源；本机CPU、工具回合和输出上限另行限额，不用客户端自报耗时作为财务计量。

### 2B.4 模型通道：完整复用Harness，不混同两种计费模式

Harness已有外部模型适配，不需要为客户端再自研一套Provider SDK。**采用哪个通道影响凭据、预算与数据处理责任，不影响Agent循环在本机运行。**

1. **平台代付/既有服务器托管BYOK：保持现行正式边界。** Harness注册一个Rental OS适配器，模型请求走原Gateway，原平台/租户配置、能力、价格和用量单账继续生效。模型/凭据由服务器解析，客户端只能选择服务器公开允许的别名或能力；不能根据图中的模型下拉开放任意模型。标题、压缩、子Agent等实际存在的附加模型请求也要计量，原结果未知不自动重试或切Provider。
2. **本地私有BYOK：可显著减少模型桥接，须另行批准新模式。** 客户端使用Harness现有适配器与本机安全保存的用户密钥，供应商费用由该账号承担，不经过平台代付模型通道。它不同于当前“密钥保存在租户后端”的BYOK；现行所有调用经Gateway规则不能由一个客户端开关绕过。必须先确认商业/预算规则、允许模型与出网、数据处理地区/同意、密钥保管和日志。平台/租户账不得把客户端自报usage认作供应商实际用量，也不能把私有调用伪记成平台结算。原服务端Gateway保留供其他端与服务器任务使用；同一原调用禁止两条通道同时执行。

未批准第二种模式前，实施默认保持现行Gateway/预算要求。本方案不擅自创建本地BYOK枚举、迁移服务器密钥或允许直连；若选择私有客户端试点，可先用获准的测试数据验证Harness原模型适配，再在正式规则中明确与平台账分离。

**当前接点的真实缺口：** [公共Gateway](../../../apps/api/src/modules/ai-native/public-ai-gateway.service.ts)、[内部模型合同](../../../apps/api/src/modules/ai-native/model-gateway.ports.ts)、[输入准备](../../../apps/api/src/modules/ai-native/gateway-intent.ts)和[shared C03](../../../packages/shared/src/ai-gateway-draft.ts)目前主要承接既有场景：消息为system/user/assistant、工具候选主要是订单解释；准备层不提供任意工具schema和完整通用tool-result往返。Public端口是服务端接口，不是已部署的开放模型代理。

如采用第一种通道，只补一个严格、版本化的客户端模型桥，复用现有Gateway，而不强转内部Context/Prisma对象或开放任意供应商代理。明确历史消息、已登记工具schema及结果、流事件、工具调用ID、终态和usage/opaque replayState的映射；服务器组装政策提示和工具许可，历史客户端文字不是新的业务事实。Harness专有replayState留在适配边界，不能随模型切换伪造或绕过数据审查。上游`LlmAdapter.stream`/`GenerateOptions`/`StreamChunk`/`registerAdapter`是复用候选，真实签名须按固定版本核验。

可信输入计数/上界的原缺口不会因改用客户端自动消失。采用原money/tokens计量时仍须正式可信来源；采用本地私有模式也不能把字符估算或本地usage写成平台可信财务事实。

### 2B.5 业务API复用：不新增平行业务系统

**客户端Agent能调用管理后台已经调用的后端API。业务功能以现有接口覆盖为上限；已有API的功能不再建设同名“AI专用实现”。** Agent需要工具说明和结构化参数，不需要执行网页里的React组件来完成API调用。

优先复用[后台API封装](../../../apps/admin/src/api)、[原OpenAPI](../../../apps/api/src/contracts/openapi-document.ts)以及[受权业务工具](../../../apps/api/src/modules/ai-native/tools/business-tools.composition.ts)。客户端新增薄工具适配：输入校验 → 原会话 → 指定API调用 → 安全结果投影 → 原收据/来源；业务校验仍在原服务端。现有只接受“原任务引用”的AI宿主不强行用作通用API入口，也不在客户端套一遍服务器Agent来换取调用权。

工具目录按业务域渐进覆盖全部合法人工功能，而非首轮把整个OpenAPI灌进上下文。按当前身份、空间能力、所处业务域选择可用工具，必要时使用受限的目录发现。接口存在、菜单可见和权限码各自不是执行许可；有对应数据权限才返回结果，每次执行仍由后端检查。

每个工具说明至少包含：原API方法/路径、输入schema、业务含义、前置依赖、数据范围、是否持久化、风险/人工确认、幂等方式、金额/单位/时间、结果与失败/unknown恢复入口。能力按原注册风险分级，不因包装成客户端工具降级；尚无批准提交链或幂等收据的高风险接口先作为人工页面入口，不为了“所有API”直接授权自动调用。

候选覆盖路线（不新增正式工具编号或业务规则）：

| 业务域 | 复用能力 | 必要限制 |
| --- | --- | --- |
| 预约/库存 | 原客户候选、商品目录、可用性、报价与预约/订单创建API | 同名客户需选择；库存/报价只认Core；查询不冒充预占；提交对应准确报价版本 |
| 订单/履约 | 原详情、检查、续租/变更预览及正式办理API | 草稿与检查提交分开，人员确认事实；不可根据模型解释更改金额/状态 |
| 门店/团队 | 原地点、日历、人员和配置API | 只在当前scope；权限/发布等高风险事项沿原管理审批 |
| 财务/结算 | 原收退款/授信/对账只读与人工入口 | 金额不重算；实际处分需原授权/批准/幂等，默认不定时自动办理 |
| 知识/资料 | 原文件上传、知识检索、确认记忆及来源读取 | 用户显式选文件；上传沿原扫描/ACL；本地摘要和缓存不授永久访问 |

不开放`http_request(url,method,body)`、SQL、终端、脚本或模型任意路径。工具内部使用固定API映射；避免靠广泛的通用HTTP工具实现所有业务。附件、文本、HTML/URL只走原安全呈现和固定Action导航。模型生成的总结不替代真实客户/商品/报价/收据卡片。

### 2B.6 登录与管理后台集成

首期复用现有管理后台，不复制所有页面源码，不换React/UIArc，不修改vendor；截图用于桌面信息布局目标，不自动覆盖现有主题规范。传统管理与AI管理不是两个身份系统，也不是同一账号拥有两个独立权限集。

建议在Harness fork中复用其聊天/桌面壳；传统管理初期作为独立、无Node权限的受限视图加载已有后台构建或受信服务地址，后续再按组件能力做更深的同屏整合。右侧工作区使用本端已有适配与业务卡片。上游桌面清单中的React主版本与现有admin不同，不能整仓升级/降级来强拼，也不默认在同一个React根内挂两份运行时。视图隔离是兼容选择，不替代业务权限校验。

[authStore](../../../apps/admin/src/features/auth/authStore.ts)和[http.ts](../../../apps/admin/src/api/http.ts)目前使用window.localStorage、浏览器路由和令牌轮换。不能把这些函数直接require到Node Host就称完成复用。需薄会话/传输适配：原登录/刷新/切空间API继续用，桌面长期凭据仅进入OS受保护存储及可信Host，界面不取得刷新令牌/模型密钥；Web保留自己的实现。避免两个页面/Host并发轮换同一令牌，命令转发必须限定来源、目标和当前代次，不暴露任意HTTP代理。

登出、撤权、切租户/空间时：先阻止该代次新工具/模型调用，中止本次可中止等待，清旧UI及读取缓存，再绑定新身份；迟到响应不能回填新空间。运行中的副作用保留原操作引用供当前有权者核对，不能把登出说成回滚。后台传统API中的自动401重试只在原规则明确可安全重放时沿用；AI写工具/模型未知不能借换令牌换操作键重发。

界面按截图组织：左侧固定域导航与会话、中央任务对话、右侧当前草稿/报价/收据。右侧必须由业务结构化结果驱动，模型不能直接生成任意组件或“确认按钮”。普通读取/导航/无副作用建议不机械弹确认；R1持久草稿、R2/R3执行按原登记风险及批准规则办理。当前截图示例数据不作为报价、租期计算或金额规则基线。

### 2B.7 调度与服务端轻量Agent

上游固定提交的调度合同已确认：`ctx.schedule`持久任务、支持单次/固定间隔/日历/cron；到期将保存的任务指令投递到原会话，必要时恢复冷会话，再由Agent调用工具。它不是直接执行任意API的cron守护进程，也不是业务提交服务。

本地首期可做“每早读取今日订单并汇总”“定期检查当前有权门店的待办并提醒”。简单固定查询可直接使用业务API和确定性规则，需要解释/规划时再调用模型；不为了显示Agent能力给每次轮询追加模型费用。Agent创建或修改定时任务要让人员确认目标、scope、频率/时区、允许动作及停用方式；用户安装客户端不等于批准持续读取或自动写业务。

调度限制：

- 客户端Host/电脑必须运行；隐藏或关闭界面与退出Host须分别定义。首期建议关窗口退出或明确提示托盘继续，不静默让敏感任务留后台；电脑休眠、离线或退出期间不承诺执行。
- 上游周期补跑只投递最后一个过期触发，不积压每个漏跑周期；这是提醒策略，不证明业务无重复。客户端UI明确补跑/跳过，业务写入不能默认批量补发。
- 投递收据只证明会话消息保存。存储窗口可能重复投递，因此按任务修订和计划触发点去重，并让写业务继续使用服务端幂等/审批；不用自造随机键绕过重放。
- 删除计划不撤回已经投递的消息或在途操作；运行前复验本计划仍启用、原用户/空间/工具政策及商业额度。暂停/登出后不得以恢复会话重授旧权限。
- 首期一个计划绑定一个明确客户端执行者。多设备复制计划先保持关闭，不能依赖本机锁防止两台电脑重复业务动作；团队共享/跨设备计划需要服务器固定原触发或业务去重依据，另行设计而非另造第二调度器。

服务器保留原已批准Outbox、到期作业、支付回调/对账和通知等确定性职责；它们不是需要搬到客户端的Agent功能。仅对确实要求7×24、没有任何客户端在线也必须运行的少数任务，使用原服务器作业/轻量Agent及独立自动主体政策。不要一开始为了覆盖桌面退出再建设与客户端完全相同的全功能云端Agent。

| 自研`runner/ai-task-runner.service.ts`、`runner/prisma-task-application.ts`及场景完整执行组合 | 保留源码、测试、已登记旧任务；停止将其作为新客户端必经编排的扩建建议 | 原任务善后、旧端与已批准后台场景；客户端仅复用必要原单步/收据边界 |
| 后台`features/ai-native`、`app`、`api`、UIArc | 保留并做桌面适配 | 原设置/预算/能力/任务观察可继续用；新对话不机械要求走旧start→runner |
| `aiTask`/`aiRun`/`aiStep`/invocation/资源与财务存储 | 保留数据及真实约束；映射按实需补 | 业务调用绑定/原累计资源和审计仍在服务器；本机会话不是第二业务任务权威 |
| Outbox/原作业与其他Web/微信端 | 原样保留 | 不随桌面切换停止必要服务器责任或扩大客户端权限 |
| 已有验证、迁移、修复WIP及output | 全部保留，不改断言变绿 | 定向验证可复用；没有提交/真实环境证据的成果仍如实区分 |

**建议暂停扩建的对象：** 新客户端用户目标的自研通用规划/循环、服务器与Harness重复的会话/定时模块，以及只为旧完整执行宿主服务的额外包装。安全、数据完整性、API恢复和已发生副作用善后不能因“暂停扩建”停止维护。方案本身不发出当前停写指令；正式主线排期由负责人确认后更新。

实现前在原受控任务/动作结构中核对是否足以绑定本地session、本单执行者、引擎/插件版本和原operation。足够就复用，不新建同义表；不足才提出最小增量字段/契约。原lease/fence由服务器发放和验证，客户端不能自造；它限制并发业务执行，不让后端重新负责智能规划。聊天投递序号、模型tool-call ID与业务幂等键分开，恢复时不随重新生成文本更换原动作。

### 2B.9 迁移顺序与验证门

以下是本方案的实施阶段，不是新增AIN任务编号/分母，也不声称已进入某阶段。逐阶段收口，复用现有定向用例，每个完整切片一次必要冒烟/类型检查，失败仅复验受影响范围；不为迁移建立大批重复测试脚本。

1. **保全与正式转向。** 核对实际树/HEAD/index/WIP归属，保全全部源码、迁移、失败证据与未跟踪产物；不reset/clean或用一个大提交夹带所有WIP。负责人确认桌面目标、模型通道及范围后，最小修订正式需求/任务和唯一接续，旧历史保留、原验收不降门槛。当前百分比不换分母重算，也不把框架已有功能记为Rental OS已完成。
2. **固定Harness fork与最小产品配置。** 建议使用单独客户端仓库保留上游pnpm工作区/lockfile，Rental OS仓库继续维护API和admin；不把上游整个工作区塞入现有npm workspace，不把产品fork变成新通用平台。固定上游版本、许可、产品标识、允许插件及安全配置。不得默许首次启动下载/安装工具、外部遥测或读开发者密钥。
3. **桌面壳与原人工后台。** 先接原登录、空间、受限传输、传统页面和UIArc；验证切空间/登出/401/迟到结果及安全渲染。保留Web行为，不为了桌面改坏原后台。新客户端仅开发运行验证不算签名安装/更新验收。
4. **完整只读Agent。** 直接复用Harness循环和选定模型模式，加载最少订单/目录读取工具，走原身份/API。验证模型正常文本/工具往返、权限拒绝、取消、预算/资源上限及原操作核对；必须取得有来源结果，不把正确拒绝当正向交付。
5. **预约目标闭环。** 复用原目录、库存、客户候选、Core报价、原批准和建单。右侧方案与确认准确绑定报价/对象版本；库存或身份变化重确认。确认与建单分别展示，ACK丢失只读原键收据，不重新建单。
6. **本地定时查询与提醒。** 复用原schedule服务，先只读，验证显式计划授权、频率/时区、休眠/补跑、重复投递、删除后已入队、登录过期及换空间。需要7×24的少数任务再按业务依赖配置服务器执行，不扩成双重Agent循环。
7. **渐进业务覆盖与正式交付。** 按工具目录覆盖订单、履约、门店、财务只读及获准写入；不一口气给所有API自动权限。分别取得真实后端/供应商、桌面宿主、签名安装/更新与目标平台证据，确认后灰度发布；原Web/微信仍按其原任务独立验收。

发布验证还包括包内无生产密钥、Node/preload权限、loopback鉴权、插件包图、日志脱敏、签名/更新渠道、客户端协议与API兼容版本。更新前停新动作并确认旧Host退出；不能只重启UI后让两个Host重复执行，也不能将更新中断当业务回滚。

### 2B.10 取消、原任务与回退

- 本地对话、任务草稿和选定材料可以保存于按API环境/账户/tenant/workspace分区的本机存储；由用户明确选择的本地文件只向批准工具开放。原业务、批准与财务收据继续在服务器，本机日志不得冒充结算依据。
- 本地缓存存在无法保证即时在线撤权的固有限制：在线取回正文逐次核权，登出/切空间清理；离线只允许经批准的非敏感本地草稿，不默认离线浏览全部客户/订单历史。落实原保留期限、加密/删除与备份责任，不能因数据在本机就放弃政策。
- 客户端关窗/退出/取消只停止本地新推进；已发模型/业务请求可能完成。下一次进入先核对原收据，未找到仍unknown，不换ID/客户端/Provider重做。
- 新旧驱动按新任务分流。旧服务端任务沿原版本完成、取消或人工核对，不直接把checkpoint转成Harness session；客户端的新任务也不因崩溃自动转给旧runner重跑。
- 首期不做运行中任务热迁移。确需交给服务器时先冻结本地推进，核对所有原动作/账务，服务器以原绑定和CAS取得唯一执行权；完整交接能力未验前只提供人工接管。
- 回退只停止创建新的客户端Agent任务，传统管理仍可用。已派发/unknown保留原收据核对通道；旧服务端执行只用于原本已支持且受权的新任务，不重发客户端未知动作。卸载/清数据不能先删除唯一未决引用。

### 2B.11 批准前需要确认的最少事项

1. 桌面首发对象/平台：建议租户经营者及运营人员、Windows x64；不自动扩大到SaaS跨租户或客户全工具。
2. 模型通道：沿用现有平台/服务器托管BYOK，或另行批准本地私有BYOK及其计费/数据政策。两者不能用同一账务承诺混同。
3. 桌面退出与调度：首期一个计划一个客户端，明确关窗/托盘/休眠与漏跑策略；哪些少数业务确需服务器全天候执行。
4. 首条业务：先订单只读，再预约确认闭环；“全部业务API”是渐进覆盖目标，不等于首发无人执行所有动作。

本方案不估算源码复用百分比、节省工期或上游安全成熟度。正式实施前仍需验证接口/依赖和实际缺口；开发记录与原任务验收保留，不将候选fork、UI相似或模型能回答当交付证明。

### 3.1 将来获准采用时的分工：通用机制与业务控制分离

以下第3～12节保留LangGraph路线的既有设计，作为备选和历史技术参考，不是Harness接入指南或当前采用决定。获准采用该备选后才按其专有机制实施；业务控制复用 Rental OS 正式服务。既有自研成果实际保留，不让两个驱动同时推进同一任务。

| --- | --- | --- |

### 3.2 实际保留要求

1. **旧自研驱动与直接测试实际留在源码树中，不以Git历史、压缩包或“以后可恢复”替代。** 不删除旧runner、恢复、输入、协议及业务实现。
2. LangGraph驱动放在独立适配目录；建议`ai-native/runtime-adapters/langgraph/`，这是待认领的目标路径，当前没有在此建空壳。
3. 原自研运行路径不能依赖LangGraph包、checkpoint类型或消息类型，不能被改成只调用LangGraph的空包装。停用LangGraph后，原路径应仍能独立编译与运行其已支持的能力。
4. 共享的是授权、登记、受控动作、结果/资源收据等稳定服务，不共享一个隐藏的“第二编排循环”。如需提取原单步逻辑，保持原顺序和语义，由两个驱动复用；提取前核对并保全固定版本，旧驱动仍须通过其原测试。
5. 不为保留两条路径复制Core算法、批准服务、业务数据库或预算账本。旧源码保留不等于旧worker与新worker对同一任务同时执行。
6. 每次框架接入或退出都记录实际修改路径、固定提交、依赖锁版本与验证；本文中的“建议/待实现”只能在有代码和证据后改成“已实现”。

  → 当前授权 / 原登记 / 原资源证据 / 原批准与Core / 唯一Gateway

### 4.1 未来实施的内部接口表

这张表把“替换运行层”落到现有入口；目前只记录目标适配，不新增空接口。

| 操作 | 现有自研入口 | 未来LangGraph适配入口 | 权威写入/返回约束 |
| --- | --- | --- | --- |
| 首次启动 | `PrismaTaskApplication.start({taskId,runId})` → `AiTaskRunner.run/runPrepared` | `LangGraphRuntimeHost.start`（目标） | 服务器解析当前task/run、claim合法lease；图只能在已持有lease和非空plan后启动 |
| 输入后继续 | `PrismaTaskApplication.resume(value)` → `PrismaTaskInputRepository.submit` → `start` | `LangGraphRuntimeHost.resumeInput`（目标） | 先提交/读原输入receipt，再以原inputRef/inputHash/planHash恢复；重复receipt只读 |
| 确认后继续 | `PrismaTaskApplication.continueConfirmation({taskId,runId,checkpointRef}, signal?)`及原批准/submit组合 | `LangGraphRuntimeHost.resumeConfirmation`（目标） | 原入口读取 phase receipt，要求合法已持有 lease；批准消费仍由业务执行边界复验，interrupt 值不授批准 |

| 恢复/核对 | `PrismaTaskApplication.reconcile`、`AiTaskRunner.recover`、effects.reconcile/readInterrupted | `LangGraphRuntimeHost.reconcile`（目标） | 只读原action/invocation/business/charge receipt；无证据保持unknown，不新发副作用 |
| 检查/事件/输入读取 | `inspect`、`readEvents`、`readInput` | 稳定应用合同继续复用 | 对外不暴露LangGraph state/thread；按当前读权限和scope返回本系统DTO |

目标Host只接受服务器构造的稳定命令和受权上下文，不接受客户端driver、threadId、lease、fencingToken、policy成功标记或任意图节点名。未来适配器负责把LangGraph的`invoke/stream/interrupt/resume`转换为表中入口，不把框架类型泄漏到shared/OpenAPI/业务工具。

### 4.2 当前入口与未来驱动的唯一组合位置

目标组合顺序如下，先满足现有业务边界，再选择运行器：

```text
request-bound/application
  -> current Auth/Guard/ALS and scope resolver
  -> task/input/proposal/approval authority
  -> engine binding (server-owned)
  -> self-hosted runner OR LangGraphRuntimeHost
  -> common step/effect/resource/result ports
  -> original Gateway / Core / business receipt / public event
```

不得在`model-input`或业务场景内直接import LangGraph；不得在LangGraph节点中调用完整`AiTaskRunner.run`；不得在旧runner中再嵌套一个图循环。未来若需要从`AiTaskRunner.runHeld`提取单步边界，应单独固定提交并让原runner先继续通过原测试，再由两个驱动分别调用该边界。

## 5. 执行权、版本与状态权威

本节为目标约束，绑定模型和切换API尚待实现。

- 在首次执行前，服务器为任务固定engine；run固定driver/graph版本、输入版本和checkpoint格式版本。持久绑定必须覆盖scope/task/run，读回精确核验；请求体、threadId或模型输出不能选择引擎。
- 建议任务级engine保持不变，避免同一任务预算与业务动作在两种引擎间隐式迁移；如实际业务确需跨engine接续，必须单独设计显式迁移记录，而不是改一列engine后重跑。
- LangGraph负责下一节点、分支、图状态与检查点调度。原lease/fence/CAS仍控制业务执行资格；不能保留两个互相独立推进同一run的调度循环。
- 图检查点负责图内部进度；原数据库中的task/step、输入、批准、业务与费用收据继续负责各自事实。公共状态从已核验事实投影，不能直接把图结束投影成“订单成功”。
- 回退只改变新任务采用哪个已就绪引擎；已派发任务仍绑定原engine及版本，直到完成或进入受权人工核对。

| 系统状态/事实 | LangGraph侧处理目标 | 始终保留的约束 |
| --- | --- | --- |
| QUEUED / RUNNING | 首次invoke及图运行 | 先合法claim/准备/登记；检查点不能伪造RUNNING或执行许可 |
| WAITING_INPUT | 持久interrupt，消费正式输入收据后resume | 重复答案收据不再继续；新输入不覆盖旧冻结 intent/plan；图内继续或新 run 的映射须显式设计 |
| WAITING_CONFIRMATION | 持久interrupt，复验真人决定后显式继续 | 普通聊天/resume值不是批准，批准不等于Core提交 |
| WAITING_EXTERNAL / UNKNOWN | 停止新副作用，按原ID只读核对 | 缺收据不当作未执行，不新建action、invocation或另收费重试 |
| CANCEL_REQUESTED / CANCELLED | 停止新节点、传AbortSignal、保留已观测结果 | 不宣称远端回滚，不删除已提交业务或费用事实 |
| SUCCEEDED / PARTIALLY_SUCCEEDED / FAILED | 根据原步骤/业务/资源证据形成终态 | 节点return或图END本身不是业务和费用完成证明 |
| 输入/批准/operation receipt | 图中只存有界引用及版本/hash | 原数据库保留不可变事实，框架状态不签发批准或替代业务收据 |

上述映射不是枚举一一强转。特别是UNKNOWN可以同时存在已观测业务成功与待核对费用，不能被框架一个异常状态覆盖。

## 6. checkpoint存储与重入合同

### 6.1 存储选型与需要落地的结构

优先沿现有MySQL/Prisma；先核准维护中的JS saver是否适配选定发布版，不宣称已有合适候选或必须从零实现。若需要薄适配，只实现其持久化协议，不复制框架调度算法。

正式DDL前须明确以下逻辑对象、字段类型、主键/复合FK、索引、大小上限和保留规则：

- 任务/run的engine与graph/schema版本绑定。
- checkpoint：服务器派生的thread标识、namespace、checkpoint ID、parent ID、typed payload、metadata、channel版本。
- pending writes：框架内部task/write序号的稳定复合键；不得与Rental OS task/action ID混用。
- head：原run/fence/revision条件下的CAS推进；旧holder不能写入可被新holder误采纳的head或pending writes。
- 所有读、列举及删除都走当前scope权限；不只在invoke入口检查一次。不把Bearer、活跃lease、服务实例或任意大段敏感正文序列化进去。

旧研究提到getTuple/list/put/putWrites/deleteThread；**实际方法、参数、分页、序列化及删除协议以锁定发布包为准**。内存saver只用于库级验证，不能冒充跨进程恢复。

### 6.2 副作用与检查点不能原子提交时

必须明确每一步真实提交顺序：当前授权与lease → 原步骤/调用登记和资源预留 → 实际动作 → 原结果/usage/业务收据 → 框架checkpoint → 公共状态投影。

框架和Core/Gateway未必共享事务，因此以原动作标识及收据实现重入核对，不许声称LangGraph自动提供跨系统exactly-once。

- 动作已提交而checkpoint未确认：重入按原action/invocation/operation查证据，不重发。
- checkpoint引用不存在或不一致：保持unknown/阻塞，不能用重新执行“修复”。
- checkpoint写ACK丢失：查原checkpoint ID/hash；不生成新的动作实例绕过未知。
- 节点重试不生成新业务操作ID；真正的新调用须有新受权输入/登记和原预算准入。模型多轮不能藏在只登记一次的节点里。
- 自动重试、缓存、流式终止行为必须按实际库验证；默认不允许对不可确定业务副作用盲重试。

## 7. 能力对照：保证可替换，不夸称一键等价

| 能力 | 未来对接与回退约束 |
| --- | --- |
| 串行计划与受控步骤 | 两个驱动分别调用同一稳定业务边界，先验证行为等价 |
| 持久恢复、取消、资源上限 | 映射原 receipt/unknown/fence 与累计资源，不只恢复图 JSON |
| 确认等待与批准后阶段 | 保留原 phase、批准消费及累计资源；不能用 interrupt 绕过审批 |
| 澄清与多轮输入 | 明确继续当前图或新 run，保持不可变输入、父预算与动作谱系 |
| 流式与公开任务事件 | 框架事件转换为稳定公开合同，不暴露内部节点或敏感上下文 |
| 分支、并行、子图 | 登记、资源、lease/fence、汇合和原线性计划边界必须适配；退回不支持的驱动时拒绝，不静默改变语义 |
| 节点缓存、历史/分叉 | 当前权限、版本、输入与费用参与边界；不能回滚/重放支付订单实现“时间旅行” |
| 跨任务记忆 | 复用正式偏好确认、知识/文件 ACL 与留存政策；图 Store 不授业务权限 |

逐项记录“自研支持 / LangGraph适配支持 / 已验范围 / 不支持时拒绝”，作为未来替换入口的能力门。不能为了宣布完整使用LangGraph，把所有高风险能力直接公开给客户端。

## 8. 正向转接：自研到LangGraph

获准施工后按以下顺序执行，当前不自动执行：

1. **确认基线与归属。** 获准实施时固定届时实际源码、依赖与在途任务版本，保全 WIP；逐项核验共用业务服务与恢复合同，不照旧快照重复开发，也不追辅助活动 HEAD。
2. **核准真实依赖。** 选定LangGraph.js/core/checkpoint版本，验证许可证、生产Node、CommonJS、TS和Zod兼容；现有根配置为CommonJS、API声明Zod3，不能照抄历史候选版本或升级全仓迁就框架。
3. **落定执行边界与存储合同。** 完成本手册第4～6节的真实接口、数据模型及调用顺序；同一run只能有一个driver，checkpoint格式与业务事实分开。
4. **最小只读纵向。** operator/workspace订单解释→真实原输入→图节点→唯一Gateway→原artifact/单账/事件；不是在旧executor里套一次图就宣称完整迁移。
5. **验证持久恢复与受控中断。** 原动作提交后checkpoint失败不重发；正式输入/批准收据才允许继续。只读通过不意味着通知设置、客户、automation或订单写入已全部接通。
6. **新任务显式采用。** 完成服务器engine绑定后再放行限定场景；旧任务留在旧engine。没有实际在途数据证据，不擅自编写/执行历史数据迁移。
7. **逐步扩展。** 再接澄清、确认写入和必要分支/子图；Provider替换不作前置。每项能力回写第7节和实际接口表。

## 9. 反向转接：停用LangGraph，回到自研或其他Runtime

### 9.1 默认安全路线

1. 在可信服务器入口停止新任务选择LangGraph；**切换配置/接口尚未实现，不能现在给出虚构命令。**
2. 按持久engine绑定列出该引擎的在途任务和版本。此列表必须当前授权，不能靠遍历checkpoint猜任务归属。
3. 已运行任务继续由锁定版本LangGraph完成或只读核对；未知/可能已提交任务不得交给旧runner重新执行。不能先卸载包再处理在途任务。
4. 用第7节能力表确认自研驱动已支持待切场景；不足就实现所缺能力或保持该场景不可用，不能把图分支偷偷改成线性流程。
5. 将新任务绑定到自研engine，保持原外部API、授权、输入/批准/业务收据和单账不变；先一个限定场景验证，再扩大。
6. 通过最小同语义验证后停止LangGraph的新增维护/默认装配。依赖移除、数据清理另行批准，全部旧源码/测试及必要版本记录继续实际保留。

### 9.2 不做隐式检查点转换

LangGraph的channel版本/pending writes/内部节点任务不能直接塞入旧runner的plan或手写step状态。若必须迁移在途任务，应另立显式转换工具和映射版本：限定可迁移的安全边界、验证全部原动作/费用收据、CAS锁定唯一所有者、留下迁移记录并保留原checkpoint；不满足条件保持原engine或人工核对。

**“可快速更换”是能按固定边界替换新任务的驱动，不是任意时刻无损热切换所有在途任务。** 目前没有实现跨引擎在途转换工具。

## 10. 最小验收与回退判据

复用原场景/runner测试，不每片新增矩阵或大量脚本。库级、离线组合、跨进程持久化、真实DB/模型/宿主证据分别记录。

集中验证至少覆盖：

- 一个真实只读纵向，原输入/动作/输出引用一致，模型派发及账本各只有原有一条路径。
- 一次持久中断/正式人类输入或决定/继续，重复收据不重跑，凭据与当前权限重新校验。
- 一次动作已提交但checkpoint写未确认的恢复，只读查原收据，无第二次业务调用或扣费。
- 旧holder迟到、取消或撤权时不推进新副作用；公开事件和正文也不泄漏。
- 同一原场景分别绑定两种driver，输入、结果/错误与费用语义可比较；**禁止双驱动并行执行真实副作用作对照。**

发现重复派发/收费、checkpoint越权或fence绕过、旧图版本被热替换、unknown被假成功覆盖，立即停止新任务采用新引擎，保留原事实并核对；不通过删记录/换ID/重跑掩盖。

## 11. 正式实施前仍需细化的设计

统一方案的单驱动、保留Core/审批/单账、Provider独立、失败语义和首片选择已纳入本文；本文仍是准备性设计，不能直接当最终施工任务书。

正式实施前至少补齐：

1. 届时的实际接口、在途任务和共用业务服务基线；明确哪些驱动能力可映射、哪些必须保持原引擎或拒绝迁移。
2. 可替换驱动与原单步边界的具体文件、方法签名、依赖方向和唯一维护者；不能只写“适度提取”。
3. 第5～6节的完整状态/动作身份映射、真实saver合同及Prisma模型/索引/CAS事务设计。
4. 线性不可变plan到图分支/多轮的合法登记方式；当前maxConcurrent=1、budget指纹含run/steps的约束如何兼容，不能只放宽数字。
5. 已核验依赖版本与实际加载证据；历史版本只作候选，不是锁定结论。
6. 每一迁移片的输入/消费者/允许改动文件/完成出口，以及第8～10节的正反向切换和验收入口。

这些补充以实施需要为限，不另写泛化框架调研或用文档数量替代功能。Provider方案保留，但不夹带进本轮LangGraph必做清单。

## 13. Provider SDK 独立接入与退出

本节整理原统一方案中比 Runtime 手册更详细的协议接入边界。它与第8～9节的 Runtime 切换互不作为强制前置，不要求同时改造两层。

### 13.1 目标接法与选型

优先评估 SDK 的低层 Provider 协议适配；只有正式功能确有需要时再评估其高层 Agent/生成循环，不因采用 SDK 增加第二个调度器。

目标链路：

```text
现有 Gateway / 单账 / 原派发所有权
  → 原 RoutedModelTransport
  → SDK ModelAdapter（未来适配层）
  → 显式 Provider 实例
  → 受控 fetch 桥
  → 原 ModelEgressTransport
```

以上是目标适配关系，不表示 SDK 桥或该组合已实现。凭据、BaseURL、模型、配置修订和能力都来自现有可信配置；SDK 不得隐式读取环境密钥、选择云代理或从模型内容解析连接目标。

ModelEgressTransport 不是 fetch 签名，不能用类型强转假装兼容。未来桥接须按锁定 SDK 的真实调用协议处理 Request / Response / ReadableStream、必要响应元数据、背压、AbortSignal、iterator return 和总 deadline，不为适配开放任意出网能力。

### 13.2 传输、派发与计量合同

- 保留原 DNS/地址审查、固定连接 IP/TLS、URL/method/header 白名单、重定向政策、响应字节限制和取消边界。不得回退 global fetch，或隐式执行媒体下载、遥测与其他外部请求。
- 一次合法派发只能产生其允许的实际请求；高层自动重试、故障转移和自动工具调用须关闭或由原边界明确受控。低层 API 也要核对真实请求次数，不能只检查高层重试参数。
- 保留 invocation、dispatch、reservation 与 request/run/step、actor、scope、配置和价格/usage 证据的关联；SDK 自有请求或 tool-call ID 不能冒充供应商返回的可信关联。
- token/call/money 分离，缺失或不完整 usage 保持 unknown/reconcile；SDK 补零、估算值或派生统计不能直接作为实际结算证据。
- 明确 provider 错误、流中 error、缺 finish、截断、取消及敏感内容回显的映射。收到文字不等于流完整、业务成功或可以结清预算。
- 派发前失败仅按原证据决定是否释放；派发后不明保留原操作核对，不换 SDK、Provider 或 ID 重发。

### 13.3 独立实施与回退门

1. 获准后锁定候选与依赖，完成第14节兼容核验；不因此改公共 DTO 或同时迁移 Runtime。
2. 对原 ModelAdapter 合同实现最薄桥接，保留现有出网、凭据、能力、取消和单账；不另建 Provider 派发许可或钱包。
3. 复用原契约入口做有界离线组合，检查编码/解析、流终态、请求次数、取消、usage 与关键拒绝路径。替身通过不等于真实供应商通过。
4. 取得外联及环境授权后，再在限定场景核验真实协议兼容性；同一调用禁止新旧适配器真实双发作对照。正式开放另行验收。
5. 回退时先停止新调用选择新适配器；已派发或 unknown 调用按原绑定完成或核对。保留原适配器、版本与收据，不能用旧适配器重发原未知调用。依赖移除和数据清理需另行批准。

## 14. 候选复核与未来实施范围

DeepSeek Harness 是 Runtime 的优先评估候选，LangGraph.js 为备选；两者均不是已批准依赖或已接入能力。Harness的聊天界面/插件可纳入复用，但与LangGraph图机制不做同名替换或一一等价承诺。Provider SDK候选仍单独选择。官方资料只能支持初步判断，实际发布包、传递依赖、许可证及加载/出网行为须在获准实施时重新核验；不以本文调整表示已验证运行或生产可用。

正式采用前逐项确认：

- 实际发布包、公开导出、维护状态、安全风险、许可证/NOTICE 与使用或局部复用时的保留义务。
- 生产 Node、CommonJS/ESM、TypeScript、schema 库及传递依赖的实际兼容。优先局部适配或适当版本，不整仓转 ESM 或升级基础设施迁就示例。
- Harness须核验会话持久化、事件/模型/工具协议、写入所有权与任务映射；如采用LangGraph备选，再核验JS checkpoint saver的序列化、pending writes、分页、并发、删除和恢复合同。优先现有MySQL/Prisma；仅在确有需要时补薄适配，不把两种存储协议混为一谈，不因研究有限就宣称没有开源实现。
- 框架/SDK 默认重试、缓存、追踪、云代理、自动工具/媒体处理与出网行为。以实际版本验证，不能依赖未经核实的默认值。
- 首个迁移切片的完整输入、真实消费者、当前权限、提交点、原收据、计量和回退出口。建议仍从当前合法 operator/workspace 的只读订单解释开始，不报价、建单或处分资金，不默认开放其他 audience。

未来功能可分片验收，但持久恢复、授权和副作用未知语义不是上线后再补的欠项。Runtime 与 SDK 均不得引入第二任务/审批/知识权威或账本，也不为“采用开源”顺带增加托管平台、队列、向量库或其他基础设施；确有正式需求时另行说明与授权。

当前开发只保持真实需要的稳定服务边界和必要说明，不建空适配层、不提前复制框架 API、不为未来迁移暂停原核心功能。接口或耦合实质变化时更新本文相应设计；功能进展和关键提交仍只进入现有协作接续/开发记录，不恢复逐片迁移论文或历史派工模板。
