# AI Native：通用 SaaS 底座与行业模块分离方案

文档版本：v1.0；日期：2026-10-16。文件名保持稳定，版本和状态只在正文维护。

> 文档分类：未来规划／设计方案，尚未启动抽离实施。目标是将可复用能力逐步整理为可独立接入、未来可开源的 AI Native SaaS 底座，Rental OS 是第一个业务宿主，Rental Core 是租赁行业模块。
> 本文不替代[正式需求](<../AI Native-需求.md>)和[开发任务](<../AI Native-开发任务.md>)，不新增本期任务、不改变原28项及 ENTRY 的范围、依赖、分期或百分比，不授权拆库、拆服务、迁移、发布或开源。
> 当前仍以 Rental OS 的真实业务闭环为主。本文只维护目标、接入边界、前置条件、抽离与回退方案，不记录当前 HEAD、派工、开发流水或完成率；实际现场见[协作接续](<../AI Native-协作接续.md>)，阶段成果见[开发记录](<../AI Native-开发记录.md>)。

## 产品目标

未来其他团队能够接入自己的身份、权限、业务工具及正式执行服务，复用目标理解、任务推进、模型调用、预算、确认、恢复、知识和审计能力，不必依赖租赁订单、品类、库存或资金规则。

底座帮助用户和受权自动主体将目标推进到结果；具体业务仍由宿主自己的正式服务决定。它不是万能聊天接口，也不是允许模型运行任意代码或直接操作数据库的平台。

目标不要求外部团队替换现有登录、组织、订阅、文件或支付系统。可提供随底座使用的公共 SaaS 实现，也应允许通过可信适配复用宿主已有能力；不为此在本期重复建设第二套权限、客户、订阅或支付服务。

## 三类能力的边界

| 层次 | 负责内容 | 不应承担 |
| --- | --- | --- |
| SaaS 公共能力及宿主接点 | 租户/组织、当前身份与权限、权益、文件、通知等公共服务；允许按明确契约接入宿主实现 | 把租赁会员、企业租赁资格、车辆或品类政策作为所有业务的必选模型 |
| AI Native 通用能力 | 唯一 Gateway、模型路由、Task/Run/Step、受控编排、预算计量、提案/确认、恢复、知识/记忆及审计机制 | 直接决定行业价格、库存、资格、资金、责任或业务状态；自行授予业务权限 |
| 行业模块与宿主应用 | Rental Core、租赁事实/报价/履约工具、场景政策、业务审批参与者、页面和导航映射 | 绕过通用执行与预算约束，直接篡改运行器状态、批准结果或计量事实 |

通用审批机制与行业业务参与者分开：底座可验证方案版本、批准和消费关联，但“批准什么、谁可批准、业务提交是否成立”仍受原业务服务及审核规则约束。AI 模型调用预算与宿主商业订阅收费、实际业务资金也分别归属，不能混为一套账。

## 与 Runtime、Provider SDK 未来方案的关系

三条路线独立，不互为启动条件：

| 路线 | 替换或分离什么 | 必须保留的控制 |
| --- | --- | --- |
| 本方案：通用底座与行业模块分离 | 可复用 AI/SaaS 能力与具体行业实现之间的依赖 | 宿主业务权威、当前授权、原操作及持久收据 |
| Runtime 替换 | 自研编排驱动与未来候选 Runtime | 本系统任务/动作语义、单一执行所有权、批准、预算与恢复边界 |
| Provider SDK 替换 | 模型协议编码、传输适配及响应解析 | 唯一 Gateway、受控出网、唯一派发、用量证据和预算单账 |

Runtime 和 SDK 的接口、状态映射及双向迁移继续只在[既有替换方案](<AI Native-Runtime替换方案.md>)维护，本文件不复制。行业分离不要求接入 LangGraph 或更换 SDK，也不因更换引擎而自动实现业务通用化。

## 现在开发时应注意的边界

以下是后续获准功能开发触及相关代码时的设计方向，不是本次批量重构授权：

- **依赖从宿主流向底座。** 由 Rental OS 的装配入口提供租赁工具、身份、权益及业务参与者；通用运行机制不应为了启动而加载 Rental Core。宿主装配层引用租赁业务是合理的，不必机械消除所有行业引用。
- **优先复用已有端口。** 区分通用机制和正式业务适配，不为未知行业建立空接口、通用业务状态机、通用计价引擎或动态插件市场。通用化由真实消费者证明，不靠重命名字段。
- **身份和资源范围由可信宿主解析。** 保留租户隔离、当前权限复验及动作级授权；通用契约不强迫所有系统都有“经营空间”，也不能在缺 scope 时回落成全局访问。跨宿主接入时明确可信签发方、标识命名空间和资源归属，客户端或模型不能自报授权。
- **行业政策留在接入层。** 租赁权限码、品类、客户/企业关系、场景和工具目录由租赁适配提供；工具严格登记输入输出、风险、副作用、原业务前置和结果查询方式，未知工具不可执行。
- **公共协议不泄漏实现细节。** 对外任务、工具、错误和来源协议避免依赖租赁实体、ORM类型、框架对象或供应商 SDK 类型；持久化实现内部使用 Prisma 不等于必须更换 ORM，需处理的是对外边界及数据归属。
- **权益和外部能力可接入但不默认成功。** 复用正式身份、订阅、文件 ACL 和集成服务；缺可信适配时拒绝相关动作，不能用恒真授权、默认无限额度或任意URL补齐通用接口。
- **保持独立替换和最小迁移。** 当次功能只处理其触及的明确耦合，保留既有源码和测试，不启动全仓库改名、搬目录或第二套驱动。

## 可复用的现有接点与需复核的耦合

下表仅用于未来实施者定位，不是代码完成度或独立可用证明；路径和实际依赖在施工前重新核对。

| 接点 | 未来处理方向 |
| --- | --- |
| [应用装配入口](../../../apps/api/src/modules/ai-native/ai-native-application.providers.ts) | 将其视为 Rental OS 宿主组合；通用底座不得被迫依赖该入口提供的会员、支付、Core及租赁权限模板。 |
| [预算授权与权益端口](../../../apps/api/src/modules/ai-native/budget/budget-dependency-adapters.ts) | 复用明确的授权/权益边界；核对公共工具导入是否仍指向 rental-core，不据接口存在宣称已可独立使用。 |
| [订阅权益读取](../../../apps/api/src/modules/ai-native/budget/prisma-subscription-budget-reader.ts) | 将当前订阅表、品类商业上下文读取留在 Rental OS 适配器；未来宿主提供同等可复核的权益证据，不猜套餐权限。 |
| [运行器契约](../../../apps/api/src/modules/ai-native/runner/ai-task-runner.ports.ts) | 保留持久任务/租约/步骤语义，核对公开边界的 Prisma类型和共享契约依赖；不另造第二套运行状态机。 |

请求指纹、精度等通用工具可在确实需要时逐步从行业目录分离，但必须保持既有算法、规范化和版本兼容；不能因为搬目录改变历史幂等比较或旧记录可核对性。

## 数据归属与一致性

- AI 层拥有任务、步骤、模型调用、预算、方案及必要审计；行业层拥有订单、报价、库存、检查和业务资金事实。知识/记忆及共享文件还须明确正文、引用、ACL、删除传播的责任。
- 可以暂时同进程、同数据库运行，但明确仓储归属、稳定引用、对象版本和写入责任，避免通用模块到处直接查询行业表。分包不自动解决共享 schema、外键或宿主用户表依赖。
- 未来公开接入需明确 task/run/step/action、宿主/租户/主体、输入指纹、业务对象版本、批准及原操作收据的关联；引用不是访问许可，重新读取仍须当前授权。
- 迁移时分别处理身份/租户标识、任务状态、审批消费、账本、知识及删除标记；聊天删除不得删除业务事实，历史订单依据不得被新配置替换。

**独立模块不等于独立远程服务。** 先验证同进程模块/包的接入边界，不预设必须拆库或微服务。若以后跨进程，原来依赖同一数据库事务的“审批消费＋业务提交”不会自动保留原子性，必须另行设计并验证可靠提交、幂等、原收据查询和故障恢复；不能以普通HTTP调用和失败重试替代。

## 抽离时机与实施出口

| 阶段 | 目标与前置 | 出口及限制 |
| --- | --- | --- |
| 当前业务开发中的边界准备 | 继续完成原任务；在触及代码时识别宿主依赖和明确耦合 | 保留 Rental OS 正常功能，不为了未来抽象推迟已可收口的业务链，不启动抽离工程。 |
| 未来获准的模块试抽离 | 代表性租赁闭环已验证目标输入、事实查询、确认执行、原结果核对及中断恢复，边界有实际证据 | 先得到可独立装配的模块/包和 Rental OS 适配器；不要求租赁全部功能完成，不同时迁移Runtime/SDK或拆数据库。 |
| 独立宿主接入验证 | 契约、可信依赖和迁移方案已明确 | 由一个最小非租赁业务宿主完成代表任务，证明无需修改通用内核即可接入；不得默认依赖Rental Core，也不能只用恒真替身证明真实接入。 |
| 开源产品化与发布准备 | 独立接入和 Rental OS 兼容验证通过，负责人批准发布范围 | 明确许可证、依赖许可、接口版本、部署/升级、示例、维护及安全政策；仓库发布、包发布和任何生产启用另行授权。 |

现在守边界可以减少未来返工，但不承诺抽离是小修改或给出未经测量的节省比例。外部团队可用的开源底座是独立产品化工作，不能按“复制目录即可开源”估算。

## 未来接入与验收要求

未来获准实施时，应交付可操作接入说明，而不只是接口清单：哪些能力必需、哪些可选、如何提供可信身份/权益/工具/业务结果、如何配置和迁移、失败怎样恢复和停用。

- 不加载 Rental Core 仍可装配通用能力；涉及租赁能力时才加载租赁适配。已有宿主接口保持明确版本与兼容策略，不建立与现有公共契约同名的私有协议。
- 独立宿主应有代表性“目标→事实→方案→必要批准→正式执行→结果核对”的实际消费者；缺依赖、撤权、重复调用、崩溃/迟到及unknown不越过原安全边界。
- 模型仍走唯一 Gateway 与预算单账，任务恢复不重置累计资源；模型计量、商业收费和业务资金分别验证。
- 宿主最终授权和业务规则不能被可替换适配器绕过；适配器受安装与运行授权约束，不因为称为“插件”就允许模型加载任意代码、SQL或HTTP工具。
- 数据/协议迁移和回退须验证旧任务、批准、原账及收据可查；不在验证过程中双发真实副作用。静态、离线行为、真实数据库/宿主/供应商及部署证据分层，不把演示称为生产验收。

## 迁移与回退原则

逐步替换模块边界，不对同一任务同时启用新旧执行者。在途任务原则上固定原实现排空，只有状态、输入、批准及账本映射已验证才可迁移；unknown只能继续核对原操作，不能借新宿主、Runtime或Provider重新发起。

保留原实现、必要兼容入口及迁移证据。回退前停止新路径准入，确认旧新执行所有权及数据版本，不能仅切换开关就恢复旧Worker；回退不撤销已提交业务事实、不重复批准消费或扣费。历史已提交结果在当前授权允许下继续可查。

## 开源前仍需确认的事项

- 首个开源范围：仅 AI Native 能力，还是同时提供可选 SaaS 公共实现；外部团队必须替换的组件应尽量少。
- 宿主信任边界、支持的运行/持久化方式和兼容承诺；不提前承诺跨语言、任意数据库或即插即用。
- 开源许可证、第三方代码/资源的许可与归属、商标/品牌和私有商业服务边界；没有核验不能直接发布现有整个仓库。
- 独立发布、升级迁移、维护责任、安全漏洞处理及示例数据；不把真实凭据、租户数据、历史output或商业资料带入开源包。

这些决定在真正启动抽离/开源产品化前确认，不阻塞当前无依赖的 Rental OS 业务开发。本文本身不构成开源发布或外部接入授权。
