## 1. 结论

**产品方向成立，基础界面方案合理；业务闭环的目标已经写全，但实现设计还不足以直接开放业务模型和通用外部客户端。** 不需要推翻 Harness 接入，也不需要重写原服务端 Agent。下一步应先补清权限、材料、运行限额和可信人类确认的实施出口，再推进具体业务。

| 评审维度 | 结论 | 关键判断 |
| --- | --- | --- |
| 产品边界 | 清楚 | 本地模型自配自付、服务端模型原 Gateway / 单账、后台一份源码、旧成果实际保留均明确 |
| 登录与页面改造 | 合理 | Electron 隔离业务视图承载原 Web，避免两套 React 混用；不复制后台业务页 |
| 业务功能目标 | 目标闭合、实现未闭合 | 已定义查询 → 澄清 / 选择 → Core 报价 → 确认 / 审批 → 唯一建单 → 原收据，但还有未落实的前置 |
| 任务组织 | 主依赖合理，任务颗粒偏大 | 08 / 09 / 13 多个独立职责重叠；10 与 12 的客户选择 / 确认 UI 有隐含交付依赖 |
| 受控模式安全 | 仍有实施级阻塞 | 普通个人对话与业务对话入口、全历史投影、通用工具隔离、最终发送绑定未形成完整实现 |
| 对外 MCP | 可以扩展，不能原样开放 | 可共享服务端业务内核；需新增独立认证授权与 MCP 传输适配，不能公开桌面 IPC 或转发 Web token |

基础阶段 57.1%、追加阶段 7.1% 是任务册登记值，不是本次重新认证的完成率。材料人工预览及其清除不构成 AGC-09 全部完成；没有真实业务模型发送、完整历史隔离和可信累计资源，不能称“业务 Agent 已可办单”。

## 2. 应保持的设计

1. **Web 是业务页面唯一维护源。** `apps/admin/` 的页面、菜单、主题和 HTTP 链继续共用；一般页面发布不要求打包桌面，原生能力和不兼容协议仍单独升级。
2. **模型运行与业务执行分开。** Harness 驱动本地模型，原服务器决定正式业务；新增 MCP 也不必调用模型，更不是提供模型 Key 的代理。
3. **每条业务动作使用同一原实现。** Core、当前权限、报价快照、确认 / 批准、幂等和收据不因 Web、桌面或 MCP 有不同副本。
4. **可信人类确认不注册成模型工具。** 模型可准备方案和查询状态，不能用聊天肯定、`confirmed: true` 或客户端工具确认替代原业务审批。
5. **unknown 按原操作恢复。** 重连、换客户端、换协议、取消等待和断线都不能成为再次创建报价 / 订单的依据。
6. **按能力分阶段启用。** 登录页面、人工目录预览、模型查询、报价保存、建单和服务端任务委托必须分别判定，不由一个 AI 总开关放开。

## 3. 需要补清的需求与方案缺口

以下按影响排序。这里的建议尚未写回正式需求和任务，涉及新范围或验收调整时仍需负责人批准。

### 高优先级：普通 AI 与受控业务 AI 的入口未落定

- 依据：需求 R03、R05、R07 与 R08.1；任务 AGC-04、06、08、09。
- 当前明确的是 AI / 传统两种展示模式；同时要求保留通用聊天 / Shell / 文件，又要求业务会话禁止这些能力取得材料和凭据。
- 缺的是可实施的选择点：哪个输入框属于业务输入、什么时候锁定本次用途、普通聊天中如何识别并拒绝业务引用、切模型 / 切业务模式后如何处理当前消息和历史。
- 后果：若把普通 Harness composer 直接连接业务工具，原文可能先进入模型；若统一禁用原工具，又违反保留普通用途的要求。
- 建议：在现有工作台明确“个人 AI”与“受控业务”用途选择及提示，业务用途先生成结构化材料、锁定允许工具和调用配置。两者沿用同一套个人会话管理，但业务材料必须有受控读取和重放路径；不是仅在标题上贴租户标签。不能证明隔离时，保留人工预览和传统页，不开放业务模型。

### 高优先级：精确模型目的地约束不能直接套给任意 MCP 客户端

- 依据：需求 R07.1、R08.1、R09.2；工作台和原生桥的实际模型准备检查。
- 桌面当前检查的是自有 Host 的准备路由，且材料明确 `human_preview / not_sent`，还不是最终发送许可。标准 MCP 没有通用机制证明外部 Agent 实际使用的提供商、重定向、模型、历史保留和其他工具访问。
- 后果：若把当前返回对象直接作为 MCP ToolResult，等于将“只供人查看”的资料变成外部 Agent 可消费数据；在结果上写 `audience=user` 或有效期无法强制对方不送模型、不缓存。
- 建议：新增独立的外部接入政策。通用客户端仅获取经批准可对外释放的最少字段；必须核验目的地的资料仅对具备额外受管控制的客户端开放。现有严格政策不修改也可以做 MCP，但只能返回不违反它的公开信息、非敏感状态或可信页面入口。详细设计见 [MCP Server 接入方案](MCP服务-接入方案.md)。

### 高优先级：业务材料留存与原个人历史的实现责任不够具体

- 依据：需求 R07.2 / R08.1；任务 AGC-08 / 09。
- 30 天材料、7 天临时附件、更短期限优先和独立撤回已经清楚；但未指定如何覆盖 Session 原日志、压缩摘要、附件索引、错误日志、导出及备份，以及历史原文无法原地删除时的受控处理。
- 当前材料只在工作台暂态展示。来源查询近 30 天不是正文清理；本轮清除按钮也只清当前预览，不能算持久清理实现。
- 建议：先交一张存储 / 读取 / 模型重放矩阵，逐个列出所有者、来源标签、清除与失败回报、派生最短期限、旧版本读取策略。普通个人历史和服务端正式审计保留；业务片段的可恢复正文及摘要不能通过其他读取入口重新出现。不为了实现清除另建按账号分区的聊天库。

### 高优先级：即时撤权、展示短期限与最终发送检查需要分开验收

- 依据：需求 R07.2、A09；当前接续的 3 秒复核、单次 5 秒展示期限。
- 服务端在执行或取数前拒绝撤权用户，与已在客户端显示的数据立即消失，是不同保证。定时复核只能提供有界观察，不能证明服务器权限改变瞬间撤回已经返回的字节。
- 建议：分别说明服务端每个敏感步骤的当前权限检查、自有客户端收到变更或失焦后的撤回、无推送时展示过期上限、模型发送前的最后检查。不能用“每 3 秒查询”宣称即时广播已经完成。外部 MCP 客户端的已交付副本不在服务器可强制回收范围。

### 高优先级：累计限额的身份和计数口径缺少落地出口

- 依据：需求 R11.1：每目标 20 次含轮询、5 分钟累计活跃时间、恢复不重置；任务 AGC-13。
- 文档要求复用原接入关联和限流，又规定不能新建任务数据库，但没有给出无服务端任务的本地目标如何获得持久关联、如何防止换 ID 规避、谁计量重试和轮询。
- 展示复核还带来计数歧义：来源页每 3 秒查询，60 秒内约 20 次，加上目录展示复核可能超过 20 次。人工展示控制流是否属于同一个“前台自动目标”尚未明确。
- 建议：分清自动业务目标额度、人工展示租约复核、协议发现、原收据善后读取的计数类别；均须限流，但不能靠客户端声称“这是复核”豁免。复用原服务端持久目标 / 调用关联的具体字段和原子扣额口，缺失即关闭自动推进，不先做一个本地 Map 冒充。

### 中优先级：任务 10 与 12 的依赖需要按交付物拆明

- 依据：任务 §8.1、§8.2、§8.4；需求 R09.1 / R10。
- 当前主链 08 → 09 → 13 → 10 → 12 → 11 合理，没有显式环；但 10 的完整客户 / 商品选择已需要可信 UI，而 12 又整体依赖 10。机械地等 10 全完成才开始 12 会卡住端到端验证。
- 建议：不改编号，10 先交受权查询和报价合同，12 的选择器 / 材料展示作为同一垂直片的消费者同步接入；正式确认与建单仍后置，11 负责唯一执行。14 的只读订单解释可独立成片，不等待建单。

### 中优先级：能力登记仍需一个现行发布所有者

- 依据：需求 R09.2、任务 AGC-10；[tool-baseline.ts](../../apps/api/src/modules/ai-native/tool-baseline.ts)明确自称工程清单，不是可执行登记或当前可用性。
- 后续不能从历史 baseline、OpenAPI 或全部 Controller 自动生成开放工具，否则会把人工确认、资金和管理接口一并暴露。
- 建议：由原服务端能力作者维护现行工具码 / 版本、当前权限、实际生产者、风险、副作用、投影、原收据与各端适配状态。Web / Harness / MCP 都消费同一发布事实，MCP 仅增加运输名称映射，不产生第二套业务能力定义。

### 中优先级：交付证据与公共产物仍存在漂移

- 依据：客户端 README 的 2026-10-23“尚未启动 GUI”记录与随后实际开发窗口启动不属同一时点；正式接续仍保留组合验收未通过，不能把启动记录提升为验收。
- 本轮按原工作台 tsconfig 类型检查发现公共 `dist-agent-desktop` 是旧合同；改用本轮私有当前协议后类型通过。这表明源码消费者和运行产物版本还需在固定集成交付中一起核对。
- 建议：工程入口仅写当前运行前置，阶段证据只放开发记录；交付时核对协议构建版本、客户端打包输入、Web 部署版本与能力兼容。不能以当前源码绿测宣称正在运行的旧窗口已包含新功能。

## 4. 业务闭环检查

| 闭环 | 正式目标是否完整 | 当前阻塞 / 证据边界 |
| --- | --- | --- |
| 登录 → 改密 → 空间 → 原页面 → 注销 | 是 | 自有桥与源码测试存在，Windows / 原后台组合、真实撤权、打印下载和发布刷新未完成本轮验收 |
| 人工目录 → 材料 → 来源恢复 → 撤回 | 有明确小闭环 | 当前实现有受权读取、原审计与新观察；本轮补关闭 / 清除。仍只是人工预览，不送模型 |
| 业务输入 → 本地模型 → 业务工具 → 再次模型输入 | 否，缺实施闭环 | 用途入口、统一输入 / 历史投影、工具旁路隔离、最终发送对象与累计额度未齐 |
| 客户 / 商品选择 → Core 报价 → 草稿 | 目标是 | 需 10 与 12 同片消费，保存的原操作键、客户安全选择与恢复先齐；不能把 `preview` 当无副作用 |
| 提案 → 人类确认 / 审批 → Core 建单 → 原收据 | 目标是 | 保留原请求 / Task / 选择 / 批准链；不开放模型自批；尚未本地整链验收 |
| 已有订单解释 → 本地 / Web 读取同一结果 | 可先独立闭合 | 先读原任务和原结果，后开放可能调用云模型的发起，不能读结果时自动新建 run |
| 外部 Agent → MCP → 正式业务 | 当前不具备 | 缺 MCP Server、OAuth 接入、外部授权登记、模型可释放投影及客户端兼容验收；不是加 URL 即可 |

## 5. 建议分工与推进方式

这是职责建议，不启动新会话，不修改现行任务依赖。若未来并行，每位作者使用独立工作树；公共文件使用唯一作者和固定交付，不依赖口头“互不冲突”。

| 职责 | 建议承担的出口 | 不承担 |
| --- | --- | --- |
| 服务端身份 / 治理 | 当前身份、OAuth / 外部 grant、租户接入政策、工具发布、撤销、限流与审计 | 客户端标题或模型内容自授权；另造业务角色系统 |
| 公共业务 / 合同 | 原能力生产者、字段投影、风险与副作用、Core / 原批准 / 幂等 / 收据；shared 版本 | Harness 专有配置、MCP 原始协议类型进入 Core |
| Harness 客户端 | 08 的受限消费、09 输入 / 历史隔离、原生状态、12 的资料 / 可信页面衔接 | 重新计算业务事实、复制后台、持有执行 lease |
| 管理后台 | 接入应用 / grant 管理、政策变更和撤销、原人类选择 / 确认页面 | 另写桌面业务表单或模型批准按钮 |
| MCP 适配 | 协议 / OAuth resource server 接点、明确白名单运输映射、兼容层与安全错误投影 | 任意 API 代理、自动从 OpenAPI 暴露全量方法、重新实现业务 |

推荐先交三份固定结果，再推进实现：

1. 08 / 09：业务用途入口及材料全生命周期矩阵，明确个人功能与业务功能切换。
2. 08 / 13：当前身份 / 政策与原目标关联、累计限额、原操作核对的真实生产者和字段。
3. 10 / 12：一个商品 / 客户安全选择 → Core 报价 → 真实页面展示的垂直片；然后才接 11，14 的已有结果读取可独立进行。

MCP 的治理、标准协议和最少只读出口可作为独立适配工作，不依赖所有 Harness 页面完成；却不能绕过相同的服务端业务 / 外发 / 原键前置。通用外部客户端与精确目的地政策的关系是需要负责人批准的新增规则，不能由适配作者自行放宽。

## 6. MCP 可行性与需要新增的部分

**可行的架构是“三种入口、同一业务内核”：Web / 自有 Harness / 外部 MCP 适配 → 原当前授权 → 受权事实或原任务 / 批准 / Core → 原收据。** MCP Server 放服务端，不依赖运营电脑在线，也不要求客户安装 Rental Harness。

已核对可复用的接点：

- [当前 Web Auth / Guard](../../apps/api/src/common/api-auth.guard.ts)：按业务原路由控制当前权限；现在按 Web Bearer 解析，不代表已经支持 MCP 专用 OAuth token。
- [业务组合](../../apps/api/src/modules/ai-native/tools/business-tools.composition.ts)：有 Guard / 当前凭据 / ALS 的受权 reader 与报价组合，不是可任意外调的 service。
- [桌面专用应用](../../apps/api/src/modules/ai-native/desktop-business/desktop-business.application.ts)：证明业务政策、最少目录和审计可复用，但绑定 Web 身份与人工预览，不能整体暴露。
- [原订单读取](../../apps/api/src/modules/ai-native/scenes/original-order-read.controller.ts)、[报价 / 人类确认](../../apps/api/src/modules/ai-native/task-request/human-quote-selection.controller.ts)：提供复用方向；其中恢复、接管和确认有各自副作用，不能仅按名称当只读工具。
- [Harness MCP 客户端](../../clients/agent-desktop/harness/packages/mcp/README.md)：是连接外部服务器的客户端，不是 Rental OS 的服务端。保留它不等于已有 MCP Server。

本轮搜索 API 源码的 MCP / OAuth 标识没有命中；没有找到 Rental OS 对外 MCP / OAuth 接入实现。不能据 Harness 依赖内存在 MCP SDK 宣称服务端已具备。

新增设计详见 [MCP 服务接入方案](MCP服务-接入方案.md)，包括协议版本兼容、Tools / Resources / Prompts、后台开通、白名单 / OAuth、撤销、可信确认、风险分层、任务安排和验收。方案不创建真实 endpoint、应用登记、token、密钥或数据库表。
