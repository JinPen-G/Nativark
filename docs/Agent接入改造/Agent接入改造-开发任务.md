## 1. 实施原则

1. 复用 Harness 的 Agent、模型适配、会话、工具与桌面壳，不另建 Agent 循环或服务器编排前置。
2. 复用 Rental OS 后台登录、空间切换、导航、页面和 API，不复制业务逻辑，也不弱化原 Auth / Guard。
3. 新客户端模型由用户本地配置并直连，不以 Rental OS Gateway、平台模型价格、预算、usage 或服务端 Task / lease 作为普通本地对话前置。正式业务工具 / 协同若复用原任务、确认和批准，不得因本地模型自付而跳过它们。
4. 桌面新增行为优先通过 Harness 的插件、配置和既有 UI 插槽接入；必要的壳层适配限于登录门槛、工作方式、业务视图及生命周期。
5. 只改确有消费者的接点，不先建设完整业务工具注册平台、通用网络代理或新的权限引擎。
6. 独立 Web后台长期保留；功能页面、菜单和请求链只在 `apps/admin/` 维护，Harness 加载同一套 Web发布的受控内容模式，不复制业务页面或随安装包冻结后台副本。宿主模式不改变后端授权。
7. 所有原服务端 Agent、业务工具、任务恢复、协议、Gateway、预算、知识、源码、测试、文档、历史和未提交成果实际保留，后续继续开发；不以 Git历史代替保留，不改成依赖客户端的空包装。原测试不改绿、旧任务不重估。
8. 客户端 Agent 做个人运营工作台；服务端为浏览器管理后台、租户官网和客户 / 员工小程序提供能力，并承接巡检与跨用户协作。两线并行，不互为整体完成前置；可交接正式任务，但同一动作不能双跑。服务端复用原模型配置 / Gateway / 单账，不能借用本地 Key。
9. Web一般页面和菜单发布后，Harness 刷新 / 重开获取新版本资源即可更新；壳层、原生能力或宿主协议变化单独管理客户端兼容和更新。同步不能强制丢弃草稿、重新提交业务或重跑模型。
10. 原登录 / 页面阶段不因本次增补扩大分母；本地受控业务和协同按第 8 节单列，服务端按第 9 节对应原任务推进。文档补充不自动授权安装、启服务、调用真实模型或启用巡检。

## 2. 工程组织与推荐接入方式

### 2.1 目录与依赖

| 位置 | 职责 | 限制 |
| --- | --- | --- |
| `clients/agent-desktop/harness/` | 固定版本的 Harness 完整源码，作为桌面改造基础 | 保留上游许可、原功能与测试；后续只改本期需要的接点 |
| `clients/agent-desktop/UPSTREAM.json` | 上游仓库、提交、归档哈希和 Windows 链接处理说明 | 来源登记不是运行或安全认证 |
| `clients/agent-desktop/README.md` | Rental OS 侧客户端工程说明与专项入口 | 不复写上游逐包说明 |
| `apps/admin/` | 原登录、会话、导航、React / UIArc 业务页面的唯一维护源 | 一份源码、同一 Web发布；浏览器完整外壳与 Harness 受控内容模式共用，不复制业务页 |
| `apps/api/`、`packages/shared/` | 既有身份与业务 API、公开协议 | 登录 / 页面阶段优先最小补接；追加业务阶段由唯一公共作者补必要生产者与正式合同，不复制私有同名 DTO |
| `docs/Agent接入改造/` | 本专项四册 | 不继续改旧 Runtime 方案或旧 AI Native 任务正文 |

Harness 是独立的 pnpm 工程；Rental OS 是 npm workspaces 工程。新目录不落入根 `apps/*`、`packages/*` 的 workspace 匹配，不合并 lockfile、不混用 node_modules，不为直接导入后台组件整体升级或降级 React。

隔离工程不等于没有公共契约依赖。若桌面适配消费 `@rental-os/shared/agent-desktop` 等已有正式出口，需核对依赖声明、专用产物、构建顺序、协议版本与安装包收集路径；不深导入后端内部代码，也不因补接 shared 覆盖共用 dist / 生成物。来源清单记录下载时的上游状态，本地补丁另行对照，不把已有适配后的源码宣称为未改上游。

### 2.2 首期选用独立业务视图

**首期采用 Electron 的隔离 `WebContentsView` 加载同一套已部署 Web后台的登录和业务内容，Harness 继续承载本地外壳与 AI 工作区。** 后台与 Harness 分别构建和运行各自 React，避免直接混入 React 18 / 19 和两套 UI 依赖。浏览器显示完整后台外壳，内嵌模式只移除重复外壳，两者共用一套页面、路由、主题和 API请求链；不把后台静态产物复制进 Harness 安装包。

Web更新后的页面来源不是客户端代码同步拷贝，而是同一个受控部署。开发态可在获准时使用该后台工程的隔离开发服务器，不能以加载了本地 Vite页面宣称正式发布同步已经通过。

- 登录视图先使用原后台登录与会话恢复；只有原服务端核验成功及改密完成后，桌面展示工作台。
- 业务视图复用同一账号对应的原后台页面，只在桌面受控模式移除重复外壳；不复制页面到 Harness。
- 后台适配将当前会话的非秘密展示信息、可访问菜单投影和空间列表通知宿主；原导航注册表仍是唯一来源。
- Harness 左侧呈现空间选择、AI / 传统切换及菜单；菜单项只以注册 ID 和受控路由通信，不能传任意 URL。
- 传统模式把业务视图定位到内容区；AI 模式退回 Harness 原主面板，业务视图隐藏或按原页面生命周期暂停展示。
- 后台原会话凭据留在其受控业务视图的原认证通路中；Harness 对话渲染器、模型工具和业务菜单投影不取得 token。首期不复制凭据到 Harness 的模型凭据仓库。
- 宿主通信只允许本期已定义的会话状态、空间切换、导航和视图尺寸等消息；验证 sender、origin、数据与会话代次。不提供任意 JS 执行或 HTTP / Shell 代理。
- 认证状态不明时先收回菜单和业务视图；空间切换仍由业务端调用原服务端，宿主不能先改一个标签就宣布成功。

现有 `DesktopPlatformView` 只处理 DeepSeek 账号的 usage / top-up 页面，带专用 token、cookie 和账号类型，**不能把它换个 URL 就当成 Rental OS 登录接入**。只参考其视图生命周期、隔离参数和导航限制，新增业务专用适配，不混用两套账号和凭据。

如果实际桌面兼容性暴露阻塞，应先在本专项记录具体限制并采用最小调整；不据此转为“重新写完整后台”或“全部调用平台 Gateway”。

### 2.3 数据与显示的来源

| 信息或动作 | 唯一负责方 | 宿主如何使用 |
| --- | --- | --- |
| Rental OS 登录、改密、会话恢复、刷新和退出 | 原后台 authStore / API 与服务端 Auth | 展示登录或工作区状态，不接受本地恒真登录 |
| 可进入经营空间、切换结果 | 原 `/auth/session-context`、`/auth/switch-workspace` | 只显示已核验结果，切换失败保留真实状态 |
| 业务菜单、权限、品类术语与可访问默认页 | 原 `APP_ROUTES`、`APP_NAVIGATION`、`canAccessRoute` | 消费无凭据投影，不手抄第二份路由表 |
| 后台业务数据、提交、审批、金额和结果 | 原页面、原 Controller / Guard / 业务域 | 承载页面；不由 Harness 推断正式结果 |
| AI 会话、模型配置、用户模型 Key | Harness 本地 Host 与原适配 | 保留原功能，不让平台账决定是否可用 |
| 工作方式与内容区选中状态 | 客户端新增 UI 状态 | 只控制展示，不授业务权限，不成为服务器任务 |

Harness 本地 Workspace 与 Rental OS 经营空间不互相代替。本期空间选择不改本机目录、不注入模型业务上下文、不自动创建会话。

### 2.4 Web页面发布与宿主兼容

- 业务 origin与 API地址由获准的部署配置确定，不由模型 / 页面输入任意选择；浏览器与 Harness 读取同一后台资产发布，客户端仍严格校验 origin、发送者和消息类型。
- 受权菜单从后台实际导航投影动态提供，不打包第二份固定菜单。一般新增页面、调整表单和菜单只改 Web，宿主只识别注册路由和消息，不硬编码每个业务页。
- 后台资产使用可辨认的版本及一致的缓存策略；Web发布后，通过刷新 / 重新打开取得新资源，不能把旧缓存界面当已同步，也不承诺实时热替换打开的页面。
- 更新提示、刷新和重开沿原草稿 / 离开提示语义；不自动保存、重提命令或重跑 Agent来“同步”。
- 业务页与宿主通信保持明确的版本兼容，页面使用新增原生功能或不兼容消息时先识别客户端支持情况；提示升级或拒绝不支持的功能，不放宽安全校验，也不让旧壳误执行未知消息。
- 普通业务页更新无需新客户端安装包；Harness 壳、Agent代码、preload、原生能力和不兼容协议更新仍可能需要客户端发布。后台离线副本及其更新方案不在首期，不用未核验副本兜底网络失败。
- 复用现有版本化会话 / 命令合同，核对 document / session 代次、request ID、actor / tenant / workspace 绑定、允许消息与数量 / 大小上限、心跳 / 截止时间、拒绝 / unavailable / unknown；这些不是业务执行许可。超时不能自动重复命令，页面恢复先重新核验。
- 按真实业务页面分别核对打印预览、blob / 获准文件下载、内部跳转和外部地址；列明允许来源 / 类型及凭据归属，不能为兼容放开全部弹窗、origin 或通用 HTTP。无合法来源的文件 / 地址明确不可用，不能以静态代码存在宣称桌面行为通过。

集成交付由AGC-01的工程所有者固定并保留以下映射，AGC-05核对Web兼容，AGC-07按当前组合验收：源码固定提交 / 本地补丁、公开协议包及运行时产物指纹、壳 / preload / 插件版本、Web资产发布版本、API合同与当前能力发布版本。不在共享dist上覆盖验证，私有隔离产物必须标明未装入当前运行客户端；缺字段或旧产物不能拿源码绿测补通过。README只维护当前使用前置，启动 / 编译的历史证据归开发记录，旧窗口运行不等于最新源码已生效。

### 2.5 并行服务端与协同的复用方向

沿需求第 1.2 节和 AGC-R13，复用现有服务端 Agent / 任务恢复 / 工具 / 协议及业务 API，为独立管理后台 Web、租户消费者官网、客户和员工小程序提供受权服务，不依赖桌面运行。管理后台 Web 必须有服务端驱动的 AI 聊天页面及多轮澄清 / 资料 / 确认 / 结果消费者，不以仅有 API 或任务列表交付代替。巡检先用确定性查询和规则发现异常，再按场景使用 Agent 解释或汇总，不让模型替代正式业务判断。

服务端共享任务和结果独立持久化，用户各自在自己的对话 / 任务列表接收必要任务、业务引用和状态；原任务结果可供不同展示渠道消费，不传整份聊天历史或凭据，也不因通知渠道增多运行多套 Agent。任务委派核对发起者和接收者权限，当前执行方明确；转交、接收、执行、完成及原收据保持区分，客户端断线不能触发换键重做。

协同是可选路径，不建设另一套任务、审批、巡检调度、通知或计费平台。服务端继续读原 AI Native 正式依据和实际实现，按其依赖开发；本地交接消费者见 AGC-14。转交条件、输入 / 批准版本、唯一执行归属和原收据是共享接点，任一未提供时该协同动作不可用，但不阻止两线其他合法功能。

### 2.6 追加业务通路与人类确认分离

基础桥只管会话 / 导航，不将已有 `agent-desktop` 消息当成业务执行授权。追加阶段按以下链路实施，不创建通用 HTTP 代理：

1. Harness 受控业务输入先按 R08.1 形成可外发条件；业务工具只提交已注册代码 / 版本、严格输入、原请求或操作引用，不能携带自授 actor、批准状态、任意 URL 或 Header。
2. 桌面受限适配核对发送者、origin、会话 / 页面代次、消息大小和期限；隔离业务视图使用原认证请求链调用指定 Controller。token 留原通路，不复制给 Host、模型、普通插件或聊天存储。
3. 服务端原 Auth / Guard / ALS 解析当前身份，再核验租户本地工具政策、SaaS / 业务权益、地点 / 数据范围、参数 / 对象版本、当前能力与上限；返回服务端最少字段投影。请求和响应两端做不可变快照与当前身份复验，旧 await 结果不可拼入新会话。
   业务材料外发前核对政策允许的提供商 / Endpoint 与信息类别；客户端改变提供商或地址不能沿用旧许可，Key 不上传。字段和值分别投影，自由备注 / 描述不因处于合法字段内而自动外发或作为工具指令。
4. 保存报价 / 材料等副作用先取得原操作定位并确保可恢复；实际建单沿原原请求、输入、任务、选择证明、批准和 Core 顺序。不得给桌面 server lease、直接调用内部服务跳 Guard，或强行把模型自报步骤视为正式执行。
5. 人类确认在原可信业务页面 / 组件完成，经原正式确认接口提交并复核显示材料；该方法不进入模型工具清单。模型能提出 / 读取提案，不得调用批准、假装用户点击或通过通用工具操纵业务 DOM。
6. 返回结果先分清业务事实、原收据和当前可办理性，再形成模型投影 / 人类页面材料；含个人资料的人类展示结果不得原样返回模型。部署 / 会话不可用时拒绝，不回退共享密钥、静态账号或缓存授权。

业务接口合同应包含或明确关联：工具码 / 版本、原请求 / 操作键、严格输入或受控引用、预期对象 / 输入修订、请求截止时间、结果来源 / 观察时间 / 版本、覆盖范围、保存 / 执行事实、缺项 / 错误与原键读取方式。身份、政策与批准由服务端补齐并验证，不接受客户端自证。复用原 shared 的实际字段名；补字段时同步校验、DTO / OpenAPI、生产者和消费者，不在此另起一套公开协议。

### 2.7 写入归属与发布开关

| 功能包 / 文件边界 | 唯一实现职责 | 给另一线的固定交付 |
| --- | --- | --- |
| 桌面接入 | Harness 适配、受限工具消费、模型外发入口、个人历史片段过滤、工作区展示 | 受支持协议版本、注册工具消费者、超时 / 取消 / 切身份行为及未支持能力 |
| 业务 Web 与服务端接点 | 原后台认证 / 确认组件、Controller / Auth / 工具政策、投影、原请求 / 收据及执行组合 | 固定接口、真实生产者、动作权限、提交点与原键核对方法；不得只给测试夹具 |
| 公共合同 | 两线指定同一位作者维护 shared 出口、输入 / 输出校验和版本兼容 | 先交付固定兼容合同再接消费者，不同时修改桥接文件或造同名私有 DTO |

这是职责分配，不是新建三个开发会话的要求；一人也可按依赖实施。开工先认领具体文件和固定依赖，已有作者继续其 WIP。按租户政策分别开放查询、保存报价 / 草稿、批准后建单、协同，默认未接通项关闭；关闭新动作不封死有当前读权的原收据。不得用一个“AI 已启用”开关默认放行全部阶段。

### 2.8 受控业务用途与实际模型发送

按需求R08.2把“AI / 传统展示”与“个人AI / 受控业务用途”分开。用途控件、受控输入和执行管理由AGC-08 / 09在原工作台插件及Host扩展点实现，不改变基础AGC-04 / 06的原功能保留要求，不修改Agent循环或新建账号聊天库。

1. 用户主动选业务用途后，以原当前身份 / 政策确定可用能力；原姓名 / 电话等选择沿可信Web，Host只取结构化允许条件。缺依赖禁用业务发送，不将普通composer先送模型再分类。
2. 本次用途、目标关联、身份 / 政策、模型准备与工具集合由操作所有者捕获；展示切换不转移在途调用，切用途 / 模型时先停止新动作并沿原键善后。普通历史中的已知业务片段也走受限投影，不在个人用途自动放行。
3. AGC-09在实际模型派发前统一消费输入 / 工具结果 / Session重放 / 摘要 / 检索 / 附件的投影；核对当前授权、期限、同一次准备对象和实际发送配置，不能检查一个对象再执行另一个可变对象。每次工具续轮都重新检查。
