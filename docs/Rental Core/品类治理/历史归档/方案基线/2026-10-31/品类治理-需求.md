## 1. 目标、范围与文档关系

### 1.1 产品目标

SaaS 平台管理员能够基于平台已经实现且通过兼容性校验的租赁能力，创建、配置和发布租赁品类；租户明确采用对应版本并设置自己的经营规则；管理后台、客户自助端和员工端使用同源定义；已有有效报价、订单和资金事实不因平台修改而改变。

本专项是“平台租赁品类管理与版本发布”，不是将整个 Rental Core 改造成任意规则编辑器，也不另建一套订单、库存或资金系统。

### 1.2 本专项完整交付范围

- 现有四品类的统一定义来源、不可变发布版本、空间绑定、采用及变更审计。
- SaaS 管理端的品类列表、分 Tab 编辑、复制、校验、预览、发布及停止新开通。
- 解除固定四品类限制，在已有内核能力覆盖的范围内，通过后台新增品类并经营。
- 术语、字段、库存、计价、履约、资质、检查及可选能力的统一配置边界。
- 各业务端的元数据消费、旧客户端兼容、历史业务保护和第五品类闭环验收。

三个阶段都是本专项的组成部分。仅完成四品类查看或编辑，不得作为“后台新增租赁品类”结项；独立 APP 的实际页面和商店发布不因此提前启动。

### 1.3 明确不包含

- 任意 JavaScript、SQL、可执行公式、插件上传或自由编排核心订单状态机。
- 尚未实现的计费算法、库存机制、硬件协议和行业专用业务模块。
- 平台批量覆盖租户实际价格、已发布经营规则、会员权益或历史订单条款。
- 重建 SaaS 订阅、支付、会员、权限或跨空间经营汇总体系。
- 自动代租户开通第三方服务、提供密钥、启用专业功能或宣称真实渠道验收通过。
- 跨品类混单、空间任意换品类和已有商品/订单的隐式品类迁移。
- 万能低代码平台、任意条件表达式编辑器、多级审批流及品类功能商城。

### 1.4 文档关系与明确替代条款

- 租户、空间、订单、计费和资金规则继续遵守[主需求](../租赁平台/租赁平台-需求.md)，尤其是一个空间一个品类、会话范围与历史事实保护。
- 主需求第 3 节原“不要求运行时无代码配置”的品类扩展边界，在本专项完成后调整为：**组合已有可执行能力的新品类须能由平台后台配置新增；新的执行算法或专用模块仍须开发、测试和发版。** 其余核心约束不变。
- 本专项不是当前代码已支持动态品类的声明。实施前的固定注册表仅是现状，目标架构以本文件为准；落地时同步技术指南、主需求入口及相应 API 文档。
- SaaS 套餐、期限与商业权益继续由[SaaS 专项需求](../SaaS订阅/SaaS订阅-需求.md)管理；本专项只定义与品类/能力的交叉校验，不改收费口径。
- 客户与员工小程序继续分别遵守[客户端需求](../小程序/客户小程序-需求.md)和[租户端小程序需求](../小程序/员工小程序-需求.md)，不增加移动端品类配置后台。
- 子任务范围、依赖和验收以本专项开发任务为唯一依据，日常只更新已核实的完成百分比；实际开发情况、验证和提交集中维护在开发记录，各端任务分册只保留引用，不复制进度台账。历史过程归档，不将其改写为新的需求或计划。
- 交付资料引用[平台需求§6.3](../租赁平台/租赁平台-需求.md#63-场景交付与证据登记)的入口/角色/消费者/事实/能力/阻断/证据登记要求。当前授权及新商业准入引用其§1.4，具体品类版本取值仍以本文件§6.3.1为准；行业参数引用平台§7.2，不新增另一套经营政策或以动态字段代替已实现能力。

## 2. 概念与管理边界

### 2.1 品类不等于商品分类或定价分组

| 概念 | 示例 | 管理主体 | 影响范围 |
| --- | --- | --- | --- |
| 平台租赁品类 | 摄影设备、车辆载具、工程设备 | SaaS 平台管理员 | 定义可支持的经营模型；空间创建时选择 |
| 空间内商品分类/子类型 | 相机机身、镜头、摄影灯 | 租户经营人员，在已有模型范围内维护 | 商品组织和适用字段；不因此新增空间 |
| 商品型号 | 某品牌某型号相机、某款车辆 | 租户经营人员 | 型号共同资料 |
| 定价分组 | 舒适轿车组、标准摄影器材组 | 租户经营人员 | 将型号归组并管理基本价与调价 |
| 实物资产/数量库存 | 某台序列号设备、某批帐篷库存 | 租户经营人员 | 具体可交付资源 |

字段或名称不同不构成必须拆为平台品类的理由。优先判断现有品类的子类型、字段或能力是否可以表达；只有经营模型和管理边界确需独立时才新增平台品类。本专项不借此重建商品分类系统。

### 2.2 三层责任

| 层级 | 负责者 | 可维护内容 | 不可越过的边界 |
| --- | --- | --- | --- |
| 可执行内核 | 开发与发布流程 | 库存一致性、计费策略、状态机、支付结算、能力实现及硬约束 | 不接受管理员任意脚本改变资金和状态逻辑 |
| 品类定义 | SaaS 平台管理员 | 术语、资料字段、支持范围、默认模板、必需/可选能力、版本 | 不能声明未实现的能力为可用，不能读取或修改租户经营事实 |
| 空间经营配置 | 有权限的租户管理员 | 在允许范围内选方式、设置实际费率/押金/逾时/续租/检查等 | 不能突破品类和内核约束，不能改写已发布版本或历史快照 |

平台展示采用数量、版本和配置完整性，不因此获得客户、订单、收入、收款及租户密钥的访问权。租户共享客户身份不等于跨空间经营授权。

## 3. 品类身份、版本与开通状态

### 3.1 稳定身份

- 品类编码采用受格式校验的稳定标识，不再将四项枚举作为所有合法品类的全集。
- 保留 `camera`、`camping`、`vehicle`、`construction` 原编码与已有引用；不改名、不清库、不重造已有经营事实。
- 编码唯一，创建后不可修改；已发布或被空间/事实引用的品类不得物理删除。未发布草稿可归档，不回收旧编码供其他含义使用。
- 每个空间仍只绑定一个品类；升级品类版本不等于更换品类。

### 3.2 状态分开表达

| 维度 | 状态或含义 |
| --- | --- |
| 定义版本 | 草稿、已发布、草稿已归档；已发布正文不可原地修改 |
| 品类新开通范围 | 未开放、指定试点租户、全部符合条件租户、停止新开通；限制新增空间绑定该品类 |
| 版本采用资格 | 每个已发布版本分别限定允许新建/升级/恢复采用的租户范围；与品类默认推荐版本分开 |
| 空间采用 | 当前绑定版本、可选升级/恢复版本、校验结果和最近采用记录 |
| 经营就绪 | 配置合法、空间开业配置齐备、渠道/业务验收证据分别表达 |

“已发布”只表示定义版本可被引用，不表示支付等渠道已接通，也不表示某个空间已满足开业要求。试点租户范围只限制采用，不扩大其业务权限。

必须能同时表达“v1 面向符合条件的租户开放，v2 仅供指定租户试点”。最新发布版本不自动成为默认推荐版本；候选列表及直接指定版本的 API 请求都必须按当前租户复核资格。品类开通政策、版本采用资格与默认推荐引用属于可调整的治理政策，独立记录修订号、原因和审计，不通过修改已发布正文变更。

| 操作 | 范围判断 |
| --- | --- |
| 新建空间绑定 | 同时满足品类新开通范围和目标版本的新建采用资格，再校验人员权限、商业权益及配置 |
| 已有空间升级 | 校验目标版本的升级采用资格和兼容性；品类停止新开通不自动禁止升级 |
| 已有空间恢复旧版 | 校验目标旧版的恢复采用资格、执行依赖及当前数据兼容性，不因版本较旧而放宽权限 |
| 维持当前绑定及历史履约 | 不因试点名单移除、采用资格收窄或默认推荐版本改变而自动改版或停用；当前安全及其他业务授权仍独立校验 |

### 3.3 版本不可变

- 品类名称、术语、字段、支持范围、规则模板与能力政策的业务性修改均通过新草稿发布。
- 每版记录唯一版本标识、展示版本号、结构版本、来源版本、发布人、时间、原因、兼容检查结果及依赖的能力/策略要求。
- 草稿采用修订号防并发覆盖；同一草稿重复发布不得产生多版或多条相互矛盾的发布事实。
- 发布与改变新开通范围分别审计。回到旧配置必须进行兼容检查，不用改写已发布内容实现“回滚”。

## 4. SaaS 管理端页面

### 4.1 导航与列表

SaaS 管理端使用“租赁内核”分组，首期两个入口：**租赁品类、内核能力目录**。租户原“品类与业务规则”“经营空间能力”保留，不直接搬到平台面。

品类列表显示名称/图标、编码、默认推荐版本、最新发布版本、品类新开通范围、待发布草稿、采用租户/空间数量和校验状态；详情按版本展示采用资格及试点范围，不将“最新发布”与“全部租户可用”合并成一个状态。操作包括查看、从通用模板新建、复制为新品类、编辑草稿、校验、预览、发布、查看使用情况、停止新开通。

复制只复制定义，不复制商品、资产、订单、客户、价格、密钥或租户真实配置。复制后重新校验能力适用性，不因来源可用就默认新品类也可用。

### 4.2 品类详情页签

| Tab | 配置内容 |
| --- | --- |
| 基本信息与术语 | 中文/英文名称、说明、受支持图标、默认空间名称、型号/定价组/资产/领取/归还等术语 |
| 商品与资产资料 | 型号字段、资产字段、类型、必填、唯一性、选项、单位、排序、列表/详情显示 |
| 库存与履约 | 序列化/数量/耗材/套装等已实现库存形态，履约方式、地点类型和配送目的地类型 |
| 计费与规则 | 已实现且可用的计价策略、默认单位、逾时/续租/取消/押金等默认模板与允许范围 |
| 资质与交接检查 | 证件模板、默认资格要求、取还检查字段、照片、读数及必要证据 |
| 能力与发布 | 必需/可选能力、依赖与冲突、差异预览、影响范围、采用情况和发布/采用审计 |

- 每 Tab 独立保存草稿中的本页字段，不隐式提交其他页内容；分页保存不代表分批生效。
- 品类整体发布一个不可变版本。未保存修改、校验失败或冲突必须明确提示，禁止静默丢弃。
- 提供商品建档、资产资料和交接检查的示例预览，明确标注“预览”；不写真实商品、不产生经营订单。
- 使用现有 React / UIArc 适配层（`@/components/ui`）、统一设计 token、主题和中英文切换，遵守[管理后台开发约定](../../apps/admin/AGENTS.md)；保留必要的 AntD Form 校验、禁用上下文、空值、ref、异步失败及键盘语义兼容。不恢复直接使用 AntD 的第二套页面体系，不修改 vendor 仿造样式，不新增 Vue 页面或自定义 CSS/脚本编辑器。

### 4.3 内核能力目录

显示能力编码、名称、实际交付状态、实现版本、配置结构、适用前提、依赖、冲突及用途。代码决定实际实现和硬兼容限制；平台只能在此范围内组合能力，不能在后台把“未实现”改成“已实现”。

只有已实现且经相应验证的能力可进入正式采用范围；未完成的能力只能作为明确不可选的规划说明。新增一个字段不等于新增一个算法或业务能力。

新品类的能力准入以代码声明的适用范围及可执行前置条件为准：全品类适用的能力也须满足其依赖和结构条件；专用品类白名单默认拒绝未列出的新品类。`shared` 标签、功能名称或复制来源不构成准入依据。计价策略按其单位、结构及组合条件校验，不假设所有策略都采用品类白名单。

若需将已有白名单能力纳入通用组合，必须在本专项中明确一次性的兼容模型改造及回归范围，经验证后随程序交付；不得通过管理员开关放开硬限制，也不得在之后每新增一个编码时再补一条白名单。第五品类验收使用的能力组合须在验收前冻结，遵守第 10 节的程序构建及样例边界。

## 5. 配置模型与校验

### 5.1 三类配置语义

| 类型 | 含义 | 修改后的影响 |
| --- | --- | --- |
| 支持范围 | 此品类允许使用的方式和能力集合 | 空间选择必须是合法子集；升级收窄须做影响检查 |
| 默认值 | 新空间初始化建议及升级时可明确选择采用的模板值 | 不动态覆盖已营业空间的自定义配置 |
| 硬约束 | 已实现机制承载的安全、结构和兼容要求 | 服务端强制校验；变更通过版本和升级检查，不能绕过历史保护 |

只为已实现配置项定义覆盖政策，不建设任意字段锁定引擎。缺省表示使用该次初始化/采用规则指定的默认值；空数组表示显式清空，仅在该字段允许为空时合法；`null` 仅在字段声明可清空时接受。不能无规则地深合并平台与租户 JSON。

实际生效结果及保存校验必须由服务端统一解析；前端下拉过滤不是安全边界。默认值必须属于支持范围，必选能力必须被声明且可执行，依赖闭合、无互斥冲突。

### 5.2 字段与表单

- 使用结构化表单维护字段，不要求业务管理员写 JSON。支持范围以现有可执行的文本、数值、布尔、日期、枚举及检查照片等控件为基础。
- 字段必须区分型号主档、单件资产和交易/交接记录；归还里程、工时等不能写入型号主档作为共同属性。
- 字段编码稳定，字段值类型、范围、长度、选项、必填和唯一性在服务端再次校验。复用已有资产动态属性唯一值声明机制，补齐型号动态属性及所有受支持写入路径的事务级唯一性保障；不能把型号的应用层预查当成与资产同等的数据库保障。
- 唯一性须明确空间、实体类型、字段及值规范化口径；普通保存、导入或批量写入等已支持入口不得绕开同一约束。属性改值或合法删除时，在同一事务中维护旧声明和新声明，失败不得误释放旧值或留下孤立声明。
- 字段由非唯一变为唯一时，先检查存量冲突并准备完整声明；声明生效与目标版本采用保持原子一致。采用失败不启用部分约束，不能先切换版本、再异步补建唯一声明。型号与资产分别验收并发同值写入只有一个成功。
- 禁止覆盖 `tenantId`、`workspaceId`、订单金额、支付状态、库存数量等核心字段；禁止任意可执行正则/脚本、HTML 和动态代码路径。
- 增加必填、改类型、删除选项或字段、改变唯一性都必须有升级影响检查。被历史引用的字段保留原解释，不能复用同一编码赋予全新含义。
- 中英文术语和选项名称与稳定代码分开保存。未译词条允许明确的中文回退，不暴露内部字段码、不伪造翻译。
- 图标首期从受控集合选择，提供通用租赁图标回退；本专项不增加任意 SVG/脚本上传执行入口。

### 5.3 库存、计价与履约

- 品类只组合已经实现的库存方式，不新增一套库存表或预占算法。
- 小时、24 小时、自然日、夜、班次、30 日月、使用量等保留各自策略含义；改显示名称不能改变算法。新增自然月等算法仍须独立开发和验证。
- 计价方式必须同时通过策略存在性、品类适用性和业务组合校验。时租转日租须有对应单位和费率条件；使用量计费须有读数来源、精度及结算规则，不能仅新增“工时”字段就开放收费。
- 商品实际价格继续由租户定价分组及整体价格版本管理；平台模板不保存租户实际成交价。
- 自取、配送、现场交付、寄送等仅在对应流程已实现且适用时可选择；地点类型、目的地、证据和库存释放条件一并校验，不能只修改称呼冒充另一种履约流程。
- 演示门店、演示价格、演示资产与正式品类模板分离；创建正式空间不注入虚构经营事实。

### 5.4 资格、检查和商业权益

- 平台提供资质及交接模板，租户仍使用已有资料、审核和附件机制；平台不复制会员身份体系。
- 只读“符合模板”不代替资料已审核、证件仍有效或交接证据已采集。
- 实际可用性分别检查：代码已实现、品类兼容、商业权益允许（如适用）、空间启用并配置、人员权限及当前业务条件。
- 套餐授权不自动启用能力；必要能力缺商业授权或配置时，空间须提示缺项，不能降级绕过。
- 本专项不自动新增收费项，不为接通治理而开发专业模块，也不把到期善后与品类退役混为一谈。

## 6. 发布、采用、升级与历史保护

### 6.1 发布与采用分离

1. 平台编辑草稿并保存各页。
2. 校验结构、实现依赖、兼容组合和当前可执行环境；预览差异与受影响空间数量。
3. 授权人员发布不可变版本，明确目标版本采用资格；品类新开通范围与默认推荐版本按第 3.2 节分别管理。
4. 新空间在原有创建权限下采用品类及目标版本均允许的发布版本，并完成开业配置。
5. 已有空间保持旧版，有权限的租户管理员查看差异，按第 6.2.1 节准备资料和配置后明确采用新版。
6. 采用后的新报价使用新版；已有有效报价和订单继续使用原版本及快照。

不得平台发布后静默批量切换空间。首期按空间确认采用，不做自动批量升级编排。新空间创建仍遵守现有 SaaS/租户权限，不因动态品类新增开放租户自建空间权限。

### 6.2 采用前检查

必须检查新增必填字段、类型/选项变化、唯一值冲突、仍在使用的计价单位和价格版本、库存形态、履约方式、检查/资质要求、能力依赖及商业授权。

不兼容项返回可理解的原因和处理入口，不自动丢弃租户配置、不删除商品、不重算订单。既有租户配置合法则保留；需要替换的默认规则须由租户明确确认，并沿用现有规则版本发布机制。

采用使用期望旧版本和修订号校验；在事务中复核前提并原子记录绑定与审计，失败全部回滚。并发报价必须完整绑定旧版或新版之一，不能混合两版定义；重复采用不重复初始化或发放能力。

### 6.2.1 候选版本的资料与配置准备

“先补齐再采用”必须有可执行的准备路径。例如 v1 不认识 v2 新增的必填字段，或者 v1 枚举只允许 A 而 v2 要求 B，不能让旧版保存接口与新版采用检查互相阻塞。

- 提供受控的候选版本预备数据机制；可按规模使用独立暂存或采用请求中的结构化补丁，实现选择须在 CAT-GOV-01 明确。只接受已支持实体和字段的变更，不接受任意 SQL、脚本或无约束的 JSON 深合并。
- 预备数据绑定目标品类版本、当前空间、来源采用修订号及涉及实体的修订依据。型号/资产属性按目标版本校验；能力配置还必须符合目标依赖的实际实现结构，不能借准备阶段引入代码不支持的配置项。
- 准备期间当前空间继续使用原版，预备数据不进入当前报价、建档 Hook、活动能力实例或对客投影；不得通过放松当前业务接口的未知字段/选项校验实现准备。
- 涉及价格、规则的调整继续使用各自的草稿和发布机制，不提前替换现行价格或规则。采用时必须确认与目标品类版本相容的生效组合；不能留下“品类已升级、所需规则尚未生效”的窗口。
- 采用时重新检查目标采用资格、当前绑定、实体修订、唯一性及配置依赖；资料补丁、必要唯一声明、相关配置生效引用、空间绑定与审计原子生效。准备后发生的并发建档或修改必须纳入最终复核，陈旧准备结果不能直接批准采用。
- 任一检查或写入失败，原版与当前经营事实保持不变；保留可修正的预备输入并提示冲突。放弃准备不改变业务数据，重复采用不重复执行补丁。

正向验收必须覆盖“v1 持续营业，v2 新必填或枚举替换可以完成准备并成功采用”，同时覆盖准备后实体被修改、出现新冲突及采用中途失败；不能仅以不兼容时拒绝作为升级功能完成证据。

### 6.3 历史业务执行

- 有效报价携带品类版本引用和必要业务快照；建单复制报价所用版本，不重新绑定平台最新版本。
- 历史订单的检查项目、字段解释和能力政策按其绑定事实执行，不因品类升级改成“取最新模板”。续租、换货、归还和结算按第 6.3.1 节区分原事实与后续变更依据；保护历史不等于禁止后续合法变更使用当前价格。
- 品类定义版本与能力实现/策略版本分开管理。保留旧配置但移除其依赖的执行实现，不算历史兼容；发版前须检查在途业务依赖并保留可执行兼容路径。
- 身份、权限撤销、租户隔离和真实安全限制仍按当前安全规则检查；历史快照不是保留过期权限的凭据。
- 存量回填只能使用可核实的既有配置和事实。无法证明历史品类版本的记录采用明确的 legacy 兼容路径并登记缺口，不伪造“它曾使用当前最新版”。

### 6.3.1 后续业务动作的版本依据

本专项不改变主需求第 4.6.9 节的两种续租计费方式，也不取消取货后换货已允许的价格基准选择。品类模板版本、价格/规则/日历版本与动作快照分别记录，不能用一个“旧订单一律取旧值”的判断代替。

| 业务动作 | 应使用的依据 |
| --- | --- |
| 有效报价转订单 | 复制报价绑定的品类版本及业务快照，不因空间升级重绑或重价 |
| 原订单取还、检查及最终结算 | 按原单及已生效续租/换货等变更各自的快照处理对应商品、时段和费用；不追改已确认事实 |
| 新增时段独立续租 | 续租模式与准入约定遵守原单规则；新增时段按申请时适用的价格、日历和规则独立计费，保存本次变更依据，不追改原租期 |
| 原价格全租期补差 | 按原订单价格及原优惠依据重算并记录差额，沿用主需求的服务、历史日历及负差额审核规则，不擅自改用现价 |
| 取货后换货 | 按客户/运营明确选择的原商品价格或替换商品确认时点当前价格处理未发生租期；替换商品、价格、检查要求及本次能力依据形成独立不可变快照 |

各动作除保留原单品类版本外，还须保存本次实际使用的品类政策、执行实现及价格/规则/日历引用或必要快照；取还后续按对应订单行、商品和变更事实执行，不把换货后的检查要求套回原商品。当前身份、资源可用性与安全校验仍执行。

若升级后的空间不再支持旧单计价单位或能力，后续动作必须检查其历史兼容路径和所需的合法价格/实现是否仍存在。新增时段使用现行价格不代表可以切换原约定计价单位；缺少依据时明确拒绝自动处理并说明缺项，不静默切单位、换算法或退回另一套价格。测试同时覆盖现价变化按约定影响新增时段、原价补差不受现价变化影响，以及新版收窄后的兼容成功/明确拒绝。

### 6.4 停止新开通与恢复

- 首期品类退役动作只禁止新增空间绑定该品类，不自动禁止已有空间升级或恢复旧版；后两者按目标版本采用资格和兼容性独立判断。既有空间原配置、查询、取还、退款、退押和结算不因此停用。
- 不通过冻结经营空间实现品类退役。停止新增订单或紧急安全停用属于另外的业务授权机制，不借品类编辑默认执行。
- 恢复新开通须重新核验可执行依赖并记录原因。空间恢复旧版是一次显式采用操作，不是修改旧版本正文或重置采用修订号；须提供差异预览、资格/兼容检查、原因和采用审计。
- 恢复旧版时保留升级后形成的资料与历史解释，不删除新版字段数据以强行通过旧版校验，也不将其未经解释地传入旧执行器。无法提供已验证的保留及兼容路径时明确拒绝；失败不改变当前绑定，重复恢复不重复初始化，已生效订单和变更仍使用各自快照。

## 7. 数据、服务与接口约束

### 7.1 数据职责

| 对象 | 目标职责 |
| --- | --- |
| 现有 `RentalCategoryDefinition` | 稳定品类身份、编码、品类新开通范围、默认推荐发布引用；不另建平行品类身份 |
| 品类定义版本 | 不可变发布正文、结构版本、来源、能力/策略依赖、校验摘要 |
| 版本采用政策 | 各版本新建/升级/恢复采用资格、试点租户范围及政策修订与审计；不混入不可变正文 |
| 经营空间 | 当前采用版本及采用修订号；保留原品类和数据隔离 |
| 采用预备数据 | 目标版本、实体修订依据、受控资料/配置补丁与校验结果；不作为当前经营事实 |
| 报价/订单及后续变更 | 本次品类版本引用及执行必要快照，与既有价格/规则/能力快照衔接 |
| 发布/采用审计 | 操作人、作用域、前后版本、原因、结果及并发控制依据 |

字段和模板可在品类版本中保存受严格校验的结构化数据，不要求每项配置单独建表；已有价格、规则、能力实例和业务事实不复制进一份巨型配置。

### 7.2 唯一读取入口

- 建立统一品类解析服务，空间初始化、字段验证、报价、订单、能力治理和各端元数据投影均通过它解析明确版本。
- 代码注册表继续定义真实实现、结构支持及硬兼容限制；数据库已发布版本定义该品类采用的组合。禁止两者分别决定同一空间的必选能力。
- 缓存按不可变版本标识组织；发布/采用只在事务成功后对外可见。多进程不能只刷新一个进程内的当前版本指针；读取空间权威绑定以保证一致性。
- 找不到合法定义时明确拒绝相关新业务并记录诊断，不静默切成另一品类或代码旧模板。历史兼容仅通过登记过的路径处理。
- Seed 只初始化缺失的内置版本，不覆盖平台维护的已发布定义；开发演示数据与正式初始化独立。

### 7.3 建议接口面

下列是待实现的契约方向，不代表接口现已存在。开发时须同步 shared、DTO、OpenAPI、权限路由和接口说明。

| 接口面 | 行为 |
| --- | --- |
| 平台品类列表/创建 | 查询品类治理信息、建立草稿品类 |
| 平台草稿版本 | 新建来源草稿、按页补丁保存、读取、归档；禁止编辑已发布正文 |
| 平台校验/预览/影响 | 返回结构和业务兼容错误、示例表单、采用影响；不建立经营事实 |
| 平台发布/开通范围 | 幂等发布、分别维护品类开通和版本采用资格、默认推荐版本、停止/恢复新开通并审计 |
| 平台能力目录 | 只读实际实现、版本、适用条件及依赖 |
| 空间升级预览/准备/采用/恢复 | 服务端会话空间、有权限的租户管理员准备目标版本数据并明确采用或恢复；复核实体修订，平台不冒充经营会话 |
| 各端有效元数据 | 读取本端权限下的空间版本及安全字段，不公开内部配置、密钥、草稿或未开放品类 |

平台接口使用独立平台命名空间，同时验证 SaaS 身份和查看/编辑/发布/停止新开通/审计权限；租户 `*` 不得越过 audience。空间采用沿用租户人员和空间权限，客户端传入 `workspaceId` 不能扩大范围。

### 7.4 程序部署与回退边界

动态编码及新结构的开放顺序与品类模板发布分开管理；多实例缓存一致不等于新旧程序已经兼容。

1. 先完成兼容性结构迁移，并部署能读取动态编码、新结构及历史快照的程序；此时仍关闭动态品类创建、采用和新结构生效入口。
2. 核对所有可能读取或执行相关业务的 API 实例、后台任务、定时任务及消费者，确认其版本和依赖满足要求。未升级实例须升级或停止承接相关流量/任务；不能只在处理发布请求的一个实例上检查“当前环境支持”。
3. 经目标环境授权及验证后才开放动态写入和采用；新实例加入或程序回退也须符合兼容要求，不能在新数据已经存在时重新接入不兼容实例。客户端兼容另按第 8 节校验。
4. 动态品类或新结构事实产生后，不得直接回退到仅识别四品类或旧结构的程序。关闭新开通入口不会清除已有数据，也不会使旧程序恢复兼容。
5. 发布说明须记录最低可回退程序版本、结构和执行依赖，分别说明品类配置恢复、兼容程序回退与数据库灾难恢复。需要恢复数据库时须另行授权、核对新增业务及资金事实并制定恢复/补偿方案，不能以删除新品类、订单或回滚已应用迁移“恢复兼容”。

验收覆盖新旧实例并存时开放被阻止、后台任务读取新品类、兼容程序回退，以及不兼容旧程序重新接入被阻止。本条要求部署检查与恢复证据，不要求本专项另建自动部署平台。

## 8. 多端与安全要求

- 管理后台：创建租户/空间候选、导航、型号/资产表单、定价、规则及能力提示统一使用有效定义。
- 客户小程序、租户预约网站：使用对客安全投影显示术语、型号资料、合法计价/履约选项；始终服务端报价，不公开完整内部规则引擎或运营字段。
- 员工小程序：在当前空间和地点授权范围内读取品类与订单检查定义，旧订单取还读取其快照；不能修改平台定义或空间版本。
- 独立 APP：预留相同契约、结构版本和兼容声明，不要求本专项建立 APP 工程或完成商店验收。
- 平台营销官网不是预约网站，不因本专项自动发布新行业支持承诺。
- 明确元数据结构版本及客户端支持范围。旧客户端可以安全降级的显示项用通用样式；无法理解的必需字段/能力须明确阻止相关新操作并提示升级，不静默漏验。旧订单仍须有兼容处理或授权后台处理入口。
- 保留正常会话、租户/空间/地点隔离、脱敏、只读投影和速率限制。配置内容限制规模、文本长度和选项数量，防止恶意超大配置或注入；不执行管理员提供的代码。

## 9. 三阶段交付门槛

| 阶段 | 必须交付 | 不能宣称 |
| --- | --- | --- |
| 一：统一基础 | 统一来源、版本与空间绑定、历史执行保护、缓存一致性、Seed 不覆盖及四品类回归 | 尚未实现后台动态新增时，不宣称已支持第五品类 |
| 二：管理闭环 | 列表、分 Tab 草稿、复制、校验、预览、发布、采用、权限审计与停止新开通 | 仅配置合法不等于商户业务或真实渠道已验收 |
| 三：动态新增与全端 | 动态编码/兼容校验、已有各端接入、第五品类闭环及现有四品类不退化 | 不宣称任意行业零开发，不以静态检查代替真库/浏览器/宿主验收 |

三阶段完整验收才满足本专项目标；真实试点和既有安全修复不因治理专项而停做。具体执行顺序和任务依赖见专项任务文档。

阶段二在动态编码尚未接通时，只开放已有品类的版本维护和复制为同品类草稿；“复制为新品类/从通用模板创建”的正式保存与开通入口待阶段三接通后开放，不展示可点却无法经营的半成品功能。最终交付仍须包含这两个新品类入口。

## 10. 验收标准

| 编号 | 必须验证的结果 |
| --- | --- |
| CAT-A01 | 单一品类定义来源；同空间同版本在初始化、字段、报价、能力运行与各端投影中一致 |
| CAT-A02 | 迁移保留四品类编码和经营事实；存量缺证据显式处理，不伪造历史绑定；重复初始化不覆盖已发布内容 |
| CAT-A03 | 平台身份与操作权限分离；租户通配权限不能管理平台品类；空间采用不越租户/空间/地点范围 |
| CAT-A04 | 每 Tab 仅保存本页草稿；未保存、并发覆盖、失败与重复发布都有明确结果；发布版本不可编辑 |
| CAT-A05 | 新品类复制不带租户事实/密钥；默认值与硬约束一致；未实现、缺依赖、冲突组合不能正式发布/采用 |
| CAT-A06 | 数据字段分层正确，必填/类型/选项/唯一性由服务端验证；并发唯一写只有一个成功；不执行配置代码 |
| CAT-A07 | 支持范围与默认值分开；平台改默认值不覆盖已有租户规则、实际价格或资金事实 |
| CAT-A08 | 发布不自动切换已有空间；采用前提示不兼容，失败不改变绑定；并发报价不混版、重复采用不重复初始化 |
| CAT-A09 | 已有有效报价建单及后续续租/换货/取还/结算按第 6.3.1 节的动作依据执行；不追改原事实，也不禁止约定允许的新增时段现价或替换商品现价 |
| CAT-A10 | 能力/策略实现升级保留在途兼容；多 API 实例、重启、缓存过期后仍解析一致，缺定义不静默兜底 |
| CAT-A11 | 停止新开通仅禁止新增空间绑定；已有空间升级/恢复按目标版本资格独立检查，旧业务可查询、取还、退款、退押和结算；恢复有复核与审计 |
| CAT-A12 | SaaS 后台、租户后台、客户小程序、员工小程序和现有租户预约网站接通动态元数据；APP 契约预留，未做宿主验收的明确标记 |
| CAT-A13 | 中英文、主题、响应式与 token 符合现有规范；资料分 Tab；未知必需结构有安全错误/升级提示 |
| CAT-A14 | 在已有可执行能力范围内后台新增第五品类，完成开空间、建档、库存、定价、报价、下单、交付、归还、结算；不修改代码注册表或增加品类专用条件分支 |
| CAT-A15 | 新品类取消释放、续租含缓冲冲突、异常归还/库存隔离、幂等及双租户双空间越权失败用例通过 |
| CAT-A16 | 四个既有品类的计价、库存、状态和历史结果不退化；文档、shared、DTO、OpenAPI 和实际实现一致，验证证据分级记录 |
| CAT-A17 | v1 营业时可准备 v2 新必填/枚举资料及合法配置并成功采用；预备数据不提前生效，准备后新增/修改数据、资格变化及中途失败均复核并保持原版，重试无重复执行 |
| CAT-A18 | 型号、资产分别验证动态唯一属性并发同值写入只有一个成功；改值声明维护、非唯一转唯一的存量冲突/声明建立、采用失败回滚均有真库证据 |
| CAT-A19 | 独立续租按申请时适用现价、原价补差按原依据、换货按所选价格基准形成变更快照；新版收窄后兼容成功或明确拒绝，不静默切单位/算法，不追改原单 |
| CAT-A20 | v1 全量与 v2 限定试点并存，非试点直接指定 v2 被拒；停止新开通、已有空间升级/恢复按操作分别判定；资格调整不追改当前绑定，恢复保留资料且失败不改绑定 |
| CAT-A21 | 新旧程序并存时动态写入/新结构生效不得提前开放；API 与后台任务均核实兼容，验证兼容回退及不兼容旧程序接入被阻止，不以删经营事实实现回退 |
| CAT-A22 | 验收能力清单明确且专用白名单未被绕过；冻结同一程序构建后，再以不同编码从后台创建第二个测试新品类并完成发布、开空间、建档、报价下单及取还结算，不补注册表/Seed/条件分支 |

新品类验收建议使用“服装租赁”等无需新算法的内部测试品类，只验证通用能力组合，不等于平台正式承诺该行业的全部专业功能。验收前固定所用库存模式、计价单位、履约方式、能力及实现版本、资格/检查要求和不覆盖的专业功能；不得临时加入洗护、试穿、尺码推荐等未授权业务来补齐样例。

允许在专项实现阶段完成通用兼容模型改造，但 CAT-A14/A22 执行时须冻结同一已构建程序，记录构建标识，再由后台产生新品类编码。第二个测试新品类可复用同一经验证的组合，不额外要求开发另一行业；它用于排除针对第五品类样例的隐藏硬编码。真库/宿主证据按实际执行分别记录。

真实支付、短信、存储及生产放行继续按各专项验收，不能由本专项测试替代。
