# 多币种收款方案调研

> 版本 v1 · 2026-09-24 · 调研阶段,未排期
> 目的:回答"平台支持不同租户不同币种,如何完整实现多币种收款",拆清场景、通道、资质与改动范围。

## 0. 结论速览

- 「多币种/跨境」实际是三个不同场景,**只有两个需要动收单通道**;最常被提到的「境外游客来华付款给境内租户」**零收单改动**,现有人民币通道已覆盖。
- 判断要不要境外收单资质的唯一判据:**谁计价、结算到什么币种的什么账户**。
  - 付款人用外币、但租户收人民币 → 不需要,换汇在付款方。
  - 租户要按外币计价并结算到外币账户 → 需要境外收单产品 + 境外/跨境商户资质。
- 现状:平台已建模 7 币种,但只接了境内 CNY-only 的支付宝/微信;且缺配置期护栏,非 CNY 空间配了也是静默失败。

## 1. 现状

- 币种建模:`packages/shared/src/core.ts:373` 定义 7 币种(CNY/HKD/MOP/TWD/SGD/USD/EUR);空间业务设置带 `pricing.currency`,报价、订单均快照 `currency`。
- 已接通道(均为**境内**产品,CNY-only):
  - 支付宝:网关 `openapi.alipay.com` + `alipay.trade.precreate/refund/query/close`。
  - 微信:`/v3/pay/transactions/native`、`/jsapi`、`/v3/refund/domestic/refunds`(路径含 `domestic`)。
- 硬编码 / 硬阻断点(来自上次审计):
  - `payment.runtime.service.ts:447` 非 CNY 订单直接抛错。
  - `payment.runtime.service.ts:1703 / 1721` 微信下单 `currency` 写死 `"CNY"`,连已存的 `intent.currency` 都不读。
  - `customer-corporate-settlement.service.ts:478 / 456 / 221` 企业授信回款 CNY 硬编码。
  - `tenant-integration.service.ts` 保存/启用支付配置时**不校验空间币种**(静默失败根源)。
- 已就绪、无需重做:`RentalPaymentIntent/Refund` 已有 `currency` 列;微信退款 `createWechatRefund` 已透传 `intent.currency`;对账 `payment-reconciliation-file.service.ts:206` 已做 `currency_mismatch` 校验。**数据层与退款/对账链路已是币种感知的,缺口集中在"创建"与"通道"。**

## 2. 场景拆解

### 场景 ① 境外游客来华,付给境内租户(inbound tourist)
- 机制:游客把境外 Visa/Mastercard/Amex 绑到 Alipay/微信,扫境内租户收款码。**租户侧就是一笔普通人民币交易,收到的是人民币**;当地货币↔人民币的换汇与手续费(约 3%)由游客的发卡行/钱包侧完成,对租户不可见。
- 结论:**现有 CNY 通道已完全支持,零收单改动。** 境内租户按人民币计价,外国游客即可用当地货币的卡付款。
- 可选体验优化(非必须):英文收银台文案、下单页展示「约合 X 外币(参考汇率)」、外卡限额与手续费提示。金额仍以人民币为准。

### 场景 ② 境外主体租户按当地币计价 + 结算(真·多币种收款)
- 例:港/澳/新/海外主体租户,按 HKD/USD 计价并结算到外币账户。
- 需要:**境外收单产品**(微信支付 Global、Alipay+/境外收单,或国际收单如 Stripe/Adyen/PayPal)+ **境外或跨境商户资质**。
- 这是唯一需要"新通道 + 新适配器"的场景,也是资质门槛最高的场景。

### 场景 ③ 境内租户外币标价、仍按人民币收款(display-only)
- 只在报价/下单页按外币展示价格,便于外国客户理解;实际仍按人民币收款和结算。
- 需要:汇率源 + 展示层折算;下单时以人民币金额快照锁定,避免汇率漂移引起金额争议。
- 不换收单通道。

## 3. 各场景改动范围

### 场景 ①(低成本,可立即做)
- 后端:零改动(收款仍走现有 CNY 通道)。
- 前端:i18n 收银台、汇率参考展示、外卡提示。
- 前置:无资质门槛。

### 场景 ③(中等)
- 新增汇率源:平台参数配置固定汇率,或接第三方汇率 API(带缓存 + 快照)。
- 展示折算:报价/下单页按外币显示,金额以 CNY 快照为准。
- 无新 provider、无资质门槛。

### 场景 ②(大,依赖资质)
- 数据契约:`TenantIntegrationProvider` 增加境外 provider 枚举(如 `wechat_pay_global`/`alipay_plus`/`stripe`);`TENANT_INTEGRATION_PROVIDERS` 补字段(境外商户号、结算币种、支持币种列表、结算账户等)。
- 新适配器:境外产品的签名链、下单、查单、退款、回调与境内**完全不同**,需按各自官方文档实现(本调研不臆造具体端点,落地前再逐条对文档细化)。
- 通道币种判据:把 `payment.runtime.service.ts:447` 的"全局 CNY 阻断"改为"按该通道声明的支持币种校验";微信下单 `currency` 改读 `intent.currency`(:1703/:1721)。
- 企业授信:`account()`/流水按订单实际币种记账,去掉 CNY 硬编码(:478/:456/:221)。
- 数据层:`RentalPaymentIntent/Refund.currency` 已就绪;funding events、对账已币种感知,基本复用。
- 资质:境外主体 / 跨境收单签约 / 外币结算账户——**这是最大门槛,属商务与合规,不是纯技术**。

## 4. 应先做的护栏(与场景无关)

无论最终做哪个场景,建议先补:**非 CNY 空间保存/启用境内支付宝、微信时明确报错或提示"该通道仅支持人民币结算"**,堵住当前"配置看似健康、真实收款必然失败"的静默坑(`tenant-integration.service.ts` 保存路径 + `runtimeConfig`)。风险低、独立可交付。

## 5. 分期建议(2026-09-24 更新:只做 ①②,③ 暂并入 ②)

- **P0**:配置期护栏(§4)+ 场景① 体验优化。低成本,立即可做,先让"境外游客付境内租户"体验闭环。
- **P1**:场景② 境外收单。核心交付。境内租户若想按外币计价,过渡期直接以境外实体身份、用外币结算走本场景,不单独做展示层折算(原场景③暂缓)。
- 前置:确定目标市场与商户资质,并按 §7 选定收单平台;按 §8 落地"按币种自动适配 provider"。

## 6. 待确认

1. 目标市场与结算币种:主要面向哪些地区/币种(HKD/USD/SGD/…)?这决定 §7 选哪个平台。
2. 单租户是否会同时运营境内(CNY)与境外(非 CNY)经营空间?这决定 §8 用"按币种多默认"还是"境内/境外二选一"。
3. provider 取向:官方境外产品(微信 Global / Alipay+ / Antom)优先,还是国际聚合收单(Stripe / Airwallex / Adyen)优先?
4. 外币结算账户由谁持有、落到哪个国家/地区主体?

## 7. 场景② 候选收单平台

除微信支付 Global、支付宝境外(Alipay+)外,主流可对接平台:

**全球卡收单 + 多币种 + 内置支付宝/微信等钱包(最贴合,一个 provider 覆盖大部分)**
- **Stripe**:全球最广,百余种结算币种,卡 + 支付宝/微信/多钱包;开发者友好,港/新可用。适合快速上线。
- **Airwallex**:香港起家,APAC 强,多币种账户 + 本地收单,支持卡 + 支付宝/微信;可 like-for-like 多币种结算(少一次强制换汇),对港/新/东南亚租户友好。
- **Adyen**:企业级,单平台覆盖全球卡 + 大量本地钱包,统一对账;技术与商务门槛较高,适合规模大。
- **Checkout.com**:全球,强在中东/欧洲/APAC,多币种 + 钱包。
- **PayPal / Braintree**:钱包 + 卡覆盖最广,C 端认知度高;Braintree 提供更完整卡收单。

**官方境外聚合**
- **Antom(蚂蚁 Alipay+ 商户版)**:一次接入覆盖卡 + 大量亚洲钱包(支付宝、微信、GCash、KakaoPay、TrueMoney 等),APAC 强。
- **微信支付 Global**:微信境外收单,多币种定价/结算。

**区域性(按目标市场补充)**
- **2C2P**:东南亚本地方式强。**Worldpay / Fiserv**:老牌全球大收单。

建议:先选一个"全球卡 + 多币种 + 内置支付宝/微信"的聚合(**Stripe 或 Airwallex**)即可覆盖大部分卡与主流钱包,官方微信 Global / Antom 作为补充或替代,避免逐个接入。具体币种/方式支持以各平台签约区域为准,落地前逐条核对。

## 8. 按结算币种自动适配 provider(硬性要求)

要求:配置页按经营空间的结算币种(`pricing.currency`)**只展示且只允许启用支持该币种的收单平台**——境内 CNY-only 的支付宝/微信绝不出现在境外(非 CNY)租户的可选列表里,反之亦然。

设计:
- **provider 声明支持币种**:`TenantIntegrationProviderDefinition` 增加 `settlementCurrencies`(境内 `alipay`/`wechat_pay` = `["CNY"]`;Stripe/Airwallex = 其签约支持的币种集)与 `audience: "domestic" | "cross_border"` 标记。
- **目录过滤**:`tenant-integration.service.ts` 的 `catalog()` 按当前租户适用币种过滤 `providers`,前端只渲染过滤后的列表。
- **后端强约束(不能只靠前端隐藏)**:`save()` 启用时校验"该 provider 支持此币种",不匹配直接拒绝;`runtimeConfig` 也按**订单币种**匹配 provider(而非只看 `isDefault`)。这与本项目既有原则一致:*前端菜单隐藏不能替代后端数据权限*。
- **运行时选路**:同一租户可能配多个 provider,收款时按 `order.currency` 选出支持该币种的默认 provider;找不到 → 明确报错(而非静默回落到 CNY 通道)。

已定(2026-09-24):**一个租户统一一种结算币种,境内/境外二选一**,支付配置保持租户级。
- 租户级增加**结算币种/属性**(`domestic` = CNY | `cross_border` = 外币),作为目录过滤与运行时选路的唯一依据;要求该租户所有经营空间的 `pricing.currency` 与之一致(保存空间币种时校验)。
- 境内租户目录只出现境内支付宝/微信;境外租户目录只出现 Stripe(及后续微信 Global / Antom),境内支付宝对境外租户**不可见、不可启用、不可填写**。
- 无需把支付配置下沉到空间级。

## 9. 实施计划(已选 Stripe 作为境外收单首发)

**Stripe 选型建议**
- 集成方式:**Stripe Checkout Session**(托管收银台,返回 checkout URL)。与现有"支付宝 Native 返回二维码 URL"模型最贴合,可直接复用 `RentalPaymentIntent` 落库、回调入账、退款、对账脚手架,前端只需跳转/内嵌。
- 支持币种:默认平台已建模的全部非 CNY 币种(HKD/MOP/TWD/SGD/USD/EUR),以 Stripe 账户签约区域为准。
- 密钥字段(存加密列,绝不进仓库/包):Secret Key、Webhook 签名密钥;设置项:账户区域、statement descriptor 等。
- 回调:`checkout.session.completed` / `payment_intent.succeeded` 入账,`Stripe-Signature` 验签;退款走 Refunds API,`charge.refunded` / `refund.updated` 回调;金额按最小货币单位(分)处理(本期币种均两位小数,复用 `toCents`)。

**分阶段(建议按序交付)**
- **A. 基础(与 Stripe 账户无关)** — 进行中:
  - ✅ provider 定义增加 `settlementCurrencies` + `audience`;支付宝/微信标注 domestic + CNY(shared)。
  - ✅ `catalog()` 按租户结算币种过滤支付平台;`save()` 启用时后端强约束拒绝币种不符(P0 护栏)。租户币种暂从空间业务设置 `pricing.currency` 派生(一租户一币种),未建空间默认 CNY;暂不新增租户级币种列。
  - ✅ 测试:`test:payment-provider-currency`(纯函数 + 目录过滤 + 启用拒绝)、`test:tenant-integration-default` 回归,均通过;shared/api typecheck 通过。
  - ⏳ 待办:保存空间业务设置时校验"同租户各空间币种一致";`runtimeConfig` 按订单币种选路(与 Stripe 一起落在 B)。
  - ⏳ Stripe 的枚举 + 定义 + 适配器移到 B 一起落地(避免暴露"可配置但无适配器"的半成品)。
- **B. Stripe 适配器** — ✅ 已落地(单测 + 独立评审 + 修复,待真实 key 联调):
  - 纯核心 `stripe-payment.ts`:回调验签、金额换算(两位小数;TWD/HUF/UGX fail-closed)、Checkout Session 状态映射。
  - `payment.runtime.service.ts`:`createStripeIntent`(Checkout Session)、`queryStripeIntent`、`closeStripeIntent`(expire)、`createStripeRefund`/`queryStripeRefund`(退款金额足额校验)、`handleStripeCallback`(验签→按事件类型入账/关单/退款,复用 settleVerifiedPayment 与事件幂等)、`testConnection`(读余额);所有 create/query/close/refresh/expire/refund 分派点补齐 stripe 分支;币种门禁改为按 provider 结算币种。

  - **境外支付宝/微信**:作为 Stripe Checkout 的付款方式交付(商户在 Stripe 后台开启,下单页自动出现),不单独接 Antom/微信 Global;若确需独立商户号,另立专项(需其官方签名规范)。
