# 跨品类合并支付方案（购物车多品类 · 一次统一收款）

> 目标：客户可在一个商户内跨多个品类（= 多个服务/经营空间）挑选商品加入清单，各品类**各算各价、各自履约与售后**，结算时形成**一个总价、一次统一收款**，收款后由系统按子订单分别入账。模型对标淘宝购物车合并支付。
>
> 状态：设计方案（未开工）。归属见 §12。日期 2026-09-25。相关：[[project_multicurrency_payment]]、docs/多币种收款方案调研-20260924.md。

## 1. 背景与关键结论（来自代码审计）

现状是严格的 **“一支付意图 → 一订单 → 一工作区”**，但**收款账户是租户级**。这两点决定了本方案的形态：

- **报价/订单都绑定单一 `(tenantId, workspaceId)`**：报价引擎 `RentalBusinessService.createQuote`、下单 `RentalOrderConfirmationService.createOrder` 都用会话解析出的**单个** workspace（`workspaceOf`/`resolveWorkspaceId`）。报价单次消费、属于一个工作区。→ **N 个品类 = N 张报价 = N 次 createOrder。**
- **收款账户是租户级**：`TenantIntegrationConfig` 唯一键 `[tenantId, capability, provider]`，**无 workspaceId**。回调也只按租户+provider 匹配。→ **同一租户所有品类共用一个收款账户，一次交易收总额天然可行，不需要跨商户分账。**（分账只在跨租户时才需要，而客户端一个实例=一个租户，不存在跨租户购物车。）
- **付款方式的“是否开通”是按工作区**：`settings.payment.enabledMethods` per-workspace。→ 合并收款要求所选方式在**每个参与工作区都已启用**。
- 押金/预授权走**独立**资金链，且当前设计押金在取货前**线下办理**；在线支付意图 `instrument` 目前只允许 `"rental"`。→ **合并收款只覆盖各单租金应付之和，押金仍各单线下，天然简化。**

## 2. 目标模型：拆多单 + 支付组统一收款

```
购物车（跨品类，多服务分组）
   ├─ 服务A(相机)  行×n   ── 报价A ── 订单A(workspace A)
   ├─ 服务B(露营)  行×n   ── 报价B ── 订单B(workspace B)
   └─ 服务C(车辆)  行×1   ── 报价C ── 订单C(workspace C)
                                         │
                        结算：合计 = A+B+C 各自应付之和
                                         │
                        支付组(RentalPaymentGroup)：向 provider 发起【一次】收款(总额)
                                         │  provider 成功回调（一个交易）
                                         ▼
                        扇出：按子订单各写一条 rental/initiate 资金事件（各自入账）
```

**一张大订单跨品类 = 排除。** 因为每个品类的**履约生命周期天然独立**（取还地点/方式、押金规则、时区、逾期赔付各异；相机能单独还、车能单独续租），且**报价引擎只在单工作区上下文算价**（日历/库存/定价/会员权益/优惠券全 per-workspace）。硬揉进一张单会把这些流程全部推倒重来且语义错乱。拆多单则每单仍走现有成熟链路，改动集中在“购物车多服务 + 结算编排 + 支付组这一层”，**核心报价/履约引擎零改动**。

## 3. 数据模型改动（归 api/shared 会话）

新增**支付组**作为 provider 交易的唯一载体，跨工作区、租户级；现有按单意图作为其**子意图**保留，最大化复用退款/对账/资金链。

**新表 `RentalPaymentGroup`（provider 交易的父）**
- `id, tenantId(+FK)`；**无 workspaceId**（跨工作区）。
- `provider, method, currency, totalAmount`。
- `merchantOrderNo @unique`（= 发给 provider 的 out_trade_no；账单上出现的就是它）。
- `idempotencyKey, idempotencyHash`（hash = 排序后的 orderIds + instrument）。
- `status`（pending/paid/closed/failed/funding_failed）、`checkoutUrl, externalTransactionId, expiresAt, paidAt, responseJson, 时间戳`。
- 关系：`intents RentalPaymentIntent[]`（子意图，每个对应一子订单）。

**扩展 `RentalPaymentIntent`（复用为子意图）**
- 新增 `groupId String?`（FK→RentalPaymentGroup，可空）。为空＝现有单订单支付，行为不变。
- 当 `groupId` 有值：该意图是**子意图**（一子订单一条），`amount` = 该单应付分摊额；**provider 字段（merchantOrderNo 对外含义、externalTransactionId）以父组为准**，子意图的 `merchantOrderNo` 退化为内部编号（保留唯一但不发给 provider）。
- 现有唯一键 `[tenantId, workspaceId, orderId, instrument, idempotencyHash]` 仍适用于子意图（每子订单一条）。

**迁移**：加表 + 加列（`groupId` 可空，纯追加，向后兼容存量单订单支付）；需验证空库/升级/seed 幂等/重启/双租户隔离（[[project_mutation_testing]] 同款验收）。

## 4. 后端编排（归 api 会话）

1. **逐服务报价**：客户端对每个服务组各请求一次 `POST client/quotes`（现有）。切换工作区仍用 `POST auth/switch-workspace`；一次结算里对 N 个工作区分别取报价快照。
2. **逐服务下单**：对每张报价调 `POST client/orders`（现有 `createOrder`，单订单幂等键 `quote:${quoteId}`）。得到 N 张独立订单。**部分失败可容忍**：已建的单各自独立，未建的提示重试；只把成功建出的单纳入下一步。
3. **建支付组**：新端点 `POST client/payment-groups`，入参 `{ orderIds:[...], instrument:"rental", method, idempotencyKey }`。服务端：
   - 校验所有 order 属同一租户、均未结清、所选 `method` 在**各自工作区**都启用（不满足→明确指出哪张单/哪个方式，不静默降级）。
   - 按 `orderId` **确定序**逐一 `FOR UPDATE` 锁 N 单（固定加锁顺序防死锁），各取 `funding.rental.balance + pendingExtensionAmount` 求和 = 总额。
   - 建 `RentalPaymentGroup` + N 条子意图（各带分摊额）；用租户级 `TenantIntegrationConfig` 解析收款账户，**向 provider 发起一次**收款（微信 JSAPI / Stripe Checkout / 支付宝），返回 JSAPI 参数或 checkoutUrl（挂在组上）。
   - 幂等：组唯一键 `[tenantId, idempotencyHash]`；扩展“一订单同时只有一个待支付意图”守卫到“一订单不能同时在两个待支付组/意图里”。
4. **回调扇出**：`settleVerifiedPayment` 增加组分支——回调按 `merchantOrderNo` 命中**组**（webhook 查找逻辑天然按 `(tenantId,provider,merchantOrderNo)`），验签+金额+`externalTransactionId` 锁定后：标记组 `paid`，**逐子意图** `paid` 并各写一条 `funding.recordEvent(tenantId, child.workspaceId, child.orderId, {rental/initiate, amount:child.amount, idempotencyKey:`payment:${child.id}`})`。回调按 `PaymentWebhookEvent(provider,eventId)` 幂等，子订单资金事件按 `[workspaceId,orderId,instrument,action,idempotencyKey]` 幂等——重复回调不会重复入账。
5. **退款**：仍**按子订单/子意图**发起部分退款（`RentalPaymentRefund` 现有模型，`paymentIntentId`=子意图、`orderId`=子单）；向 provider 退款时用**父组的 `externalTransactionId`** 作为原交易号，`out_refund_no` 用子退款单号。各子单退款相互独立。
6. **对账**：账单只出现**组的 `merchantOrderNo`（总额）**。扩展 `payment-reconciliation-file.service.ts` 的本地匹配：`merchantOrderNo → 组`（金额对总额）；子订单拆分是内部事实，不要求出现在账单。退款行仍按 `merchantRefundNo → 子退款单` 匹配（不变）。

## 5. 契约改动（packages/shared，归 shared 会话）

- `ClientCreatePaymentGroupRequest { orderIds: string[]; instrument: "rental"; method: string; idempotencyKey: string }`。
- `ClientPaymentGroupView / ClientPaymentGroupIntentResponse`：组级 `status/totalAmount/currency/expiresAt/jsapi 参数或 checkoutUrl` + 子项 `[{ orderId, workspaceId?, amount, status }]`。
- 结算预览：可选 `ClientCheckoutPreview`（把 N 个报价的分组小计 + 合计聚合返回，或客户端本地聚合，二选一，见 §13）。
- 订单列表/详情：增加“同批合并支付”弱关联展示（可选，非阻塞）。

## 6. 客户端改动（apps/miniprogram，本会话负责）

- **购物车多服务**：现 `CartState` 单 `serviceCode`。改为清单可按 `serviceCode` 分组持有多组行（保留“同款同选项合并数量、同一定价组不重复行”的既有规则，只是允许多组）。加入他服务商品不再弹“清空并切换”，而是**新增一个服务分组**。跨租户仍不可（客户端本就单租户）。
- **详情页入口**：把“立即预约→直跳确认页”改造为可**“加入清单（留在浏览流）”+“去结算”**，并在分类/详情显示清单件数徽标（解决当前“多商品发现性差”的老问题）。
- **结算页分组**：按服务分块展示，每块各自报价、各自小计（券/会员/押金 per-service 只在本块内），底部合计总额。任一服务报价失败→该块置灰可重试，其余照常可付。
- **提交**：逐块 quote→逐块 createOrder（各自幂等键）→建**一个支付组**→进**合并收银台**一次付款。收银台按组核对到账，成功后各子订单各自可在“订单”里独立查看/售后。
- **pay 页**：支持“按组发起/按组核对”的新流程（现为按单 `POST /orders/:id/mini-program-payment-intents`）；组内每单仍可独立进入原按单付款作兜底。

## 7. 约束与边界（务必对客说清）

- 券/会员权益/押金/取还地点/时区都 **per-service**；合计只是**求和**，跨品类不共享优惠。
- 合并收款要求所选支付方式在**每个参与工作区都已启用**；否则该服务不能并入这次统一付款（提示单独支付或移出）。
- 押金/预授权**不进**这笔在线合并收款，仍按各单线下办理。
- 报价过期/库存变化按现有机制各块独立失效重报；不因一块失效卡死整单。

## 8. 失败与幂等矩阵

| 场景 | 处理 |
|---|---|
| 下单部分成功 | 已建订单独立保留；未建的提示重试；只对成功的建组 |
| 建组时某单已结清/取消 | 拒绝并指名该单，客户端移出后重试（保证金额精确） |
| 收款回调延迟/丢失 | 客户端“刷新结果”按组查单；`refreshPaymentIntent` 同款查单再入账 |
| 回调重复 | `PaymentWebhookEvent(provider,eventId)` + 子订单资金事件唯一键双重幂等 |
| 支付成功但扇出中断 | 组 `paid`、未完成的子订单资金事件可由查单/对账补写（幂等键保证不重复） |
| 一单在两个待支付组 | 守卫拒绝（一订单同一时刻只允许一个待支付组/意图） |

## 9. 里程碑（建议分两步落地，降低风险）

- **里程碑 A（拆单链路验收，内部）**：多服务购物车 + 分组结算 + 拆 N 独立订单 + **复用现有按单支付**（此时是多笔付，仅作为拆单/报价/下单链路的验收点，非最终对客形态）。此步不动支付库表，风险最低。
- **里程碑 B（对客最终形态：统一收款）**：支付组表 + 建组端点 + 回调扇出 + 退款/对账支持组。交付“一次付款”的淘宝式体验。

> 若不想要中间态，可直接做 B；A 的价值是先把“购物车+拆单”这块大改独立验收，再叠加支付组，避免一次性大改。

## 10. 影响面与跨会话分工

- **本会话（Claude / 客户小程序 apps/miniprogram）**：购物车多服务、详情页入口、结算分组+合计、合并收银台、pay 页按组流程。

## 12. 结论与下一步

推荐：**按 §9 里程碑 A→B 推进**，最终形态是“多品类购物车 → N 独立订单 → 一次统一收款 → 按子订单扇出入账”。核心报价/履约引擎不动；新增的只有“支付组”这一层，且退款/对账最大化复用现有按单机制。**请确认：(a) 是否按 A→B 分步；(b) 是否要我这就与另一会话对齐 §5 契约草案并开写客户端购物车多服务改造（里程碑 A 的客户端部分）。**
