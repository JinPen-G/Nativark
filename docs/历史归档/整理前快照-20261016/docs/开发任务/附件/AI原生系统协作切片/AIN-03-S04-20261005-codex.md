## 真实代码链

`createPersistedTenantModelConfiguration` → `TenantModelConfigService` → 新 `PrismaTenantModelProfileRepository` → 同一个 Prisma `$transaction`：

1. 复用原 `PrismaTenantModelConfigRepository` 的验证/配置 CAS，在事务内锁定配置修订；失败则不写 Profile。
2. 复核当前 manage 权限，查询既有规范 `AiScope` TENANT row（复用 `aiPersistenceScopeColumns`），核对 tenantId/kind/scopeKey/workspaceId，不拼 scopeId、不自动建 scope。
3. 创建/更新已有 DEFAULT tenant_managed Profile，配置与 Profile 使用同一下一修订、协议/模型和 `tenantModelCredentialReference`；Profile 更新也带旧修订 CAS。
4. 当前权限再次复核后提交；中途失败/撤权会回滚两表。此授权复验是顺序检查，不宣称数据库与身份源之间原子授权。

仓储直接用本树真实生成的 Prisma 事务/delegate 类型；没有手写 delegate、类型强转、第二套加密/价格/状态算法。原低层配置 adapter 继续承担只读和事务内 CAS；默认持久化组合不再用它单独保存。无 AppModule/Controller/后台循环注册。

`createScopeBoundTenantModelConnection` 在最后规范 owner/身份检查之后增加 `selectionForInvocation` 复读：等待期间换 mode/改配置时拒绝旧 BYOK 凭据。依然经过既有 resolver/transport，不增加供应商派发器。

## 兼容与安全语义

- 新租户读取仍默认 Rental OS AI/not_verified，不创建记录或 Profile；首次显式平台模式保存可不创建 BYOK Profile，但规范租户 scope 必须已存在。
- mode 切平台保留原密文、停用默认 BYOK Profile、两表修订同步；切回使用保留配置、同时更新修订。clear 使配置和 Profile 都停用，不把空密钥当可用。
- 新 DEFAULT Profile 的 `allowedCapabilities=[]`，没有把保存配置当 live 能力验真。已有 Profile 的白名单保留，但旧 revision/fingerprint 的能力证据不可用于新配置。
- 这是既有单模型设置到 DEFAULT Profile 的投影，不宣称完成租户多 Profile 管理。其他角色 Profile 不被静默重写或跨角色回退。
- 已有 Profile 修订与配置不符、错误 mode/唯一键冲突都会拒绝并回滚；不盲目把较新的 Profile 改回旧值。
- 通用 `PrismaProviderProfileRepository.update` 的同一原子 CAS 增加 NOT credentialRef 前缀条件，拒绝更新 `tenant-model:`/`platform-model:` 配置所属 Profile；也拒绝通过通用更新设置保留前缀引用。配置管理必须经绑定密文的事务，不留下仅更新 model/capability 白名单导致修订漂移的旁路。
- save/changeMode 在第一个 await 前复制输入；请求身份也保持既有 detached context。模型或调用者不能在授权等待时替换请求目的地。
- 旧 system-rules.aiModel 未受权转换时继续拒绝，不丢失/覆盖旧数据；本批没有变更其兼容边界或偷偷迁移。旧写入口协调和版本冻结仍待处理。
