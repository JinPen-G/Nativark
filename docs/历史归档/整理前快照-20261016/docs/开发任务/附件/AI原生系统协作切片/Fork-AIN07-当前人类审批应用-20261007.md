## 正式应用

- `composeControlledApprovedOrder(...).approvals` 提供 `readProposal(taskId, reference)`、`decide(taskId, AiProposalDecisionRequestDraft)`、`readReceipt(taskId, AiProposalDecisionRequestDraft)`。使用现有 `AI_PROPOSAL_DRAFT_VERSION` 和共享 `approve/reject` 请求；taskId为独立资源路径参数，拒绝请求中的 context/actor/人工普通文本。未创造第二套公共批准 DTO。
- 当前人类身份由既有 session/Auth、持久 read_metadata 策略与 scope/owner/audience 校验导出。决策额外读取 `AiTaskActionPolicy(scopeId, taskId, operation='decide_approval')`，要求有效 revision/expiry、全部 requiredPermissions 且包含现有 `rental-os:order:create`；没有该明确政策即 unavailable，不默认授权或 seed。
- 决策检查三层预算开关及真实订阅读取器的 `ai.native.use` 权益，不创建预算消费或第二账。支持 RUNNING / WAITING_CONFIRMATION 的人类审批，但取消请求后不批准；不自行推进 task/run/step。
- 原 proposal/revision/hash 与持久 INPUT/PREVIEW、原 target/quote版本相互核对；展示原事实及生成文案空槽，绝不从最新报价重建审阅内容。GET 原 quote Guard/ALS 和 POST 原订单 Guard/ALS 分离，GET不是批准权。每个应用在异步读取及返回前复验身份与绑定。
- `AiApprovalService.decide` 消费正式当前人类 authority，原 `PrismaAiApprovalRepository` 的决策唯一约束和 proposal CAS 置于授权前后复验的同一审批事务；没有新增通用事务框架，也未把审批事务和订单事务混成一个业务成功。
- 相同决策重试返回原收据；相反决策、旧版本/异 hash 冲突。丢决策应答用 `AI_RESULT_UNKNOWN / retryable=false / nextAction=read_decision_receipt`；收据读取不重批、不 submit。已记录决策仍需当前读权限，但不重过输入有效期、订阅或决策资格。
