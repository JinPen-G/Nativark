## 真实组合

`composeAiApprovedOrder` 显式装配：

1. 只接受 `taskId / proposalId / proposalRevision / reviewedPayloadHash / approvalId / actionId / lease`；严格拒绝额外 payload/context/scope/key/approved/success。该调用本身不创建或批准方案。
2. 必需 policy 端口解析当前真实身份，使用既有 `aiTaskAccessFromContext` 查询 owner/audience/scope 约束。实际读取 Prisma task、proposal head、不可变 version、action/step、approval、consumption；查询命中后仍逐项核对精确绑定。
3. 复用 `fingerprintAiProposalDraft` / `checkAiApprovalBindingDraft` 与 Core `requestFingerprint`，校验原 C05 payload、当前修订、确认人、scope、期限和正式动作版本。当前只支持 `rental.order.commit` 的 `single_action`；不把多动作提案伪装为全批原子成功。
4. C05 payload 是引用，不是订单 body。必需 snapshot 端口读取其 input/preview 原记录；复核 recordId/revision/contentHash、scope/task/action 及实际内容哈希，不从调用者或模型重建。input 哈希须与持久 action/step 请求指纹一致。preview 必须是原 Core 报价快照，目标 quoteId 一致。
5. 实例化已有 `AiApprovedOrderRouteAuthority`，实际复用原 POST orders `ApiAuthGuard`、原 DTO/ValidationPipe、独立 ALS；业务 context 从 `RentalCoreService` 的既有 profile/category/settings/catalog/location 查询装配，不用调用方 context。非空或显式 `capabilityExceptions` 继续 unavailable。
6. 使用原 `PrismaAiApprovalConsumptionRepository.createOrderTransaction` 参与 `RentalOrderConfirmationService.createApprovedOrder` 的既有事务。任务取消、RUNNING step、当前 run holder/revision/fencing/有效租约及 proposal head 在提交点检查；approval consumption、Core 订单/报价消费和原业务幂等同事务提交/回滚。
7. 当前报价与批准 preview 的内容再次比较（只去掉报价消费时间/消费订单这两个可变消费标记）；仅在 Core 事务内且 ALS 的 user/tenant/workspace 与当前上下文精确匹配时访问原报价事实仓储，避免初始读取落到默认空间。不计算价格、资格或库存，也不改变 Core 的拒绝规则。
8. 成功只能从原 COMMITTED consumption 指向的订单读回；GET order Guard + Core `getOrder` 再验当前业务访问/资源范围。复用原幂等参与者核对，不相信 create 返回布尔值或调用方 resultRef。
9. `reconcile` 是只读入口：没有原 COMMITTED consumption 就拒绝，绝不转成 create。Core 提交尝试抛错保守返回 `AI_RESULT_UNKNOWN / nextAction=reconcile`，不把应答丢失改写成未执行或已回滚。已提交后撤权只能抑制返回，不能删除原事实。

消费 key 由 `[scopeId, taskId, actionId]` 使用现有 canonical fingerprint 派生为 `ai-order:<hash>`，不由调用者指定；恢复仍使用相同原动作。原 Core 幂等记录保留窗口过期后，已提交的 approval consumption 仍阻止再建单。

`approved-order-route.authority.ts` 仅调整可信 callback 错误传播：隔离 Guard 拒绝与业务提交异常，避免把已提交但应答丢失错误误标成 access denied。没有放宽 Guard、DTO 或风险例外授权。

## 主线确认的必需接入端口

文件：`apps/api/src/modules/ai-native/approval-execution/approved-order-composition.ports.ts`。

- `ApprovedOrderPolicyAuthority.resolve(reference, 'read', tx?)`：当前身份/合法元数据读取授权。
- `resolve({...reference, action}, 'execute' | 'replay', tx?)`：action 来自持久 C05，包含 toolCode/toolVersion/input/preview/target，不接受调用方自选 action 内容。execute 必须检查正式 AI 权益与三级启用、动作权限；read/replay 仍验当前身份、原业务权限及 owner 范围，但不因 AI 额度到期关闭合法已提交事实读取。
- `ApprovedOrderSnapshotSource.read({context,scopeId,taskId,proposalId,proposalRevision,action}, tx?)`：返回原不可变 input/preview envelope。每个 envelope 含 recordId/revision/contentHash/scopeId/taskId/actionId/payload。
- `quoteFacts.findQuote` 必须是 Core 原报价事实读取，`confirmation.createApprovedOrder` 必须接同一业务数据库上的原订单确认服务。

主线已确认端口方向并承担正式来源；本树没有恒真生产实现或假的持久输入表。缺任一端口不能构建组合；存量缺快照、工具版本未知、身份不支持等均拒绝。原 Core 会做的业务输入规范化（例如正式 membership 开启时补 bookingIdentity）也必须由提案生产者在持久批准之前固化；消费端不偷偷补值改变批准内容。

外部 Auth/订阅/策略复验是顺序检查，不声称与数据库提交构成原子授权锁。只有原参与者负责的数据库事实在同一业务事务内。
