### 3.3 Provider不能“直接替换”的已查差异

发布源码 `@ai-sdk/openai-compatible@2.0.81`：

- 默认请求字段是`max_tokens`；旧适配器用`max_completion_tokens`。需要服务器按已验证协议作受控映射，不能默默丢输出上限，也不能让客户端选转换函数。
- Provider/provider-utils会加User-Agent；当前`ModelEgressTransport.performPost:74`只接受Authorization与Content-Type两项。fetch桥应拒绝未知敏感header，只处理明确的SDK技术header，并转成既有封闭请求形状；不直接放宽任意headers。
- 自定义fetch是必选依赖：限定POST、已解析URL、JSON字符串、原credential、signal与响应字节；底层继续用已有固定IP/TLS传输。缺fetch时SDK会回落globalThis.fetch，构造器必须在此前拒绝。
- 把受控post/postStream桥为Response/ReadableStream；处理status、内容类型、reader.cancel/return、背压、总deadline和错误中止。不是新建第二套网络安全实现。
- `convert-openai-compatible-chat-usage.ts:18–54`在usage整个缺失时保留undefined，但usage对象存在而某个token字段缺失时默认补0。**不能直接把SDK的total用于扣账**：必须核验`usage.raw`中的prompt_tokens/completion_tokens均存在且是有效计数，否则unknown/reconcile。
- 非流式工具解析允许缺tool-call id时生成ID；这不满足旧适配器的严格来源约束。首片模型只允许文本总结、不开放自动工具调用；后续工具支持必须检查原始响应/`includeRawChunks`证据，不把SDK补值冒充供应商事实。
- 流中错误可能作为`type:error`事件返回，不一定throw；完整finish/usage/取消检查不可省略。SDK输出不能直接标记任务成功，reasoning内容不持久化/不展示为内部思维链。
- 直接Provider方法不具备高层`maxRetries`选项；本次源码所读路径每次方法一次postToApi，无重试循环。仍须用实际包故障夹具统计请求次数。若用高层ai，官方默认重试2次，必须设0。

## 4. MySQL/Prisma checkpoint结论

**未找到本轮可直接批准的成熟官方JS MySQL saver；不把这个结论扩大成“全世界没有”。** 官方JS持久化文档列出Postgres/SQLite等；npm中两个直观mysql包名404，有限搜索没有得到已核验候选。Python的同名实现不能直接当JS依赖。搜索范围有限，不继续无限选型。

建议保留现有MySQL，通过**有界Prisma存储适配**实现发布包的BaseCheckpointSaver接口，不重写图执行或checkpoint算法。内存saver只用于随后获准的离线实际图测试，不作为跨进程恢复证据。若后续找到成熟兼容saver，只替换存储适配，不改公开任务契约。

### 4.1 必须实现的上游契约

依据checkpoint@1.1.6的`dist/base.d.ts`：`getTuple`、`list`、`put`、`putWrites`、`deleteThread`；继承`get`、版本生成及默认parent遍历。不是仅保存一段state JSON。

- 保存checkpoint版本、id、父checkpoint、channel_values/channel_versions/versions_seen、metadata和pending writes；尊重上游typed serializer格式及新channel versions。
- `putWrites`中的taskId是LangGraph内部执行任务ID，**不是Rental OS AiTask.id**。唯一键必须同时包括授权绑定、checkpoint、内部taskId和write index；保留WRITES_IDX_MAP特殊索引与正常write重放语义。
- 非默认DeltaChannel/跨线程store/子图fork首片不启用；不能因为不用某项就无声丢字段。未知格式/版本拒绝，回到人工或旧实现。

### 4.2 建议最小存储形状（待实现阶段schema审查）

1. 一个task级运行实现绑定：scope/task唯一，记录owner/audience、engine、graphVersion；run/thread绑定包含输入revision/hash、namespace白名单和当前checkpoint/head CAS。task不随新run自动换引擎。
2. checkpoint存储：绑定ID + run + namespace + checkpointId唯一；父引用、序列化格式版本、typed payload、metadata、内容hash、留存期限。
3. pending writes存储：同绑定/run/namespace/checkpoint + LangGraph内部taskId + index唯一，记录channel与typed value。

可在最终schema设计合并绑定字段，不能把这些内部数据重建成第二套task、审批或账本。用Prisma Bytes/JSON及有界长度，避免MySQL长字符串复合索引和默认大小写排序的错误授权；授权标识、namespace/hash要求精确匹配，必要二进制排序/定长哈希索引。新表无默认授权/历史回填。

每个读/写/list/delete入口捕获服务器当前授权绑定；threadId不是凭据。读完成后复验身份/修订，写入在短事务中校验现有run fence及绑定head，旧worker不能推进head。删除必须是明确获权维护动作，不能因清聊天级联删订单/账本。

**checkpoint写与业务/模型调用不构成同一个事务。** 网络调用不进入checkpoint事务。写入后COMMIT应答不明时读同checkpoint ID/hash判定，不能生成新动作；新head未确认前停止图向后推进。跨实例MySQL锁、二进制排序、pending writes及进程重启必须留到获准真库测试，离线替身不替代。

## 5. 执行设计与唯一归属

### 5.1 一个所有者，避免双重循环

- LangGraph：决定下一节点、条件分支、interrupt和checkpoint；不持有业务权限、不直接调用SDK或Core。
- 既有Rental执行层：唯一领取/lease/fence、登记/启动/结束步骤、资源占用和恢复核对所有者。
- 既有Gateway：唯一模型准入、配置/Vault解析、dispatch与计量入口；SDK只做一次协议请求。
- 既有预算仓储：唯一财务预留、结算与核对账本；LangGraph计数不是余额。
- 原Core：业务事实与提交事务。图结束、节点返回、checkpoint落盘都不等于Core提交。

当前runner是固定`plan.steps`的单体run方法，不假称已有可直接从图调用的`executeOne`。最小改法：从该方法**提取原有单步执行边界**为内部方法/服务（保留registration、资源、effects、receipt、unknown顺序与测试），由现有执行层host领取一次run租约，在租约期间运行图；图节点仅请求这个执行边界。旧run仍调同一边界，新任务只走图驱动，不同时再启动旧plan遍历。不要在每个节点重新调用完整`runner.run()`，否则会重复领取/结束整个任务。

这段提取是复用已有代码，不是另建可插拔通用引擎或新调度服务。框架内部retry显式maxAttempts=1；不额外withRetry。上游retry实现在未提供policy时不重试，policy缺maxAttempts时默认3，不用模糊“默认安全”的假设。

### 5.2 图状态与证据绑定

图状态只含版本、不可变输入引用、registrationRef、step/result/invocation/charge引用及受控分支标识。scope/owner/audience/graphVersion/inputRevision由服务器绑定记录验证，不能信任state携带值。活跃lease、credential和服务实例只在运行闭包，不写checkpoint；恢复重新领取当前lease。

- 一个既有动作保持原actionId/registrationRef/requestFingerprint；不能用checkpointId/重试次数生成新动作或callId。
- 一个模型调用复用原invocationId、配置/价格版本、intentHash、reservation/dispatch绑定。预算不足在SDK请求前失败。
- 模型结果先持久为既有step artifact并绑定调用收据，资源/账本按原生命周期结算，随后提交step/task事件，再推进checkpoint；任一阶段失败读取既有收据，不重派。
- checkpoint引用结果也要重新按当前权限读取。已撤权用户不能因“合法恢复”得到旧正文；内部核对和对用户展示分离。
- 明确拒绝外部传来的threadId/checkpoint_ns、任意goto、updateState、fork/time-travel。首片没有开放这些维护接口。

### 5.3 失败窗口与必验条件

| 情况 | 正确行为及断言 |
| --- | --- |
| 节点重入/框架恢复同一input | 同registration/action/call；已有收据读回，执行/派发次数不增加 |
| putWrites成功、checkpoint未成功 | 保留pending writes；读权威step结果，不能当尚未执行；无新扣账 |
| 模型/业务结果已保存、checkpoint失败 | 恢复读原结果及计量，不重新请求；断言artifact与usage各一份 |
| checkpoint存在但引用收据缺失/篡改 | 不标成功、不猜未执行；unknown/manual，零自动补发 |
| dispatch成功、响应丢失 | 使用原invocation读派发/结果/用量；缺证据待核对，禁止自动重新生成callId |
| dispatch确认不存在、准备失败 | 由原派发/预算状态决定是否可继续，不凭图异常自动重试 |
| 模型文本返回但usage缺/半缺 | 保留结果与保守占用，unknown/reconcile；不得SDK缺值补0 |
| 取消发生在派发前/后 | 前者拒绝新请求；后者abort传至传输并保留unknown，不能声称远端回滚 |
| interrupt恢复 | 先查输入收据/原修订；审批场景先查原批准事实，resume对象不授予批准 |
| 双实例/旧holder迟到 | 现有run fence约束业务动作和checkpoint head；最多一个新派发，旧结果不得冒认新worker成果 |
| 撤权/切空间/图或政策版本变化 | 当前授权失败不读正文、不执行；不热迁移历史run |
| 恢复跨多轮 | Steps/Calls/ActiveMs/OutputBytes及费用累计不归零；图recursionLimit只是额外上限 |
| 回退旧实现 | 新任务关闭新图；已绑定图的在途任务沿原版本排空/人工核对，不能换引擎重做动作 |

上表为验收设计，本轮未执行实际LangGraph/SDK测试。LangGraph interrupt重入节点起点的行为已从官方资料核查；不在interrupt前放未经幂等保护的外部动作，不吞框架中断异常。
