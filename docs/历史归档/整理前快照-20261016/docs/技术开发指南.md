## 2. 架构边界

### 2.1 通用租赁内核

`apps/api/src/modules/rental-core` 是新业务的通用内核，API 前缀为 `/api/rental/v1/*`。

当前核心对象：

```text
Tenant -> BusinessWorkspace -> WorkspaceRentalProfile -> RentalCategoryDefinition
RentalItemGroup -> RentalAsset / RentalStockBalance / RentalBundleComponent
RentalQuote -> RentalOrder -> RentalOrderLine
RentalReservation -> RentalAllocation
InspectionTemplate -> InspectionRecord
PricingPlan / DiscountPlan / Coupon / ValueAddedService
RentalRuleVersion / BusinessCalendar
RewardLedger / BenefitAccount / NotificationTemplate
```

`vehicle`、`camera`、`camping`、`construction` 共用以上核心对象。新建跨品类能力必须进入 Rental Core 或通用模块，不得添加只做字符串替换的车辆页面。

扩展层次固定为：通用领域对象与流程 → 品类定义注册 → 计费策略注册 → capability 扩展模块。品类差异只能由定义、策略或独立 capability 模块提供，不能反向侵入通用商品、库存、报价、订单、预占和履约流程。

### 2.2 旧门市租赁参考模块

`apps/api/src/modules/store-rental`、管理端旧车辆页面和 `/api/store-rental/*` 是历史门市租赁实现，仅保留作业务规则与实现方式参考，不属于新平台目标架构。

- 新页面、新接口和新业务事实不得依赖或写入该模块。
- 不建设 Rental Core 到旧 DTO 的兼容 facade，不迁移或对账旧门市租赁数据。
- 车辆品类同样使用 Rental Core；调度、TBox、驾驶资质等以 capability 形式在新模块中重新建设。
- 未经项目负责人明确授权，不删除历史代码和表，也不得因其存在而改变新平台字段、流程或优先级。

### 2.3 平台管理域

`apps/api/src/modules/platform` 负责 SaaS 租户、组织、账号、角色、权限、参数和初始化。

- SaaS 平台管理员只进入平台管理面。
- 租户管理员的 `*` 只代表当前租户内全权限。
- 一个租户可拥有多个经营空间；每个空间只有一个品类，品类在空间原子初始化时确定，不能使用普通资料接口修改。
- 运营用户身份归属租户，通过成员关系进入一个或多个经营空间；运营角色和数据范围允许按空间配置，不因客户会员共享而改变。
- 客户主档、客户账号、个人/企业会员身份状态、注册策略与审核、免费方案/版本/授予及企业员工关系属于租户；订单、库存、价格、优惠券、资金和报表仍属于经营空间。

租户统一会员模型（已批准目标，`MEMBER-TENANT-01` 测试进行中、尚未部署/验收）：

- `CustomerMembership` 替代 `CustomerWorkspaceLink`，数据库唯一键为 `(tenantId, customerId)`；不随空间创建、登录或切换批量复制会员。
- 注册策略统一由租户持有；注册审核与资格审核仍分开，`Review.sourceWorkspaceId` 仅是来源，不能决定会员归属、审核列表范围或授权。企业员工引用同租户个人/企业会员，关系状态、角色与有效期在租户级判定。
- 免费个人/企业方案、不可变版本和授予租户共享；每条已实现金额权益设置 `scope=tenant/workspaces/categories`，指定空间或品类列表必须非空，服务端校验空间归属及品类编码，按目标空间实际品类判断命中。
- 资格 Ref 为租户共享客户资料，资格 Type 和目标订单规则按目标空间、品类/capability、状态和有效期解析。不能仅以 Ref 的来源品类不同拒绝身份证通用资料，也不能把资料共享当成目标资格已满足。
- 账号状态控制认证，会员状态控制业务资格；租户会员暂停阻止全部空间新业务，不自动停用账号，不阻断仍被授权的本人历史读取与善后。

### 2.4 基础设施域

`integrations`、`files`、`notifications`、`jobs`、`database`、`health` 和 `openapi` 提供业务需要的基础边界。未接真实供应商时必须明确标记 `mock` 或 `reserved`，不得宣传为真实支付、通知、签章、IoT 或物流。

## 3. 管理端架构

### 3.1 目录与职责

- `src/app`：路由、导航、Query Client 和全局 Provider。
- `src/components`：应用框架、页面容器和通用交互。
- `src/api`：HTTP client、DTO 适配和租赁 API。
- `src/features/rental-core`：租赁工作台、通用订单和详情。
- `src/features/catalog`：商品、资产和库存。
- `src/features/fulfillment`：经营主体和履约地点。
- `src/features/commercial`：定价、优惠、优惠券和增值服务。
- `src/features/settings`：品类和业务规则。
- `src/features/customers`：个人客户、企业客户和会员。
- 历史门市车辆页面不进入新平台菜单；后续重新建设的车辆专属页面只能在 `vehicle` 品类及对应 capability 下显示。

### 3.2 路由、菜单与权限

路由和菜单的唯一注册表是 `apps/admin/src/app/navigation.tsx`。每条业务路由定义：

- `path`；
- `permission`；
- 可选 `capability`；
- 可选适用品类 `categories`；
- 是否出现在菜单。
- `audience`：`saas` 或 `tenant`，用于平台管理面与租户营运面的强制分流。

页面访问必须同时满足：

`audience 匹配 AND 权限通过 AND capability 通过 AND 品类适用`

普通租户即使拥有租户级全权限也不能匹配 `saas` 路由；SaaS 平台管理员不能匹配 `tenant` 路由。菜单过滤和直接 URL 访问必须共用同一判断，前端判断只用于体验，后端 Guard 和数据库查询仍需独立校验。

### 3.3 经营空间切换与缓存

React Query 缓存不能跨租户或经营空间复用。登录、退出、会话更换、经营空间切换、上下文不一致或重新认证时，应取消旧请求并清空业务缓存。新增业务查询键必须包含会影响返回结果的 `tenantId` 和 `workspaceId`，不能依靠固定保鲜时间掩盖上下文变化。

右上角经营空间切换器只显示当前账号有权进入的启用空间。切换成功后必须刷新会话、权限、品类、capability、导航和工作台；当前路由不适用于目标空间时跳转目标空间工作台。前端选择值不能直接成为可信业务范围。

### 3.4 Ant Design 规范

- 使用 Ant Design 6 `ConfigProvider`、token 和官方算法，不复制官网品牌导航。
- 框架窗口允许小幅浏览器边距和整体圆角；窄屏贴边。
- 一级页面切换使用工作区上的圆角 `Segmented`，不要塞入内容 Card。
- 面包屑用于定位，可在有并列入口时提供下拉；不要统一复制“大标题 + 小标题”模板。
- 表格保持浅表头、清晰行分隔和可辨识的行操作；筛选和列控制只在真实需要时出现。
- 主题通过 token 实现；不得用大量全局 CSS 覆盖组件内部结构。

## 4. API 与认证

API 全局前缀为 `/api`，`ApiAuthGuard` 是全局 Guard。

### 4.1 请求身份

- token 解码后建立 `tenantId`、`workspaceId`、`userId` 和 `isSaasAdmin` 请求上下文；平台管理接口可无经营空间，租户经营接口必须有当前经营空间。
- 请求入口使用 `AsyncLocalStorage.run()` 建立隔离上下文。
- 缺少租户身份的租户业务请求必须 fail-closed，不能默认 `tenant_001`。
- 缺少经营空间、空间停用或用户不属于当前空间时，经营业务请求必须 fail-closed。
- SaaS 平台接口和租户业务接口必须明确分流。
- 客户端提交的 `tenantId` 或 `workspaceId` 不得覆盖认证上下文；切换空间必须调用专用会话接口。运营端校验空间成员关系；客户端校验租户会员、目标服务空间归属与启用状态后更新 session，不要求目标空间再次入会。
- 同租户一个小程序，客户端注册目标为 `tenantCode`，`workspaceCode` 可选，仅是来源或初始服务空间。验证码挑战、一次性验证身份与注册幂等以租户为边界，不能通过更换来源空间重复注册、重复消费证明或重置审核。
- 客户端 session 的当前 `workspaceId` 仍是目录、报价、订单、优惠券与资金的可信服务端上下文；会员资料按租户和本人校验。订单归属校验覆盖读取、写入、凭证及幂等结果回放，不能先返回幂等缓存再校验本人订单。

### 4.2 权限

API 权限由路径、动作、经营空间成员、权限码、品类和 capability 共同决定。新增 Controller 操作必须：

1. 定义所需权限；
2. 定义品类或 capability 限制；
3. 进入 OpenAPI 文档；
4. 通过契约检查；
5. 在经营事实 Repository 查询中附带租户、经营空间和数据范围条件；共享客户主档与租户会员事实附带租户条件，客户自助接口另校验当前客户归属。

租户会员管理路由（客户/会员、注册策略、审核、方案及授予、企业员工等）从用户**基础租户角色**解析对应操作权限，并要求租户级 `dataScope=all`，或为租户管理员；不能取空间覆盖角色、空间 `*` 或空间全部范围来放大权限。空间经营路由仍按当前空间成员、角色、数据范围校验，租户会员授权不包含订单、库存、价格、优惠券、资金与报表的跨空间访问。

代客下单最小会员/企业身份选择器按当前空间订单创建权限授权，只返回下单必要的脱敏候选，不复用全客户维护接口；租户会员共享不意味着仅有订单创建权限者可以维护客户、读取证件或修改方案。

### 4.3 DTO 与错误

- 公共枚举和 DTO 优先定义在 `packages/shared`。
- Prisma 枚举与领域枚举在 Repository 边界显式转换。
- Controller 不直接暴露 Prisma 模型。
- 金额使用明确币种和舍入规则；禁止使用前端最终金额作为订单事实。
- 业务冲突返回稳定错误码或可识别错误消息，不能静默降级到演示数据。

## 5. Rental Core 规则

### 5.1 品类与动态字段

品类 schema 决定商品、资产、地点、使用量、资质和检查字段。前端渲染 schema，服务端再次校验必填、类型、枚举和唯一性。

- 商品目录和资产使用 `rental-core:catalog:*`、`rental-core:asset:*` 通用权限；历史车辆权限只能作为升级兼容入口，不得成为新页面或新角色的主权限。
- schema 新增、删除或改变字段约束时必须提升品类定义版本，并同步管理端、服务端校验、Seed 样本和 E2E。
- `unique` 表示当前经营空间内按归一化值唯一。服务端预查只提供友好错误；资产动态唯一值必须在同一事务写入 `rental_attribute_unique_values`，由 `(workspaceId, entityType, fieldCode, normalizedHash)` 唯一键保证并发双写只有一个成功。未来其他实体范围出现 `unique` 字段时，必须接入同一声明机制后才能发布。

扩展契约：

- `packages/shared/src/index.ts` 的 `RENTAL_CATEGORY_DEFINITIONS` 是品类定义注册表，集中声明术语、动态字段、库存与地点能力、默认业务规则、检查字段、计费单位和 capability。
- 品类初始化、默认规则与动态表单必须读取定义，禁止在 Core 服务或页面中使用 `categoryCode === "camera"` 一类分支提供默认值。
- 新增品类时允许新增 Prisma 枚举迁移、品类定义、专属 capability 和测试；不得修改既有品类定义来迁就新品类。
- `rental-extension-registry.ts` 在启动和测试阶段校验品类编码、默认计费单位、初始地点类型、计费策略与 capability 注册完整性。
- 演示 Seed 的品类样本放在独立样本注册表中；样本工厂不是生产领域规则，也不得成为 Core 的运行时兜底。

新增品类不是“只加一条定义即可零代码接入”。必须按以下注册顺序完成并逐项核对：

1. 在 `packages/shared/src/core.ts` 注册品类编码和 `RENTAL_CATEGORY_DEFINITIONS`：明确可用库存形态、计价单位白名单及默认单位、履约方式、地点类型、配送目的地、术语、动态资料字段、默认能力和适用的扩展能力。取还方式、计价单位和资产属性均按真实品类场景声明，不得复制其他品类的全量选项。
2. 在 `apps/api/prisma/schema.prisma` 的 `RentalCategoryCode` 增加持久化枚举值，并创建只前进的 Prisma 迁移；数据库结构与共享契约缺一不可。不要直接改已应用迁移。
3. 检查 `rental-extension-registry.ts` 是否能校验该品类的计价策略、能力依赖/适用范围、地点初始类型和 capability 配置；专属行为以显式 capability/服务规则实现，不能散落 `categoryCode === ...` 分支。
4. 对照 `apps/admin` 的动态商品/资产/地点/规则表单和 `apps/api` 的 DTO、服务端校验、报价、库存及履约入口，确保各端都消费注册定义，并在服务端重复校验。客户端目录应由 API 下发当前品类术语和计价单位标签，禁止客户端猜测或回退为另一个品类的文案。
5. 为新品类建立真实业务样本和测试，覆盖：支持/不支持字段、单位与取还方式、有效期边界、报价与库存、订单快照、切换空间后的文案，以及错误配置被服务端拒绝。同步 `packages/shared`、Prisma、OpenAPI/DTO、种子样本和客户端；按需添加领域实现，不把“编译通过”当接入完成。

当前四个首发品类的 `requiredCapabilities` 为空，表示没有任何**可选扩展模块**被定义为全品类启用前置条件；不表示 Rental Core 基础能力可缺失，也不表示无需做租户开业配置和报价/履约校验。新增品类时只有确实属于该品类的硬性扩展依赖才应列入此项，不能为了让列表非空而把通用库存、定价、地点、订单或取还重复登记成扩展能力。

### 5.2 库存

- 序列化：一件资产一次只能分配给一个有效占用。
- 数量：按地点和期间计算可用数量。
- 套装：预占时展开组成并合并相同组件需求。
- 套装替代组使用“一个非可选默认组成 + 至少一个可选候选”的统一结构；替代只允许发生在订单已确认且尚未配货时，并在事务内锁定、重算目标库存。
- `RentalAllocation.itemGroupId` 保存配货时的实际组成商品；序列化资产同时保存 `assetId`，数量库存保存实际数量。历史套装数量分配若无法无歧义回填实际组成，保持空值并只允许整单归还。
- `RentalReservation.releasedQuantity` 保存累计释放量。部分归还按实际分配项拆分并只释放对应数量；最后一批仍通过整单归还或归还检查完成，以集中处理异常费用。
- 软预占、确认预占、分配、领取、归还和取消必须形成明确状态与流水。
- 生产实现需要事务和并发控制，不能只依靠进程内对象。

### 5.3 经营主体与履约地点

- 经营主体决定自营/合作、联系人和结算方式；地点归属一个启用主体，并声明领取、归还、配送和仓储能力。
- 报价和订单必须同时验证履约模式、地点能力、地点状态和主体状态；配货与领取再次校验当前状态，不能依赖报价时的旧判断。
- 订单写入 `fulfillmentLocationSnapshot` 与 `returnLocationSnapshot`，完整保存地点及经营主体的编码、名称、类型、能力、联系方式、营业时间和结算方式。主档改动只影响新订单。
- 地点或主体停用阻止新报价、配货与领取；归还动作按订单快照继续受理，以保证客户可交还资产并释放库存。

### 5.4 报价与订单

报价由服务端根据商品、租期、数量、地点、客户、日历、规则、优惠券和服务计算。订单保存所有版本快照。确认订单时，订单创建、库存预占、优惠券锁定和价格事实必须原子提交。

- `rental-pricing-strategy.ts` 是计费策略注册入口；报价主流程只按计费单位查找策略并调用，不包含具体单位的 `if/else`。
- 每个公开计费单位必须有且只有一个已注册策略。新增策略必须覆盖正常值、边界值、非法输入和既有报价回归。
- 计费策略负责可计费单位数与行金额计算；价格计划负责适用范围、基础金额、最小单位和版本；订单继续保存最终命中的价格、规则和日历快照。
- 个人和企业分别解析租户内当前有效免费方案，按预约身份只选择一套；每条金额权益先匹配 `scope` 再参与计算，同类取实际减免最大值、不叠加，仍沿用营销方案→优惠券→会员权益的顺序。服务端保存方案版本、授予、命中范围、未命中原因及金额分摊，不能信任前端计算结果。
- 会员方案、授予或范围变更不重算旧订单或改写原快照与金额；续租、取消等动作继续用该动作适用的原单价格/优惠快照，不拿当前会员方案替换历史商业事实。资格/状态复查与历史金额计算是不同边界。
- capability 的共享注册表只声明能力代码、归属和扩展点；具体业务实现放在独立模块，并由后端权限与经营空间品类共同校验，不能只依靠前端隐藏。

### 5.5 奖励与通知

奖励、优惠券和通知均需租户与经营空间隔离并保持幂等。营销余额不是资金账户。通知目标必须脱敏，真实 provider 需回执、重试、验签和失败补偿。

## 6. 数据与迁移

- `schema.prisma` 是当前模型定义，migration 是部署历史，两者必须一致。
- 已共享或已应用的 migration 默认不可修改；若项目决定重建预发布基线，必须先确认所有环境可销毁并写入开发任务决策。
- 迁移不得通过无说明的 `DROP TABLE` 丢弃业务数据。
- 任何迁移同时验证空库 `migrate deploy` 和已有库升级。
- 经营空间迁移必须先为每个现有租户创建默认空间，将全部现有账号及其角色关系回填到默认空间，再回填业务表 `workspaceId`；旧行全部可归属且验证通过前不得收紧非空或唯一约束，不得根据品类名称猜测归属。
- 本轮租户统一会员采用增量迁移，不重置共享库：旧同客户多空间会员保守合并到唯一 `CustomerMembership`，不能把受限状态自动放宽；注册模式冲突取 `manual`；旧方案权益保留原空间范围；同客户有效授予保留最新，其余追加撤销并记录迁移原因。账号、客户、订单、库存、报价/订单快照与金额保留；具体安全规则见数据库文档。现有数据均为测试数据、无正式数据不等于获准清库，共享库部署另行确认。
- Seed 必须可重复执行，不保存明文密码，不依赖固定演示租户作为生产兜底。
- 当前聚合 JSON 快照适用于 v0.1 恢复；生产事实需投影到规范化表并使用事务。

具体命令和安全边界见 `数据库启动与初始化.md`。

## 7. 测试与验收

基础命令：

```powershell
npm run test:rental-foundation
npm run build
git diff --check
```

`test:rental-foundation` 覆盖类型、管理端静态契约、OpenAPI、Prisma schema、Seed 类型、Rental Core、商业规则、快照恢复、SaaS 权限、会员隔离和报表 fixture。

它不等于真实 MySQL E2E。数据库改动还必须在独立测试库验证：

- 空库迁移；
- 已有库升级和数据保留；
- Seed 重复执行；
- HTTP 登录和租户初始化；

- 基础租户角色权限加租户级 dataScope=all 的会员维护边界、空间星号不越权、最小代客选择器、客户端租户级注册幂等与本人订单回放校验；

- 报价、订单、履约和重启恢复；
- 双租户并发隔离；
- 测试数据安全清理。

### 7.1 品类版本预备资料（专项进行中）

- 租户 GET `/api/rental/v1/category-adoption/candidates?operation=upgrade|restore` 读取会话空间同品类、获对应资格的发布目标；仅返回版本 ID/标签与正文可执行标记，不返回平台内部政策。停止新开通不一并禁止既有空间准备升级/恢复；候选目录不是最终采用许可，保存及未来正式采用仍须事务内复核。
- 租户内部 GET/PUT `/api/rental/v1/category-adoption/{targetId}/preparation` 用于读取和保存目标版本的型号/资产候选字段，不是客户端注册或正式采用接口。
- 独立权限 `rental-os:category:adopt`，要求当前会话空间全部数据和地点范围；平台管理员不得代租户操作，请求不能自行指定空间。
- 保存携带来源版本、空间采用修订、准备修订及每个实体的 ISO 更新时间，事务内复核政策和绑定。新准备修订为 1；冲突返回 409，原活动资料不变。
- 候选记录保留退役字段及媒体，不改写旧快照；准备结果不得当作正式经营事实。`adoptionImplemented=false` 表明最终原子采用尚未交付；当前实体校验不替代价格/规则/能力组合检查。
- 预览分别返回 `validationScope`（实体字段、库存方式、唯一性）和 `businessCompatibility`。后者检查原始经营设置、启用地点及当前/未来价格单位、规则计价依赖、预授权及会员减免、资质审核支持范围与必检阶段模板存在性，不读取过滤后的缓存来隐藏不兼容项；旧历史版本不被改写，不按平台默认值替换租户模板。`complete=false` 明确仍未覆盖完整能力、证件/检查字段及履约费用组合，`valid=true` 只表示这一局部范围相容，不等于开业就绪或允许正式采用。
- 已在一次性专用库验证 172 条迁移、无 drift、重复部署/Seed 与准备 HTTP 正反例；未部署共享业务库，也不代表全专项已完成。
- 能力预览只读取会话空间实例，复用能力服务参数校验，并按目标定义判定必选、适用/声明、依赖、互斥和当前进程登记的明确实现版本。Core 遗留实例不参与扩展组合；已登记旧 Hook 仍可执行。不会修改实例、初始化默认值或自动升级；这不是所有部署实例都已兼容的证明。结果汇入 `businessCompatibility`，继续保留 `complete=false`。

## 8. 开发流程

1. 从 `多品类租赁平台开发任务.md` 总索引进入对应分端任务文档并选择任务 ID。
2. 阅读 `多品类租赁平台需求说明.md` 对应规则和验收。
3. 检查前端、API、共享契约、数据库、权限、审计和测试影响。
4. 先写可验证的领域规则和异常，再补页面。
5. 保留用户无关改动，不覆盖脏工作区中的其他修改。
6. 运行标准验收；数据库任务运行专用 MySQL E2E。
7. 仅更新对应分端任务状态；完成后移入统一归档，不创建分支流水账或重复路线图。
